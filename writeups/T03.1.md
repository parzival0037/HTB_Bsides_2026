**What you are about to read:** why `rm` is not an erasure. A review note references a delivery
fixture that no longer exists at its documented path; the content is still an immutable object in
the repository's history, one `git show` away. The interesting part is not the recovery — it is
what the recovered fixture reveals about the behaviour it was written to exercise.

## Objective

> A delivery fixture named in a review note is missing at its documented path; recover it from
> the checkout's version-control history (deleted content), and identify the behavior it covered.

The developer-artifacts desk publishes a checkout plus review documentation, and the docs still
promise a fixture the tree no longer holds. Recovering the file is half the task; the answer is
bound to identifying *what behaviour* it covered.

## Background you need

- **Git stores content, not files.** Each committed version of each file becomes a blob keyed by
  the hash of its content and reachable from a commit. Deleting a file and committing adds a new
  tree that no longer references the blob; it does not remove the blob.
- **Deletion is searchable.** `git log --diff-filter=D --name-status` lists commits that deleted
  files, and `git show <commit>^:<path>` prints the file as of the parent commit.
- **A served checkout is a full checkout.** A smart-HTTP clone hands over the whole object
  database, history included, so deleted content comes with it — a rendered file list would not.

## Walkthrough

### 1. Read the desk and the review note

The desk's front page and linked review documentation describe a delivery fixture and the path it
should occupy. Requesting that path returns a miss: the fixture is absent from the working tree,
not merely unlinked from an index page.

### 2. Get the repository, not just the files

The desk links a browsable checkout, so obtain the repository itself and keep history:

```bash
# illustrative: clone the served checkout with history
git clone http://developer.training:8080/<repo>.git
cd <repo>
```

### 3. Find the deletion

Search history for the path the note names:

```bash
# illustrative: locate the commit that removed the fixture
git log --diff-filter=D --name-status --oneline -- <path/from/review/note>
```

The deletion commit shows the path as `D`, and its parent still contains the file:

```bash
# illustrative: print the blob as of the parent commit
git show <commit>^:<path/from/review/note>
```

Because blobs are content-addressed, the same content is reachable from any commit that touched
it (`git log --all -- <path>`) — useful when the deleting commit is not the one you guessed.

### 4. Identify the behaviour the fixture covered

The recovered file is a **delivery fixture**: sample input for the connector's delivery path.
Reading it tells you which case it exercised — field names, expected outcome, and the consumer
behaviour the reviewers cared enough about to name it in a note. That identification, not the
bytes alone, is what the challenge asks for, and it is the part that a pure "undelete" tool
would not give you.

## Why this works (the vulnerability explained)

Deletion in a version-control system is an **append**, not an erase. The developer's mental model
is "I removed the file"; the system's model is "I added a commit whose tree omits it". The blob
survives until something explicitly rewrites history and garbage-collects unreachable objects —
and even then, copies survive in every clone taken before the rewrite.

That gap between intent and mechanism is the whole bug class: secrets committed and later deleted
still authenticate because they were never rotated; removed test data and internal fixtures stay
readable to anyone who can clone; "we deleted the credential file" is often true of the tree and
false of the repository. The extra lesson is the *documentation trail* — a review note pointing
at a file that no longer exists is a perfect index into history, telling an outsider exactly
which path to look for and removing the guesswork that normally makes history mining expensive.

## Detection and fix

- **Log signal:** clones or archive downloads by principals who never push; object-endpoint
  requests (`/info/refs`, `objects/…`) from outside the team; commits whose only effect is
  deleting sensitive paths.
- **Fix:** treat deletion as disclosure. If the file held secrets, rotate them; if it held
  customer data, treat it as breached. To truly remove content, rewrite history
  (`git filter-repo`), force-push, expire reflogs, garbage-collect, invalidate every existing
  clone, then verify the blob is gone.
- Serve a sanitised export or a rendered view instead of an anonymous repository where history
  matters, and keep review notes free of removed paths.
