**What you are about to read:** the payoff of the preview chapter — using an identity collision

viewer is isolated" is not "the content is isolated".

## Objective

Deliver a crafted support document that crosses the viewer's intended isolation boundary and
recovers the protected preview content.

## Background you need

- **The isolation being crossed is between documents.** Each preview renders in its own context;
  the assumption is that rendering A never surfaces B's bytes. Identity is the connection: the
  renderer picks the stored preview for a `DOC-…` id.
- **A support document is an input channel.** Support attachments are uploaded by customers and
  staff, delivered through the support service, then previewed. Crafting one is normal usage;
  the vulnerability is in how it is *resolved*.
- **Why hard (200p):** you must combine the association (K10.1), the collision (K10.2) and a
  delivery path that survives support validation, then get the *other* document's content back.
- Known data: this chapter's protected association resolves to `DOC-9BC054D6F95DFA6A`; the
  support surface is osTicket plus the support API on `:8443`.

## Walkthrough

### 1. Recon — what the viewer serves, and from where

```bash
# illustrative: baseline render of the protected association
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  'https://preview.keplerops.test/api/render/<preview from K10.1>' | jq .
```

Distinguish "content" from "metadata": if the baseline returns content you cannot read as your
own identity, the render path is where substitution must happen.

### 2. Finding the flaw — identity is chosen before content is fetched

The pipeline is `preview id → document identity → stored content → response`. Your crafted input
influences the first two steps; the third is a lookup keyed only by identity. Once your document
resolves to `DOC-9BC054D6F95DFA6A`, the bytes served are whatever is stored under that identity —
the protected preview, not your upload. Your document is a *key*, not the payload.

### 3. Exploitation — craft, deliver, render

```bash
# illustrative: deliver the crafted document as a support attachment
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Authorization: Bearer <support client bearer>" \
  -F 'file=@crafted-support-doc' \
  https://support.keplerops.test:8443/api/diagnostics/<job>/package

curl -sS ... -X POST --data-binary @crafted-support-doc \
  https://preview.keplerops.test/api/prepare | jq -r '.preview'
curl -sS ... https://preview.keplerops.test/api/render/<preview> -o rendered.bin
pdftotext rendered.bin - | head -40
```

The rendered output is the protected document's content, not yours: your artefact was accepted as
the protected identity, and the viewer served the stored preview.

### 4. Getting the flag

Solved by a team agent; no request/response was retained, so the flag is **accepted, value not
recorded**. The card's success condition is content recovery — the protected preview's contents
in the render response, obtained through a support document you delivered.

## Why this works (the vulnerability explained)

This is **identity confusion used as an access-control bypass**, because the pipeline conflates
three questions: *what did the user send?* (bytes, provenance), *what document is this?*
(normalised identity), and *what may be served for it?* (authorization). The service answers the
third using the second and drops the first, so authorization is performed on an
attacker-steerable value and content is fetched from a store keyed by that same value. The
isolation that fails is not the container sandbox — that holds — it is the assumption that
rendering can only surface what was uploaded. Once rendering means "serve the stored preview for
identity X", any input reaching X retrieves the stored bytes.

## Detection and fix

- **Detect:** an identity receiving uploads from a source that did not create it; support
  attachments whose normalised content matches an internal document; render responses whose
  served digest differs from the uploaded digest for the same preview.
- **Fix:** key stored previews by the hash of the delivered bytes and serve only the preview
  generated from them; treat "same normalised text" as a dedup hint, never an access key.
  Authorize the upload against the document's owner before associating it.
- **Defence in depth:** keep a provenance chain (uploader → bytes digest → preview → document)
  and refuse to render when the first hops do not match the document's recorded origin.

## Notes and dead ends

- Evidence is thin: description and solved-state metadata plus the chapter-wide preview routes
  and the `DOC-9BC054D6F95DFA6A` association noted by the K02 lane. The exploit is
  **reconstructed** from those facts and K10.1/K10.2 mechanics; the delivery command is a
  template, not captured traffic.
- A document that merely *looks* like the protected one (same title, same template) is a dead
  end: identity comes from normalised content, so cosmetic similarity changes nothing.
- Do not expect the render to hand you the original filename or metadata — the viewer presents
  the stored preview, and its provenance will describe the protected document, which is exactly
  the evidence you want.
