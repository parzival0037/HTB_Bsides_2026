# K04.2 — Read past the index

> **Category:** 2. KeplerOps · **Points:** 400 · **Difficulty:** expert
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Read primitive from the indexer's own extraction context — the bundle path that lets you write sideways also lets you read what the service can see |
| **Tools** | `tar`/`ln`, the indexer client routes, `curl`, `python3` |
| **Attack surface** | `https://indexer.keplerops.test` (10.77.51.70), continuing from the K04.1 capability |
| **Prerequisite** | K04.1 — a bundle whose member paths the indexer honours |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a write-shaped bug becomes an information disclosure. The bug
class is *filesystem confused deputy*: the indexer reads bundle members as files, so pointing one at a
path outside the bundle makes it read that file **as itself** and publish the result through the index.
Ordinary bundles cannot see those paths; a bundle that lies about its layout can.

## Objective

> Use the compromised indexing behavior to recover protected runtime information that an ordinary
> bundle cannot see.

"Protected runtime information" means data that lives with the service rather than with the customer:
its configuration, its credentials, its process environment, its mount layout. K04.1 gave you control
over *where* a member lands and *which* object claims it; this card points that same control at the
service's own files.

## Background you need

- **A symlink is a read when the reader follows it.** Extract a link member and index "through" it and
  the indexer opens whatever it resolves to — `/proc/self/environ`, a config file — and that file ends
  up in the index content.
- **The indexer's privileges set the ceiling**: it reads bundles, its own state and usually a service
  credential, so its readable set is larger than the uploader's.
- **Confused deputy**: the attacker may submit a bundle; the *service* may read its own runtime data.
  The bug is exercising the second permission on the first party's behalf without a scope check.

Reconstruction: the evidence records the objective and the K04.1 foothold, not an observed file list.

## Walkthrough

### 1. Map what the indexer can read

Start from a normal extraction job's output: the index lists member paths and sizes. Anything the index
reports is something the indexer read, so the index is your oracle for what the service can open.

```bash
# illustrative template — read the index for one object
curl -sS 'https://indexer.keplerops.test/<object-route>' | jq '.members[] | {path, size}'
```

### 2. Claim a member outside the bundle

Two carriers work with the K04.1 primitive:

```bash
# illustrative: a link member pointing at the service's own runtime files
ln -s /proc/self/environ environ.link
ln -s <service-config-path> config.link
tar -cf bundle.tar environ.link config.link
```

If links are rejected but traversal names are honoured, use a member name that resolves out of the
extraction root (`../../proc/self/environ`). Either way the target is chosen, not guessed.

### 3. Read the result through the index

The published index is what you see. Read the member content or its size: a thousand-byte member named
`environ.link` is the process environment, and a configuration path is the material K04.3 needs.

```bash
curl -sS 'https://indexer.keplerops.test/<object-route>' | jq -r '.members[] | select(.path|test("environ|config"))'
```

### 4. Iterate on the target list

Each read suggests the next: an environment variable naming a mount, a config naming a state directory,
a state directory naming a token file. Keep one target per member so a rejection tells you exactly which
path the implementation blocks.

## Why this works (the vulnerability explained)

The indexer is a **confused deputy**: it holds permissions the caller does not and exercises them on
caller-supplied input. The missing check — "is this path inside the job root, after canonicalisation?"
— is the same one K04.1 needs, which is why the cards share a root cause.

The class appears everywhere file paths meet a privileged reader:

- an importer that follows a symlink out of an upload directory;
- a backup tool that archives `../` in a user-supplied file list;
- a log shipper configured with a glob that the tenant can influence;
- a build step that reads a path from a manifest (the classic "read any file" in CI).

What makes the read *useful* is that the result is published: the index returns to the uploader, so
confidential bytes cross the boundary as ordinary output. Output channels are part of the attack
surface. The fix is canonicalisation plus a prefix assertion at *open* time, not parse time: resolve the
final path, confirm it is under the job root, refuse links. Done once in the extraction code, every
later reader inherits the guarantee.

## Detection and fix

- **Log signal:** index members whose resolved path leaves the job root; indexer reads of `/proc/*`,
  `/etc/*`, config or token paths; member sizes matching service files rather than bundle content.
- **Fix:** open via a directory fd (`openat` with `O_NOFOLLOW`), assert the resolved prefix, refuse
  links, and run extraction as a user that can read only the job sandbox.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K04.2 was solved by the team agent; the
  record is the description plus the indexer's range-map entry. No transcript exists, so the commands
  are labelled illustrative and target paths are placeholders.
- `/proc/self/environ` is the canonical demonstration but rarely the most useful: the mount and config
  paths it reveals matter more.
- Errors are informative — a permission error on one target and success on another maps the indexer's
  effective privileges, which the next card needs to plan a write.
- A successful read is not the end of the chain: K04.3 needs a *write* against protected state and
  K04.4 needs execution; the files read here are the tools for both.
