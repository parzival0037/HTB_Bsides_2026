# K21.2 — A conversation kept too long

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K21

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Retention failure in the assistant overlay — a conversation flagged `deleted_from_ui` is still served, and reading it requires only a support bearer in a cookie |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://assistant.keplerops.test/api/conversations/CONV-SUP-2841-19` |
| **Prerequisite** | The support bearer token from the workstation config (`fk_support_rowan_…`) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a chat transcript that the UI has "deleted" remains a
first-class API object, and why the restriction that the model applies in conversation is not
applied at all when you read the transcript directly. This is the second half of the
"deletion is a view" pattern from K17.1, now inside the LLM overlay.

## Objective

> Recover the separately retained support conversation and the unpublished case detail it
> contains.

"Separately retained" is the tell: the conversation was kept outside the ticket lifecycle. The
unpublished detail is the escalation reference the assistant worked out during the session.

## Background you need

An LLM assistant that is wired into a ticketing system keeps three kinds of state:

| State | Where it lives | Who reads it |
|---|---|---|
| conversation | assistant store (`/api/conversations/{id}`) | the overlay, the UI |
| context | retrieval scope (`/api/contexts/{id}`) | the assistant |
| documents | the sources retrieval must cite | the assistant, the document route |

`deleted_from_ui: true` usually means "hide the row from the sidebar". The conversation body,
its messages and its metadata are untouched. If the API still answers `GET`, the deletion was
cosmetic — and an assistant transcript is not cosmetic: it contains the model's synthesised
answer, i.e. the conclusions, not just the raw documents.

**The overlay session.** The support integration authenticates with a bearer
(`fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b` in our notes). The assistant accepts it as a
cookie — `fieldkest_support` — which is what makes the transcript routes answer outside the UI.
That single trick unlocks K21.2, K21.3 and both K23 conversation cards.

## Walkthrough

### 1. Get the support bearer

`rowan-dev`'s support client config holds it:

```bash
jq -r .token ~/.config/fieldlink/support-client.json
# fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
```

### 2. Find the conversation id

The assistant configuration from K21.1 names the workspace and context
(`support-private` / `ctx-support-private-v4`); the open context inventory (K23.1) lists that
context's conversation as `CONV-SUP-2841-19`. The id embeds the ticket number, which is why the
K21 series is addressable at all.

### 3. Read the conversation as an overlay session

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b

curl -sS -H "Cookie: fieldkest_support=${TOKEN}" \
  "https://assistant.keplerops.test/api/conversations/CONV-SUP-2841-19" | jq
```

The response is the transcript, including its UI state:

```json
{
  "id": "CONV-SUP-2841-19",
  "deleted_from_ui": true,
  "tenant": "TEN-ARWC-047",
  "messages": [ "…" ]
}
```

`deleted_from_ui: true` with a full `messages` array is the finding in one line.

### 4. Read the unpublished case detail

The messages are the valuable part. The user asks for the escalation reference; the assistant
answers with material that is not in any published view:

- `ESC-SUP-2841-R3 (restricted)` — the escalation record id, marked restricted;
- `DIAG-CRR-MIXED-19` — the diagnostic bundle reference;
- connector `FLK-7.4.2`;
- asset `CRR-OG2`.

That is the "unpublished case detail": ids and revision numbers that describe an incident the
customer-facing ticket does not mention.

### 5. Getting the flag

The conversation response carried the flag. Lane notes record it as
`FLAG{302e391567fb7188}` and state it was accepted; the card entry stores no value, so it is
recorded here as accepted/not recorded.

## Why this works (the vulnerability explained)

Three separable failures line up:

1. **Soft delete.** `deleted_from_ui` is a presentation flag. The row, the messages and the
   citations survive, and the read route has no notion of "this conversation is deleted".
2. **Cookie-shaped bearer.** The overlay's bearer is accepted as a cookie value with no session
   binding (no expiry, no device binding, no CSRF story). A token that lives in a workstation
   JSON file becomes a portable session.
3. **The assistant is a summariser, not a filter.** The model's job in this conversation was to
   answer a support question — so it wrote down the restricted escalation id. Once written, the
   restriction is a property of a *document*, not of the sentence, and the transcript route
   never re-applies it.

Point 3 is the transferable lesson: any system that lets an LLM read restricted sources and
then stores the answer unaudited is a data-laundering pipeline. The model's output inherits the
maximum classification of its inputs, and the transcript store is the weakest copy.

Correct design: hard-delete (or move to a restricted store) when `deleted_from_ui` is set;
authenticate conversation reads with a real session scoped to the case and the caller's role;
and classify transcripts at the level of the highest-classified source they cite.

## Detection and fix

- **Log signal:** conversation reads by an overlay bearer for conversations flagged deleted;
  the same bearer read across multiple conversations/tenants; reads that immediately follow the
  open `/api/contexts` inventory.
- **Fix:** make deletion a row-level access change; expire and rotate the support bearer; bind
  it to a session and a tenant; on read, evaluate the conversation's classification against the
  caller's role and redact restricted ids from `messages`.
- **Retention:** if support wants transcripts for audit, keep them in the compliance store —
  not in the assistant's live object store — and require a separate role to read them.

## Notes and dead ends

- The lane's "golden trick" is exactly the cookie form:
  `Cookie: fieldkest_support=fk_support_rowan_…`. Without it the conversation routes do not
  answer, so this is the credential to look for first in any later assistant card.
- `CONV-RILL-442-8` is also readable with this cookie and returns a different flag — that one
  belongs to K23.2. Do not submit across cards.
- AnythingLLM's `stream-chat` path is a dead end for extraction: the request `mode` is ignored
  and the workspace's `chatMode` (`automatic`) wins, so you cannot force tool-calling to make the
  model dump context. Read `/api/conversations/...` instead.
- `POST /api/answers` with `{"request":"private_escalation", …}` fails with `502 retrieval_failed`,
  and `POST /api/completions/context` is `403 context_ownership_denied`. The retrieval/answer
  paths are the ones that *do* enforce something; the document route in K21.3 is where the
  restriction is missing.
