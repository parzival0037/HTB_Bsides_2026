# K21.2 — A conversation kept too long

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K21

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Retention failure in the assistant overlay — a conversation flagged `deleted_from_ui` is still served, and reading it needs only a support bearer in a cookie |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://assistant.keplerops.test/api/conversations/CONV-SUP-2841-19` |
| **Prerequisite** | The support bearer from the workstation config (`fk_support_rowan_…`) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a transcript the UI has "deleted" remains a first-class API
object, and why the restriction the model applies in conversation is not applied when you read the
transcript directly. This is "deletion is a view" (K17.1), now inside the LLM overlay.

## Objective

> Recover the separately retained support conversation and the unpublished case detail it contains.

"Separately retained" is the tell: the conversation was kept outside the ticket lifecycle. The
unpublished detail is the escalation reference the assistant worked out during the session.

## Background you need

An assistant wired into a ticketing system keeps three kinds of state: the **conversation**
(`/api/conversations/{id}` — transcript and UI state), the **context** (retrieval scope) and the
**documents** the answer cited.

`deleted_from_ui: true` usually means "hide the row from the sidebar". The body, messages and metadata
are untouched, so if the API still answers `GET`, the deletion was cosmetic — and a transcript is not
cosmetic: it holds the model's synthesised conclusions, not just raw documents.

**The overlay session.** The support integration authenticates with a bearer
(`fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b` in our notes), which the assistant accepts as the
cookie `fieldkest_support`. That one trick unlocks K21.2, K21.3 and both K23 conversation cards.

## Walkthrough

### 1. Get the support bearer

```bash
jq -r .token ~/.config/fieldlink/support-client.json | cut -c1-24
# fk_support_rowan_2fxtXNkU…
```

### 2. Find the conversation id

The assistant config (K21.1) names the workspace and context (`support-private` /
`ctx-support-private-v4`); the open context inventory (K23.1) lists that context's conversation as
`CONV-SUP-2841-19`. The id embeds the ticket number, which is why the K21 series is addressable.

### 3. Read the conversation as an overlay session

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
curl -sS -H "Cookie: fieldkest_support=${TOKEN}" \
  "https://assistant.keplerops.test/api/conversations/CONV-SUP-2841-19" | jq
```

`{ "id": "CONV-SUP-2841-19", "deleted_from_ui": true, "messages": [ "…" ] }` — a soft delete flag
with a full message array is the finding in one line.

### 4. Read the unpublished case detail

The user asks for the escalation reference; the assistant answers with material that is in no
published view: `ESC-SUP-2841-R3 (restricted)` — the escalation record id, marked restricted —
`DIAG-CRR-MIXED-19` (diagnostic bundle), connector `FLK-7.4.2`, and asset `CRR-OG2`. Those ids and
revision numbers describe an incident the customer-facing ticket does not mention.

### 5. Getting the flag

The conversation response carried the flag. Lane notes record it as `FLAG{302e391567fb7188}` with the
submission accepted; the card stores no value, so it is accepted/not recorded.

## Why this works (the vulnerability explained)

Three separable failures line up:

1. **Soft delete.** `deleted_from_ui` is a presentation flag; the row, messages and citations survive
   and the read route has no notion of "deleted".
2. **Cookie-shaped bearer.** The overlay bearer is accepted as a cookie value with no session binding
   (no expiry, no device binding, no CSRF story), so a token living in a workstation JSON file becomes
   a portable session.
3. **The assistant is a summariser, not a filter.** Its job here was to answer a support question, so
   it wrote down the restricted escalation id. Once written, the restriction belongs to a *document*,
   not to the sentence, and the transcript route never re-applies it.

Point 3 is the transferable lesson: any system that lets an LLM read restricted sources and then
stores the answer unaudited is a data-laundering pipeline. The output inherits the maximum
classification of its inputs, and the transcript store is the weakest copy.

Correct design: hard-delete (or move to a restricted store) when `deleted_from_ui` is set;
authenticate conversation reads with a real session scoped to case and role; classify transcripts at
the level of the highest-classified source they cite.

## Detection and fix

- **Log signal:** conversation reads by an overlay bearer for conversations flagged deleted; the same
  bearer reading across multiple tenants; reads immediately following the open `/api/contexts` list.
- **Fix:** make deletion a row-level access change; expire and rotate the support bearer and bind it to
  a session and tenant; evaluate the conversation's classification on read and redact restricted ids
  from `messages`. For audit retention, keep transcripts in the compliance store behind another role.

## Notes and dead ends

- The lane's "golden trick" is the cookie form `Cookie: fieldkest_support=fk_support_rowan_…`; without
  it the conversation routes do not answer. Look for it first in any assistant card.
- `CONV-RILL-442-8` is readable with the same cookie and returns a different flag — that one belongs
  to K23.2. Do not submit across cards.
- `stream-chat` is a dead end: the request `mode` is ignored and `workspace.chatMode = automatic` wins,
  so you cannot force tool-calling to dump context.
- `POST /api/answers` (`{"request":"private_escalation", …}`) fails with `502 retrieval_failed` and
  `POST /api/completions/context` is `403 context_ownership_denied`: the retrieval paths enforce
  something, while the document route in K21.3 does not.
