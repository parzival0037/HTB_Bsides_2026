# K23.3 — A missing tenant boundary

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K23

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Cross-tenant object read on a RAG document route — the assistant serves another customer's restricted document because the request validates the context/conversation pair but never the document's tenant |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/contexts/ctx-rill-support-v3/conversations/CONV-RILL-442-8/documents/DOC-RILL-442` |
| **Prerequisite** | K23.1's inventory (ids), K23.2's conversation binding (`TEN-RILL-022`), and the `fieldkest_support` cookie |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the payoff of the K23 chain — reading Rillhaven's restricted
support document (`RILL-442.md`) out of an assistant that was supposed to keep tenants apart. It
is the same shape as K21.3 but across customers rather than across classification, and it is the
clearest example in the range of a RAG pipeline where the *vector store* is the real
authorization boundary.

## Objective

> Use the exposed context and conversation evidence to recover another customer's restricted
> support document.

With the open inventory (context, conversation, document ids) and the overlay cookie, the
document route is one request away. The exercise is to prove the tenant boundary is missing,
not merely that an id leaked.

## Background you need

**RAG stores are shared.** A single vector index usually holds every tenant's chunks; tenancy is
a metadata filter (`tenant: TEN-…`) applied at query time. Three consequences:

1. If a route can fetch "document X in context Y", and the context belongs to tenant A while the
   document belongs to tenant B, the only thing standing between the attacker and B's text is a
   filter that the route may not apply.
2. Chunks are stored **whole** for citation purposes (`sources[].text`), so a single lookup
   returns the full document, not a snippet.
3. Document ids are stable (`DOC-<tenant-hint>-<number>`), so the id itself announces the
   tenant — and still the route does not compare it with the caller's scope.

**Why the parent ids matter.** The route has three path segments: context, conversation,
document. Validating the first two and trusting the third is the archetypal nested-resource IDOR.
Here the first two *do* belong together — the conversation is genuinely Rillhaven's — so the
request looks well-formed; the tenant check that would matter is on the caller, and there is
none.

## Walkthrough

### 1. Assemble the three ids

From K23.1's open inventory and K23.2's conversation read:

```
context       ctx-rill-support-v3     (published:false, tenant TEN-RILL-022, workspace rill-support)
conversation  CONV-RILL-442-8         (tenant TEN-RILL-022)
document      DOC-RILL-442            (Rillhaven asset RILL-PUMP-442)
```

The interesting detail is that `DOC-RILL-442` is *also* listed in the ARWC support context
(`ctx-support-private-v4`). Same document, two contexts, two tenants — which is why this card is
about a missing boundary rather than a single bad id.

### 2. Establish the session

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
C="Cookie: fieldkest_support=${TOKEN}"
```

### 3. Fetch the document

```bash
curl -sS -H "$C" --max-time 90 \
  'https://assistant.keplerops.test/api/contexts/ctx-rill-support-v3/conversations/CONV-RILL-442-8/documents/DOC-RILL-442' \
  | jq '.sources[0]'
```

Two practical notes learned the hard way in this lane:

- the route is slow — the lane recorded **30–45 seconds** for this fetch (and 42 s for the
  ARWC-context variant), so a default 30 s timeout fails intermittently;
- the response is a `sources[]` array, not a document object: the text is at
  `sources[0].text` with a `reference` naming the file.

### 4. Read what came back

`sources[0].text` is the full restricted document, `RILL-442.md`:

```
Customer:   Rillhaven              tenant  TEN-RILL-022
Asset:      RILL-PUMP-442
Connector:  FLK-7.4.1-RILL
Diagnostic: DIAG-RILL-MIX-08
Document token: <the flag>
```

This is another customer's support document, retrieved from a context the ARWC support case can
address. The tenant id in the body confirms the cross-boundary read; the flag is the proof the
challenge wants.

### 5. Getting the flag

The document token in `sources[0].text` is the flag. Lane notes record it as
`FLAG{4a4620cd59307eb7}` with the submission accepted; the card entry stores no value, so it is
recorded here as accepted/not recorded.

## Why this works (the vulnerability explained)

Authorization was applied to **reachability**, not to **content**:

```
route check:  context + conversation exist and belong together   -> pass
route check:  caller holds a support overlay session              -> pass
route check:  document.tenant == conversation.tenant == caller.tenant -> absent
```

The result is a cross-tenant read that is structurally identical to a classic nested IDOR, with
one twist: the leaked object is a *chunk of a shared vector index*, so the attacker never had to
reach the customer's database. The RAG layer had already copied the document into a namespace
that both tenants can resolve.

Three design lessons:

1. **The index is a copy, so it needs its own ACL.** Adding documents to a shared vector store
   duplicates them outside the original access control. Tenant filters must be enforced on
   *every* retrieval route, not just the chat path.
2. **Parent validation is not child authorization.** Checking that context and conversation match
   tells you the URL is well-formed — not that the caller may see the document inside it.
3. **Citations return full text by design.** `sources[].text` exists for UX; it must be
   redacted, not merely referenced, when the caller lacks the document's classification or
   tenant.

## Detection and fix

- **Log signal:** document reads where `document.tenant` differs from the context/conversation
  tenant; a single support cookie reading documents across tenants; the same document id
  appearing under two contexts (the index-consistency alarm that should have fired at ingest).
- **Fix:** enforce tenant and classification at the document route (compare against the document's
  metadata, not the URL); filter `sources[].text` by the caller's role; make the vector query take
  a mandatory tenant predicate so a cross-tenant document can never be retrieved, let alone
  listed; and keep per-tenant namespaces/physical separation for regulated customers.
- **Containment:** re-index — a document in the wrong namespace is a data-protection incident
  regardless of whether this route is fixed. Audit who else read `DOC-RILL-442` from the ARWC
  context (K21.3's fetch is exactly that read).

## Notes and dead ends

- Recorded facts: the route and its response shape (`sources[0].text`), the document contents
  (Rillhaven, `TEN-RILL-022`, `RILL-PUMP-442`, `FLK-7.4.1-RILL`, `DIAG-RILL-MIX-08`, document
  token), the 30–45 s latency, and the fact that the same document is listed under
  `ctx-support-private-v4` for the ARWC case. The request line above follows the lane's path;
  the flag cell stays accepted/not recorded because the card has no stored value.
- Cross-context variant: fetching `ctx-support-private-v4/CONV-SUP-2841-19/DOC-RILL-442` returns
  the *ARWC* escalation material (`ESC-SUP-2841-R3.md`, two copies, plus `COMP-JOB-17.md`) in
  42 s. That is K21.3's finding, not this card's — the document id in the URL is not what decides
  what you get back.
- `CONV-RILL-442-8` (K23.2) and `CONV-SUP-2841-19` (K21.2) are both readable with the same
  cookie. The assistant will happily serve conversation after conversation; the only guard is
  knowing the ids, and K23.1 hands those out unauthenticated.
