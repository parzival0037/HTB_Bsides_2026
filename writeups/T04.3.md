# T04.3 — A request is not a movement

> **Category:** 1. Training · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Accepted ≠ executed — an HTTP `202` is treated as proof of a physical transfer; the true effect is only visible in the device's observation stream |
| **Tools** | `curl`, JSON bodies, timestamp comparison |
| **Attack surface** | `http://state.training:8080/` (10.77.40.50): `POST /api/practice/hold`, `POST /api/practice/transfer`, `GET /api/practice/observations` |
| **Prerequisite** | A working `service_hold` finding (T04.2); the documented bounds — 1–200 L per transfer, 20 L/s, ≥200 L must remain in the tank |
| **Flag** | `FLAG{03993cc3de147e23}` |

**What you are about to read:** the difference between an API that queues work and a plant
that performs it. We clear the hold, request a bounded 200 L transfer with unique request IDs,
then refuse to trust the API — the flag is handed over only by the *terminal observation* the
device wrote after the water moved.

## Objective

> Move the specified bounded amount of water through the training outlet, then verify the
> transfer from the tank's observations. Respect the stated bounds; verify before and after.

The desk documents the physics and the limits: transfers of 1..200 L at 20 L/s, leaving at
least 200 L in the tank, and *hold blocks new transfer*. Every request carries a caller-chosen
`request_id`; the device emits numbered observations. The transfer must be legal and provable.

## Background you need

- **Command/execution split.** `POST /api/practice/transfer` answering `202 Accepted` means
  "valid request, queued" — not that the valve opened or that a later stage did not drop it.
  Treating a response code as the outcome is the most common mistake in testing physical APIs.
- **Device observations are the ground truth.** The controller emits numbered samples (level,
  status word, valve position, timestamp, `terminal` marker). Rate limits leave a signature:
  at 20 L/s a 200 L transfer takes ~10 s, so the level must walk down in proportion to elapsed
  time, and a "successful" log with no such walk is fiction.
- **Idempotency keys.** `request_id` makes retries safe (different IDs = two transfers, same ID
  twice = one) and descriptive IDs make the register readable later, as T04.4 needs.

## Walkthrough

### 1. Read the tank, then clear the hold

The live object reported `status_word 5` (`ready` + `service_hold`), `1200.0 L`, outlet closed
— the state T04.2 explains, and a transfer attempted here is refused. So the hold goes first,
with its own request id:

```bash
# evidence: documented practice API, request id chosen by the caller
curl -sS -X POST http://state.training:8080/api/practice/hold \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"t04-hold-clear-1","active":false}'
```

The desk answered `200` and `status_word` moved `5 → 1`: hold bit cleared, ready bit still
set. Comparing the word before and after, not the status code, is what proves the transition.

### 2. Request exactly the bounded amount

```bash
curl -sS -X POST http://state.training:8080/api/practice/transfer \
  -H 'Content-Type: application/json' \
  -d '{"request_id":"t04-xfer-200-1","quantity_l":200}'
```

`202` accepted, logged at `17:15:21.735208Z`. `200` is the maximum legal step and satisfies the
"leave ≥200 L behind" rule — valid on its face, but still only a request.

### 3. Prove the movement from observations

```bash
curl -sS http://state.training:8080/api/practice/observations
```

- Level walked `1200.0 L → 1000.0 L` in 20 L/s steps, consistent with ~10 s of flow.
- Terminal sample `PT-OBS-000011`, `terminal: true`, at `17:15:31.735437Z`, `status 1`,
  outlet closed again.
- That terminal sample's `batch_reference` is the challenge flag:
  `FLAG{03993cc3de147e23}`.

Note the ordering: the terminal observation is timestamped after the ~10 s of flow, not when
the request was accepted. Only that sample closes the batch and releases the flag.

## Why this works (the vulnerability explained)

Process automation has **three states that are routinely conflated**: *requested* (the API
accepted a well-formed command, `202`), *applied* (the controller acted: valve opened, hold
cleared) and *observed* (the instrument measured the result and wrote a sample). Each fails
independently — the request queues behind a hold, the actuator faults, the sensor is stale, the
batch is cancelled mid-flow. An integration that stops at state 1 reports transfers that never
happened: the mechanism behind real incidents where a dashboard shows product shipped while the
silo is still full.

Verifying at state 3 forces you to reconcile volume change, rate, timestamps and a terminal
marker — and the desk's bounds make it checkable, since a legal 200 L step takes a predictable
~10 s. An observation set that disagrees with that profile is provably not your transfer.

## Detection and fix

- **Log signal:** accepted transfers whose observation window shows no matching level change,
  or a change whose rate contradicts the configured flow rate; batches with no terminal sample.
- **Fix (client):** poll the observation stream until a terminal sample for your batch appears,
  compare start/end level against the requested quantity within tolerance, and only then report
  success. Never map `202` to "done".
- **Fix (server/device):** return the batch reference as an explicit correlation ID at
  acceptance, close every batch with an immutable terminal observation, alert when a batch has
  no terminal sample inside its expected duration, and re-check the hold and the reserve at
  execution time rather than only at submission.

## Notes and dead ends

- `OPTIONS` on the API returns `501`, and undocumented paths such as `/api/practice/sealed`
  return `404` — probing is a waste of time; the documented GET/POST interface is the whole API.
- The flag is not in the transfer response, only in the terminal observation: stopping at the
  `202` body would have looked like success and produced nothing. Nor do the frozen captures
  (`VC-017`, `SC-018`, `OR-042`) change when `PT-01` is operated, so they prove nothing here.
- The desk was left at `1000.0 L`, hold cleared, outlet closed, with `t04-hold-clear-1` and
  `t04-xfer-200-1` in the request register and 11 observations recorded.
