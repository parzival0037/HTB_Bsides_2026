**What you are about to read:** how an operation left half-finished can be completed by someone else.
The bug class is *collector-side trust*: the callback authenticates with a key the staging material
contains, and the collection is addressed rather than browsed, so whoever holds key and address can
take delivery — no exploitation of the ARWC side needed.

## Objective

> Reconstruct the earlier operation's callback configuration and recover its lost collection. Find
> out what it learned about the unresolved ARWC maintenance ticket.

Three things: the **callback configuration** (where the earlier stage was meant to report), the
**lost collection** (staged, never retrieved), and the **finding** about the maintenance ticket —
`SUP-2841`, "ARWC connector callback latency", with `ESC-2841` and `REV-2841` as siblings on the
support instance.

## Background you need

- **A callback is a rendezvous.** The K03.2 stage prepares data and reports to a host with an
  identifier and a key; if the host is gone but the identifier and key survive, the rendezvous can be
  re-established anywhere.
- **Object storage is addressed, not browsed.** Retained collections under `s3://fieldlink-exports`
  are not listable and need the exact bucket, key and digest — which is why K03.1's manifest matters.
- **Half-finished operations are the norm.** An operator who loses access leaves staged data with no
  reader: the writer side is complete, the collector side is not. That absence protects nothing.
- **The ARWC side is sealed.** `connector.arwc.test` (10.77.60.20) answers `403
  channel_identity_denied` to staff mTLS and SPNEGO, and only a handful of relay routes exist.

## Walkthrough

### 1. Recover the callback configuration (reconstructed)

No transcript survives, so this is technique, not capture. The configuration lives in the K03.1/K03.2
material: the stage's literals (host, path, identifier, key) and the instructions around them.
Enumerate the stage for assignments rather than reading it end to end:

```bash
# illustrative template
grep -nE '^[A-Z_]+=|https?://|token|key|collection|bucket' stage.sh
```

Look for the *shape* of a beacon: an endpoint, an operation identifier, a shared secret. Fill the
placeholders from the manifest — K03.2's reconstruction is what makes them usable.

### 2. Stand up the missing half

The collector side is nothing more than a listener that accepts the report, so a scratch HTTP server
on a host you control is sufficient:

```bash
# illustrative template — receiving end only
python3 -m http.server 8080 --bind 0.0.0.0          # or nc -l -p 8080
```

Keep it off the range's own services: this is your listener, and the staging material already knows
how to talk to it once the identifiers match.

### 3. Recover the lost collection

With the address from the manifest, the collection is a direct object-store read rather than a
search:

```bash
aws --endpoint-url https://objects.keplerops.test s3 ls s3://fieldlink-exports/<collection>/
aws --endpoint-url https://objects.keplerops.test s3 cp \
  s3://fieldlink-exports/<collection>/<key> ./lost-collection.json
```

If the listing is denied — as the range notes warn — go straight to the exact key and digest in the
manifest. Addressed reads succeed where browsing does not.

### 4. Read what it learned about SUP-2841

The collection is the earlier operation's answer to the ARWC question: observed callback latency, the
revision in play, and what the operator concluded about why the ticket never closed. That conclusion
is the substantive output — the collection is evidence, the *finding* is the answer.

### 5. Getting the flag

The accepted answer is recovered from the completed callback's delivery or from the recovered
collection. Accepted; which of the two carried the value was not recorded in the lane notes, so it is

## Why this works (the vulnerability explained)

Two design choices combine. **The collector authenticates, the data does not**: the callback accepts a
report because it presents the right identifier and key, and nothing asks whether the sender is the
*original* operator. **Object storage is capability-addressed**: bucket plus key is authorisation
enough, and keys stop being secret the moment they appear in a manifest.

The reusable lesson: **"lost" is not "protected"**. Data staged by an operation that cannot retrieve
it belongs to whoever recovers the configuration — usually because the rendezvous credentials were
stored beside the payload. Contrast the ARWC connector, which refuses staff certificates and SPNEGO
with `channel_identity_denied`: a bound channel identity is exactly what the callback lacks.

The mitigation is not endpoint secrecy (the material contains it) but *sender binding*: per-operation
callbacks revocable independently, and staged data encrypted to a key the writer does not hold. When
an operation is abandoned, its collection should be destroyed or re-keyed, not left addressed.

## Detection and fix

- **Log signal:** object reads for a key no active operation references; a callback key used from a
  new source address; deliveries to a listener outside the collector inventory.
- **Fix:** bind callback credentials to the sender, not just the operation; expire staged collections
  with the operation; destroy or re-key on abandonment; alert on first use of a callback key.
- **Data-side:** inventory retained collections against active operations — anything retained with no
  owner is a finding in itself.
