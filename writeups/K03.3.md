**What you are about to read:** how an operation left half-finished can be completed by someone else.
The bug class is *collector-side trust*: the callback authenticates with a key the staging material
contains and the collection is addressed rather than browsed, so whoever holds key and address takes
delivery.

## Objective

> Reconstruct the earlier operation's callback configuration and recover its lost collection. Find
> out what it learned about the unresolved ARWC maintenance ticket.

Three things: the **callback configuration** (where the earlier stage was meant to report), the **lost
collection**, and the **finding** about `SUP-2841`, "ARWC connector callback latency", with
`ESC-2841` and `REV-2841` as siblings on the support instance.

## Background you need

- **A callback is a rendezvous.** The K03.2 stage reports to a host with an identifier and key; if the
  host is gone but those survive, the rendezvous can be re-established anywhere.
- **Object storage is addressed, not browsed**: retained collections under `s3://fieldlink-exports`
  are not listable and need the exact bucket, key and digest — hence K03.1's manifest.
- **Half-finished operations are the norm**: an operator who loses access leaves staged data with no
  reader — writer side complete, collector side not.
- **The ARWC side is sealed**: `connector.arwc.test` (10.77.60.20) returns `403
  channel_identity_denied` to staff mTLS and SPNEGO, with only a handful of relay routes.

## Walkthrough

### 1. Recover the configuration

No transcript survives, so this is technique, not capture. The configuration lives in the K03.1/K03.2
material — the stage's literals (host, path, identifier, key) and the instructions around them:

```bash
# illustrative template
grep -nE '^[A-Z_]+=|https?://|token|key|collection|bucket' stage.sh
```

Look for the *shape* of a beacon: endpoint, operation identifier, shared secret. Fill placeholders
from the manifest — K03.2's reconstruction is what makes them usable.

### 2. Stand up the missing half

The collector is just a listener that accepts the report, so a scratch HTTP server on a host you
control is enough:

```bash
# illustrative template — receiving end only
python3 -m http.server 8080 --bind 0.0.0.0     # or: nc -l -p 8080
```
Keep it off the range's own services.

### 3. Recover the collection

With the address from the manifest, the collection is a direct read, not a search:

```bash
aws --endpoint-url https://objects.keplerops.test s3 ls s3://fieldlink-exports/<collection>/
aws --endpoint-url https://objects.keplerops.test s3 cp \
  s3://fieldlink-exports/<collection>/<key> ./lost-collection.json
```

If the listing is denied — as the range notes warn — go straight to the key and digest in the
manifest: addressed reads succeed where browsing does not.

### 4. Read the SUP-2841 finding, and get the flag

The collection is the earlier operation's answer to the ARWC question: observed callback latency, the
revision in play, and why the ticket never closed. The *finding* is the substantive output; the
collection is only evidence. The accepted answer comes from the completed callback's delivery or from
the collection itself — accepted, value not recorded.

## Why this works (the vulnerability explained)

Two design choices combine. **The collector authenticates, the data does not**: the callback accepts a
report because it presents the right identifier and key, and nothing asks whether the sender is the
*original* operator. **Object storage is capability-addressed**: bucket plus key is authorisation
enough, and keys stop being secret the moment they appear in a manifest.

The reusable lesson: **"lost" is not "protected"**. Staged data belongs to whoever recovers the
configuration — usually because the rendezvous credentials were stored beside the payload. Contrast
the ARWC connector, which refuses staff certificates and SPNEGO with `channel_identity_denied`: a
bound channel identity is exactly what the callback lacks. The mitigation is not endpoint secrecy (the
material contains it) but *sender binding*: per-operation callbacks revocable independently, and
staged data encrypted to a key the writer does not hold.

## Detection and fix

- **Log signal:** object reads for a key no active operation references; a callback key from a new
  source address; deliveries to a listener outside the collector inventory.
- **Fix:** bind callback credentials to the sender, not the operation; expire staged collections with
  the operation; re-key on abandonment; alert on first use of a callback key.
- **Data-side:** inventory retained collections against active operations — anything retained with no
  owner is itself a finding.
