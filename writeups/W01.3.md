**What you are about to read:** how to answer a business-process question from leaked

supplementary water, and which purchasing documents govern that supply.

## Objective

Determine how ARWC handles a dry-period shortfall and which purchasing records govern
supplementary water. This is a records-and-reasoning question, not an exploit: the answer
describes the arrangement and the identifiers of the purchasing instruments behind it.

## Background you need

- **"Buying time" is a real utility pattern.** When reservoir yield drops below demand a
  utility can restrict demand or purchase bulk water from a neighbour, carrier or trader.
  Purchased water is temporary capacity, deferring the capital decision — which is why the
  paper trail matters.
- **Three layers of purchasing record.** A *framework/standing agreement* authorises a
  supplier for a period; a *call-off / purchase order* draws a specific volume against it;
  an *invoice or delivery docket* evidences what actually moved. Confusing these three is
  the usual analysis error — "which records govern" means the authorising layer, not the
  invoice.
- **Retention overlap.** Those records are commercial, not operational, so they are rarely
  scoped like SCADA data. They end up in the same retained customer document set that the
  supplier reads for handover purposes.

## Walkthrough

### 1. Establish the shortfall narrative first

Before touching purchasing records, build the timeline you will test against: the short
period, the volume gap, and the response (restriction, transfer, purchase). Handover and
planning documents give the period and asset scope; purchasing records must line up with it.

### 2. Enumerate the retained commercial documents

With a working integration credential, pull the customer document set and filter for
commercial rather than engineering artefacts. The shape below is illustrative; the real
folder and file names come from the retained material:

```bash
# illustrative: list the retained set, then filter for commercial records
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: Bearer $SUPPORT_TOKEN" \
  "https://support.keplerops.test:8443/api/handovers/current" \
  | jq -r '.. | strings' | sort -u > /tmp/arwc-refs.txt

grep -Ei 'purchase|procure|supply|water|shortfall|drought|tanker|bulk' /tmp/arwc-refs.txt
```

You want a named arrangement (supplementary / bulk / emergency water supply) plus the
instrument identifiers that authorise drawdown against it.

### 3. Separate authorisation from evidence

For each candidate record, classify it:

| Layer | What it proves | Typical identifier |
|---|---|---|
| Framework / standing agreement | who may supply, how long, on what terms | agreement/contract number |
| Call-off / purchase order | a volume was authorised in the shortfall window | PO number, period, volume |
| Invoice / docket | water physically moved | delivery reference, date, volume |

Which records *govern* the supplementary water? The framework and call-offs; invoices only
corroborate.

### 4. Correlate against the shortfall window

Check that call-off dates and volumes sit inside the dry-period gap from step 1 and that the
agreement covers the same asset/network scope. Records dated outside the window, or scoped
to another supply zone, are decoys.

The accepted answer describes the shortfall response and names the governing purchasing
records. The solve record does not retain the literal values, so they are reported as
accepted, not reproduced.

## Why this works (the vulnerability explained)

The disclosure mechanism is the same retention problem as W01.1 and W01.2: commercial
documents sat in a document set whose access model is "anyone holding the integration
credential". No purchasing-specific control exists, because the supplier never modelled
these files as customer-confidential at all.

The analysis skill is the transferable part. Leaked business records are only useful if you
can reconstruct the decision chain: period → volume gap → authorising instrument → drawdown.
Attackers use this to profile a target's suppliers, contract values and operational stress;
defenders rarely log reads of "just documents", so the disclosure stays quiet.

## Detection and fix

- **Log signal:** bulk retrieval of a customer document set by a handover/delivery
  integration principal; reads of procurement filenames by a non-commercial role.
- **Fix:** separate commercial records from delivery evidence, scope shares per document
  class, and give integration tokens the minimum folder needed. Add classification
  metadata at upload and keep contract/PO metadata (supplier, period, volume, scope)
  structured so correlation is auditable.

## Notes and dead ends

- **Reconstructed, not observed.** This card was solved by the team agent; the record has no
  flag value and no transcript. The method comes from the challenge description plus the
  infrastructure notes, and no response is quoted because none was retained.
- Do not treat the supplier's delivery receipt as a purchasing record — it describes
  software delivery, not water.
- Volumes and dates are the join key. A record matching the supplier name but not the
  shortfall window is a decoy, not the governing instrument.
