| **Tools** | `tar`/`ln`, `curl`, `python3` |

**What you are about to read:** how a path confusion becomes a *deliberate* write: choose the target,
choose the bytes, confirm the change. The bug class is **write-what-where** derived from partly
attacker-controlled allocation — here the "allocation" is where the indexer decides a member belongs,
and the "where" is whatever that resolves to.

## Objective

> The indexer still restricts what your corrupted object can influence. Establish a controlled write
> capability under those restrictions and demonstrate it against the designated protected state.

The restrictions matter: the indexer writes only members it believes belong to the bundle, into storage
it believes it allocated, with content it validated as that type. The card asks you to work *inside*
those constraints and still land a chosen write on the designated protected state.

## Background you need

- **A write primitive has three parts**: destination control, content control, repeatability.
- **Allocation in an indexer is metadata**: per member it records a destination (path or slot id) and a
  size. If either comes from the manifest and is later used as the write address, the attacker chooses
  the address.
- **Two implementations of one flaw**: following a link/traversal on write (destination confusion), and
  honouring a declared size/offset that overlaps a neighbour (allocation overlap).

Reconstruction: the evidence records the objective and the K04.1/K04.2 chain, not this bundle format.

## Walkthrough

### 1. Fix the destination

From K04.2 you know the indexer's reach. Choose one *protected state* target whose change is observable
(a record field, a counter, a status). Fix the choice before touching anything: a primitive you cannot
aim is not a primitive.

```bash
# illustrative: a write-shaped member aimed at the chosen target
ln -s <protected-state-path> state.link; printf '%s' '<desired content>' > payload
tar -cf bundle.tar state.link payload
```

### 2. Fix the content, and overlap the allocation if links are refused

Content control has limits: a member claiming to be JSON must parse, one claiming to be an archive must
open — satisfy the validator *and* the target. If link members are refused but declared extents are
trusted, declare a size/offset landing inside the neighbouring record, so the write covers the protected
state's bytes instead of its own slot.

```bash
# illustrative: a declared extent overlapping the next allocation
python3 -c 'import json;print(json.dumps({"members":[{"name":"overlap.bin",
  "size":4096,"offset":<target-offset>}]}))'
```

Same arithmetic bug as an out-of-bounds write in native code: a length and offset from input, used to
compute a destination without checking the span against the allocation.

### 3. Demonstrate it

Write, then read back through a *different* path — the index, an API read, the object's own view. A
change visible only through your own request proves nothing. Confirm the protected state changed and
that a benign bundle cannot reproduce it.

## Why this works (the vulnerability explained)

The indexer decides two things per member: *what it is* and *where it goes*, both from the bundle.
Validation covers the first and is usually decent; the second is bookkeeping and rarely checked. That
asymmetry is the bug: strong content validation plus unvalidated destination control is a
write-what-where primitive with a well-formed payload.

Real-world twins:

- extraction tools that honour absolute paths or links (the write lives outside the sandbox);
- archive formats with attacker-controlled offsets or lengths — the classic `..`-in-a-header bug;
- allocators that trust a size field and hand back a span overlapping a neighbour;
- tenant-configurable output paths in log/metrics agents.

The lesson is *capability vs incident*. Most such bugs get reported as "can write a file outside the
directory", which is serious — but the exploitable question is whether the attacker picks the file *and*
the bytes. When both are controllable the bug composes, and composition is what K04.4 does.

Fix: derive destination server-side (job-assigned directory and slot), assert the resolved prefix at
open, bound declared extents against the real allocation, and keep content validation as the second
line of defence.

## Detection and fix

- **Log signal:** declared extents overlapping another record's span; resolved write paths outside the
  job root; indexer writes to protected-state paths; content valid for the validator but written
  outside its own slot.
- **Fix:** server-assigned destinations and slots, prefix assertions at open, extent bounds checks, and
  a write path that refuses links and traversal after canonicalisation.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K04.3 was solved by the team agent and the
  record is the description plus the indexer context. No transcript exists; commands are labelled
  illustrative and targets are placeholders.
- A write you cannot verify is not a capability: if the only evidence is your own upload response, you
  have proved nothing.
- Blindly overwriting the record is wrong: it is *protected* because damaging it breaks K04.4. Prefer a
  structural change (a field edit, not a truncate).
- Do not escalate to a crash: a dead process takes the indexer's identity with it, and K04.4 needs that
  identity alive.
