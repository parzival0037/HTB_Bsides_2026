**What you are about to read:** the pattern behind "a different way to recover" — one piece of

## Objective

> Recover the same retained support material by a route other than the one used in K17.1.

K17.1 recovered the retention note from the ticket panel. This card asks you to show the same
session is reachable when the panel is not the source — retention was applied to a *view*.

## Background you need

Every support workflow fans one conversation out into several stores: the ticket thread (osTicket,
agent role), the support handover (`:8443/api/handovers/current`, support bearer), the export
artefact (`EXP-2841` → `s3://fieldlink-exports`, export role), the assistant transcript
(`assistant.keplerops.test`, conversation ids) and worker run artefacts
(`review.keplerops.test/api/runs/...`).

That is normal engineering — and the canonical reason deletion fails: five writes, one delete.
"Retained" is replicated in all five, and the weakest access rule wins. The technique: identify the
artefact, enumerate the surfaces that carry it using ids from the ticket (`SUP-2841`, `EXP-2841`,
`ESC-SUP-2841-R3`, `REL-FLK-6.9.8-ARCHIVE`), then pick the one whose authorisation is weakest.

## Why this works (the vulnerability explained)

This is **copy proliferation without centralised revocation**. The content is duplicated for good
reasons; each copy gets its own guard, implemented by a different team at a different time; nothing
links them. Deleting or restricting one copy leaves the others untouched.

Two mechanisms:

1. **Identifier-driven retrieval.** Every copy is reachable by the *same* ids, with no per-copy
   secret and no globally revocable capability: case id plus any one bearer is enough.
2. **Weakest-link authorisation.** Agent role for the ticket, a support bearer living in a
   workstation file for the handover, an exchangeable audience token for the export — the union is
   weaker than the intersection the data owner imagines.

Correct design: one authoritative store with derived, short-lived views; a single "restricted"
marker every consumer re-checks at read time; and deletion that walks every derived copy (or a
content-addressed store where deleting the blob kills all views).

## Detection and fix

- **Log signal:** the same case read through two services in a short window; handover/export reads
  for a retained or closed case; access to `REL-FLK-6.9.8-ARCHIVE` by anything but the compliance job.
- **Fix:** centralise restricted-content authorisation so every view asks the same question; make
  retained content resolvable only through an audited compliance service; propagate deletion by
  content id, and keep an inventory of which stores hold a given ticket.
