## Background you need

Export systems partition data by tenant, then bind partitions to destinations. `partition_bindings`
is the glue: `partition | tenant | destination | state`.

Why that is sensitive with no customer records in it: it answers "who is affected", it reveals
co-tenancy (two customers in one partition makes any export defect cross-tenant — the K23 shape),
and it names destinations (the targets of the export-redirection cards). Metadata like this is
usually granted broadly because "it is only identifiers" — which is the mistake here.

## Why this works (the vulnerability explained)

Authorisation was applied at the level of **schema**: `support` is closed, so customer data is safe;
`export` stays readable because it holds "plumbing" — which encodes the relationship between
customers and export destinations. The requirement is not "don't show rows about customers" but
"don't reveal which customers are affected by which processing", and the binding table is exactly
that.

| What defenders classify | What attackers actually need |
|---|---|
| Customer PII rows | tenant ↔ partition ↔ destination map |
| The exported file | the definition that selected it (K15.2) |
| The conversation body | the conversation id and its tenant (K23.2) |

Least privilege implemented per schema instead of per question leaves the *relational* metadata
open. And `permission denied for schema support` is itself signal: the designers knew the data was
sensitive and treated the adjacent metadata as harmless — usually where the finding is.

## Detection and fix

- **Log signal:** `SELECT`s on `export.partition_bindings` from a role that never runs exports, or
  schema sweeps (`\dp`, `information_schema`) by developer roles.
- **Fix:** move binding metadata behind the export service (no direct SQL grant) or expose a view
  that omits tenant ids unless the caller owns them; grant reads only to `fieldlink_data_owner` and
  the export worker.
