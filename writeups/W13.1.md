# W13.1 — Window on Thursday

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Object-level authorisation gap on a scheduling API — an outlet-inspection appointment is readable by identifier, and the appointment body includes the maintenance reference |
| **Tools** | `curl`, `jq`, the SOCKS pivot |
| **Attack surface** | The scheduling resource on the cloud API (`cloud-api.keplerops.test` → `/api/schedules/{schedule_id}`), plus any appointment route the client reference advertises |
| **Prerequisite** | A valid session for the planning/appointment service (the retained staff account works) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how calendars leak operational detail, how to find the one
appointment that matters (the upcoming outlet inspection) in a list of many, and how the
maintenance reference on that appointment links it back to the plant records.

## Objective

Recover the upcoming outlet-inspection appointment and its maintenance reference. The card
wants the scheduled window ("Thursday") and the maintenance identifier the appointment is
booked under — not the roster (that is W13.2).

## Background you need

- **Schedules are data, not UI.** An appointment is a row: owner, subject, asset, start/end,
  attendees, free-form references. APIs return the row even when the UI renders only
  "Thursday 09:00–12:00".
- **Identifier-based retrieval.** Scheduling services expose `/api/schedules/{id}`. When the
  id is sequential, guessable or leaked elsewhere, lookup is effectively unauthenticated for
  anyone with a session — and authorisation is often "logged in", not "entitled to this row".
- **Maintenance reference.** Inspection windows are booked against a maintenance case (work
  order, defect, statutory inspection) — that reference ties the calendar entry to asset
  history.

## Walkthrough

### 1. Locate the scheduling surface

`ARWC-FINDINGS.md` lists `cloud-api.keplerops.test` and `/api/schedules/{schedule_id}`.
Confirm route and auth from the well-known contract:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  https://cloud-api.keplerops.test/.well-known/fieldkest-client | jq .
```

### 2. Read a known schedule, then walk the ids

Fetch one schedule you already have a handle for, note the id format, then walk neighbouring
ids (pattern only — not a captured session):

```bash
# illustrative: walk a bounded id space and keep the hits that look like inspections
for id in $(seq 1 200); do
  out=$(curl -sS --socks5-hostname 127.0.0.1:1080 -k -o /dev/null -w '%{http_code}' \
        "https://cloud-api.keplerops.test/api/schedules/$id")
  [ "$out" = "200" ] && echo "hit: $id"
done
```

Filter on content, not id: you want an appointment whose subject is an outlet inspection and
whose window is the upcoming Thursday.

### 3. Read the appointment body

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  "https://cloud-api.keplerops.test/api/schedules/$ID" | jq .
```

Expect the window, the asset/outlet group in scope, an owner, the attendee list and free-text
references (names vary by service). The maintenance reference is the identifier matching the
maintenance/work-order namespace, not the calendar's own id.

### 4. Confirm the window and the reference

Two checks make the answer defensible: the window is the expected upcoming slot and not in
the past, and the asset scope matches the outlet inspection with the maintenance reference in
the same record. If the reference is absent, inspect the owner/attendee objects returned
beside it — some implementations project references only on the related object.

### 5. Getting the answer

The card wants the window and the maintenance reference. The solve record does not retain
the values, so they are reported as accepted without being reproduced.

## Why this works (the vulnerability explained)

The endpoint authenticates the caller but never asks whether this caller may see *this*
schedule. A schedule is shared by design — owner, attendees, contractors — so implementers
treat "in the planning group" as sufficient. That collapses object-level authorisation: any
session can walk ids and read every appointment, including maintenance references that
disclose defects, outages and inspection history.

Sequential ids turn the gap into enumeration, and random ids still leak through other
responses (attendee lists, inspection records), so unguessability is not a control. The real
control is a per-object entitlement check on read.

## Detection and fix

- **Log signal:** one principal requesting a long run of `schedule_id` values; 404/200
  patterns indicating sequential walking; reads of schedules the caller is not an attendee of.
- **Fix:** authorise each schedule read against owner/attendee/tenant entitlement, return a
  projection that omits maintenance links for attendees who are not entitled, use
  unguessable ids, and rate-limit per principal.
- Secondary: keep maintenance references in the maintenance system and return a stable
  opaque handle from the calendar, so a schedule leak does not become a defect leak.

## Notes and dead ends

- **Reconstructed, not observed.** Solved by the team agent; the retained record holds only
  the description and route map — no captured response and no flag value. The enum loop is an
  illustrative template, not a transcript.
- Do not conflate this with the access roster (W13.2) or with replacing the attendee
  (W13.3); the appointment body is enough for this card.
- The maintenance reference is a link, not a location: reading it does not require access to
  the maintenance system, only to the appointment that quotes it.
