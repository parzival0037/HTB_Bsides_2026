# K23.2 — The conversation reference

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K23

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Dangling cross-tenant reference — a retained selection in one customer's case points at another customer's conversation, and the conversation route serves it |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/conversations/CONV-RILL-442-8` |
| **Prerequisite** | The support overlay cookie (`fieldkest_support=…`) and the conversation id from K23.1 |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how following a *reference* out of the ARWC support case lands in
Rillhaven's conversation, why the customer binding is the answer, and what a missing tenant check on
the conversation route means for the whole overlay.

## Objective

> A retained support artifact refers to a conversation outside the current case. Recover the actual
> reference and its customer binding.

Follow the pointer (`SEL-SUP-2841-12` → `ATT-DIAG-698` → case `SUP-2841`, tenant `TEN-ARWC-047`), find
that the referenced conversation is `CONV-RILL-442-8`, and read it to confirm its customer
(`TEN-RILL-022`).

## Background you need

**Cross-references are normal; unvalidated ones are not.** An agent working two tenants can
legitimately produce a selection naming another conversation; the bug is that the *read* of the
referenced object does not re-check the caller's tenant.

**Selections** are stored pointers recording which attachment an answer was drawn from
(`SEL-SUP-2841-12` → `ATT-DIAG-698`) — provenance, and provenance is what an investigator follows.
**Binding vs containment.** "Conversation X belongs to tenant Y" is a data field; "the caller may read
X" is an authorisation decision. With only the first, the id plus any support session is enough.

## Walkthrough

### 1. Read the map

```bash
curl -sS https://assistant.keplerops.test/api/contexts | jq 'keys'
# ctx-support-private-v4, ctx-rill-support-v3
```

`ctx-support-private-v4` (workspace `support-private`) lists `CONV-SUP-2841-19` and `DOC-RILL-442`;
`ctx-rill-support-v3` (tenant `TEN-RILL-022`) lists `CONV-RILL-442-8`.

### 2. Get the cookie and follow the reference out of the ARWC case

```bash
C="Cookie: fieldkest_support=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b"
```

```
SEL-SUP-2841-12  ->  ATT-DIAG-698  ->  case SUP-2841, tenant TEN-ARWC-047
                                    ->  references CONV-RILL-442-8
```

Nothing about `SUP-2841` suggests Rillhaven: an ARWC case's retained selection carries a Rillhaven id.

### 3. Read the referenced conversation

```bash
curl -sS -H "$C" https://assistant.keplerops.test/api/conversations/CONV-RILL-442-8 | jq
```

```json
{ "id": "CONV-RILL-442-8", "tenant": "TEN-RILL-022", "workspace": "rill-support" }
```

`tenant: TEN-RILL-022` — a different customer. That binding is the deliverable: it proves the
reference crosses the tenant boundary.

### 4. Getting the flag

The conversation response carried the flag. Lane notes record it as `FLAG{25723607dbdb5768}` with the
submission accepted; the card stores no value, so it is recorded as accepted/not recorded. (The K21
lane saw the same value when it fetched every conversation with the cookie — different card.)

## Why this works (the vulnerability explained)

The conversation route authorises on the **overlay session**, not on the conversation's tenant:

```
check:  is the caller a support overlay session?   -> yes (shared bearer)
check:  does this conversation id exist?           -> yes
absent: does conversation.tenant match the case?   -> never evaluated
```

The overlay bearer is a single shared credential — not per-agent, not per-tenant — so "a support
session" implies "every tenant's conversations"; the only protection left is id unguessability, and
K23.1 publishes ids unauthenticated.

The cross-tenant *reference* is the second half: stored provenance creates a graph edge from the ARWC
case to the Rillhaven conversation; systems validate the edge at write time and never at read time, so
it survives as a permanent bridge. **A reference is an authorisation claim; re-validate it on every
dereference.**

## Detection and fix

- **Log signal:** conversation reads where `conversation.tenant != caller.tenant`; one cookie reading
  across tenants; ids first seen in an unauthenticated inventory read.
- **Fix:** tenant-scope the overlay session; enforce `conversation.tenant == caller.tenant` (or an
  explicit grant) on every read; validate selection targets at read time; stop returning conversation
  ids in the open inventory. Check existing selections' target tenants — a cross-tenant provenance
  edge is a latent breach even if unwalked.

## Notes and dead ends

- Recorded facts: `CONV-RILL-442-8` reads with the support cookie and returns `tenant:
  "TEN-RILL-022"` plus the flag; `SEL-SUP-2841-12` belongs to `ATT-DIAG-698` / `SUP-2841` /
  `TEN-ARWC-047`; the inventory lists the conversation under `ctx-rill-support-v3`.
- Do not confuse this with `CONV-SUP-2841-19` (ARWC, K21.2): both read with the same cookie.
- Reading the conversation is not the end: the same pair serves `DOC-RILL-442`'s full text in K23.3,
  and that route is much slower (30–45 s) — budget timeouts.
- `stream-chat` stays a dead end: `mode` is ignored and `workspace.chatMode=automatic` wins.
