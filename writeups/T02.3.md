# T02.3 — Recovery is another way in

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Weak recovery proof — the takeover flow accepts knowledge that the desk itself discloses (account handle + case fragment + staff detail), so recon output becomes an authenticated session |
| **Tools** | `curl`, `jq`, a cookie jar |
| **Attack surface** | `POST http://accounts.training:8080/api/recovery/redeem` (10.77.40.30); released session used on `GET /api/handover` |
| **Prerequisite** | `case_fragment` from T02.1 (`CASE-7Q4M`) and `staff_detail` from T02.2 (`Blue cabinet 17`) |
| **Flag** | `FLAG{0efa33511b93dccd}` |

**What you are about to read:** how a password-recovery workflow turns two pieces of
enumerable metadata into a full account takeover, and what the released session gives you.
The interesting part is not the request — it is that the "second factor" was printed by
another unauthenticated endpoint of the same service.

## Objective

> Use the identity evidence to take over the rehearsal account through its recovery
> workflow, then read its private handover.

T02.1 and T02.2 produced two values: a case reference bound to `rhea.moss` and a staff
detail from her hidden directory record. This card is the composition — feed both into the
documented recovery endpoint, receive a session, and use it to read the material the desk
only shows a logged-in owner.

## Background you need

- **Recovery is an authentication path.** Whatever the flow accepts as proof *is* the
  credential for that account. Reviews tend to look at `/login` and forget
  `/api/recovery/redeem`.
- **Proof quality is everything.** A good flow uses a channel the attacker does not control
  (email link, TOTP, push). A weak flow uses *knowledge*: date of birth, employee number,
  case id. Knowledge is only a factor if it is not published.
- **Correlation across endpoints is the attack.** Each disclosed field is low value alone —
  a case reference, a cabinet label. The desk releases them from different routes and
  assumes the combination is private. It is not: both routes are anonymous.
- **State change, not read.** Redemption typically mints a session and consumes a one-time
  token. That means the action is auditable and leaves a footprint — useful for the
  defender, and a reason not to repeat it needlessly.

## Walkthrough

### 1. Recon — the flow is documented on the front page

The markdown index advertises the complete contract, including the body shape:

```bash
H=http://accounts.training:8080
curl -sS $H/ | sed -n '1,60p'
```

```
POST /api/recovery/lookup   {"account": "exact.handle"}
POST /api/recovery/redeem   {"account", "case_fragment", "staff_detail"}
GET  /api/handover          (session)
GET  /api/assignments       (session)
```

Three inputs, all of which we already have:

| Field | Value | Source |
|---|---|---|
| `account` | `rhea.moss` | `/candidates.md` + the active branch of the lookup (T02.1) |
| `case_fragment` | `CASE-7Q4M` | `200` body from `POST /api/recovery/lookup` (T02.1) |
| `staff_detail` | `Blue cabinet 17` | `GET /api/directory/staff/STF-204/assignment` (T02.2) |

That table is the vulnerability in miniature: two of the three "secrets" were read from
endpoints that require no authentication at all, and the third is a public handle.

### 2. Finding the flaw — the proof is inventory, not identity

Compare what the flow calls the fields with what they actually are:

- `case_fragment` — an *account-bound reference*, explicitly described that way by the desk,
  returned by the lookup endpoint to anyone who names the account.
- `staff_detail` — a *physical location* (`Blue cabinet 17`) stored on the staff directory
  record, returned by a sub-resource that forgot its authorization check.

Neither is a secret held by the user. They are attributes of the account, and every attribute
of this account was readable anonymously. The recovery flow therefore authenticates the
caller against information the service publishes — a knowledge check where the knowledge is
public.

### 3. Exploitation — redeem, capture the session

Send the three values in one request and keep the cookie:

```bash
curl -sS -i -c /tmp/rhea.jar -H 'Content-Type: application/json' \
  -d '{"account":"rhea.moss","case_fragment":"CASE-7Q4M","staff_detail":"Blue cabinet 17"}' \
  $H/api/recovery/redeem
```

```
HTTP/1.1 201 Created
Set-Cookie: CINDER_REHEARSAL_SESSION=…; HttpOnly; SameSite=Strict
```

```json
{"flag": "FLAG{0efa33511b93dccd}", "session": "…", "subject": "rhea.moss"}
```

`201` rather than `200` is the honest signal: something was *created* — a session bound to
`rhea.moss`. The session is accepted both as the `CINDER_REHEARSAL_SESSION` cookie and as a
bearer value, so either of these works:

```bash
curl -sS -b /tmp/rhea.jar  $H/api/handover
curl -sS -H "Authorization: Bearer $SESSION" $H/api/handover
```

### 4. Getting the flag — and the handover

The flag is in the redeem response itself (`FLAG{0efa33511b93dccd}`, accepted on the second
global attempt / first correct submission by this lane). The takeover also unlocks the
private handover, which is the real prize for the chain:

```bash
curl -sS -b /tmp/rhea.jar $H/api/handover
```

That document describes the reception rehearsal: rhea's own assignment `ASG-204`, the paired
dispatch assignment `ASG-317`, and a pointer at `GET /api/assignments/{id}/brief` — the route
that T02.4 abuses. The session (`subject: rhea.moss`) remained valid afterwards, which is
why the next card needs no new recovery.

## Why this works (the vulnerability explained)

Recovery flows exist to restore access when the primary credential is lost, which means they
are an alternative authentication path with its own (usually weaker) proof requirements. The
security of the whole login system is the *minimum* over all paths that can produce a
session.

This desk's path required: a public handle, a reference returned by an anonymous lookup, and
a location returned by an anonymous directory sub-resource. Every input was either published
or leaked, so the proof proved nothing an attacker did not already have. In effect the flow
was a *password-free login for anyone who had done the recon*.

Two design mistakes are worth naming separately:

1. **Choosing account attributes as the proof.** "Case fragment" and "staff detail" are
   inventory fields. Using them as a challenge is the digital equivalent of a security
   question ("what is your mother's maiden name") where the answer is in the corporate
   directory.
2. **Publishing the challenge.** Even a mediocre knowledge factor can be acceptable if it
   is not disclosed. Here the same service returned it to unauthenticated callers, so the
   factor was not weak — it was *already given away*.

Correct design: proof must come from a channel the attacker cannot read (the account's
verified mailbox, a hardware token) or be delivered out of band; and the redeem step must
be single-use, expiry-bound, and rate-limited per account and per source.

## Detection and fix

- **Detection:** a successful `/api/recovery/redeem` preceded, within a short window, by an
  anonymous lookup of the same handle and an anonymous request for that staff record. The
  sequence is the signature; any one event alone looks like a user who forgot their
  password. Also alert on recovery from a new source IP or user agent and on sessions
  created outside business hours.
- **Fix:** do not accept directory attributes as recovery proof. Send a one-time token to
  the account's verified contact channel and require it, then bind the redeemed session to
  the same client (short TTL, rotate on use). Rate-limit and lock out after N attempts,
  make fragments single-use, and remove `case_fragment`/`staff_detail` from any anonymous
  response. Add an explicit audit event per recovery attempt with the source and the
  account, so the recon→redeem sequence is visible.

## Notes and dead ends

- Facts are from the identity-desk lane artifacts: the redeem request body, the `201`
  status, the session cookie flags (`HttpOnly`, `SameSite=Strict`) and the response fields
  (`flag`, `session`, `subject`) are captured; the session value itself is omitted here.
- The redeem body is exact-match: `{"account","case_fragment","staff_detail"}` with those
  three keys. Extra or renamed fields are rejected, so "send everything you saw" does not
  work — the proof has to be the right attributes, which is the point of the card.
- The handover route is the authenticated payoff, but the flag for *this* card comes from
  the redeem response, so no additional request is needed to satisfy it. Keep the session
  though: T02.3 does not end the chain, it starts the authenticated half of it.
- Sessions are cookie-or-bearer; if a client ignores `SameSite=Strict`, remember that the
  attribute only limits cross-site *browser* sends — it does nothing against a script that
  holds the token.
