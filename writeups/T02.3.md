# T02.3 — Recovery is another way in

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Weak recovery proof — the takeover flow accepts knowledge the desk itself discloses (handle + case fragment + staff detail), so recon output becomes an authenticated session |
| **Tools** | `curl`, `jq`, a cookie jar |
| **Attack surface** | `POST http://accounts.training:8080/api/recovery/redeem` (10.77.40.30); the released session reads `GET /api/handover` |
| **Prerequisite** | `case_fragment` from T02.1 (`CASE-7Q4M`) and `staff_detail` from T02.2 (`Blue cabinet 17`) |
| **Flag** | `FLAG{0efa33511b93dccd}` |

**What you are about to read:** how a password-recovery workflow turns two enumerable pieces of
metadata into an account takeover — the "second factor" was printed by unauthenticated endpoints.

## Objective

> Use the identity evidence to take over the rehearsal account through its recovery workflow, then
> read its private handover.

T02.1 and T02.2 produced a case reference bound to `rhea.moss` and a staff detail from her hidden
record; this card composes them into a session, and reads what the desk shows only to its owner.

## Background you need

- **Recovery is an authentication path.** Whatever the flow accepts as proof *is* the credential;
  reviews watch `/login` and forget `/api/recovery/redeem`.
- **Proof quality is everything.** A sound flow uses a channel the attacker does not control
  (mailbox link, TOTP); a weak one uses *knowledge* — a factor only if it is not published.
- **Correlation across endpoints is the attack.** A case reference and a cabinet label are low
  value alone, so the desk releases them from different routes and assumes the combination is
  private — but both routes are anonymous.
- **Redemption is a state change** (new session, one-time token) — auditable.

## Walkthrough

### 1. Recon — the flow is documented on the front page

```
POST /api/recovery/lookup  {"account":"exact.handle"}
POST /api/recovery/redeem  {"account","case_fragment","staff_detail"}
GET  /api/handover, /api/assignments   (session)
```

Three inputs, all already in hand: `account` = `rhea.moss` (`/candidates.md` + active lookup),
`case_fragment` = `CASE-7Q4M` (T02.1's `200`), `staff_detail` = `Blue cabinet 17` (T02.2). That is
the vulnerability in miniature: two of the three "secrets" came from endpoints requiring no
authentication, the third is a public handle.

### 2. Finding the flaw — inventory is not identity

`case_fragment` is an *account-bound reference* returned by the lookup to anyone naming the
account; `staff_detail` is a *physical location* from a sub-resource that forgot its check (T02.2).
Neither is a secret held by the user: both are account attributes, and every attribute of this
account was readable anonymously.

### 3. Exploitation — redeem, capture the session

```bash
H=http://accounts.training:8080
curl -sS -i -c /tmp/rhea.jar -H 'Content-Type: application/json' -d \
 '{"account":"rhea.moss","case_fragment":"CASE-7Q4M","staff_detail":"Blue cabinet 17"}' \
 $H/api/recovery/redeem
```

```
HTTP/1.1 201 Created
Set-Cookie: CINDER_REHEARSAL_SESSION=…; HttpOnly; SameSite=Strict
{"flag": "FLAG{0efa33511b93dccd}", "session": "…", "subject": "rhea.moss"}
```

`201` is the honest signal: something was *created* — a session bound to `rhea.moss`. It is
accepted as the `CINDER_REHEARSAL_SESSION` cookie or as a bearer value, so both work:

```bash
curl -sS -b /tmp/rhea.jar $H/api/handover
curl -sS -H "Authorization: Bearer $SESSION" $H/api/handover
```

### 4. Getting the flag and the handover

The flag is in the redeem response (`FLAG{0efa33511b93dccd}`, accepted on the second global
attempt). The takeover also unlocks the private handover — `curl -sS -b /tmp/rhea.jar
$H/api/handover` — which names rhea's own assignment `ASG-204`, the paired dispatch assignment
`ASG-317`, and `GET /api/assignments/{id}/brief`, the route T02.4 abuses. The session stayed valid
afterwards, so the next card needs no new recovery.

## Why this works (the vulnerability explained)

The security of a login system is the *minimum* over every path that produces a session. This
recovery path needed a public handle, a reference from an anonymous lookup and a location from an
anonymous sub-resource — every input published or leaked, so the proof proved nothing new.

Two design mistakes. First, **account attributes were chosen as the proof**: inventory fields are
a security question whose answer sits in the corporate directory. Second, **the challenge was
published**: even a mediocre knowledge factor is acceptable if it is not disclosed, but here the
service handed it to unauthenticated callers. The factor was not weak, it was given away.

## Detection and fix

- **Detection:** a successful redeem preceded shortly by an anonymous lookup of the same handle and
  an anonymous request for that staff record. The sequence is the signature; any single event looks
  like a user who forgot their password. Alert on new source IPs too.
- **Fix:** stop accepting directory attributes as proof. Send a one-time token to the verified
  contact channel and require it; bind the session to the client (short TTL, rotate on use);
  rate-limit and lock out after N attempts; make fragments single-use; remove
  `case_fragment`/`staff_detail` from anonymous responses; audit every attempt.

## Notes and dead ends

- Facts are from the identity-desk lane artifacts: the request body, `201` status, cookie flags
  (`HttpOnly`, `SameSite=Strict`) and response fields (`flag`, `session`, `subject`) are captured;
  the session value is omitted.
- The body is exact-match on those three keys; extra or renamed fields are rejected, so "send
  everything you saw" does not work.
- The flag comes from the redeem response, so the handover request is not needed for this card;
  keep the session for T02.4. `SameSite=Strict` only limits cross-site *browser* sends.
