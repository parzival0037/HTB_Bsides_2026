# K04.1 — A bundle with consequences

> **Category:** 2. KeplerOps · **Points:** 200 · **Difficulty:** hard
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unsafe extraction / trusted bundle metadata — paths and object identities taken from the bundle itself |
| **Tools** | `tar`/`zip`, `python3`, `curl` against the indexer client routes |
| **Attack surface** | `https://indexer.keplerops.test` (10.77.51.70) — the support bundle upload/index path |
| **Prerequisite** | Any identity the indexer accepts as an uploader; the indexer's published client reference |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a routine "upload a bundle, let the indexer sort it out" flow
becomes a write primitive outside the uploaded object. The bug class is *bundle-declared state*: the
archive decides where its members land and what they claim, and the indexer trusts both.

## Objective

> The support indexer treats uploaded bundles as routine work. Construct a bundle that causes a
> controlled change beyond the object it should be allowed to affect.

The word to hold onto is **controlled**: not a crash or arbitrary writes anywhere, but a *specific*
change to something other than the object you uploaded — a capability, and what the next cards build
on.

## Background you need

- **A bundle is a container with instructions**: a manifest (which object, which members) plus the
  members; the indexer reads it, extracts and indexes.
- **Two classic mistakes follow.** Extracting by declared member names lets `../` and absolute paths
  escape the extraction directory (*tar-slip / zip-slip*); using the manifest's object identity
  without a scope check lets a bundle claim an object it does not own.
- **Indexers are deliberately forgiving**: they must handle malformed third-party archives, so they
  normalise and "best effort" write — turning a bad path into a successful write.

This is reconstruction: the evidence records the objective, not the bundle format.

## Walkthrough

### 1. Read the indexer's own contract

```bash
curl -sS https://indexer.keplerops.test/.well-known/fieldkest-client | jq .
```

The client reference names the upload route and, more importantly, the *manifest schema* — which says
which fields the indexer reads from the bundle, hence which it trusts.

### 2. Establish the baseline behaviour

Upload a benign bundle and read the answer: which object id it echoes, which member paths it returns.
A confirmation of "member `a/b.json` landed under object `<id>`" tells you whether names are honoured
literally.

The upload is a single multipart field (illustrative: `curl -F 'bundle=@bundle.tar' .../<route>`),
where route and field name come from the client reference, not guesswork.

### 3. Build the bundle that reaches sideways

Three constructions, in order:

| Technique | Bundle content | Expected effect |
|---|---|---|
| Traversal member | `../../<other-object>/<file>` | write lands in another object's area |
| Symlink member | link `here` → `../<other-object>`, then a member under `here/` | write follows the link |
| Identity claim | manifest `object_id` of another object | indexer updates the wrong entry |

```bash
# illustrative: a traversal member inside an otherwise normal tar
tar --transform='s|^|../../<other-object>/|' -cf bundle.tar members/
```

Choose `<other-object>` deliberately: one whose change is observable (a status field, a count, a
marker file), so you can prove the write landed.

### 4. Verify the effect, not the response

Read the *other* object through a normal path, not the upload response. If upload returns `200` but the
target is unchanged, the path was normalised — try the next technique.

### 5. Getting the flag

The accepted answer follows from the demonstrated out-of-scope change. Accepted; value not recorded.

## Why this works (the vulnerability explained)

The indexer has two responsibilities that must be separate and are not: *decoding an untrusted
container* and *deciding which object the content belongs to*. Both come from data inside it.

The bug class generalises well beyond support bundles: **archive extraction** where member names are
relative paths (`tar-slip`, `zip-slip`, and the symlink variant where the link exists before the
members passing through it), **manifest-driven identity** where the upload names the resource it wants
to modify, and **"best effort" error handling** that turns a rejection into a partial write.

The correct implementation is boring: canonicalise every member path and reject anything resolving
outside the extraction root, refuse links in inbound archives, derive object identity from the
authenticated uploader's scope, and extract into a directory the server names. This is a *capability*
rather than a curiosity because the indexer has more reach than the uploader — writing through it
means writing as it.

## Detection and fix

- **Log signal:** members with `..`, absolute paths, links or duplicate names; extracted paths outside
  the job prefix.
- **Fix:** canonicalise and prefix-check every member, reject links, derive identity from the session,
  extract into a sandbox, make failure atomic.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K04.1 was solved by the team agent; the
  record is the challenge description plus the indexer's range-map entry and `.well-known` client
  reference. No transcript exists — commands are illustrative and the bundle schema stays generic.
- A bundle that simply fails validation proves nothing: the card wants a *change elsewhere*, so a
  schema error is a dead end. If traversal members are normalised, do not escalate to "corrupt it until
  something breaks" — a crash is not the controlled change.
- The indexer is support-facing, not a customer system: ARWC (`10.77.60.x`) is a separate boundary.
