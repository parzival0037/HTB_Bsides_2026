# K21.1 — The policy beside the prompt

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K21

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unauthenticated configuration disclosure — the assistant's `/api/config` exposes its system prompt, policy wiring and internal context/workspace identifiers |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://assistant.keplerops.test/api/config`, `/api/workspaces` |
| **Prerequisite** | None — network reachability to the assistant |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how an LLM assistant's configuration endpoint, left open for the
front-end, publishes the system prompt and with it the *pointer* to restricted data — the workspace
and context id the K21/K23 cards dereference. The leak is a map, and the map is enough.

## Objective

> Recover the support assistant's exposed configuration and identify the restricted support context
> attached to it.

Two artefacts: the configuration blob (which contains the flag), and the restricted context it names
— workspace `support-private`, context `ctx-support-private-v4`.

## Background you need

AnythingLLM-style assistants split into a **workspace** (a room with instructions, model and attached
documents), a **context** (the retrieval scope: documents, selections, conversations) and the
**system prompt** (`openAiPrompt`) containing instructions, policy references and tool wiring.

A single-page front-end needs the prompt and workspace metadata to render, so `/api/config` is
frequently unauthenticated. That is tolerable only if the prompt contains nothing sensitive. Here it
carries the **policy reference** — written by the security team, so it describes exactly what is
protected — and the context id where the restricted material lives.

Note also that `published: true/false` is a UI/visibility flag, not an access control (see K23.1).

## Walkthrough

### 1. Ask the assistant for its configuration

```bash
curl -sS https://assistant.keplerops.test/api/config | jq
```

No `Authorization` header, no cookie. The response includes `openAiPrompt` (with the policy reference
inside it), example objects used for tool/answer demos — selection `SEL-SUP-2841-12`, completion
example `COMP-JOB-17`, tool review `DREV-2841-2` — the workspace/context wiring for `support-private`
/ `ctx-support-private-v4`, and the flag.

### 2. Enumerate workspaces with the same missing auth

```bash
curl -sS https://assistant.keplerops.test/api/workspaces | jq
curl -sS https://assistant.keplerops.test/api/config \
  | jq -r '.openAiPrompt' | grep -iE 'support-private|ctx-|policy'
```

`support-private` is the workspace behind the support assistant, and `ctx-support-private-v4` is the
handle every later request needs.

### 3. Read the configuration like an attacker

The prompt tells you what the *model* is told to refuse; the context id tells you where the material
it must refuse to reveal actually lives:

```
policy:      "do not disclose escalation notes to support-tier callers"
evidence:    the notes are documents in ctx-support-private-v4, conversation CONV-SUP-2841-19
consequence: the model's refusal is a text filter; the document route is the real boundary
```

That gap — policy expressed in prose versus authorisation in code — is exactly what K21.3 exploits.

### 4. Getting the flag

`GET /api/config` returns the flag in the same unauthenticated response. Lane notes record it as
`FLAG{bda988856f374cc1}` (the "policy ref") with the submission accepted; the card stores no value, so
it is recorded as accepted/not recorded.

## Why this works (the vulnerability explained)

The endpoint was scoped by *what the UI needs*, not *what a caller may know*. A front-end genuinely
needs the prompt to render the "how this assistant behaves" panel — but that need is per authenticated
user, not public, and the missing check turns a rendering convenience into publication.

The compounding issue is what teams put in prompts: policy references, internal tool names, data-source
ids, escalation rules and sample records. Anyone reading the prompt learns which guardrail exists (so
how to phrase around it), which context/tenant/document ids matter (so where to go directly), and which
demo objects are real — `SEL-SUP-2841-12`, `COMP-JOB-17` and `DREV-2841-2` are live ids, not fixtures.

The prompt is configuration, and configuration leaks are the most reliable kind: they need no exploit,
only a `GET`. Correct design: authenticate `/api/config`, return only fields the caller's role needs,
resolve policy server-side at inference time, and treat context ids as capabilities rather than names.

## Detection and fix

- **Log signal:** `/api/config` and `/api/workspaces` requests from unauthenticated clients or hosts
  outside the front-end; a spike of config reads followed by document-route calls (the K21/K23 pattern).
- **Fix:** require a session for config; redact `openAiPrompt` to a summary for non-admin roles; move
  `ctx-*` ids into server-side configuration; stop shipping live object ids as prompt examples; put
  the authorization check in the retrieval layer and let the prompt *describe* it.

## Notes and dead ends

- The lane recorded four concrete disclosures: workspace `support-private`, context
  `ctx-support-private-v4`, and the example ids `SEL-SUP-2841-12`, `COMP-JOB-17`, `DREV-2841-2`. The
  exact JSON shape was not preserved, so the field list is descriptive.
- `/api/config` being open does not mean the conversation routes are: they need the
  `fieldkest_support` cookie (K21.2).
- AnythingLLM's chat path is a dead end for "ask the model to reveal it": `stream-chat` ignores the
  requested `mode` and uses `workspace.chatMode = automatic`, so native tool-calling never fires.
