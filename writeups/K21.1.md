# K21.1 — The policy beside the prompt

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K21

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unauthenticated configuration disclosure — the assistant's `/api/config` exposes its system prompt, policy wiring and internal context/workspace identifiers |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://assistant.keplerops.test/api/config`, `/api/workspaces` |
| **Prerequisite** | None — network reachability to the assistant |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how an LLM assistant's configuration endpoint, left open for the
front-end, publishes the system prompt and with it the *pointer* to restricted data — the
workspace and context id that the later K21/K23 cards dereference. The leak here is a map, and
the map is enough.

## Objective

> Recover the support assistant's exposed configuration and identify the restricted support
> context attached to it.

Two artefacts: the configuration blob itself (which contains the flag), and the restricted
context it names — workspace `support-private`, context `ctx-support-private-v4`.

## Background you need

Assistants built on AnythingLLM-style stacks split into:

| Piece | Purpose | Typical exposure |
|---|---|---|
| workspace | a chat "room" with instructions, model, and attached documents | admin UI |
| context | the retrieval scope for a conversation (documents, selections) | internal API |
| `openAiPrompt` / system prompt | the instructions, including *policy* text and tool wiring | served to the browser |
| vector store | the embedded documents | internal |

A single-page front-end needs the system prompt and workspace metadata to render, so `/api/config`
is frequently unauthenticated. That is tolerable only if the prompt contains nothing sensitive.
Here the prompt carries the **policy reference** — the rule set the assistant must follow — and
the context id where the restricted material lives. Policy text is written by the security team,
which means it describes exactly what is protected.

`published: true/false` on contexts is a UI/visibility flag, not an access control; the K23.1
card shows the same pattern on `/api/contexts`.

## Walkthrough

### 1. Ask the assistant for its configuration

```bash
curl -sS https://assistant.keplerops.test/api/config | jq
```

No `Authorization` header, no cookie. The response includes:

- `openAiPrompt` — the support assistant's system prompt;
- a policy reference inside that prompt (the assistant's guardrails, named so an operator can
  look them up);
- example objects used for tool/answer demos: selection `SEL-SUP-2841-12`, completion example
  `COMP-JOB-17`, tool review `DREV-2841-2`;
- the workspace/context wiring for `support-private` / `ctx-support-private-v4`;
- the flag for this card.

### 2. Enumerate workspaces with the same (missing) auth

```bash
curl -sS https://assistant.keplerops.test/api/workspaces | jq
```

`support-private` is the workspace backing the support assistant. The name and the
`ctx-support-private-v4` id are the handles every later request needs:

```bash
curl -sS https://assistant.keplerops.test/api/config \
  | jq -r '.openAiPrompt' | grep -iE 'support-private|ctx-|policy'
```

### 3. Read the configuration like an attacker

The prompt tells you what the *model* is told to refuse, and the context id tells you where the
material it must refuse to reveal actually lives. Example of the reasoning:

```
policy:        "do not disclose escalation notes to support-tier callers"
evidence:      the notes are documents in ctx-support-private-v4, conversation CONV-SUP-2841-19
consequence:   the model's refusal is a text filter; the document route is the real boundary
```

That gap — a policy expressed in prose versus an authorization check in code — is exactly what
K21.3 exploits.

### 4. Getting the flag

`GET /api/config` returns the flag in the same unauthenticated response. Lane notes record the
value as `FLAG{bda988856f374cc1}` (the "policy ref") and state it was submitted and accepted;
the scoreboard card itself stores no value, so treat it as accepted/not recorded.

## Why this works (the vulnerability explained)

The configuration endpoint was scoped by *what the UI needs*, not by *what a caller may know*. A
front-end genuinely needs the prompt text to render the "how this assistant behaves" panel — but
that need is per-authenticated-user, not public. The missing auth check turns a rendering
convenience into publication.

The compounding issue is **what teams put in prompts**. Modern system prompts contain policy
references, internal tool names, data-source ids, escalation rules and sometimes sample records.
Anyone reading the prompt learns:

1. which guardrail exists (so how to phrase around it),
2. which context/tenant/document ids matter (so where to go directly),
3. which demo objects are real (here, `SEL-SUP-2841-12`, `COMP-JOB-17`, `DREV-2841-2` are all
   live ids, not fixtures).

The prompt is configuration, and configuration leaks are the most reliable kind: they require no
exploit, only a `GET`.

Correct design: authenticate `/api/config`, return only the fields the caller's role needs, and
keep policy/binding metadata out of the client-visible prompt (resolve it server-side at
inference time). Treat context ids as capabilities, not names.

## Detection and fix

- **Log signal:** `/api/config` and `/api/workspaces` requests from unauthenticated clients or
  from hosts outside the assistant's front-end; a spike of config reads followed by document
  route calls (the K21/K23 pattern).
- **Fix:** require a session for config; redact `openAiPrompt` to a "policy summary" for
  non-admin roles; move `ctx-*` ids into server-side configuration; stop shipping live object
  ids as prompt examples.
- **Design review:** any assistant that enforces policy *only in prose* is relying on model
  obedience. Put the authorization check in the retrieval layer, and make the prompt describe
  the check rather than implement it.

## Notes and dead ends

- The lane recorded four concrete disclosures in the config: workspace `support-private`,
  context `ctx-support-private-v4`, and the example ids `SEL-SUP-2841-12`, `COMP-JOB-17`,
  `DREV-2841-2`. The exact JSON shape around them was not preserved, so the field list above is
  descriptive rather than verbatim.
- `/api/config` being unauthenticated does not mean `/api/contexts` is: K23.1 found the context
  inventory open too, but the *conversation* routes need the `fieldkest_support` cookie (K21.2).
- AnythingLLM's chat path is a dead end for the "ask the model to reveal it" approach —
  `stream-chat` ignores the requested mode and uses `workspace.chatMode = automatic`, so native
  tool-calling never fires. Read the data routes, not the chat.
