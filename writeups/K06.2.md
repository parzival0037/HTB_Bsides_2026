# K06.2 — A private package in the wrong view

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-privileged CI identity — a build job holds a registry credential for a package developers cannot read, and the credential is recoverable from the job's own configuration or output |
| **Tools** | `curl` (Jenkins JSON API), `git`, `npm` |
| **Attack surface** | `https://ci.keplerops.test` (`fieldlink-report`, `fieldlink-report-review`) → `https://packages.keplerops.test` |
| **Prerequisite** | The publishing credential from K06.1; route to the CI host |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how an independent package-check build becomes a second,
differently-privileged identity on the same registry, and how to find its credential in CI
metadata rather than in source.

## Objective

Your publishing account cannot read the private support package. Investigate the
independent package-check build and recover the distinct CI identity that *can* read it.

## Background you need

- **CI is a principal.** Jenkins jobs authenticate to other services with credentials from
  the Jenkins store, injected into the build environment. To the registry a build is just
  another user — a service account with a different (often narrower) scope than any human.
- **"Independent build"** matters: the package-check job is not the job you already have
  access to. It validates a package against the support interface, so it must be able to
  *install* the private package — i.e. read it.
- **Where CI credentials leak:** job `config.xml`, `withCredentials`/`environment` blocks,
  `consoleText` from a build that echoes its environment, bind-mounted `.npmrc` files, and
  lockfiles with resolved URLs. The scope in the range's client references is
  `@keplerops/support-rehearsal`.

## Walkthrough

### 1. Recon — list jobs and read their contract

```bash
# illustrative: enumerate job metadata
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://ci.keplerops.test/job/fieldlink-report/api/json?tree=name,description,builds[number,result]'
```

`fieldlink-report-review` is the interesting one: it accepts a package zip via
`buildWithParameters` (documented in the range notes). A job that accepts a package and
reviews it is a job that installs it.

### 2. Finding the flaw — the job authenticates as someone else

Two independent signals:

1. **The job reaches a scope the developer token cannot.** If the package-check could only
   use the developer credential, it would fail on the private package — yet its builds are
   green.
2. **A package-check console shows the private install succeeding**, typically with the
   resolved tarball URL and the auth scope line. A build installing what you allegedly
   cannot see is proof of a second identity.

The credential itself surfaces in the usual places: a credential binding in `config.xml`, an
`environment {}` block, or a console line from a step that prints npm configuration. It is a
*different* string from K06.1's token — that is the point of the card.

### 3. Exploitation — use the CI identity, not yours

```bash
# illustrative: confirm the new identity and read what yours could not
npm --userconfig /tmp/ci.npmrc whoami --registry https://packages.keplerops.test
npm --userconfig /tmp/ci.npmrc view @keplerops/support-rehearsal \
  --registry https://packages.keplerops.test
npm --userconfig /tmp/ci.npmrc pack @keplerops/support-rehearsal \
  --registry https://packages.keplerops.test
```

`view`/`pack` succeed where K06.1's token returned a permission error. The package's
metadata and contents are what the card wants; manifests, fixtures and embedded
configuration in the tarball are now readable.
### 4. Getting the flag

Solved by a team agent; `wu_data.json` retains only metadata, so the accepted value is
**not recorded**. The demonstrated route is: Jenkins package-check build → distinct CI
registry identity → read of the private support package.

## Why this works (the vulnerability explained)

This is **over-privileged automation**, with a discovery twist.

- The package-check job legitimately needs read on one private scope. That alone is fine.
- But the job is reachable and inspectable by a developer identity, and it carries its
  credential where that identity can read it. The registry ACL is intact; the **credential
  boundary** is not.
- Human and machine identities are also conflated in monitoring: the registry sees a valid
  service token doing a valid read. Only *provenance* — a workstation network position
  instead of a build agent — is anomalous.

The general lesson: a build system is a credential aggregator. Every job is an identity,
and the union of job credentials is usually far larger than any user's permissions.

## Detection and fix

- **Detect:** registry reads by a CI service token from a non-build source; Jenkins
  credential use outside a build; secret scanners over `config.xml` and console output.
- **Fix:** give the job the narrowest token — read on exactly one package scope, no publish
  — and make it short-lived (OIDC-federated, job-scoped) instead of a static string. Mask
  secrets in logs, never echo npm config, and separate "can trigger a build" from "can see
  a build's environment".
- **Fix structurally:** run package checks on ephemeral agents whose credential is minted
  for the build and dies with it, so a leaked console line is worthless afterwards.

## Notes and dead ends

- Evidence is thin: description and solved-state metadata only, no captured build output.
  Job enumeration, the credential location and the `npm view`/`pack` checks are
  **reconstructed**; the commands are templates, not observed traffic.
- Retrying the private read with the K06.1 token is a dead end by design: "publish" and
  "read this private scope" are different grants, and the second lives on a build identity.
