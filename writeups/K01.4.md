# K01.4 — Put it on the workbench

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Client-supplied metadata trusted as fact — a helper that copies `asset_id`/`connector_revision` out of the uploaded sample instead of deriving them |
| **Tools** | `curl --form`, `jq`, a text editor |
| **Attack surface** | `http://127.0.0.1:8701/api/inspection-summary` on `rowan-dev` |
| **Prerequisite** | Local access to the workstation; a sample file under `samples/` (e.g. `FK-SAMPLE-017.json`) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a "local helper with an unfinished job" becomes a lesson
about provenance. The helper renders the summary straight from the fields inside the file you
upload, so whatever the sample *claims* about its asset and revision is what the summary
reports. Nothing validates the claim.

## Objective

> The local FieldKest helper has an unfinished support-report job — make it produce a fresh
> inspection summary from the developer's supplied sample, with that sample's asset and
> revision correctly represented.

"Unfinished" is the important word: the job exists but has never produced an acceptable
summary. "Correctly represented" is the other half — the summary must name the sample's own
asset and revision rather than a default, a placeholder, or a stale value copied from an
earlier run.

## Background you need

- **The helper is a workstation-local service** on `127.0.0.1:8701`, not part of the shared
  platform: it lets a developer preview what the connector would report.
- **Inspection samples are self-describing JSON.** They carry the asset identifier, the
  connector revision and the observations taken at a timestamp; the helper *formats* them.
- **Provenance is the bug class.** A renderer that echoes identity fields from its input
  instead of resolving them lets the input choose its own identity — the same mistake behind
  forged log lines, spoofed `X-Forwarded-For` and `asset_id` columns built from CSV uploads.

## Walkthrough

### 1. Talk to the helper the way it documents

The documented invocation (range notes) is a single multipart form field:

```bash
curl --fail --form sample=@samples/FK-SAMPLE-017.json \
  http://127.0.0.1:8701/api/inspection-summary
```

`--fail` matters: a non-2xx from the helper can look like an empty success otherwise.

### 2. Look at what came back

The first attempts return the helper's complaint about the unfinished job rather than a
summary. The useful step is to compare the summary's *shape* with the sample: the template
wants an asset identifier and a revision, and both are already in the file.

```bash
jq '{asset_id, connector_revision, captured_at, observations}' samples/FK-SAMPLE-017.json
```

### 3. Make the sample say what it actually is (reconstructed)

No transcript survives, so this is reconstruction, not a capture. The job is finished by
handing the helper a sample whose header fields are complete and consistent — `asset_id`
matching the observations, `connector_revision` matching the payload, a real `captured_at` —
so the helper renders those values instead of substituting defaults.

```jsonc
// illustrative shape of a complete sample header — not captured from the range
{ "asset_id": "<asset from the sample>", "connector_revision": "<revision used>",
  "captured_at": "2026-09-…T…Z", "observations": [ { "name": "…", "status": "…" } ] }
```

### 4. Getting the flag

The accepted answer is emitted by the helper once it produces a valid summary for that
sample — i.e. the finished job's report. The card was submitted and accepted; the exact
field of the summary was not recorded in the lane notes, so the value is not reproduced
here.

## Why this works (the vulnerability explained)

The helper has no notion of who the sample belongs to: it parses a file and formats its
fields. Fine for a preview tool, fatal once the output is treated as evidence about a real
asset — the summary inherits the sample's self-declared identity, so whoever writes the file
writes the report.

The pattern is **provenance laundering**: a trusted component (helper, report template, log
forwarder) accepts an untrusted field and re-emits it where readers assume verification. The
reader sees "produced by the helper" and concludes "true", while the only verified fact is
"the helper formatted some JSON".

The fix resolves identity from the system of record — look the asset up from an authenticated
reference — and treats every identity field in the upload as an assertion to check, not a
value to copy. Where the tool is a preview, label its output so it cannot be mistaken for
evidence.

## Detection and fix

- **Log signal:** summaries whose `asset_id`/`connector_revision` are absent from the asset
  registry, or change between two runs on the same sample.
- **Fix:** validate the sample's identity fields against the registry before rendering and
  reject mismatches; keep the helper bound to loopback and treat its output as
  developer-local, never as a report of record.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K01.4 was solved by the team agent
  and only the chapter brief and the documented helper call survive. The JSON above is marked

- Guessing at the helper's internal job state (`/api/jobs`, status endpoints) is wasted
