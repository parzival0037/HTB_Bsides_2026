# K12.1 — The reviewer arrives second

> **Category:** 2. KeplerOps · **Points:** 200 · **Difficulty:** hard
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Review-state race / TOCTOU — the review binds to a document identity whose content can still change before the privileged reviewer opens it |
| **Tools** | `curl`, `jq`, a scripted prepare/render loop |
| **Attack surface** | `https://preview.keplerops.test` (prepare/render/reviews) and the reviewer's preview workflow |
| **Prerequisite** | K10.1/K10.2 mechanics (association and collision) plus a reviewable document you control |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how "review this document" and "the document's content" drift
apart when review state attaches to an identity instead of immutable bytes, and how to land your
content in the reviewer's window without holding their account.

## Objective

Place your controlled preview content in the privileged reviewer's effective workflow despite the
account and review-state boundaries.

## Background you need

- **Two boundaries are named.** *Account:* you are not the reviewer, so you cannot open their
  queue. *Review state:* the review has a state (requested, in review, decided) that should
  freeze what is being reviewed.
- **Effective workflow** is what the reviewer actually opens, not what the system assigned. If
  the UI resolves a document identity at open time, the content served then is the real input.
- **TOCTOU:** the check happened when the review was requested against content A; the use happens
  at render, possibly content B. Nothing re-verifies that A and B are the same bytes.
- 200 points because you must combine a legitimate review request, an identity your content can
  reach, and correct timing — not because the primitive is complicated.

## Walkthrough

### 1. Recon — how a review points at a document

```bash
# illustrative: request a review and inspect what it stores
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -X POST -H 'Content-Type: application/json' \
  -d '{"document":"<your document id>","preview":"<your preview id>"}' \
  https://preview.keplerops.test/api/reviews | jq .
```

Two details decide everything: does the record store the **preview id** (immutable snapshot) or
the **document id** (mutable pointer), and does a state of `requested` lock further changes?

### 2. Finding the flaw — the reviewer's UI resolves late

The workflow is: open queue → pick review → render. Render is the late resolution, so the window
between request and render is the attack window. Evidence of this shape: the stored reference
does not change when the document's preview is regenerated, and `reviews` accepts a new preview
for a document already under review. Both mean the review is bound to an identity, not to bytes.

### 3. Exploitation — win the window

```bash
# 1) benign content under identity X, then request review of X
curl -sS ... -X POST --data-binary @benign.pdf https://preview.keplerops.test/api/prepare
curl -sS ... -X POST -d '{"document":"X"}' https://preview.keplerops.test/api/reviews

# 2) replace content for identity X (same document id, new preview)
curl -sS ... -X POST --data-binary @controlled.pdf \
  https://preview.keplerops.test/api/prepare | jq -r '.preview'

# 3) poll the review; when state moves to in-review/rendered,
#    the render it performed used the substituted content
curl -sS ... https://preview.keplerops.test/api/reviews/<review id> | jq .
```

Timing notes: keep the identity stable (K10.2 gives more than one way to land on it); if the swap
is rejected while `state=in-review`, look for the state that still permits it — `requested`
before assignment is usually permissive. Confirmation lives in the review record: the rendered
artefact corresponds to the controlled document while the review metadata still describes what
was requested.

### 4. Getting the flag

Solved by a team agent; no transcript survived, so the flag is **accepted, value not recorded**.
The accepted shape is a review whose rendered content is yours, while the reviewer's account and
the review state were never yours.

## Why this works (the vulnerability explained)

This is a **state-machine integrity failure** — the review-pipeline form of TOCTOU. The review's
*authorization* was decided once, on content A; the *action* (render and assess) happens later on
whatever the identity resolves to. Review state is meant to be the freeze: `requested` should
snapshot the artefact. If the state is enforced on the review object but not on the content it
references, the freeze is cosmetic. And because the reviewer is privileged, the substituted
content is rendered and assessed under their authority — you needed their *timing*, not their
account.

## Detection and fix

- **Detect:** preview content changing for a document with an open review; render digests
  differing from the digest recorded at request time; rapid re-prepares after a review request.
- **Fix:** snapshot the artefact at request time (copy-on-review, addressed by content hash) and
  render only the snapshot; require the reviewer's render to verify the digest against the review
  record. Make content immutable for the review's duration and audit mutation attempts.
- **Fix the model:** attach reviews to `(document, digest)`; a new digest needs a new review,
  which is also better UX than reviewing stale bytes.

## Notes and dead ends

- Evidence is thin: description and solved-state metadata plus the chapter's preview routes. The
  commands and exact state names are **reconstructed**; treat the sequence as the technique, not
  a transcript.
- Racing after the review is decided is pointless — the decision consumed the old content. The
  window closes at decision time, not submission.
- Do not try to obtain the reviewer's account. The premise is that you cannot; the workflow is
  what lets your content in without it.
