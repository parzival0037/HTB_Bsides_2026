# W03.1 — An annex left with the order

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane W03B

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Retained annex disclosure with a version-pinned inspection oracle — the supplier order keeps the work-order annex, and the inspection trace reveals it (and a flag) only for the exact pinned revision |
| **Tools** | `curl`, `jq`, the SOCKS pivot |
| **Attack surface** | `delivery.keplerops.test:8443` → `GET /api/package-meta/fieldlink-connector`, `POST /api/inspections`, `GET /api/inspections/{id}/trace` |
| **Prerequisite** | Basic auth as `rowan.ito` with the developer token |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how the work-order annex survives in supplier order metadata,
how to make the inspection endpoint reveal it by pinning the right version and request id,
and why the trace answer moved after an unrelated delivery.

## Objective

Recover the work-order annex retained with the supplier order and identify its engineering
drawing reference — the identifier that correlates the annex with the inspection record.

## Background you need

- **Order annex.** Works orders carry an annex (scope, drawings, acceptance criteria), usually
  distributed with the order rather than in a DMS, so it is retained in order metadata.
- **Inspection as an oracle.** `POST /api/inspections` does not inspect "the package" in
  general; it inspects a pinned `version` + `request_id` pair and returns an id whose trace
  describes what was inspected. Change either pin and you inspect something else.
- **Mutable trace.** If the trace is generated from live state, the same id can return a
  different body later. A value observed once is evidence about that moment, not a constant.

## Walkthrough

### 1. Read the supplier order metadata

The package-meta route is the order-side record — pending release, channel, rollback slot:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector | jq .
```

Observed content: `_rev 22-f28b25f4f521b26f`, pending release `7.4.3-cinder.rset1`, and
`channels.arwc-stable.rollback_slot 7.4.2`. The `_rev` is the annex revision retained with
the order; `7.4.2` is what is live for ARWC; `7.4.3-cinder.rset1` is the pending Cinder
release.

### 2. Pin the inspection to the live revision

The accepted request is exact — action, package, request id, schema, version:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  -H 'Content-Type: application/json' \
  -d '{"action":"inspect_public_manifest",
       "package":"@keplerops/fieldlink-connector",
       "request_id":"release-742",
       "schema":"fieldkest.inspection/v1",
       "version":"7.4.2"}' \
  https://delivery.keplerops.test:8443/api/inspections
```

Response: `INSP-2047`. Only `version 7.4.2` with `request_id release-742` is accepted; other
combinations do not produce the ARWC inspection record.

### 3. Read the trace for the annex content

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  https://delivery.keplerops.test:8443/api/inspections/INSP-2047/trace | jq .
```

The trace resolves the annex to its engineering drawing reference and returns this card's
flag: an order-side document plus a public inspection API that renders it once you pin the
revision.

### 4. The value is not stable

At 19:59Z the trace returned one flag value; after a support diagnostics delivery at 22:16Z
the identical request returned a different one. The trace is state-dependent: capture,
submit promptly, re-read before concluding a value is wrong. Only the pinned `7.4.2` /
`release-742` pair yields the record.

The card is solved, but the solve record keeps neither the flag value nor the drawing
reference, so neither is quoted here.

## Why this works (the vulnerability explained)

Two issues combine. The order annex is retained in supplier-side metadata with no tenant
scoping beyond "you can reach the delivery service" — the annex is customer documentation,
but the order API treats it as ordinary package metadata. And the inspection endpoint is a
**version-pinned oracle**: it describes whatever artefact you pin, its trace includes the
annex/drawing linkage, and the service never checks that the caller is entitled to the
customer whose order is inspected. Pinning is a correctness requirement, not a control.

A correct implementation separates "inspect an artefact" from "disclose an order": the trace
should reference artefacts the caller already holds, and annex/drawing data should go only to
a principal entitled to the order, from a stable snapshot rather than live state.

## Detection and fix

- **Log signal:** inspection requests whose `request_id` the caller never created; repeated
  traces of one inspection id returning different content over time.
- **Fix:** authorise inspections against the order/customer, not just the package; return a
  stable, signed trace snapshot; keep annex and drawing references in the tenant-scoped order
  record; reject unpinned requests and record which revision produced which trace.
