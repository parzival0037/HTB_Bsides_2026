# W01.2 — The planner's unfinished handover

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

| **Tools** | `curl`, Gitea content API, `gobuster`/DNS wordlist brute, the Workboard (Kanban) UI |

**What you are about to read:** how supplier onboarding documentation advertises a shared
document folder, why the planning handover in it exposes a customer-side inspection and
assignee, and why identifier correlation, not filenames, makes the record trustworthy.

## Objective

Find the planning handover retained with the supplier documents and identify the
inspection that is still outstanding and the planner to whom it is assigned.

## Background you need

- **Supplier documents outlive the project.** Onboarding gives the supplier a document
  service and an *external* folder for handovers, minutes and attendance sheets. It is a
  delivery channel; in practice it becomes an uncontrolled copy of the customer's plan.
- **Folder-scoped authorisation.** A Nextcloud-style share or app password grants access
  per folder or per account, not per document. One leaked integration token reads every
  "ordinary planning and attendance document" in the folder, including documents the
  customer never meant to hand over.
- **Names drift, identifiers do not.** The same job appears as an internal work order, a
  supplier job and an engineering drawing; filenames differ, so correlation must use the
  identifiers embedded in the document.

## Walkthrough

### 1. Read the supplier onboarding material

The onboarding material names the document service and the external handover folder. It
lives in the supplier's source browser, so the Gitea contents API is the fastest way in:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: token $FK_DEV" \
  "https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/contents/docs?ref=main" \
  | jq -r '.[].path'
```

Look for onboarding/access notes rather than product docs: the folder name given to the
customer is the thing you need.

### 2. Locating the document service (the hard part)

The lane tried to resolve the named service directly. A ~12k-word DNS brute against
`*.keplerops.test` and `*.arwc.test` produced no document host, so the Nextcloud named in
the onboarding material is **not** discoverable by hostname guessing in the documented
zones. Use the service name and the access method from the onboarding material (share
link, configured base URL, integrator account).

### 3. Rule out the Workboard as the document store

Logged in as the retained staff account `maya.ranscombe`, the Workboard shows only
project 1 (four FieldLink release tasks). Projects 2 and 3 exist but return `403`, and a
global search for `cairn`, `inspection` and `handback` returns nothing. The Workboard is a
task board, not the document folder — a plausible-looking dead end.

### 4. Correlate the handover rather than trusting its filename

Inside the external handover folder, read the ordinary planning and attendance documents.
The handover you want is the one whose embedded identifiers match the accepted delivery,
for example:

```
JOB-BA11FC0CCB19
RPT-CRR-OG2-BASELINE
package _rev 22-f28b25f4f521b26f
```

Match the internal work order and report reference in the document against the package
revision from `delivery.keplerops.test:8443/api/package-meta/fieldlink-connector`. The
document that agrees on all of them is the planning handover; the outstanding inspection
and its planning assignee are stated inside it, not in the filename.

The card wants those two values. The solve record does not retain them, so they are
reported as accepted, not reproduced.

## Why this works (the vulnerability explained)

This is a classification failure plus a sharing-scope failure. The customer's planning
state was filed in a folder whose access model is "anyone with the folder token", and the
folder was handed to a third party for a different purpose (delivery evidence). Nothing in
the document service knows which documents are deliverable and which are internal
planning, so the integration token is effectively a read grant on the customer's plan.

The correlation step matters because over-sharing alone does not tell you *which* record
answers the question. Cross-system identifiers (work order, report id, package revision)
are the join key; carrying them as structured metadata would let access be scoped by
project rather than by folder.

## Detection and fix

- **Log signal:** a single integration/app token enumerating and downloading an entire
  external folder; downloads of planning or attendance documents by a delivery-only
  principal.
- **Fix:** scope shares per document set with expiry, give the supplier a minimal folder
  containing only delivery evidence, and attach structured project metadata to each
  document so authorisation works per project. Rotate and audit integration tokens, and
  publish a manifest mapping work order ⇄ supplier job ⇄ drawing ⇄ package revision
  instead of relying on free-text filenames.
