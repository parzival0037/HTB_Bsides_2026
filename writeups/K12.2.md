# K12.2 — A value across the action boundary

> **Category:** 2. KeplerOps · **Points:** 400 · **Difficulty:** expert
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Broken binding of a one-time/CSRF-style token — a protected value minted for one action is accepted by a separate privileged action |
| **Tools** | `curl`, browser devtools (or `--trace`), `jq` |
| **Attack surface** | `https://preview.keplerops.test` (privileged preview action) and the value's minting service |
| **Prerequisite** | A privileged preview path reachable from your session, and the ability to observe a browser value |
| **Flag** | accepted, value not recorded |

**What you are about to read:** what "a value across the action boundary" means concretely — a
nonce or token that should die with the action it was minted for — and how to make a *separate*
action accept it, which is the difference between a token and a capability.

## Objective

Recover the protected browser value required for a privileged preview action and make that
separate action accept it.

## Background you need

- **Action-bound tokens.** Anti-CSRF tokens and nonces are bound to a session, an action, a
  purpose and a short lifetime. The binding makes a stolen value useless.
- **The failure here** is a minting service that issues values without the action binding, plus a
  consumer that validates only "issued by us, still fresh?" rather than "issued *for this
  action*?".
- **"Browser value"** signals where to look: the value goes to the client (form field, header,
  JSON body, page asset), so it is recoverable by observation.
- The range's policy-compiler client exposes a `nonces` route alongside `evaluations` — the
  likely minting surface for this chapter.

## Walkthrough

### 1. Recon — find the value in a normal flow

```bash
# illustrative: fetch the action page and keep token-bearing fields
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -b cookies.txt -c cookies.txt \
  'https://preview.keplerops.test/<privileged preview action>' -o page.html
grep -oE '(name|id)="[^"]*token[^"]*"[^>]*value="[^"]+"' page.html
```

Or mint directly if the client reference advertises a nonce route:

```bash
curl -sS ... -X POST https://source-tools.keplerops.test:8443/api/policy-compilers/fieldkest-policyc/nonces | jq .
```

Record the value, the request it was minted for, and the session under which it was issued.

### 2. Finding the flaw — the value is not scoped to the action

Test the binding with minimal, reversible probes: replay against the **same** action (a single-use
token must fail the second time — note the error), present it to a **different** privileged
action in the same session, then in a **different** session or after a delay. The vulnerability is
confirmed when step two succeeds: the value crosses the action boundary. Acceptance in a
different session is a separate, more serious finding — distinguish them, since the fix differs.

### 3. Exploitation — make the separate action accept it

```bash
# illustrative: separate privileged action carrying the borrowed value
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -b cookies.txt \
  -H "X-<Action>-Token: $TOKEN" -H 'Content-Type: application/json' \
  -d '{"document":"<target>","preview":"<target preview>"}' \
  'https://preview.keplerops.test/api/<separate action>'
```

If the action returns the privileged result instead of a token error, the boundary is crossed: a
value minted for one operation authorised a different one.

Practical notes: keep `cookies.txt` in play (most schemes still check session identity — the bug
is that they check *only* identity); mint in the same script that performs the second action if
the TTL is short; and if the value is rejected in a header but accepted in the body (or vice
versa), that inconsistency is itself the finding.

### 4. Getting the flag

Solved by a team agent; no request/response survives in the retained data, so the flag is
**accepted, value not recorded**. The demonstrated condition is a privileged preview action
accepted while carrying a value minted for a different action.

## Why this works (the vulnerability explained)

A token is a **capability** only if it is bound to what it authorises. Strip the binding and you
have a short-lived bearer credential — still useful, because the attacker can mint or observe one
at will. The mistakes, in increasing severity: no action binding at mint time (the record stores
session and expiry, not purpose, so validation cannot distinguish "for preview" from "for
publish"); validation by lookup only (exists, unexpired, session matches — purpose never
compared); inconsistent enforcement (two endpoints share the validator, one checks purpose, the
weaker one does not); and per-action rather than global consumption. The correct construction
binds `(session, action, resource, expiry)` and verifies all of it at use, ideally against a
server-side record keyed by all four.

## Detection and fix

- **Detect:** a nonce presented to an endpoint other than the one that requested it; validation
  failures clustered on one consumer while another accepts the same values.
- **Fix:** include action and target resource in the nonce's signed payload (or record) and
  compare on use; consume atomically and globally; prefer `SameSite` cookies plus origin checks to
  a bare token.
- **Fix consistency:** one validator used by every consumer, with purpose as a required argument,
  so a new endpoint cannot opt out of the check.

## Notes and dead ends

- Evidence is thin: description and solved-state metadata plus the documented
  `nonces`/`evaluations` routes. The technique is **reconstructed** from "protected browser
  value" and "separate action"; endpoints are placeholders, not observed traffic.
- Replaying against the *same* action repeatedly is a dead end and may burn the token; mint
  fresh values per probe.
- Do not assume the value is a cookie — check headers, hidden fields and JSON bodies first, since
  placement usually reveals which validation path is weak.
