**What you are about to read:** the easiest card in chapter 5, and a genuinely useful pattern: the
service publishes its own interface including an example request, and feeding that example back to the
validator produces a successful check whose response carries the value. The lesson is that **a
self-documenting interface is a live oracle** — replay its examples first.

## Objective

> Speak the package's language.

The brief for this card is a hypothesis rather than a sentence: run the documented example
(`consumer-request.json`, v3) through `/api/consumer-checks` and read the response's flag / check id.
That is the whole task. The card is testing whether you read the published contract before you start
guessing at endpoints, and whether you notice that the vendor ships a working request alongside it.

## Background you need

- **FieldKest publishes a client reference**: `/.well-known/fieldkest-client` describes routes, schema
  versions and the example payloads the vendor expects integrators to use — the document a customer's
  developer would read.
- **A checker is an oracle.** A validation endpoint answers "does this conform?" and usually returns
  detail: check id, normalised fields, sometimes the parsed object.
- **Schema version matters.** Here it is `v3`; a v2-shaped body fails for the wrong reason and teaches
  you nothing, so the example is the authoritative shape.
- **Example payloads are usually real**, captured from a working integration — replaying them is not a
  shot in the dark.

## Walkthrough

### 1. Read the published contract

```bash
curl -sS https://source-tools.keplerops.test:8443/.well-known/fieldkest-client | jq .
```

Note the consumer-check route (`/api/consumer-checks` on `delivery.keplerops.test:8443`) and schema
version `v3` with its example. Take the example as-is: a successful baseline proves your tooling works.

### 2. Replay the example

```bash
curl -sS -X POST https://delivery.keplerops.test:8443/api/consumer-checks \
  -H 'Content-Type: application/json' \
  --data @consumer-request.json | jq .
```

If the example lives in the reference rather than a file, extract it with `jq` and post that — send the
documented object, not a paraphrase.

### 3. Read what the check returns

The response reports the check result and an identifier. The accepted value is in that response; the
exact field (`flag` and/or check id) was not recorded, so the value is not reproduced here.

### 4. Notice what else the response confirms

Two useful facts fall out of a successful consumer check, and later chapter-5 cards depend on them:

| Observation | Why it matters |
|---|---|
| The delivery service accepts unauthenticated consumer checks | the "consumer" side is not the privileged side |
| The response echoes normalised fields | you can use the checker to test schema variants cheaply |
| `v3` is current, `v2` is legacy | version confusion is the next card's whole subject |

## Why this works (the vulnerability explained)

This is *disclosure through an interface*, not injection. The service does its job — publishing a
contract and validating against it — but the published example is itself a valid artefact, and
replaying it returned more than "your request is well formed". Two transferable observations:

1. **Documentation replay is the cheapest recon there is.** Vendor examples, SDK smoke tests and
   `curl` snippets in internal wikis are working requests. Analysts who start by replaying them find
   the reachable surface in minutes instead of enumerating blindly.
2. **Validation endpoints leak structure.** A checker tells you which fields it parsed, which it
   ignored and which it rejected — enough to reconstruct the schema without ever seeing the code.

It is a vulnerability only in that the surface should be minimal: a conformance check should say the
document conforms and nothing else. Returning check ids or normalised objects makes the validator a
data source.

## Detection and fix

- **Log signal:** identical example payloads replayed from many identities; consumer checks from
  addresses that never use the rest of the API.
- **Fix:** minimal validator responses (pass/fail plus request id), no parsed content echoed,
  rate-limited unauthenticated checks; treat published examples as public.
