## Objective

> Reconstruct enough of the compiler's internal instruction behavior to reproduce the supplied
> policy fragments.

The README decomposes the policy into four fragments (`tenant-state`, `connector-version`,
`signer-lineage`, `compatibility-exception`) and states each condition in prose. No `.fkpc`
bytecode ships for them. The card is the assembly step: derive the opcodes from the retained
binary and emit one minimal program per fragment.

## Background you need

- **The header is twelve bytes.** Magic `FKPC`, a little-endian `u32` program offset relative to
  the header, a `u16` instruction count, and a `u16` instruction width.
- **Instructions are four bytes.** Opcode (1), flags (1, always 0 in this revision), operand
  (`u16`, little-endian).
- **Operands are indices, not values.** `PUSH_FIELD` takes a field index 0–3, `PUSH_CONST` a
  constant index, `IN_SET` a set index. The constants and sets come from the repository README /
  binary, not from the fragment text.
- **The fragment validator is server-side.** It runs each assembled program against hidden
  accept/reject cases, so a correct assembly passes every case rather than one hand-picked input.

### 2. Pull the embedded program and the opcode map

The binary is an unstripped ELF, and the link map names the opcode handlers. Find the embedded
table (it starts with the magic bytes):

```python
import struct
data = open("fieldkest-policyc", "rb").read()
i = data.find(b"FKPC")
off, count, width = struct.unpack("<IHH", data[i+4:i+12])
program = data[i:i+12+count*width]
print(i, off, count, width, len(program))
```

On the live range this produced `offset=1682464`, `count=14`, `width=4`, and a 68-byte table:

```text
464b5043 0c000000 0e00 0400
00000000 04000000 00000100 01000000 03000000 05000000 00000200
04000100 05000000 00000300 01000100 02000000 05000000 07000000
```

The map file supplies the mnemonics:

```text
fieldkest_opcode_00_PUSH_FIELD
fieldkest_opcode_01_PUSH_CONST
fieldkest_opcode_02_EQ
fieldkest_opcode_03_SEMVER_GTE
fieldkest_opcode_04_IN_SET
fieldkest_opcode_05_AND
fieldkest_opcode_06_OR
fieldkest_opcode_07_RETURN
```

Decoding the table with those opcodes gives the canonical predicate:

```text
0  PUSH_FIELD 0        ; tenant_state
1  IN_SET 0
2  PUSH_FIELD 1        ; connector_api
3  PUSH_CONST 0
4  SEMVER_GTE 0
5  AND 0
6  PUSH_FIELD 2        ; signer_lineage
7  IN_SET 1
8  AND 0
9  PUSH_FIELD 3        ; compatibility_exception
10 PUSH_CONST 1
11 EQ 0
12 AND 0
13 RETURN 0
```

The constants and sets are visible as adjacent strings in the binary: `3.0.0`, `true`/`false`,
`active`, and `fieldkest-release-2026`. That fixes `const[0]=3.0.0`, `const[1]=true`,
`set[0]={active}`, `set[1]={fieldkest-release-2026}`.

### 3. Assemble each fragment as a minimal FKPC program

Each fragment needs only the instructions for its own condition plus `RETURN`; the header is
rebuilt with the new instruction count. For example, `tenant-state` is three instructions:

```python
import base64, hashlib, struct

def ins(op, arg, flags=0):
    return bytes([op, flags]) + struct.pack("<H", arg)

def program(body, program_id):
    header = b"FKPC" + struct.pack("<IHH", 12, len(body)//4, 4)
    blob = header + body
    return {
        "instruction_count": len(body)//4,
        "instruction_width": 4,
        "opcode_model": {
            "instruction_width": 4,
            "opcodes": {
                "0x00": "PUSH_FIELD", "0x01": "PUSH_CONST", "0x02": "EQ",
                "0x03": "SEMVER_GTE", "0x04": "IN_SET", "0x05": "AND",
                "0x06": "OR", "0x07": "RETURN",
            },
            "schema": "fieldkest.policy-opcode-model/v1",
        },
        "program_base64": base64.b64encode(blob).decode(),
        "program_id": program_id,
        "program_sha256": hashlib.sha256(blob).hexdigest(),
        "schema": "fieldkest.policy-program-model/v1",
    }

tenant = program(ins(0x00, 0) + ins(0x04, 0) + ins(0x07, 0),
                 "FKPC-FRAGMENT-TENANT-STATE")
```

The same three-instruction shape covers `tenant-state` and `signer-lineage`; the version and
exception fragments are four instructions (`PUSH_FIELD`, `PUSH_CONST`, comparison, `RETURN`).

## Why this works (the vulnerability explained)

The README gives the bytecode *format* but withholds the *fragments*, relying on the fact that
the format alone is not executable knowledge. It is not much of a barrier: the opcode names sit
in an unstripped symbol table, the embedded table sits behind a four-byte magic, and the
constants and set members are printable strings. Publishing the encoding while shipping the
compiler means the instruction set is a short extraction away.

The deeper issue is the same as K11.1: a policy program distributed to clients is public
policy. Hiding the fragments does not hide the decision — it only adds one parsing step.

## Detection and fix

- **Detect:** fragment validation requests that walk the four program IDs; compiler artefacts
  shipped with symbols/maps; extraction of the `FKPC` table.
- **Fix:** strip and separate the evaluator from the sample programs; keep acceptance decisions
  server-side and return an opaque verdict; if fragments must ship, sign them and bind them to a
  client identity so a re-assembled fragment is not accepted.

- The card was accepted by the platform on **2026-11-20 21:15:45Z** (attempt 80, +80 points,
  board total 92), per `ops/ctf/SOLVES.log`. The original submission transcript was not

- The extraction above was **re-run on 2026-11-23** against the still-live range; the program
  bytes, opcode mapping, constants and sets are literal outputs from that run (see
  `docs/07-live-range-2026-11-23.md`). The four `fragment-check` POSTs were replayed on
  2026-11-23 and each returned the same value, **`FLAG{5f3e067c00b70ca5}`** — so the flag value
  is now recovered rather than unrecorded. The platform rejects re-submission for an
  already-solved card, which is why the value is evidence rather than a new acceptance.
- Guessing opcode numbers from byte frequency is a dead end; derive them from the map/symbols.
  The operand is a `u16`, but every index used here fits in one byte — read it as little-endian.
- `AND`/`OR` chain the comparisons in the embedded program; the fragments do not need them,
  because each fragment evaluates one condition independently and returns.
