# T04.4 — Yesterday's green light

> **Category:** 1. Training · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual) · second attempt (one attempt was burned before this analysis)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Stale, misattributed evidence — an earlier successful attempt's result is presented as the result of a later request that was rejected and moved nothing |
| **Tools** | `curl`, JSON correlation (`attempt_id` / `request_id` / `source_request_id`), timestamp comparison, decryption |
| **Attack surface** | `http://state.training:8080/` (10.77.40.50): report `OR-042`, frozen capture `replay/report-sealed.enc`, `GET /api/practice/observations` |
| **Prerequisite** | The `OR-042` report, the `AT-0xx`/`RQ-0xx` registers, and observations covering 09:00–10:00 |
| **Flag** | `FLAG{51b9f00459e54f0b}` |

**What you are about to read:** how to disprove a green test result. The report says the latest
outlet test passed and 200 L moved; the registers say that attempt was rejected by a service
hold and nothing moved. The flag is the report's displayed result string, sealed with its id.

## Objective

> The report claims the latest outlet test succeeded but the observations disagree —
> reconstruct what actually happened from the evidence (timestamps, logs, values) and explain
> the discrepancy.

## Background you need

- **A report is derived, not evidence.** It should be a function of one request, one attempt and
  the observations covering that attempt's window; loosen any link and it can assert an outcome
  that never happened.
- **Three identifiers, three meanings.** `request_id` is the operator's intent, `attempt_id` is
  the execution the system actually ran, `source_request_id` is which request the report thinks
  it reports. When the last two name different tests, the report is showing you both at once.

## Walkthrough

### 1. Line up the claim and the identifiers

`OR-042` reports `display_result = green` and a 200 L transfer for the latest outlet test: green
light, populated volume column, nothing red. The registers contradict it immediately:

| Time | Object | State |
|---|---|---|
| 09:00:00 | `RQ-041` / `AT-041` | successful test, 200 L |
| 10:00:00 | `RQ-042` / `AT-042` | request **rejected** — `service_hold` |
| 09:59:59 | observation | `1000.0 L` |
| 10:00:01 | observation | `1000.0 L` |

The green was produced by `RQ-041`/`AT-041` at 09:00 — the genuinely successful test — and
carried onto `AT-042`, whose request was refused an hour later. The level is identical either
side of that attempt: nothing moved.

### 2. Prove "no movement" instead of assuming it

The confirmation is the observation pair around the command, not the report:

```bash
curl -sS http://state.training:8080/api/practice/observations
```

Between `09:59:59` and `10:00:01` the volume stays at `1000.0 L` — a two-second window around a
200 L transfer that should have taken ~10 s at 20 L/s. Zero movement, no transfer, so the green
belongs to somebody else. A rejected request still has an `attempt` row, though: "there is an
attempt" is not "something ran".

### 3. Getting the flag

The sealed replay is keyed on the report's *displayed* result string plus the report id —
`green:OR-042` — not a status-bit name and not `service_hold`. Illustrative shape of the open
(the desk's exact cipher flags were not retained):

```bash
openssl enc -d -aes-256-cbc -pbkdf2 \
  -pass "pass:$(printf '%s' 'green:OR-042' | sha256sum | cut -d' ' -f1)" \
  -in replay/report-sealed.enc -out report.plain
```

Valid padding plus a `FLAG{...}` body confirms the finding; the plaintext carries
`FLAG{51b9f00459e54f0b}`.

## Why this works (the vulnerability explained)

This is **result laundering**: a truthful result from attempt *N* is presented as the result of
attempt *N+1*. It needs only one small shortcut — a renderer that reads "the last successful
attempt for this device" instead of "the attempt correlated to this request". The rejected
request still creates an attempt row, so a naive join finds *an* attempt; that attempt has no
observations, so the renderer falls back to the last batch with data; the fallback's volume and
result look plausible, so nobody queries the timestamps.

The trust boundary being crossed is **provenance**: the report is trusted to describe one
specific execution while nothing binds it to that execution. The pattern recurs in CI dashboards
reusing cached results, monitoring that renders the previous deployment's health, and
reconciliation that attributes a rejected transaction to the last accepted one. The defence is
structural — correlate on one immutable identifier *and* check an independent source (here, the
observation stream) — because a report that only agrees with itself cannot expose this.

## Detection and fix

- **Log signal:** a report whose `source_request_id` differs from the request that triggered it;
  `rejected` attempts that still carry a result; result timestamps earlier than the attempt they
  are attached to; "successful" batches with no observations in their own window.
- **Fix:** bind every report row to one `attempt_id` and refuse to render a result when that
  attempt has no terminal observation. Never fall back to the previous successful batch — render
  `unknown`, loudly. Carry request/attempt/batch IDs into the report so provenance travels with
  the number, and expire results older than the request.
- Treat a hold rejection as a first-class outcome with a reason code, so an older success
  cannot silently replace it.
