# W01.1 — The customer's copy

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane W01D

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Broken tenant/copy isolation — the customer's retained handover is served by the *supplier's* support API behind one shared integration bearer, so "customer-owned" is a label rather than an access-control boundary |
| **Tools** | `curl`, `jq`, the SOCKS pivot on the range box |
| **Attack surface** | `support.keplerops.test:8443` → `GET /api/handovers/current` |
| **Prerequisite** | Support-client bearer from `~/.config/fieldlink/support-client.json` on `rowan-dev` (principal `rowan.ito`) |
| **Flag** | accepted, value not recorded |

The customer's copy is a retained handover, not the supplier's receipt, and it is served
from the supplier's support API behind the same integration token as everything else.
Read it back, separate the two records, and correlate the delivery to its maintenance
case.

## Objective

Recover the retained customer handover and identify the maintenance case attached to the
accepted FieldLink delivery: the handover record itself (the customer's copy, not the
supplier's shipping receipt) plus the maintenance case reference it carries.

## Background you need

- **Two records, one delivery.** A delivery produces a supplier-side *receipt* (package,
  revision, release channel, approval) and a customer-side *handover* (what was accepted,
  who signed it off, what maintenance follows) — different services, different IDs.
- **Retention copies.** Support keeps a copy of the customer's handover so it can answer
  questions later. That copy is customer data stored in supplier infrastructure — the
  classic place where a tenant boundary quietly stops being enforced.
- **Integration bearer.** The support client uses one long-lived token; whatever it can
  read, the holder can read, unless the service adds per-tenant authorisation.

## Walkthrough

### 1. Recon — the support client and its one read route

`NETMAP.md` records the support client config on `rowan-dev`
(`~/.config/fieldlink/support-client.json`), and `ARWC-FINDINGS.md` records the handover
route:

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: Bearer $TOKEN" \
  https://support.keplerops.test:8443/api/handovers/current | jq .
```

The response is the customer handover. Fields observed in the lane notes include a
callback reference ending `cb4…43e57`, `"state": "success"`, and an assessment rating of
`callback-review-required`.
### 2. Separate the customer record from the supplier receipt

The delivery service (`delivery.keplerops.test:8443`) authenticates with basic auth as
`rowan.ito` and answers package metadata, not handovers:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector | jq .
```

That record carries the package `_rev`, the pending release and the rollback slot — the
supplier's view. The hint says it plainly: start from the customer-owned handover
associated with the *accepted* delivery, then use its ordinary client reference to
identify the retained handover route. Package metadata is not the handover, and the
maintenance case does not live there.

### 3. Correlate the handover with the delivery

Match on three things before trusting the record: the connector identity
(`fieldlink-connector`) and accepted version, the customer/tenant the handover names, and
the callback assessment — here `callback-review-required`, meaning the delivery was
accepted but the callback path still needs review.

The maintenance case is the case reference carried by the handover for that delivery. In
our map `SUP-2841` is the open ARWC ticket for connector callback latency, the same
subject as the `callback-review-required` assessment; treat that as a correlation to
verify, not an assumption.

### 4. Getting the flag

The flag is returned in the handover body itself, alongside the customer record. The card
record does not retain the value, so it is reported as accepted, literal string omitted.

## Why this works (the vulnerability explained)

Retention copies blur an ownership boundary. The supplier keeps "the customer's copy" for
support purposes and serves it from the same API, under the same integration token, as its
own operational data. Authorisation is therefore *token-scoped*, not *record-scoped*:
possessing the support bearer is sufficient to read a record that belongs to ARWC.

The developer's mistake is treating "this is our support service" as equivalent to "this
data is ours to hand out". A correct implementation authorises per customer and per
record: the principal must be entitled to the tenant named in the handover, and the
response should be assembled from fields the caller may see, not the stored document
wholesale. Retention copies also need provenance metadata (tenant, delivery, case) so
the linkage can be proven instead of guessed from names.

## Detection and fix

- **Log signal:** one support bearer reading handovers across multiple tenants; reads of
  `/api/handovers/current` by a principal not attached to the named customer.
- **Fix:** enforce tenant scoping inside the service (tenant from the caller's
  entitlement, not from the URL or the stored document), split the support token per
  tenant, return only contract fields, and keep the maintenance case in a structured
  field so correlation does not depend on free-text matching.

## Notes and dead ends

- The support service is effectively **read-only**: `POST`/`PUT` return `404`, `PATCH`
  returns `501`, with no handback or records routes. Any plan that *changes* the customer
  record through this service is a dead end (that is W01.4, and it needs another service).
- Delivery package metadata is a tempting shortcut but it is the supplier's receipt; it
  does not contain the customer's maintenance case.
- A lane log records a `FLAG{…}` value in the handover body attributed to this card, but
  the card's solve record does not retain it. It is deliberately not reproduced.
