**What you are about to read:** how one stage hides another and how to rebuild something that runs.
The bug class is *layering*: resistance to review comes from encodings and carriers, not
cryptography, so each recovered piece is the wrapper of the next. The skill is mechanical patience —
identify, decode, verify, repeat — plus the discipline to read the operator's notes before executing
anything.

## Objective

> The recovered staging material conceals another stage. Reconstruct the usable script and recover
> the instructions needed to understand what the earlier operator collected.

Two deliverables: **a usable script** — the stage as the operator meant it to run, not the mangled
blob — and **the instructions** saying what the earlier operation collected.

## Background you need

- **Layering is cheap obfuscation.** `base64`, `gzip`, `xxd -p` and quoted-printable survive being
  pasted into a document or chat, and each defeats a reviewer who runs one decoder and stops.
- **Wrappers are recognisable.** A shebang followed by an encoded blob, a huge literal that gets
  evaluated, a file that starts as text and ends as binary — each implies a next step.
- **"Usable" has a definition.** The stage must parse, its placeholders must resolve, and it must not
  depend on the carrier's wrapping. A script that runs but contacts `TODO_HOST` is not reconstructed.
- **Instructions are data too.** Operators keep a manifest beside the code: what to collect, from
  where, under what key — often the most valuable part, and the part reviewers forget.

## Walkthrough

### 1. Identify what you actually have

```bash
file stage.bin; head -c 200 stage.bin | hexdump -C
```
Text with a long literal, or text that turns binary part-way through, both mean "decode next". Check
which layer answers to `file` before guessing at decoders.

### 2. Peel layers, verifying each one

```bash
# illustrative template — one layer at a time, check every step
base64 -d blob.b64 > l1.bin 2>/dev/null || echo 'not plain base64'
file l1.bin; head -c 16 l1.bin | xxd
(gzip -dc l1.bin || xz -dc l1.bin) > l2.bin 2>/dev/null; file l2.bin
```


Do not chain decoders blindly: identify each layer before the next decode, or a partial success
(gzip accepting a truncated stream) quietly yields a corrupt stage you then debug for an hour.

### 3. Reconstruct the script

Three things usually need fixing first:

| Problem | Looks like | Fix |
|---|---|---|
| Carrier wrapping | base64 broken every 76 chars, `=` early | strip whitespace, re-pad to a multiple of 4 |
| Placeholders | `HOST=""`, `KEY="TODO"`, `<callback>` | fill from the K03.1 manifest |
| Quoting damage | wrapper escaped `$` or backticks | re-quote, don't re-type, to keep literals |

Sanity-check without executing (`bash -n stage.sh`, `python3 -m py_compile stage.py`), then read it
all. The stage is small; there is no excuse for running it unread.

### 4. Find the instructions

The note is usually adjacent rather than embedded: a manifest in the recovered bundle, a comment block
at the end of the stage, or a file named after the collection. It states what the operation was
collecting — explaining K03.3's "lost collection" — and the unresolved ARWC maintenance ticket the
earlier operator chased.

### 5. Getting the flag

The accepted answer comes from the reconstructed stage or the instructions recovered alongside it.
Accepted; which of the two carried the value was not recorded, so it is not reproduced here.

## Why this works (the vulnerability explained)

Nested payloads exploit a review process that stops at first success. A reviewer who decodes one
layer feels finished; the operator only needed to be one layer deeper. Nothing here is strong
cryptography — each layer is a published encoding — so the protection is *attention economics*: make
continuing cost more than the reviewer's patience. The same mechanism appears as:

- **double-encoded command-and-control** (base64 inside a signed blob inside a comment field);
- **polyglots** — a file that is simultaneously a valid image and a valid archive, so the scanner
  sees the image and the loader sees the archive;
- **staged droppers** where the first stage contains no capability at all, only a fetch-and-decode
  routine for the second.

The defence is a *termination condition*: analysis ends when the artifact is understood, not when one
decoder fails, and scanners must extract recursively to exhaustion.

## Detection and fix

- **Log signal:** text headers with rising entropy; base64 literals wider than a screen; egress to a
  host that appears only in a comment or literal.
- **Fix:** recursive extraction with a depth limit; block executable content and long encoded literals
  in uploads; analyse recovered scripts in a disposable container, and hash every layer you keep.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K03.2 was solved by the team agent and
  only the description and a lane brief survive: every command above is an illustrative template.
- Running the stage on the workstation is the wrong shortcut: it is the previous operator's tooling,
  its callback is unfinished, and the workstation is the only foothold you can lose.
- A single decoder gives nothing back and looks like a dead end. That is the design: assume at least
  two layers, and confirm each with `file` before decoding again.
- Expect a *preparation* tool, not an exploit: the collection work is K03.3.
