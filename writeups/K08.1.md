**What you are about to read:** why "we still accept the old format" is a vulnerability in
its own right, and how an archived, signed legacy client becomes an oracle for the modern
checker — plus the protected compatibility record it exposes.

## Objective

FieldKest still recognizes an old entitlement format. Recover its protected compatibility
record and determine what the checker considers an entitlement.

## Background you need

- **Entitlements** are claims about what a tenant may use: product, channel, version range,
  expiry. A checker takes a record and decides whether a feature is allowed.
- **Legacy tolerance** is a compatibility feature: the checker accepts both the current
  schema and a superseded one so old clients keep working. That doubles the input surface —
  every field the old parser read is now attacker-controlled input to the same decision.
- **Signed clients as oracles.** The archived connector is signed and still runs. If its
  diagnostic path builds or validates legacy records, it reveals which fields the checker
  reads and returns the record itself.
- The retained material names the legacy route
  `/internal/fieldlink/legacy-diagnostics/CRR-OG2`, note `ENG-FLK-LEGACY-42`, and the
  protected record `ENT-ARWC-DIAG-0698` (AES-256-GCM).

## Walkthrough

### 1. Recon — find the archive, then the client

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/connector-archive/contents/?ref=main'
```

The archive holds the FLK 6.9.8 connector. Its notes name the legacy diagnostics entry point
and `ENG-FLK-LEGACY-42`; the connector carries the signed diagnostic loader that knows how to
build a legacy entitlement record.

### 2. Finding the flaw — the old path is still wired up

Two observations confirm the bug: the archived connector's diagnostic run **succeeds**
against the current service (a decommissioned client that still validates means the legacy
branch is live), and its output names an internal route
`/internal/fieldlink/legacy-diagnostics/CRR-OG2` that appears in no public documentation.

The distinction matters: the archive is not just historical source, it is a *working client
of a protocol the server still implements*.

### 3. Exploitation — drive the legacy loader

```bash
# illustrative: run the archived connector's diagnostic configuration
node ./flk-6.9.8/bin/diagnose.js --config ./diag/legacy-crr-og2.json
```

The loader does what a hand-rolled request cannot: it signs the diagnostic envelope and
formats the legacy entitlement fields the compatibility branch expects. The response is the
compatibility assessment for `CRR-OG2`, and it is where the accepted value appears.

### 4. Getting the flag

The lane notes record that running the archived connector's signed diagnostic loader produced
the accepted value and named the route and note above. The per-card `flag` field in the
retained dataset is empty, so this write-up records it as **accepted, value not recorded**.

The second half of the card — "what the checker considers an entitlement" — is answered by
the record: `ENT-ARWC-DIAG-0698` is an AES-256-GCM blob, i.e. the checker's notion of an
entitlement is an encrypted, authenticated structure, not a plain JSON claim.

## Why this works (the vulnerability explained)

Backwards compatibility is a *second parser* on the same trust boundary, and old parsers are
almost always weaker. The legacy format predates whatever validation the modern schema added
(stricter types, binding to tenant/release, signature checks, expiry policy), so accepting it
re-admits inputs the current design rejects. The decision surface becomes the union of both
formats, and the attacker picks the weaker branch — the one nobody tests because "it's only
for old clients". A signed legacy client in an accessible archive then turns protocol into
documentation: field order, AAD, signing scheme and expected responses are all readable.
Finally, the protected record is guarded only by cryptography — but the client that
legitimately decrypts it is in the archive, so the problem becomes "obtain the key the client
already uses" rather than "break the cipher".

## Detection and fix

- **Detect:** calls to legacy/deprecated routes from outside the known legacy fleet (client
  version header, user agent, source); legacy-format entitlements in tenants with no old
  installations; the archived client's diagnostic signature replayed against another tenant.
- **Fix:** retire the legacy branch or gate it per tenant with an allow-list and a sunset
  date. If it must stay, normalise legacy input into the current schema *before* the decision
  and validate the normalised form — never decide on legacy fields directly.
- **Fix the archive:** an archived client must not keep working credentials or reach
  production routes; remove its signing key from the trust store at retirement.

## Notes and dead ends

- The lane's own dead end is instructive: a large set of direct SHA-256/HKDF-SHA256
  derivations, with several AAD variants, did **not** decrypt `ENT-ARWC-DIAG-0698`. The
  intended path is the legacy client, not key guessing.
- Delivery `/api/releases/*` requires Basic auth, and the compatibility check needs a real
  release id/context. Guessing release ids is a dead end (K08.2/K08.3 territory).
- Evidence quality: the retained data quotes lane notes rather than command output, so the
  `node … diagnose.js` invocation is an **illustrative reconstruction** of "run the archived
  connector's signed diagnostic loader". Route, note id, record id and the AES-256-GCM
  detail are verbatim.
