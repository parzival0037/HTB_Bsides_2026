**What you are about to read:** how to recover the *complete* acceptance predicate from a
compiled policy — including hidden constraints — and why a policy whose documentation is weaker
than its bytecode is a vulnerability, not just sloppy docs.

## Objective

Recover the complete acceptance conditions enforced by the embedded policy program, and account
for the constraints the ordinary documentation omits.

## Background you need

- **Two sources of truth.** The README documents rules ("channel must be stable", "version in
  range"); the compiled program is what runs.
- **Control flow, not just opcodes.** The interesting constraints sit in the uncommon path: a
  reject branch reachable only for certain field combinations, or a conjunct nobody documented.
- **`IN_SET` is where hidden policy lives.** An allow-list of channels, versions, roles or
  tenants *is* a constraint; members the docs do not describe are part of acceptance.
- **The evaluator is the oracle.** `POST …/evaluations` (with `…/nonces` alongside) lets you
  confirm each constraint with an input that isolates it.

## Walkthrough

### 1. Reconstruct the instruction stream

From K11.1 you have magic, header, 4-byte words, and `PUSH_FIELD` (fields 0–3), `PUSH_CONST`,
`IN_SET`. Dump a listing with resolved operands:

```text
PUSH_FIELD 0
IN_SET     1        ; accepted values for field 0
JUMP_IF_FALSE  reject
PUSH_FIELD 2
PUSH_CONST 3
LT                  ; hidden ordering constraint
JUMP_IF_FALSE  reject
PUSH_FIELD 3
IN_SET     4
```

Each `JUMP_IF_FALSE reject` marks a conjunct; the listing is the skeleton of the predicate.

### 2. Finding the flaw — the documented rules are a subset

Compare the README's prose rules, the listing's conjuncts, and the contents of every `IN_SET` and
`PUSH_CONST`. Any conjunct with no counterpart in the README is an **undocumented constraint**:
a field never mentioned but required non-empty, a set that silently excludes documented-valid
values, or a comparison encoding a version/date floor. Users reason about the documented policy
while the engine enforces something stricter — or different.

### 3. Exploitation — confirm each conjunct with the evaluator

```bash
# illustrative: single-field probe
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H 'Content-Type: application/json' \
  -d '{"policy":"fieldkest","input":{"field0":"<value>","field1":"<baseline>","field2":"<baseline>","field3":"<baseline>"}}' \
  https://source-tools.keplerops.test:8443/api/policy-compilers/fieldkest-policyc/evaluations
```

Hold all other fields at an accepted baseline and vary one. A value that passes while the docs
say it should fail (or the reverse) localises the hidden conjunct. Probe every `IN_SET` member
and every `PUSH_CONST` boundary. The deliverable is a complete ordered predicate — field 0 ∈ S1,
field 2 > c, field 3 ∈ S4 — with the undocumented parts flagged.

## Why this works (the vulnerability explained)

Policy drift is a security bug because **the enforced policy is the only one that matters**, and
the one people read is not it. Documentation is an interface: a documented-valid input the
engine rejects is an availability problem; a documented-invalid input the engine accepts is a
bypass. Compiled policy hides conjuncts — one extra comparison can turn "any stable channel"
into "only these three builds", and nobody reviews the bytecode. Allow-lists are the usual hiding
place, easy to extend during an incident and easy to forget to document. An evaluation endpoint
that returns accept/reject then makes the hidden constraints a search problem with instant
feedback.

## Detection and fix

- **Detect:** accepted evaluations for inputs failing the documented rules (or rejections of
  documented-valid ones); `IN_SET` members with no documented origin; policy version changes with
  no doc/release note.
- **Fix:** derive the published rule table from the compiled program in CI and diff it on every
  change; require review for new constants or set members; sign, version and audit the program.
- **Fix exposure:** the evaluator should not be a general oracle — rate-limit, require a nonce
  per evaluation (the `nonces` route exists for this), and log boundary probing.

## Notes and dead ends

- Evidence is thin: description, the K11.1 hints, and the note that K11.3/K11.4 remain unresolved
  in the source lane, with no disassembly or evaluation output. The listing is an
  **illustrative** FKPC program and the probe is a template; route names come from the client
  reference.
- Brute-forcing the input space is a dead end: four realistic domains is combinatorially large
  and the route is nonced/rate-limited. Read the jumps; probe the boundaries.
- Reject branches are not the only hidden behaviour: accept branches can set a derived
  "entitled" flag that never appears in output but changes later decisions.
