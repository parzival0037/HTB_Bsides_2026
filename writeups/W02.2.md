# W02.2 — Three names for one job

> **Category:** 3. ARWC · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Correlation-graph disclosure — an inspection trace returns the internal work order, the supplier job and the engineering drawing for the same job, plus a flag, to a caller who only needed the public manifest result |
| **Tools** | `curl`, `jq`, the SOCKS pivot |
| **Attack surface** | `delivery.keplerops.test:8443` → `POST /api/inspections`, `GET /api/inspections/{id}/trace` |
| **Prerequisite** | Basic auth as `rowan.ito` with the developer token |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how one inspection carries three identifiers in three
systems, how the trace hands you the mapping, and why the version pin makes it reproducible.

## Objective

Reconcile the internal work order, supplier job and engineering drawing that refer to the
same outlet inspection. The deliverable is the agreed mapping between the three names, plus
the flag the reconciled record carries.

## Background you need

- **Identifier drift.** The same physical job is a *work order* to the utility, a *job* to
  the supplier, and a *drawing* to engineering. Each system mints its own key; nothing
  enforces that the keys look alike, so reconciliation is normally a manual, error-prone
  exercise.
- **Trace as join table.** Diagnostic traces often include every identifier a request
  touched, which makes them an accidental join table across trust boundaries.
- **Pinning.** An inspection of a package is only meaningful against a fixed version and
  request id. Re-running against a different version inspects different bytes and produces a
  different verdict — hence the version gate.

## Walkthrough

### 1. Create the inspection

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  -H 'Content-Type: application/json' \
  -d @inspection-normal.json \
  https://delivery.keplerops.test:8443/api/inspections | jq .
```

Observed result: `INSP-2047`. The public-manifest action returns an inspection id; that id
is the only handle you get back at this stage.

### 2. Read the trace — this is the reconciliation record

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  https://delivery.keplerops.test:8443/api/inspections/INSP-2047/trace | jq .
```

The trace is the "three names for one job" record: it ties the internal work order, the
supplier job and the engineering drawing together, and it carries the flag for this card.
The same endpoint also served a flag for W02.1/W03.1 work at different times, which is why
you must check *which* record you are looking at before submitting.

### 3. Respect the version gate

The inspection only accepts the intended revision pair — version `7.4.2` with
`request_id` `release-742`. Anything else fails to produce the reconciled trace: the route
does not inspect "the package", it inspects a pinned artefact plus a request identity. See
W03.1 for the exact accepted request body.

### 4. Do the reconciliation explicitly

Write the mapping down and check it against the delivery metadata before trusting it:

| System | Identifier | Cross-check |
|---|---|---|
| Utility work order | internal job reference from the trace | must match the handover/planning documents |
| Supplier job | inspection/job id (`INSP-2047` family) | must match the package `_rev` inspected |
| Engineering drawing | drawing reference from the trace | must match the asset scope in the order |

If one leg disagrees, you have the wrong job — the same asset can appear in several orders.

### 5. Getting the flag

The flag for this card is returned by the trace response itself. The solve record does not
retain the value, so it is reported here as accepted without the literal string.

## Why this works (the vulnerability explained)

Reconciliation is a legitimate business need, but the trace implements it by dumping every
identifier it knows, without asking whether the caller is entitled to the customer-side
keys. The caller is authenticated as a supplier developer and authorised for the public
manifest flow; the trace then discloses the *correlation graph* — work order ⇄ supplier job
⇄ drawing ⇄ package revision. That graph is the valuable object: with it you can pivot from
a public inspection id into the customer's internal work-order namespace.

Two defensive lessons follow. First, an endpoint can be "authenticated but over-privileged":
the check is about *fields*, not about who may call. Second, pinned inputs are part of the
contract — if `version` and `request_id` are not enforced, the same endpoint returns
different answers for different callers at different times, which destroys auditability.

## Detection and fix

- **Log signal:** trace reads by callers that never created or own the inspection; repeated
  traces against the same id with different `version`/`request_id` values.
- **Fix:** return a projection that contains only identifiers in the caller's namespace,
  gate customer-side identifiers behind an entitlement check on the customer, and reject
  unpinned inspection requests with a validation error rather than silently re-inspecting.
- Secondary: keep the authoritative reconciliation in the order record, not in a diagnostic
  endpoint that happens to join everything.
