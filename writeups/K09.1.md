# K09.1 — A runner tells on itself

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Information disclosure via CI run metadata — the runner publishes its own record (profile, command, revision) to an API any authenticated user can read |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://review.keplerops.test/api/runs/{run_id}` (and `/log`) |
| **Prerequisite** | A valid developer credential for the review service |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the smallest finding in this chapter — run metadata that
describes the machine and the command that produced a result — and why "the CI told me how it
is configured" is a real leak, not trivia.

## Objective

The description is empty in the retained dataset; the title and chapter define it. Make a CI
runner disclose its own identity and configuration through the run metadata it retains,
rather than through the code it runs.

## Background you need

- **Run metadata** is the bookkeeping a CI service keeps: run id, job name, profile, state,
  timings, command line, working directory, connector revision, output digests and retained
  artifacts.
- **Metadata describes the environment.** A runner reporting `profile`, image tags, mounted
  paths or injected variables is describing its own attack surface to whoever can read the
  record.
- The report service exposes `/api/runs/{run_id}` with `/log` and `/artifacts/{name}`
  sub-resources; `POST /api/review-jobs` returns an `RJ-XXXXXXXX` handle.
- 50 points / easy means a single GET, not a chain.

## Walkthrough

### 1. Recon — find a run id

```bash
# illustrative: submit a trivial job to obtain a run handle
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' -H 'Content-Type: application/json' \
  -d '{"template":"report-consumer-v2","input":{}}' \
  https://review.keplerops.test/api/jobs
```

### 2. Finding the flaw — the record describes the runner

```bash
# illustrative: read the run record
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://review.keplerops.test/api/runs/<run_id> | jq .
```

Two things make this a finding: the record includes fields a consumer does not need (profile,
command, connector revision, enough environment detail to describe the runner), and there is
no per-run ownership check beyond "is authenticated" — so runs you never submitted are
readable too.

The value for this card is in the run record itself (or its `/log`), which is why it is
scored easy: no exploitation step beyond reading.

### 3. Exploitation — enumerate, don't guess

```bash
# illustrative: walk retained runs and keep the informative fields
for id in $(seq -w 1 40); do
  curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
    -u 'rowan.ito:<fk_developer token>' \
    "https://review.keplerops.test/api/runs/<prefix>${id}" \
  | jq -c '{id, profile, command, connector_revision, state}'
done
```

The interesting record is the one whose `profile` is not the template you submitted — the
runner describing a job designed to run something else.

### 4. Getting the flag

Solved by a team agent; the retained evidence is challenge metadata plus a cross-lane note
that K09.1 was already solved before the K09 lane run, so the accepted value is **not
recorded**. The demonstrated surface is `/api/runs/{run_id}` on `review.keplerops.test`.

## Why this works (the vulnerability explained)

This is **disclosure through the observability layer**. The service exposes run metadata so
operators can debug jobs, and it authenticates the *request* but not the *relationship*
between requester and run. Three issues compound: missing object-level authorization
("authenticated" is treated as "may read any run", and ids are short and enumerable);
excessive fields (profile/command/revision exist only because the same serialiser feeds the
operator UI); and a classification failure — teams protect the *artifacts* and forget that
the *description of how they were produced* names internal paths, images and the identity the
job ran as.

## Detection and fix

- **Detect:** one credential reading many distinct run ids in a short window; reads of runs
  the caller never submitted; clients iterating sequential id shapes.
- **Fix:** authorize every run read against caller ownership/tenant, not just authentication;
  use unguessable ids; return a consumer-shaped DTO that omits profile, command and
  environment, keeping the operator view on a separate audited endpoint.
- **Fix defaults:** never include environment variables, mount paths or image tags in run
  metadata that leaves the build system.

## Notes and dead ends

- Evidence is minimal: title/points plus a lane note that the card was already solved. The
  endpoint shape, enumeration loop and field names are **reconstructed** from the range's
  documented `/api/runs/…` routes and the CI source comments quoted in sibling cards.
- Reading `/api/runs/{id}/log` for a run you did not submit is the same bug class; if the
  metadata endpoint is closed the log usually is not, but both are one finding.
- Do not chase the Jenkins UI here — the review service retains more than the Jenkins results
  page shows.
