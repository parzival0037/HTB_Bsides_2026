## Objective

> Recover the retained completion-job example and the private job note that explains its
> intended support use.

A discovery card, not an exploit chain: the material is reachable once you hold the support
session, and the work is recognising which assistant record is the retained job.

## Background you need

- The assistant is a support-facing overlay exposing a small contract under `/api/*`; it
  authenticates the *session* with the support integration token as a cookie
  (`fieldkest_support=…`).
- A **completion job** is the overlay's unit of work: a prompt/context pair plus a record
  naming the identity it executes as, a credential reference and the handover it produces.
- API documentation usually ships as a **worked example**. If that example is a copy of a
  real record rather than a fixture, every reference in it is live.

## Walkthrough

### 1. Recon — the config names its own artefacts

The overlay publishes a config blob listing the retained artefacts it is working with.

```bash
TOK=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Cookie: fieldkest_support=$TOK" \
  https://assistant.keplerops.test/api/config
```

The support-relevant keys are the context, the selection/attachment pair from SUP-2841 and
the **completion example** id (`COMP-JOB-17`). The blob holds pointers, not content — which
is why the next request exists.

### 2. Finding the flaw — the example route serves a real job

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Cookie: fieldkest_support=$TOK" \
  https://assistant.keplerops.test/api/completions/examples/COMP-JOB-17
```

What comes back is not a schematic — the retained record carries the job's operative
references:

- `cred-completion-handover` — the credential the job uses to reach the handover store;
- `svc-assistant-completion` — the identity the job actually runs as;
- `HANDOVER-COMP-2841` — the handover document that job produces;
- the card's `flag` field.

Any one alone is uninteresting; together they describe one execution path — *this* account,
with *this* credential, writes *that* handover. That is the private job note.

### 3. Confirming it is the intended support use

The references line up with the rest of the case material: SUP-2841 is the ARWC connector
case, and the completion job is the assistant-side step that packages case evidence into a
handover. The same identifiers appear on the overlay's job routes, so the example is a
snapshot of a live job, not a mock. The flag sits on the example record itself.
Accepted value: `FLAG{664724eb7d7073e9}`.

## Why this works (the vulnerability explained)

The bug class is **fixture/live-data confusion**: an endpoint whose review process assumes
the payload is documentation, while the payload is a production record. Three things
combine:

1. **Copy instead of construct.** The example was generated by exporting a real job, so
   every field — including the identity and credential handle — came along. A hand-built
   fixture would have said `svc-example`, not `svc-assistant-completion`.
2. **Weaker authorization on the "harmless" route.** Example endpoints are usually left
   readable because "it's just a sample". But the sample *is* the sensitive record, so the
   route is a second, less-protected door to the same data.
3. **The flag is on the object, not behind an action.** Scoring checks that you reached the
   record, so nothing in the response looks like an exploit — no bypass, no injection.
   The vulnerability is an information-design decision, not a parser bug.

The transferable lesson: **any endpoint that returns an object returns everything in the
object.** Enumerating the fields of a "documentation" response is recon in its own right.

## Detection and fix

- **Detect:** example/template/sample resources whose stated identities later show up in
  real audit entries; log the identifier returned, not just the route hit.
- **Fix:** generate examples from a scrubbed schema (principals, credential handles and
  handover ids replaced by placeholders) or keep them in the docs repo, not an API route.
- **Fix the authorization:** an example with live references inherits the live object's
  authorization — same policy, no special case.

## Notes and dead ends

- The card's retained evidence is the accepted flag plus the identifier triple
  (`COMP-JOB-17` → `cred-completion-handover` / `svc-assistant-completion` /
  `HANDOVER-COMP-2841`). The request transcript above is **reconstructed** from the K23
  lane's documented overlay contract; the exact response body was not retained per card,
  so field ordering and extra keys are illustrative.
- A bearer header or AnythingLLM JWT returns `{"error":"session_required"}`; only the
  `fieldkest_support` **cookie** is accepted.
- Reading the whole conversation/document set behind SUP-2841 yields other cards' flags
  (K21.x, K23.x); this card is only the completion example.
