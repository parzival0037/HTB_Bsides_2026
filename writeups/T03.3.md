# T03.3 — What installation really runs

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Install-time code execution in a package — a hook (`setup.py`, `postinstall`, install script) that runs with the installer's privileges and touches data the package never needed |
| **Tools** | `tar`, `unzip`, `ar`, a text editor/pager, `strings`; no installer required |
| **Attack surface** | The supplied package artefact from the developer-artifacts desk (`http://developer.training:8080/`, 10.77.40.40) |
| **Prerequisite** | The package file itself; the card explicitly forbids installing it |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how to answer "what would happen if I installed this?" without
installing it. Installation is code execution, so the package is treated as an executable and read
statically: what hook runs, what it reads, where the result goes. That discipline separates a
supply-chain review from a gamble.

## Objective

> Inspect the supplied package WITHOUT installing it; recover the extra action installation would
> trigger, the data involved and its destination (install hooks / setup.py / postinstall scripts).

The desk hands out a package, and installing it is out of scope — which is the lesson, because the
interesting behaviour only happens *during* installation. The answer is three facts: the hook, the
data it handles, and where that data goes.

## Background you need

- **Installation is execution.** Every mainstream ecosystem lets a package run code as part of
  being installed: `setup.py` (or a build backend hook) for Python, `preinstall`/`install`/
  `postinstall` scripts for npm, `%post` for RPM, `postinst` for Debian packages. It runs with the
  privileges of whoever installs — often a CI runner with registry tokens and cloud credentials in
  its environment.
- **The hook has no business reading your files.** A legitimate build hook compiles, copies and
  records metadata. Anything touching `~/.ssh`, `~/.aws`, `.npmrc`, `.env`, browser profiles,
  environment variables or `/etc` is exfiltration dressed as setup.
- **Static inspection is sufficient.** Archives are just archives: `tar`/`unzip`/`ar` plus reading
  the hook text answers the question without running anything.
- **Destination is part of the finding.** "It reads X" is half an answer; "it POSTs X to Y" is the
  finding, and both are visible in the hook's source.

## Walkthrough

### 1. Identify the artefact type before opening it

The extension (or, failing that, the magic bytes) tells you which extractor to use; `file` is the
cheapest first step:

```bash
# illustrative: identify the artefact, then list it without extracting
file ./<package-artifact>; tar tzf ./<package-artifact>  # or: unzip -l, ar t for .deb
```

### 2. Extract into a scratch directory and find the hook

```bash
# illustrative: extract into a throwaway directory and locate install hooks
mkdir -p /tmp/t033 && tar xzf ./<package-artifact> -C /tmp/t033
find /tmp/t033 -maxdepth 3 \( -name 'setup.py' -o -name 'package.json' \
     -o -name 'pyproject.toml' -o -name '*.postinst' \) -print
```

The hook set is small: `setup.py` / build-backend config for Python, the `scripts` block of
`package.json` for npm, maintainer scripts for OS packages. `pyproject.toml` matters because a
`build-backend` can move the execution elsewhere.

### 3. Read the hook for the three facts

Read the hook text and answer, in order: **what runs** (a custom `cmdclass`, a `build`/`install`
override, a `postinstall` command, a maintainer script — anything that is not the default backend);
**what data is involved** (trace every file open, `os.environ` lookup, `subprocess` call and network
client); and **where it goes** (the sink — an HTTP client, a socket, a DNS label, a file written
outside the package directory). Obfuscation such as base64, `exec` or string splitting is itself a
signal, and `strings` over a bundled hook is enough to surface URLs and credential paths.

### 4. Record the finding

The answer is a sentence, not a payload: *this hook reads <data> and sends it to <destination>*.
Submitting that identification is what the desk accepts. The flag was accepted; its value was not
recorded in the lane evidence.

## Why this works (the vulnerability explained)

Package installation is a **trust decision that executes code**, made dozens of times a day without
review. The opportunity is structural, not a bug in one tool: the hook runs before any review of the
library would matter; the environment is richer than the filesystem, since CI runners hold registry
tokens, cloud keys and SSH agents that a `postinstall` inherits; and consumers do not distinguish
"dependency" from "installer", so `npm install` runs scripts from every transitive dependency and one
compromised leaf executes in every downstream build. Automated installers print progress, not
provenance — a hook posting 200 bytes to an attacker's host looks exactly like a successful install.

Static inspection beats dynamic here: you cannot safely test an install hook in an environment that
holds the credentials you are protecting, and the hook's text is fully available unrun. The
transferable skill is reading a package as an artefact with behaviour, not a library with an API.

## Detection and fix

- **Signal:** hooks that read paths outside the build tree or contain any network client;
  `postinstall` scripts in a dependency with no build step; first-install traffic to an unknown host
  from a CI runner; CI egress from build steps that is not the package registry.
- **Fix (consumer):** install with scripts disabled where possible (`npm ci --ignore-scripts`,
  binary-only pip policies), pin and mirror dependencies, build in a sandbox with no credentials,
  and review the hook set of any new direct dependency before adopting it.
- **Fix (publisher):** keep hooks minimal and declarative, never read the environment or user home,
  and sign releases so consumers can verify what they got.

## Notes and dead ends

- The card's trap is impatience: installing the package "just to see" executes the payload you are
  trying to characterise, in an environment that may hold real credentials.
- No command transcript for this card was retained in the lane evidence. The lane brief states the
  approach (inspect the package without installing it; recover the extra action, its data and its
  destination) and nothing more, so the shell blocks above are **illustrative templates** with
  artefact names left as placeholders. The flag value is unrecorded, so none is invented here.
- A hook being present is not itself malicious — many packages legitimately compile native code.
  The finding is the *data and destination*, which is why all three facts matter.
