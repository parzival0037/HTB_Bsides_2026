## Background you need

Support systems are append-only in practice. A ticket moves through open → escalated → resolved →
*retained*, and "retained" usually means "kept for audit for N years". Three consequences:

- **The thread is not lost when the UI hides it.** `closed` / `deleted_from_ui` are display flags;
  the rows and attachments stay queryable by any agent-level principal.
- **Retention metadata is content too.** A retention record must point at what is retained — a
  release id, an archive record, a conversation id. Those pointers are often more informative than
  the discussion.
- **Every copy is an independent leak.** Ticket, email notification, assistant transcript and
  export artefact hold the same text under different access rules (see K17.2).

## Why this works (the vulnerability explained)

Retention is implemented as a *flag on a row*, not as a separate archive with its own access
control. The agent's normal read path — open the ticket, list entries — therefore returns material
that should only be visible to the compliance role. There is no second authorisation decision
between "this agent can read the queue" and "this agent can read a retained, withdrawn release
record".

Two design errors:

1. **Scope collapse.** "Retained" and "visible to the support team" are treated as the same
   visibility. A retention hold is about *keeping* data, not *publishing* it.
2. **Pointer leakage.** Even with the discussion redacted, the retention reference
   (`REL-FLK-6.9.8-ARCHIVE`, plus the flag here) points at the artefact. A valid reference is an
   invitation — K17.2 uses exactly that kind of pointer to reach the same material another way.

## Detection and fix

- **Log signal:** agent reads of tickets in `retained`/`closed-retained` state by principals
  outside the compliance group; bulk listing of the retention queue; access to retained attachments
  long after the last customer interaction.
- **Fix:** separate retention storage from live tickets, with its own role; redact
  withdrawal/retention pointers from the agent view or replace them with an opaque handle resolved
  only by the compliance service; make the UI flag an actual row-level access change. Never embed a
  submission token in retention metadata — rotate and re-file if it is already there.
