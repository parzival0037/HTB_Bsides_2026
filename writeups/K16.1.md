## Objective

> Recover the scheduled support workflow that will run after the current operator's shift ends.

Support does not work the ARWC case by hand at night. A scheduled workflow picks up the open
ticket, assembles diagnostic material and writes the result somewhere. This card asks for that
job: its identity, its trigger, and what it runs.

## Background you need

A CronJob is an object with two halves: when it fires (`schedule`) and what fires — the
`jobTemplate`, which carries the image, `command`/`args`, env and `serviceAccountName`.

A readable schedule answers three questions at once:

1. *When* will something run unsupervised? (a window for racing or planting input)
2. *As whom* will it run? (`serviceAccountName`, often more privileged than any interactive account)
3. *What* does it consume? (mounts, ticket ids, package versions — inputs you can influence)

Nothing here needs a memory-safety bug: the exposure is that the scheduler's own description is
treated as low-sensitivity metadata.

### 3. Read the schedule object

```bash
curl -sS -H "Authorization: Bearer ${TOKEN}" \
  https://cloud-api.keplerops.test/api/schedules/SCHED-2841 | jq
```

Extract, in order of usefulness: the `schedule` (a night-window trigger is what "after the
operator's shift ends" means), the `serviceAccountName` (the real privilege being exposed — a
schedule is how you borrow an identity you cannot authenticate as), the `command`/`args`/`image`
(the workflow itself), and the env/mounts (the parameters K16.2 rewrites).

## Why this works (the vulnerability explained)

Schedules are control-plane objects that *cause* privileged execution later, yet they are treated
as operational metadata — visible in dashboards, returned by convenience APIs, cached in status
endpoints. What they actually represent is a stored, repeating authorisation decision: *at this
time, run this code as this identity*.

The API mirrors the CronJob but authorises on "may this caller read schedules at all", not "does
this caller own this schedule". The support workflow was created by the support team, so any other
tenant of the same API can read its command line, service account and next run time.

The deeper issue is that the same object is writable (K16.2). If you can read the spec you are one
`PATCH` from changing what executes — and the scheduler will run your version at the next tick,
with the original service account.

## Detection and fix

- **Log signal:** schedule reads by principals that never created or edited one; reads clustered
  with a later write to the same object; `/api/schedules/*` calls outside the support tooling.
- **Fix:** object-level authorisation on schedules (creator/team scoping); redact `env`, mounts and
  image digests from list/summary views; require a privileged role for spec reads. Keep each
  scheduled workflow's service account minimal and distinct. Alert on spec changes outside a
  change window — a changed nightly command is a high-signal event.
