# T01.3 — A token with a job

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Long-lived bearer credential published in a "retired client" profile; scope declared as `manifest:DL-204:read` but reusable by anyone who reads the file |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `http://workbench.training:8080/retired-client/profile.json` (10.77.40.20) → courier API `http://workbench.training:8082` |
| **Prerequisite** | Nothing — the profile is served anonymously and carries the token |
| **Flag** | accepted, value not recorded |

**What you are about to read:** why a bearer token shipped inside a client profile is a
credential leak, how `scope` turns "a token" into "a token with a job" (one delivery, one
verb), and how to test what a leaked token really authorises.

## Objective

> Use the credential the desk keeps handing out, and obtain what it was issued for.

The workbench keeps a retired courier client configuration online for compatibility: API base,
courier, delivery and an `Authorization` value. The card is about that token — what it grants
and what it opens for `DL-204`.

## Background you need

- **Bearer tokens are self-presenting.** Whoever holds the string is the caller — no second
  factor, no binding to machine or process, so a token in a JSON file is in everyone's hands.
- **Scope is the only containment.** `manifest:DL-204:read` means object `manifest`, instance
  `DL-204`, action `read`; anything outside that triple must be rejected. The question is not
  "does it work" but "does the server enforce instance *and* verb".
- **"Retired" is a lifecycle word, not a revocation.** Job-scoped tokens are good design
  (small blast radius) until the token ships in a world-readable file.

## Walkthrough

### 1. Recon — the desk advertises a client profile

```bash
curl -sS http://workbench.training:8080/retired-client/profile.json | jq .
```

```json
{
  "profile": "retired-courier-client",
  "courier_id": "CR-17",
  "api_base": "http://workbench.training:8082",
  "request_history": "request-history.txt",
  "delivery_id": "DL-204",
  "authorization": "Bearer courier_DL204_CR17_4N7Q2M9K",
  "scope": ["manifest:DL-204:read"]
}
```

Every field is a decision: where the token is used (`api_base`), the resource the client
fetched (`request_history`), the instance it is scoped to (`delivery_id`), and the credential.

### 2. Finding the flaw — the credential is the whole access story

No cookie, no certificate, no login: the profile *is* the credential handout, served by the
same anonymous desk as the delivery notice (`:8081/notice-DL-204.md`):

> Courier CR-17 is assigned three sealed rehearsal parcels for the Cinder receiving desk. The
> public notice does not include the bay amendment.

The profile supplies the machinery to ask the courier API about a job that is explicitly
described as incompletely published — what a job-scoped token is for.

### 3. Exploitation — replay the token against the API it names

```bash
TOK='courier_DL204_CR17_4N7Q2M9K'
B=http://workbench.training:8082

curl -sS -i -H "Authorization: Bearer $TOK" "$B/request-history.txt"
```

Read the status as an authorization statement: `200` = inside scope, `401` = revoked (stale
profile), `403` = valid but out of scope, the *correct* behaviour. Then test the same request
without the header, and with `?delivery_id=DL-205` (another instance). If the second returns
`200`, `scope.instance` is decorative — the token is a key to the service, not the job.

### 4. Getting the flag

The accepted value came from the courier API response for `DL-204` — the job document or
request history the leaked bearer opens. The record keeps no body, so it is not reproduced.

## Why this works (the vulnerability explained)

A bearer token is a capability: possession equals permission, so **distribution** is part of
the security boundary. This desk put the capability in a static file under a public document
root, next to deliberately public documents — its protection collapsed to "nobody looks at
`retired-client/`".

`scope` is a bound worth exactly what the resource server enforces. Three sub-cases matter:
(1) **none** — the API authenticates the token and ignores `scope`, so the leak reads
everything; (2) **partial** — object/verb checked, `delivery_id` not, so `DL-204`'s token reads
`DL-205` (a horizontal authorization gap in a scope's clothes); (3) **correct** — token maps to
(object, instance, action), else `403`.

## Detection and fix

- **Detection:** one bearer used from two source addresses; a token whose `delivery_id` differs
  from the resource requested; a fetch of `retired-client/profile.json` followed seconds later
  by an API call with that token.
- **Fix:** never ship a credential in an anonymously served document; have the profile reference
  a secret store. Revoke on retirement, bind the token to its instance server-side, keep it
  short-lived and log per-instance use.

## Notes and dead ends

- Solved by the team agent; the per-card evidence holds only the challenge listing, so there is
  no captured transcript. **The technique is reconstructed** from the desk's profile and notice,
  both quoted from real lane captures of this desk (`k17`/`w01` artifacts). The profile JSON is

- Two dead ends: using the token on the *desk* port `:8080` instead of the profile's `api_base`,
