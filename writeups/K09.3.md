# K09.3 — A job input with reach

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K09

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Server-side reference resolution — a job carries a "linked support reference" that the render-review worker resolves and whose content is returned to the submitter |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `POST https://review.keplerops.test/api/review-jobs` → `GET /api/review-jobs/{RJ-XXXXXXXX}` |
| **Prerequisite** | A developer credential; knowledge of the review job body shape |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a job parameter naming a server-side object turns a
review worker into a file-read primitive, and how the returned job record shows which branch
of the worker resolved your input.

## Objective

The description is empty in the retained dataset; the title and chapter define it. Submit a
render-review job whose input names a server-side reference, and make the worker resolve it and
return the referenced content.

## Background you need

- **Job templates take structured input.** `report-consumer-v2` takes
  `{"template": …, "input": {"archive_base64": …}}`; a render-review job instead takes a
  *reference* to a linked support document.
- **Reference resolution is an authority transfer.** The worker resolves `linked_support_ref`
  with its own identity, not the submitter's. Without a check against the submitter's
  entitlements, the worker reads documents the submitter cannot.
- The service stores each submission as `REVIEW_JOBS/<run_id>.json` and accepts only ids
  matching `RJ-[0-9A-F]{8}` — the handle format is part of the contract.
- The acceptance branch is explicit: when the job has `review.maintained_reference` set, the
  render-review job resolved the linked reference and returned the
  diagnostic-request-reference content.

## Walkthrough

### 1. Recon — learn the job body

```bash
# illustrative: confirm the service contract
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  https://review.keplerops.test/.well-known/fieldkest-client | jq .
```

### 2. Finding the flaw — the reference is resolved blindly

```bash
# illustrative: submit a render-review job with a linked support ref
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' -H 'Content-Type: application/json' \
  -d '{"template":"render-review","input":{"linked_support_ref":"<support reference>"}}' \
  https://review.keplerops.test/api/review-jobs
```

The response is an `RJ-XXXXXXXX` handle. Validation is on the *handle*, not on your right to
the document it will resolve.

### 3. Exploitation — poll the record, read the branch result

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://review.keplerops.test/api/review-jobs/RJ-AB12CD34 | jq .
```

The decisive field is `review.maintained_reference`: its presence means the worker resolved
your reference and returned the referenced content — success for this card. A job that fails
to resolve returns without the field, which distinguishes "my reference was wrong" from "the
worker refused".

### 4. Getting the flag

The lane report records this card as solved, and the service source shows the flag attached to
the returned job when `maintained_reference` is present. The per-card `flag` field is empty in
the retained dataset, so the value is recorded as **accepted, value not recorded**.

## Why this works (the vulnerability explained)

The bug is **reference resolution as an authority transfer** — SSRF-adjacent but local, and
easier to overlook because it feels like ordinary application logic. The submitter controls an
identifier that selects a server-side object; the worker resolves it with its own privileges
(it must be able to read support documents to do its job); and the resolved content is
returned as part of the job result. No step alone is wrong. Together they delegate the
worker's read permissions to whoever can submit a job — the developer credential only
*submits*, while the sensitive read runs as the worker, so per-user ACLs on the document are
never consulted.

## Detection and fix

- **Detect:** submissions whose `linked_support_ref` names a document the submitter cannot
  read; one reference resolved by many distinct submitters; job results embedding document
  content rather than a rendered summary.
- **Fix:** resolve references under the submitter's identity (token exchange) or authorize the
  reference explicitly first. Return a rendering, not the source material, and log every
  resolution with both identities.
- **Fix the output shape:** a review job should return a verdict and a link, not the material
  it read.

## Notes and dead ends

- Evidence is real but partial: the retained snippets quote the service source
  (`/opt/fieldkest/ci.py`, mirrored at `/opt/fieldkest-ci/ci.py`) showing the
  `maintained_reference` branch and the `RJ-[0-9A-F]{8}` validation, plus the lane's solved
  table. Request bodies and the polling loop are **reconstructed** from those branches.
- Guessing handles is a dead end: retrieval needs a well-formed `RJ-` id *and* an existing job
  file, and there is no listing endpoint for other submitters' jobs.
- The `report-consumer-v2` template with `archive_base64` is a different input path (whole
  archive in the body); it does not resolve references and will not set
  `maintained_reference`.
