# W31.1 — The vault's misleading length

> **Category:** 3. ARWC · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Parser differential — a declared length does not describe the real record boundary, so the naive reader stops early and never reaches the record holding the protected diagnostic reference |
| **Tools** | `xxd`/`hexdump`, `python3` (`struct`), `strings` |
| **Attack surface** | The diagnostic vault supplied with the case (an on-disk container of diagnostic records) |
| **Prerequisite** | The vault file plus the case identifier telling you which record you need |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a declared record length can disagree with the bytes that
follow, why that is a security bug, and how to establish the vault's *real* boundary rule before
parsing anything out of it.

## Objective

Recover the vault's actual record-boundary behaviour and the protected diagnostic reference for
the supplied case: the boundary rule, and the reference stored in the record a naive parse
misses.

## Background you need

- **Length-prefixed containers.** A header carries a length or count, then the payload. Readers
  trust it and jump to the next record — fast, and fatally fragile when the length is wrong.
- **Boundary rules differ.** A length may count payload only, include the header, be counted in
  words, cover a padded span, or be capped by a 16-bit field. Writer and reader disagreeing
  produces a **parser differential**.
- **Hidden is not encrypted.** A skipped record is still readable by anything that finds its
  real boundary; "protected" means "not shown by the tool".

## Walkthrough

### 1. Identify the container before parsing

```bash
file vault.bin
xxd -l 128 vault.bin
strings -n 6 vault.bin | head -40
```

Note magic/version, any declared count or length, the first header, byte order and each numeric
field's width — a 16-bit length is the classic misleading bound.

### 2. Parse the way the format *claims* to work

Write the naive parser first, to see exactly what it skips. This is illustrative Python for a
generic length-prefixed layout, not the vault's actual format:

```python
import struct

blob = open("vault.bin", "rb").read()
off, records = 0, []
while off + 8 <= len(blob):
    magic, declared = struct.unpack_from("<II", blob, off)
    start = off + 8
    records.append((off, declared, blob[start:start + declared]))
    off = start + declared          # <- trust the declared length
print(len(records), "records by declared length")
```

If records look truncated, or the last ends mid-sentence/mid-JSON, the declared length is not
the boundary.

### 3. Find the real boundaries

Boundaries reveal themselves: repeated magic, a newline/NUL delimiter, or alignment padding
before the next header. Scan for the next magic rather than computing from the length:

```bash
grep -abo $'\x4d\x5a\x00\x00' vault.bin | head    # candidate record starts
grep -abo $'\n{2}' vault.bin | head               # if records are text-delimited
```

Compare, per record, `next_offset - payload_start` with the declared length. The difference is
the boundary error: header size, padding, word-vs-byte counting, or a wrapped value.

### 4. State the rule, then read the protected record

State it in one sentence — e.g. "the length counts payload bytes but excludes the 8-byte
trailer" — and verify it on several records. Then walk the true boundaries, enumerate *all*
records including skipped spans, and resolve the reference against the supplied case.

The reference and flag appear once you parse by the real boundary. The solve record retains
neither, so both are reported as accepted / unresolved rather than quoted.

## Why this works (the vulnerability explained)

At least two components read the vault: the producer and the consumer. They implement the same
format with different boundary arithmetic. The producer writes a length correct for *its own*
reader; the consumer treats it as absolute. Every record after the first error shifts, and the
tail becomes unparseable or invisible. No corruption is needed — placing a record inside the
discrepancy hides it from the tool of record while it stays on disk.

The class is broader: ZIP central-directory vs local-header disagreements, image formats with
declared vs actual dimensions, TLS records with wrong lengths, over-running archive entries.
A length is a *claim* to validate against the container, not an instruction to seek blindly.

## Detection and fix

- **Log signal:** parse warnings about trailing bytes, payloads shorter than declared,
  consumer and producer disagreeing on record counts.
- **Fix:** bounds-check every length against the remaining container, verify alignment/trailer
  rules, reject records that do not end where the next magic begins, and add a differential
  test that parses one file with two independent implementations. Prefer canonical framing and
  alert on unparsed bytes — silent truncation is how hidden records stay hidden.
