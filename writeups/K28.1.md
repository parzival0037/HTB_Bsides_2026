# K28.1 — A connector with two faces

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Hidden behaviour behind a signed configuration switch — the same binary exposes an ordinary interface and a diagnostic loader that only activates for a specific signed setting |
| **Tools** | `curl`, the source browser, `source-tools` exercise route, `sha256sum` |
| **Attack surface** | `https://source.keplerops.test` (connector archive) and `POST https://source-tools.keplerops.test:8443/api/exercises/connector-archive/run` |
| **Prerequisite** | Read access to the archived connector repository; no customer credential needed |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how one binary behaves in two unrelated ways depending on a
configuration field, how to find the switch, and what proves the second behaviour.

## Objective

> Determine when the archived connector behaves differently from its ordinary interface and
> recover the diagnostic evidence for that difference.

The deliverable is a *condition* plus the *evidence the other branch emits* — not a guess.

## Background you need

- The archive retains a whole connector release: binary, link map, sample inputs and more than one
  configuration. The README documents the ordinary invocation a customer would run.
- A "diagnostic loader" is a feature flag with teeth: a signed value makes the connector interpret
  an embedded program instead of its report pipeline, so identical input yields a *different output
  shape*.
- The program's key is bound to the binary's build identity and associated data, so the ciphertext
  cannot be lifted and decrypted elsewhere.
- The same bounded run exists server-side (`/api/exercises/connector-archive/run`), so results are
  comparable without shipping the binary around.

## Walkthrough

### 1. Recon — inventory the archive before running anything

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/connector-archive/contents/?ref=main'
```

The listing is the map: binary, `maps/…`, `examples/…`, two configurations (ordinary and
diagnostic) and a retained engineering note. The note documents the *second* face; the README the
first.

### 2. Finding the flaw — the configuration selects the interface

Run it the documented way first, so the baseline is unambiguous:

```bash
cd /tmp/k28 && /var/tmp/fc --config config/ordinary.conf --input examples/fieldkest.bin
```

Then run it with the diagnostic configuration. The output is not a variant of the same report: it
names a *route* and an *engineering note id*, telling you where this customer's retained material
lives. That change of shape answers "when does it behave differently" — **when the signed
diagnostic-loader setting is present and valid**.

Two checks make the claim solid: corrupt one byte of the signed setting and confirm the loader does
not activate (the switch is verified, not merely read); and repeat the run to confirm a stable
output digest.

### 3. Recovering the embedded program (the interesting part)

The program is not a separate file; it is embedded as a tagged blob. The loader derives its key
from the build identity and uses the build id as associated data:

1. read the build id from the ELF (`readelf -n`, or the archive note);
2. derive the key from the KDF inputs visible in the binary and its link map;
3. decrypt and confirm the first bytes look like an instruction stream, not a report.

The program is short — "emit this route / this note id" — which is exactly the evidence wanted.

### 4. Getting the flag

Solved by a team agent; value not recorded. Scoring: the condition plus the evidence it emits.

## Why this works (the vulnerability explained)

The bug class is **undocumented dual behaviour**: a signed configuration switch that changes the
meaning of the input, not just its parameters.

- **One interface is documented, both are shipped.** Operators reason about the binary in the
  README; a flag selecting a different interpreter makes that reasoning false — same input, same
  binary, different semantics.
- **The flag is signed but not published.** The signature proves the vendor produced the setting;
  it says nothing about customers knowing the capability exists — integrity without transparency.
- **The blob is protected by build identity.** Deriving the key from the build id prevents
  copy-paste decryption but not analysis: whoever holds the binary holds the KDF inputs.
  Derivation is obfuscation, not confidentiality.

The standard shape of a hidden diagnostic path: ordinary behaviour in the documented
configuration, a second one gated by a value only the vendor is supposed to set.

## Detection and fix

- **Detect:** parsers accepting settings absent from the published schema; strings near a signature
  check naming a "loader"/"interpreter" mode; identical inputs yielding different output shapes.
- **Fix:** do not ship a second interpreter in the production artefact. If a diagnostic mode is
  needed, build a separate binary with its own signing identity and publish the flag and its
  effects. Validate configuration against a schema enumerating every accepted key, so an unknown key
  is an error rather than a code path.
  Log which configuration/mode the connector selected at startup so a customer can tell which face
  was active.

## Notes and dead ends

- Evidence is thin: the card retains the description plus the documented source and exercise
  routes. Archive file names come from retained material, but no per-card transcript survived —
  treat quoted shapes as **reconstructed**.
- Running from `/tmp` on the range box fails (`noexec`); copy to `/var/tmp` and run there.
- Do not treat the diagnostic output as a customer report: it is metadata (route plus note id), and
  the retained note explains the retention. Its fields are not comparable with the production
  interface — different implementations sharing one customer reference.
