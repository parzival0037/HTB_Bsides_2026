# K13.1 — The listing nobody closed

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K13

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Anonymous object-storage listing — a workspace bucket allows unauthenticated `ListBucket`, exposing deployment notebooks that contain tokens |
| **Tools** | `curl`, `jq`, an S3-compatible object store |
| **Attack surface** | `https://objects.keplerops.test/` → bucket `fieldkest-workspaces` |
| **Prerequisite** | Route to the service network (SOCKS pivot); no credentials |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the cheapest finding in the cloud chapter — an S3-compatible
bucket with public listing — and why a directory listing is a credential leak even when no file
is "public" by design.

## Objective

The description is empty in the retained dataset; the lane evidence defines it. Notice that the
workspace object store answers an unauthenticated listing request, enumerate what is stored, and
recover the deployment notebook — including the workspace token it holds.

## Background you need

- **S3 has three separate permissions:** `ListBucket` (see keys), `GetObject` (read one), and
  `PutObject`. Bucket policies commonly grant `s3:ListBucket` to `*` while believing objects are
  "private".
- **Listing is reconnaissance, not access.** Even if every object were unreadable, the key list
  reveals naming conventions, tenant ids, dates, job ids and file types.
- **Deployment notebooks are credentials.** A notebook that deploys a workload usually carries a
  workspace token, a schedule id and the target namespace.
- The range hosts an S3-compatible endpoint at `objects.keplerops.test`; the lane found
  `fieldkest-workspaces` by asking the endpoint root with no credentials.

## Walkthrough

### 1. Recon — ask the endpoint who it is

```bash
curl --socks5-hostname 127.0.0.1:1080 -k https://objects.keplerops.test/
```

The lane's output:

```text
-> bucket fieldkest-workspaces (anonymous listing)
```

No credentials were supplied — that is the entire finding. The root `GET` is `ListBuckets`, and a
public answer means the deployment never restricted it.

### 2. Finding the flaw — list, then fetch

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  https://objects.keplerops.test/fieldkest-workspaces/notebooks/deploy-2026-09.json
```

returned the deployment notebook, whose fields (verbatim from the lane note) were:

```text
workspace_token = F...        ; the workspace token (this card's value)
... 841, job SCHED-2841
```

The notebook also names `SCHED-2841`, which makes the later cards in this chapter reachable: token
and schedule id belong together.

### 3. Exploitation — understand what you hold

The lane tested the artefact before building on it: the workspace token in the notebook is a
**flag**, not a usable credential — the S3 STS endpoint rejects it (`web identity token must be a
valid JWT`). So this card's answer is the token value itself; it authenticates nothing. K13.4's
workload identity comes from a different route.

### 4. Getting the flag

The lane report records this card as solved on version 2 of `notebooks/deploy-2026-09.json`, where
the value appears in `workspace_token`. The per-card `flag` field is empty in the retained
dataset, so it is **accepted, value not recorded**.

## Why this works (the vulnerability explained)

This is **exposure by default configuration**. Bucket-level and object-level permissions are
confused: "the objects are private" and "the bucket is private" are different statements, and a
policy granting `ListBucket` to everyone makes the key space public while `GetObject` stays
denied — and teams test only the read. Naming is information: `notebooks/deploy-2026-09.json`
tells an attacker the environment, cadence and file type, converting blind guessing into a
targeted request. The store is treated as a filesystem, so one listing is effectively a directory
tree of the deployment process; and artefacts that must authenticate carry tokens inline, so a
listable deployment notebook is a compromised credential by definition.

## Detection and fix

- **Detect:** anonymous `GET /` or `?list-type=2` against the object endpoint; `ListBucket` grants
  with principal `*`; access to notebooks from outside the build network.
- **Fix:** remove public `ListBucket` (block public policies at account level); grant read by
  exact key or prefix to specific roles. Keep deployment notebooks out of object storage, or
  encrypt them with a KMS key only the deployment role can use.
- **Fix the artefacts:** never store long-lived tokens in notebooks — mint at run time via
  workload identity (K13.4), so a leaked notebook yields nothing usable.

## Notes and dead ends

- Evidence is real: the lane report contains the curl invocations, bucket name, object key, the
  `workspace_token` field and the STS rejection message. The flag value is not reproduced.
- Using the notebook token as an S3 credential is a dead end: `AssumeRoleWithWebIdentity` rejects
  it because it is not a JWT. The lane recorded this explicitly.
- Do not stop at the listing. The value is in the object; the listing is only the reconnaissance
  that found it.
