# K02.1 — The missing fixture

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K02

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Data still present in history after deletion — a "removed" test fixture recoverable from the git object store, plus a build log that retains the failure detail |
| **Tools** | `curl` (Gitea API, Jenkins API), `jq`, `base64`, `git` |
| **Attack surface** | `https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/...` and `https://ci.keplerops.test/job/fieldlink-report/1842/` |
| **Prerequisite** | `rowan.ito` developer credentials (Gitea and Jenkins basic auth) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a fixture deleted from `main` is recovered from an earlier
commit, and how the failing build keeps the evidence of what it expected. The bug class is
*deletion that is not erasure*: git keeps every blob a branch pointed at, and CI keeps the
console long after the workspace is gone.

## Objective

> The report test has been failing since its reference fixture disappeared. Recover the
> fixture from the development artifacts so the intended report is visible again.

The failing job is `fieldlink-report` build **#1842**. The commit that broke it says what it
did — `remove generated report fixture …` at `c37effd7cc86ae4d44f18e95f899b7557d65e0a9` — so
the fixture exists in an ancestor commit and the expectation in the build's retained output.

## Background you need

- **Git is content-addressed.** Deleting a file removes it from *that commit's tree*, not from
  the object database; any earlier commit still resolves the blob by its SHA, which the Gitea
  contents API exposes with `?ref=<sha|branch|tag>` — no clone needed.
- **CI consoles are development artifacts.** Jenkins keeps `consoleText` per build, and the
  *failing* log usually describes the expected input best.

## Walkthrough

### 1. Read the failing build

```bash
curl -sS -u 'rowan.ito:fk_developer_…' \
  https://ci.keplerops.test/job/fieldlink-report/1842/consoleText | tail -40
```

The tail is where the test reports its verdict: the last line before
`Build step … marked as failure` carries the challenge value; above it the log names the
fixture path and the baseline reference (`fk-test-6d1e9f7`).

### 2. Confirm it is gone, then find the commit that still has it

```bash
curl -sS -u 'rowan.ito:fk_developer_…' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/contents/fixtures?ref=main' \
  | jq -r '.[].name'
curl -sS -u 'rowan.ito:fk_developer_…' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/commits?path=fixtures/report-crr-og2.json&limit=5' \
  | jq -r '.[] | "\(.sha[0:7]) \(.commit.message | split("\n")[0])"'
```

`fixtures/report-crr-og2.json` is absent from `main`. The commit history for that path is the
shortest route back: the last entry is the deletion, the one before it, `80560bc`, is the
version the test wants.

### 3. Pull the blob at that revision

The contents API returns base64 in `content`, which is what allows a byte-exact restore:

```bash
curl -sS -u 'rowan.ito:fk_developer_…' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/contents/fixtures/report-crr-og2.json?ref=80560bc' \
  | jq -r '.content' | base64 -d > fixtures/report-crr-og2.json
```

The recovered fixture is the baseline report the test compares against:

```text
schema              fieldkest.report/v2
report_id           RPT-CRR-OG2-BASELINE       asset_id   CRR-OG2
connector_revision  FLK-7.4.2                  captured_at 2026-09-18T14:22:16Z
observations        connector-heartbeat delayed 1840 ms; archive-synchronization ok 28
```

Byte-exactness matters later: the file ends with `}` plus an extra trailing newline and the
review consumer binds the fixture by digest, so restore the blob rather than regenerating it.

### 4. Getting the flag

The accepted value is printed by the failing build's console, not by a field inside the
fixture. Accepted; the value is not reproduced here.

## Why this works (the vulnerability explained)

Two retention behaviours make "deleted" data readable. **Git's object model**: commits are
immutable snapshots, so deleting a path creates a tree that omits the blob while older trees
still reference it — `git show <sha>:<path>` is documented behaviour, and remote APIs expose
the same view. **CI log retention**: the console prints inputs, expected baseline and result
for humans debugging failures, and it outlives the workspace.

The lesson: *access control must cover history and logs, not just the current tree*. A secret
removed from `main` is still readable while the commit that held it is reachable; if data must
disappear, rewrite history, rotate whatever it contained, and keep expected-value dumps out of
build logs.

## Detection and fix

- **Log signal:** `contents`/`commits` reads pinned to SHAs before a deletion commit; test logs
  printing complete expected payloads.
- **Fix:** generate fixtures at test time or pull them from a controlled store; keep console
  output free of full expected documents; rotate any secret that landed in history.

## Notes and dead ends

- **This card's evidence is solid**: lane K02 recorded the repository, the removal commit, the
  revision that still has the fixture, its fields and the Jenkins route. The `curl` calls above
  follow those routes; the base64 pipe and `jq` filters are conventional usage.
- Looking for the flag *inside* the fixture is the natural wrong guess — the fixture is the
  baseline report, the value is in the build console. Lane K02 considered and discarded it
  ("the fixture itself should hold a token but we got the fixture without one").
