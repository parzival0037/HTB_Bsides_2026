# K27.2 — Our diagnostic, their interface

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Interface-only trust — a package is accepted on shape (`fieldkest.connector/v3`, one exported function) plus a caller-declared output, with no signature or provenance binding |
| **Tools** | `curl`, `node` (to develop the module), the support bearer |
| **Attack surface** | `PUT https://support.keplerops.test:8443/api/diagnostics/{job}/package` |
| **Prerequisite** | A job bound to the target tenant (K27.1): `TEN-ARWC-047` on `FLK-7.4.2` |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how to replace a diagnostic implementation while preserving the customer
connector's contract, and why "returns exactly what we expected" is a compatibility
test, not an authenticity test.

## Objective

> Alter the diagnostic package while preserving the interface the ARWC connector expects. Make
> the job accept the changed package for this customer.

Acceptance is narrow: same interface, same exported entry point, same declared return value —
different behaviour inside.

## Background you need

- A diagnostic package here is **source**: CommonJS exporting `diagnostic_summary`. The
  connector loads it, calls it and compares the result to a recorded `expected_output`.
- The accepted interface is `fieldkest.connector/v3`; anything else is a different contract and
  is refused before the code is read.
- `expected_output` must equal the return value **exactly** — same shape, types, key set. That
  rule is both the compatibility requirement and the weakness.
- The contract never asks *who built the package*, only what it declares: no signature, no
  vendor digest, no allow-list.

## Walkthrough

### 1. Recon — read the job's recorded interface

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -H "Authorization: Bearer $TOK" \
  https://support.keplerops.test:8443/api/diagnostics/$JOB
```

### 2. Finding the flaw — the comparison is symmetric

Whatever you put in `expected_output` is what the package must return, so the alteration is not a
bypass of the comparison but a redesign of **both** sides so they agree again, while the payload
carries what you want the connector to report.

The interface must still hold: CommonJS, export named `diagnostic_summary`, a call signature
taking the diagnostic input, a JSON-serialisable return equal to the declaration.

### 3. Exploitation — write the package, declare its output

```js
function diagnostic_summary(input) {
  return { ok: true, asset_id: input && input.asset_id, mode: 'diagnostic' };
}
module.exports = { diagnostic_summary };
```

Put the **literal** return value into `expected_output`, derived by running the module —
hand-written values drift on key order and types.

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -X PUT -H "Authorization: Bearer $TOK" -H 'Content-Type: application/json' \
  -d '{"interface":"fieldkest.connector/v3",
       "source":"<contents of diagnostic.js>",
       "expected_output":{"ok":true,"asset_id":"<from the job>","mode":"diagnostic"}}' \
  https://support.keplerops.test:8443/api/diagnostics/$JOB/package
```

The job accepts the package when the interface matches and the declared output is consistent
with what the source returns for the job's input. The diagnostic that runs on the customer side
is now yours, and still fits the connector's expectations.

### 4. Getting the flag

Solved by a team agent; the accepted value is not recorded. Scoring: an accepted package on the
bound ARWC job — interface preserved, output declared, implementation changed.

## Why this works (the vulnerability explained)

The bug class is **conformance-as-authentication**: the service answers "is this package
compatible?" and treats that as "is this package legitimate?".

- **Structure is not identity.** An interface constrains names, types and call shape; a module
  can satisfy every constraint and compute something else. Schemas validate the boundary, not
  the behaviour.
- **The expected value is attacker-supplied.** Because `expected_output` ships with the package,
  equality is *self-consistency* and can always be satisfied. A real control compares against
  something the submitter cannot write.
- **No provenance.** No signature over the source, no vendor-pinned digest, no allow-list —
  nothing distinguishes "the vendor's diagnostic" from "a diagnostic returning the vendor's
  shape". Dependency confusion is the same failure: a name and a range are validated, not the
  content.

## Detection and fix

- **Detect:** a PUT whose declared output differs from the job's previous output; source hashes
  absent from the vendor manifest; interface-conforming packages from a new principal.
- **Fix:** sign the package and verify against a pinned key/lineage, or pin a content digest fixed
  at job creation; compute `expected_output` server-side from the job's fixture. Support may bind
  and deliver a job — altering its content should need a second, build-side identity.

## Notes and dead ends

- Evidence is thin: the card retains the description plus the documented package contract; the
  module and request above are **reconstructed**, with no per-card response retained.
- A different interface (e.g. the legacy v2 identifier in older archive material) is a dead end:
  the job is bound to v3 and the connector picks its interpreter from the interface string.
- Returning the original values satisfies the interface but fails the card: output must differ
  from the baseline and still equal the declaration exactly.
