# W14.1 — The field bag

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Artifact retrieval authorised by run id only — a retained field export sits in the contractor review workspace, readable by anyone who knows (or derives) the run and artifact name |
| **Tools** | `curl`, `jq`, `aws` CLI, the SOCKS pivot |
| **Attack surface** | `review.keplerops.test` → `/api/runs/{run_id}`, `/api/runs/{run_id}/artifacts/{name}`; object storage `s3://fieldlink-exports` |
| **Prerequisite** | The review client contract (`https://review.keplerops.test/.well-known/fieldkest-client`) and any run id reachable from the inspection/handover records |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a "contractor workspace" stores an inspector's field
export as a review-run artifact, why an unlistable bucket is still readable, and how run ids
become the capability that unlocks the export.

## Objective

Recover the inspection's field export from the contractor workspace: the data the field crew
collected for the outlet inspection — the "field bag" — retained as an artifact of the review
run that processed it.

## Background you need

- **Review runs.** The review service ingests an input object, runs a report/review template
  and produces artifacts. Each run has an id and a name-keyed artifact set:
  `/api/runs/{run_id}` and `/api/runs/{run_id}/artifacts/{name}`.
- **Import contract.** `fieldkest.review-import/v1` takes a `run_id` plus an `object` under
  `inputs/` — the run id joins "an inspection happened" to "here is what it produced".
- **Capability semantics.** Storage keys act like bearer capabilities: a bucket can refuse
  `ListBucket` and still serve `GetObject` for any key you name. `NETMAP.md` says retained
  collections in `s3://fieldlink-exports` are **not listable**, with the exact key/digest
  coming from retained material.

## Walkthrough

### 1. Read the review client contract

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  https://review.keplerops.test/.well-known/fieldkest-client | jq .
```

That gives the artifact route and the auth the worker expects, so you are not guessing paths.

### 2. Obtain the run id from the records you already hold

The export is listed nowhere: you must arrive with a `run_id`, which appears in the
inspection/handover material (the chain `POST /api/inspections` → inspection id → review run).
Once you have a candidate id:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  "https://review.keplerops.test/api/runs/$RUN_ID" | jq .
```

The run record names its artifacts — the field bag's filename. You never needed listing.

### 3. Fetch the artifact

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  "https://review.keplerops.test/api/runs/$RUN_ID/artifacts/$NAME" \
  -o field-export.bin
```

If the route requires the import contract instead, post the `fieldkest.review-import/v1`
document (`run_id` + the `inputs/` object) and read the returned artifact reference.

### 4. Cross-check against object storage

The export may also be retained in `s3://fieldlink-exports`. Listing fails by design, but a
known key can still be fetched:

```bash
aws --endpoint-url https://objects.keplerops.test s3 ls s3://fieldlink-exports   # denied/empty
aws --endpoint-url https://objects.keplerops.test \
  s3 cp "s3://fieldlink-exports/$KEY" field-export.bin                          # by key
```

This is the point of the card: **not listable** is not **not readable**.

### 5. Get the flag

The flag is carried in the field export for the correct run. The solve record does not retain
it, so it is reported as accepted without the literal value.

## Why this works (the vulnerability explained)

Two weaknesses line up. The review service authorises *runs* (do you hold a worker/consumer
identity?) but not *artifacts scoped to a tenant or inspection*, while artifact names are
predictable from run metadata. And the object store buys confidentiality by non-disclosure
(no listing) instead of key-level authorisation — the common false assumption that
unguessable keys are access control.

The class is **capability-by-identifier**: an id that was meant to be internal becomes the
only thing between a caller and the data. It shows up in CI artifacts, report workers, backup
buckets and export jobs. Correctly, the artifact read checks entitlement to the owning
run/inspection, and storage enforces per-prefix policies so a leaked key alone is useless.

## Detection and fix

- **Log signal:** artifact downloads for runs the principal never created or consumed;
  `GetObject` calls with no matching run; 403-heavy listing followed by successful gets.
- **Fix:** authorise artifact reads against the owning inspection/tenant, randomise artifact
  names *and* keep the check, enforce bucket policies per tenant prefix, and expire retained
  exports with a recorded digest so a leaked copy is attributable.

## Notes and dead ends

- **Reconstructed, not observed.** Solved by the team agent, but the retained record holds
  only the description and infrastructure notes — no run id, artifact or flag value. The
  commands show documented routes and storage behaviour; they are not a captured session.
- Do not spend time trying to list `s3://fieldlink-exports`. `NETMAP.md` states retained
  collections are not listable; the key must come from retained material.
- The field export is per inspection, not per tenant: one run id answers one inspection, and
  a nearby run may belong to a different asset.
