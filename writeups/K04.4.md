> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Write-to-execute — a file the service loads on start or on reindex turns a controlled write into code running as the indexer |
| **Tools** | the K04.3 write primitive, `curl`, `python3`, the indexer's own client credentials |
| **Attack surface** | `https://indexer.keplerops.test` (10.77.51.70), plus the queue behind its service identity |
| **Prerequisite** | K04.3 — a controlled write against protected state |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the last step of the chain — turning "I can write a file" into "my code
runs as the service", and using that identity to read a queue the support engineer could not clear. The
bug class is *executable configuration*: anything a service loads (plugin, hook, template, a config
with a command field) is code to that service, so write access to it is execution.

## Objective

> Turn the indexer compromise into execution under its service identity. Recover the release-exception
> queue the support engineer has been trying to clear.

Two halves: **execution under the service identity** (the indexer's account, not yours) and **the
release-exception queue** — readable only with the identity the indexer holds.

## Background you need

- **"Configuration" is often code.** A hook script, plugin directory, template include or notification
  command is loaded and interpreted by the service: write access to it is code execution with its
  privileges, no memory corruption required.
- **A service identity is a capability set**: the indexer talks to the object store, the record store and
  downstream support APIs, so its token is the key to the exception queue.
- **Minimal and reversible wins.** One load is enough; a payload that edits state risks breaking the
  queue you came for.

Reconstruction: the evidence records the objective and the K04.1–K04.3 chain, not an observed transcript.

## Walkthrough

### 1. Find what the indexer loads

K04.2's reads give you the indexer's configuration and mount layout. The useful lines name a script, a
module directory, a template or an include read at start or reindex time — inside storage K04.3 can
reach.

Grep the recovered config for `hook`, `plugin`, `include`, `entrypoint` or `command` (illustrative);
those lines name what the service will execute or interpret on the next load.

A writable `hook`/`plugin` path is the shortest route, a template directory second. A path the service
executes but you cannot reach is useless: keep the two capabilities aligned.

### 2. Write the payload

Nothing new: the same destination-confused write, aimed at the loadable path. Keep the payload
side-effect free — read one thing, store it where you can fetch it. A callback works only if the indexer
can reach it; otherwise write into a path K04.2 proved readable.

An illustrative hook payload is one line: `open("<readable-path>/out.json","w").write(...)` around a
call that records `id` and the environment — proof of the account it ran as, written where you can
read it.

### 3. Trigger the load and confirm the identity

The write matters only when the service next loads that file: a restart or the next job — trigger it
through the normal path (submit a job), not by touching the process.

Then read the output through the path you control:

```bash
curl -sS 'https://indexer.keplerops.test/<object-route>' | jq -r '.members[]|select(.path|test("out"))'
```

The `uid`/`env` in that output is the proof of service identity: it names the account, and the
environment usually carries the service's credential paths.

### 4. Read the release-exception queue and get the flag

With the service identity you authenticate where your own cannot: read the queue with the indexer's
credential (environment or config), not by guessing endpoints — the answer is whatever the service
already sees. The accepted value is in that queue; the exact entry was not recorded, so it is not
reproduced here.

```bash
# illustrative: authenticate as the indexer with the credential its environment exposes
curl -sS -H "Authorization: Bearer <service-token>" '<queue-route>' | jq .
```

## Why this works (the vulnerability explained)

No memory corruption appears here; every step is a *policy* failure: members extracted by declared paths
(K04.1), the same paths opened by a privileged reader (K04.2), destinations and extents from the
manifest (K04.3), and a path the service loads writable by the extraction code (K04.4).

The last step is what defenders underestimate: **anything loaded is code**. It does not look like code —
a hook file, a plugin, a template, a YAML field naming a command — so writable directories beside a
service get filed as a permission issue rather than remote code execution. The chain also shows why
identity beats endpoint: the queue is not hidden, it is behind a check your identity fails and the
indexer's passes. Service accounts should hold the minimum, be rotatable, and never write to their own
executable surface.

## Detection and fix

- **Log signal:** writes to a loadable path that no deployment made; the indexer opening files it never
  read; its credential used from a new process lineage; queue reads outside the team's pattern.
- **Fix:** mount code and config read-only; extract in a `noexec` sandbox with no write access to
  loadable paths; verify config integrity at load; scope the identity so the queue is out of reach.

## Notes and dead ends

- **Evidence is thin; this walkthrough is reconstructed.** K04.4 was solved by the team agent; the
  record is the description plus the K04.1–K04.3 chain. No transcript exists: the payload and commands
  are illustrative and routes are placeholders.
- Reading the queue with your own identity is a dead end by design: the identity, not the route, is the
  barrier.
- A read-only payload is best: a noisy one invites the cleanup that ends your access.
- If the hook path is not writable from the extraction context, look for a second loadable path in the
  same tree instead of escalating bug classes.
