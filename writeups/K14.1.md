# K14.1 — The trust document

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K13

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Workload-identity trust material stored where the workload itself can read it — a self-authorising credential loop |
| **Tools** | `kubectl`, `curl`, `jq` |
| **Attack surface** | `https://cloud-api.keplerops.test:6443`, namespace `fieldlink`; record `trust-flx-04` |
| **Prerequisite** | The kubeconfig service-account token dropped on `rowan-dev` |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a workload's trust document — issuer, audience, target role
and a bootstrap `access_token` — ended up readable by the very service account it authorises,
and why putting the credential in the same RBAC scope as the credential collapses federation
into one `get`.

## Objective

> Recover the workload's current trust document and the service relationship it describes.

The record is not a secret in the usual sense: it is the configuration saying *this workload, for
this audience, may become that role*. Its value is the relationship it encodes — plus the fact
that this deployment kept a usable token inside it.

## Background you need

Workload identity federation replaces static keys with a short-lived signed JWT:

1. The workload mounts a projected service-account token (audience = the exchange).
2. It `POST`s that JWT to a token-exchange endpoint and receives a second, differently scoped token.
3. The exchange trusts the JWT because of a **trust record** (issuer, subject, audience, target
   role, sometimes a bootstrap secret).

That record is a configuration object, so it is a first-class target. Two questions set the
severity: *who can read it*, and *what else is in it*.

## Walkthrough

### 1. Recon — a service account with a narrow view

```bash
kubectl config view --minify -o json \
  | jq '{server:.clusters[0].cluster.server, ns:.contexts[0].context.namespace}'
kubectl -n fieldlink auth can-i --list
```

`secrets`, `pods`, `serviceaccounts`, `leases` and `rolebindings` all return `forbidden`. What
the token *can* read is `configmaps` — the workload's own configuration surface.

### 2. Finding the record

```bash
kubectl -n fieldlink get configmaps
kubectl -n fieldlink get configmap trust-flx-04 -o yaml
```

`trust-flx-04` is the workload's trust document. The same object is mirrored through the cloud
API as `/api/trust-records/TRUST-FLX-04`, but that view is *stricter*: with a delegated export
token it answers `k3s_rbac_denied`. The readable path is the Kubernetes one, using the workload's
own identity.

### 3. What it describes

```yaml
# illustrative shape — the record names the workload, the audience it may exchange
# for, and the bearer that bootstraps the exchange
kind: ConfigMap
metadata: { name: trust-flx-04, namespace: fieldlink }
data:
  service_relation: <workload principal -> exchange audience>
  access_token: <the flag>
```

The `access_token` value is the flag. Note what it *is*: the bootstrap credential for the
exchange. Anyone who can read the document can mint the identity it describes — it is not merely
descriptive, it is enough to act. Before it was attributed here the value had been submitted against
**K13.4** and rejected, which is how the team learned it belonged to this card and not to the k3s
build-record chain. The relation it encodes is what K14.2 dereferences: audience
`fieldkest-export-access` resolving to a role for a different consumer.

## Why this works (the vulnerability explained)

Two mistakes compound.

**Classification.** Trust records are configuration, so they land in ConfigMaps, and ConfigMaps
are not Secrets. But a trust record routinely carries a bootstrap bearer, so every principal with
`get configmaps` can read the credential — including the workload being federated.

**Scope.** The record sat in the same namespace and was granted to the same service account it
authorises. That is a self-authorising loop: compromise of the workload immediately yields the
ability to re-mint its identity and everything the record references.

| Component | Where it belongs |
|---|---|
| Trust metadata (issuer, audience, roles) | ConfigMap, readable |
| Bootstrap credential / access token | Secret, write-only to the exchange |
| Proof of identity | short-lived projected JWT, never persisted |

The workload should be able to *use* the exchange without being able to *describe* its anchor.

## Detection and fix

- **Log signal:** `get` on trust objects by the service account those objects authorise, or trust
  material read from a workload namespace instead of a control-plane one.
- **Fix:** move bearer material into a Secret or remove it (projected tokens, short TTL, audience
  bound to the exchange). RBAC the federated workload out of its own trust record. Rotate
  `access_token` — treat it as compromised the moment the workload is.

## Notes and dead ends

- Only ConfigMaps (and the build record `bld-1842`) opened up for this identity.
- The lane report preserves the record name and its `access_token` value
  (`FLAG{418e19c3ed0c13ef}`) but not the full YAML, so the shape above is marked illustrative
  and the value is lane-reported only — the scoreboard card stores no flag.
- `/api/trust-records/TRUST-FLX-04` through the export token is a dead end (`k3s_rbac_denied`).
