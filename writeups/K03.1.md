**What you are about to read:** how an operator hides a tool inside a document a reviewer will open
and "read", and how to get it out. The bug class is *carrier confusion*: a `.docx` is a zip and a
PDF has object streams, so both can carry a payload that never renders — a document that looks
reviewed has not been reviewed at all.

## Objective

> Someone from Cinder worked this lead before you. Recover the staging artifact buried in their
> retained document and identify the collection it belongs to.

Two parts: extract the staging material — the tooling the earlier operator left behind — and name
the **collection** it targets. Retained collections are not listable here, so the identifier has to
come out of the artifact itself rather than from an S3 listing.

- **Office formats are zip archives.** A `.docx` is an OOXML package: `[Content_Types].xml`,

## Walkthrough

### 1. Treat the document as an archive (reconstructed)

The material is the Cinder document set — the work-board attachment from K01.3 and the handover from
K01.1 — and the filenames look like ordinary operations paperwork, which is the point. No transcript
survives, so this is technique, not capture. An OOXML file lists its parts without office software:

```bash
unzip -l retained/<document>.docx
```

Look for parts a text document has no reason to contain: `word/embeddings/*`, `customXml/*.xml`,
oversized `docProps/` entries, or a name that does not match the schema. Extract to a scratch
directory and identify each with `file`.

### 3. Carve the payload

```bash
# illustrative template
binwalk --dd='.*' retained/<document>.pdf     # embedded streams, appended archives
grep -aEo '[A-Za-z0-9+/]{80,}={0,2}' doc.xml | head   # long base64 blobs
base64 -d blob.txt > stage.tar.gz && tar tzf stage.tar.gz
```

A staging artifact is usually a small script plus a manifest — enough to prepare a collection, not
a full implant. Read before running: a script that checks for a file before acting tells you what
environment it expects.

## Why this works (the vulnerability explained)

Reviewers validate *rendered content*. A document is approved because the page says the right thing,
and the file is then trusted as "a document". But the format is a container with parts that never
render: embedded objects, custom XML, properties, unused media. A payload there passes human review
and most scanners, because both look at the page. The general pattern — the *carrier* is trusted and
the *content* never enumerated:

- archives inside archives, and nested encodings (`base64(gzip(base64(x)))`) that survive a
  one-pass decoder;
- data appended after a valid file's end-of-file marker, which most parsers ignore;
- metadata fields (author, company, revision) as a small covert channel.

The defensive rule: a received file must be *enumerated*, not opened — list and hash every part, and
reject documents whose parts do not match their declared schema. Reviewing the page is not reviewing
the file.

## Detection and fix

- **Log signal:** documents with embeddings or custom XML where the workflow needs only text;
  external attachments containing archives; oversized `docProps` payloads.
- **Fix:** sanitise inbound documents (strip embeddings, custom XML, metadata) before they reach a
  shared store, and keep the sanitised copy in the record.
- **Process:** treat a retained document as untrusted input forever — retention is what keeps a
  payload available years later.
