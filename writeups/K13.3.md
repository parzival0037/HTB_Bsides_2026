## Objective

The description is empty in the retained dataset; the lane evidence defines the card as the
tenant export record stored beside the notebooks. Recover the handover export for `EXP-2841` and
its accepted value.

## Background you need

- **Prefixes are not tenants.** `notebooks/`, `exports/` and `handovers/` in one bucket share one
  policy: separating data by key prefix is a naming convention, not an authorization boundary.
- **Exports are the highest-value objects in a data platform** — a consolidated copy of a
  tenant's records, produced for a support handover or migration, often containing identifiers
  the live API would paginate or redact.
- **"Next door" is the hint.** From K13.1's listing, the interesting sibling keys are
  `exports/EXP-2841/handover.json` for export `EXP-2841` (the same tenant numbering as
  `SUP-2841`, `SCHED-2841`).
- The lane tried an export token against cloud-api and was denied (`k3s_rbac_denied`); the object
  store is the way in for this card.

## Walkthrough

### 1. Recon — enumerate the prefix

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  'https://objects.keplerops.test/fieldkest-workspaces?list-type=2&prefix=exports/'
```

The `ListBucketResult` lists the keys under `exports/`: the handover file and whatever else the
export process left there. Nothing about the request requires a token — that is the finding.

### 2. Finding the flaw — retrieval is equally open

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  https://objects.keplerops.test/fieldkest-workspaces/exports/EXP-2841/handover.json
```

returns the handover export. Note the pairing with K13.1: the notebook was readable for the same
policy reason. One misconfiguration, two cards.

### 3. Exploitation — the old version holds this card's value

The current `handover.json` is not where the value lives. The lane recorded that the accepted
value for K13.3 is in the **old version** of the export, in its `flag` field — the same
versioned-overwrite pattern as K13.2:

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  'https://objects.keplerops.test/fieldkest-workspaces/exports/EXP-2841/handover.json?versions'
curl --socks5-hostname 127.0.0.1:1080 -k \
  'https://objects.keplerops.test/fieldkest-workspaces/exports/EXP-2841/handover.json?versionId=<old>'
```

Read the export for context as well: handovers describe the service relationship (channel,
release, callback contract), which makes the later cloud cards navigable.

### 4. Getting the flag

Solved on attempt 1 by the lane; the per-card `flag` field is empty in the retained dataset, so
the value is **accepted, value not recorded**. It was found in the `flag` field of the superseded
version of `exports/EXP-2841/handover.json`.

## Why this works (the vulnerability explained)

This is the **shared-namespace** failure: several logical datasets, one policy. A bucket policy
applies to the bucket, and prefixes help only if the policy uses them (`s3:prefix` conditions,
per-prefix IAM) — most "make the notebooks readable" fixes do not. Data classification is not
reflected in storage layout: notebooks are deployment artefacts, exports are customer data, and
they belong in different buckets with different principals, not different folders. Versioning
compounds it: after the export was corrected, the old copy remained readable under the same
prefix policy, so remediation never removed the exposure. And exports are the *joined* result of
many records, so one leaked object can be worse than the underlying API leak — there is no
per-record authorization left to enforce.

## Detection and fix

- **Detect:** anonymous listings or fetches with a prefix outside the caller's expected dataset;
  access to `exports/` by anything that is not the export pipeline; `GetObjectVersion` on
  non-current export versions.
- **Fix:** separate buckets (or KMS keys) per data class; deny anonymous access and use
  presigned, short-lived URLs minted per requester; scope the export pipeline's credential to
  `exports/*` only.
- **Fix versioning:** expire non-current export versions aggressively — a tenant export should
  have no readable history at all.

## Notes and dead ends

- Evidence is real: the lane records the key `exports/EXP-2841/handover.json`, the old-version
  `flag` field, and a first-attempt solve. The `?versions`/`?versionId=` calls are the standard S3
  form used elsewhere in the lane; exact bodies were not retained.
- The export token in these objects does not grant cloud-api access:
  `/api/exports/EXP-2841/runs` answers `k3s_rbac_denied`. Chasing the API with an object-store
  token is the recorded dead end — the workload identity comes from the exchange route (K13.4).
- Do not confuse `EXP-2841` with `SCHED-2841` (schedule) or `SUP-2841` (support ticket). The
  numbering is shared; the identifiers are not interchangeable.
