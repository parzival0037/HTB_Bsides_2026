# W02.1 — The asset and the contractor

> **Category:** 3. ARWC · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Cross-system identity disclosure — an inspection trace endpoint correlates an internal work order with supplier job metadata, exposing asset and contractor identifiers a delivery-only caller should not see |
| **Tools** | `curl`, `jq`, the SOCKS pivot |
| **Attack surface** | `delivery.keplerops.test:8443` → `POST /api/inspections`, `GET /api/inspections/{id}/trace`; `support.keplerops.test:8443` → `/api/customers/{tenant}/diagnostics` |
| **Prerequisite** | Basic auth as `rowan.ito` for delivery; the support-client bearer for diagnostics |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a public inspection flow plus supplier package metadata
identify the plant asset and contractor behind an "outlet inspection order", and why the
diagnostics endpoints that look most promising return the *other* cards' flags.

## Objective

Identify the asset and the contractor associated with the outlet inspection order. The
answer is an asset identifier and a contractor identity, not a shell: both are exposed by
the supplier's inspection and package surfaces.

## Background you need

- **Inspection order.** A request to inspect a delivery or installation. It has an internal
  work-order number, a supplier-side job, and usually a drawing defining "correct".
- **Asset register.** Utilities name assets systematically — a site code plus an outlet
  index, e.g. `CRR-OG2` for an outlet group. That code joins the work order to the plant.
- **Contractor channel.** Releases are provisioned per integrator/contractor channel; a
  channel like `7.4.3-cinder.rset1` and a "Cinder review" assessment name the contractor.

## Walkthrough

### 1. Create the public inspection

The delivery service accepts an inspection request and returns an id:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  -H 'Content-Type: application/json' \
  -d @inspection-normal.json \
  https://delivery.keplerops.test:8443/api/inspections | jq .
```

Observed result: `INSP-2047`. This is the public-manifest flow and the entry point for the
inspection chapter, not a tenant-scoped customer API.
### 2. Read the trace, but credit the right card

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -u "rowan.ito:$FK_DEV" \
  https://delivery.keplerops.test:8443/api/inspections/INSP-2047/trace | jq .
```

The trace returns a flag — but it is the "three names for one job" record, i.e. **W02.2**.
Submitting it here costs an attempt and gains nothing. Read the trace for its *fields*:
there the asset and contractor correlation becomes possible.

### 3. Enumerate the tenant boundary

The support client knows one ARWC tenant. Probing the range shows the boundary at once:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: Bearer $SUPPORT_TOKEN" \
  https://support.keplerops.test:8443/api/customers/TEN-ARWC-001/diagnostics
# {"error":"customer_not_found"}
```

`TEN-ARWC-001..060` yields exactly one hit, `TEN-ARWC-047`; enumeration is cheap but does
not widen scope, so the single tenant is the whole ARWC surface.

### 4. Do not confuse the diagnostics flags with this card

The support diagnostics chain for `TEN-ARWC-047` / `FLK-7.4.2` returns a flag at each step
(job creation, package upload, delivery). All three were submitted for this card and all
were **rejected**: they belong to the diagnostics flow, not the outlet inspection order.

### 5. Read the identifier off the package metadata

The identifying content comes from the delivery side: asset `CRR-OG2` (Cedar Run Reservoir
outlet group 2), contractor `Cinder` with release channel `7.4.3-cinder.rset1`, and the
handover assessment "Cinder review". Those three agree with each other and with the
inspection record, which makes the identification defensible rather than a guess.

The exact flag was not retained in the solve record, so it is reported as accepted without
the literal value. The remaining hop was the ARWC-side connector (`connector.arwc.test`:443),
which rejects every caller without a channel identity — the boundary the next cards attack.

## Why this works (the vulnerability explained)

The inspection trace is a diagnostic endpoint returning the supplier's internal view of a
job: work-order linkage, package revision, integrator/contractor channel. It is not filtered
to the caller's need, so a delivery-only principal learns the customer's asset naming and
the contractor engaged for the work. The disclosure is an *over-detailed response*, not a
missing authentication check: the caller may call the endpoint, but it returns fields from
a different trust boundary.

The second lesson is analytical: a flag in a response does not mean it belongs to the card
you are working. Correlate its content with the description before submitting.

## Detection and fix

- **Log signal:** inspection traces read by a principal that never created the order;
  trace responses containing integrator/contractor identifiers.
- **Fix:** return a caller-scoped projection of the trace (ids the caller already holds),
  require entitlement to the customer before including cross-system identifiers, and keep
  contractor/channel data in the contract rather than in diagnostics.
- Secondary: make flags card-specific so an operator cannot burn attempts on another card.

## Notes and dead ends

- **Evidence is partial.** The card is solved by "team agent" but no flag value is retained;
  the content answer (asset `CRR-OG2`, contractor `Cinder`) comes from the lane's notes,
  while the missing hop and rejected diagnostics flags are recorded observations.
- `connector.arwc.test` (10.77.60.20) rejects staff mTLS certificates and SPNEGO with
  `403 channel_identity_denied`; the order data sits behind a channel identity we lacked.
- Tenant enumeration is a dead end for scope: one tenant, no siblings.
