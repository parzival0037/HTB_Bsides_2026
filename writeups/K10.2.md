# K10.2 — Two inputs, one identity

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Identity collision in a normalising preview pipeline — two byte-different inputs normalise to the same document identity, so the viewer treats one as the other |
| **Tools** | `curl`, `jq`, `qpdf`/`pdftotext`, `sha256sum` |
| **Attack surface** | `https://preview.keplerops.test` — `prepare`, `render`, `associations` |
| **Prerequisite** | The two supplied rehearsal documents; the association concept from K10.1 |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how content normalisation creates collisions, so "different
input" and "different document" stop being the same statement — the ambiguity K10.3 weaponises.

## Objective

Find distinct preview inputs that the viewer treats as the same protected document identity,
and demonstrate the ambiguity with the supplied rehearsal documents.

## Background you need

- **Identity is computed, not declared.** A preview service derives a document id from
  normalised content: extracted text, a hash of the converted output, or a canonical form with
  metadata removed.
- **Normalisation is lossy.** Two files differing only in producer metadata, timestamps,
  object ordering, whitespace or compression are identical afterwards.
- **Collision is not a cryptographic break.** You need the *input to the identity function* to
  be equal — usually the extracted text — not a SHA-256 collision.
- The rehearsal documents are the two preview fixtures shipped with the range: they look
  different but share a normalised identity.

## Walkthrough

### 1. Recon — establish each input's identity

```bash
# illustrative: prepare each rehearsal document
for f in rehearsal-a rehearsal-b; do
  curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
    -X POST --data-binary "@$f" \
    'https://preview.keplerops.test/api/prepare' \
  | jq -c '{input:"'"$f"'", document, preview}'
done
```

Two responses, one `DOC-` value. That observation is the finding.

### 2. Finding the flaw — where the inputs differ and where they don't

```bash
sha256sum rehearsal-a rehearsal-b        # file hashes differ -> distinct artefacts
pdftotext rehearsal-a - | sha256sum      # extracted text -> equal, or one contains the other
qpdf --qdf --object-streams=disable rehearsal-a a.qdf
diff <(sed 's/\/CreationDate.*//' a.qdf) <(sed 's/\/CreationDate.*//' b.qdf)
```

If the file digests differ but the text digest matches, the pipeline keys on extracted content.
If the diff shows only metadata lines, it keys on a stripped canonical form. Either way the
input to the identity decision is attacker-controllable while the artefacts remain distinct.

### 3. Exploitation — demonstrate the ambiguity end to end

```bash
# illustrative: render both previews and compare what each says it is presenting
curl -sS ... https://preview.keplerops.test/api/render/<preview-a> | jq '{document, source}'
curl -sS ... https://preview.keplerops.test/api/render/<preview-b> | jq '{document, source}'
```

Both report the same `document`. The demonstration is complete when the *server* states the
identity, not when you infer it.

### 4. Getting the flag

Solved by a team agent; no transcript was retained, so the flag is **accepted, value not
recorded**. The accepted shape is two distinct inputs, one protected identity, confirmed
through `prepare`/`render`.

## Why this works (the vulnerability explained)

Identity in a document pipeline is a *derived* value and inherits the weaknesses of the
function that produces it. The function is normalisation, not hashing of the artefact:
conversion deliberately discards producer strings, timestamps, object order, fonts and layout
whitespace — and everything discarded is an input you can vary freely. Collisions are
therefore cheap: you construct two files whose *normalised forms* are equal, searching
metadata rather than digests. The identity is then used as an access key downstream: if two
inputs map to one `DOC-…`, the mapping says nothing about provenance, and the viewer serves
material associated with the protected identity.

This is why content-addressed systems hash the exact bytes delivered and verify them at read
time. A pipeline that hashes a derived form must protect the derived form, and must never
conflate "same preview" with "same document".

## Detection and fix

- **Detect:** distinct upload digests mapping to one identity; one identity receiving previews
  from more than one source; inputs whose text matches an existing document but bytes do not.
- **Fix:** derive identity from the delivered bytes (content hash) and store the normalised
  form as a derived artefact keyed by that hash. Keep provenance (who uploaded which bytes)
  beside the identity; if dedup by text is needed, make it an explicitly untrusted index.
- **Fix presentation:** name the *preview/upload* in the render response, not only the shared
  document identity, so ambiguity is visible in logs.

## Notes and dead ends

- Evidence is thin: description and solved-state metadata only. The commands are
  **reconstructed** from the preview route set and standard document tooling; "two rehearsal
  documents, one identity" is the card's stated goal, not an observed response.
- Do not chase a hash collision — the card is normalisation ambiguity, and a SHA-256 collision
  is both infeasible and beside the point.
- Different preview ids with the same document id is success: preview is per upload, document
  is shared. Do not discard the result because the handles differ.
