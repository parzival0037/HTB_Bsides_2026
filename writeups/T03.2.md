## Background you need

- **A published artefact is an aggregate.** A release bundle is not only its code: it carries
  metadata (`package.json`, `METADATA`, manifests), sometimes source maps, lockfiles, changelogs
  and a debug or verbose log from the publish step.
- **Verbosity is a build-time decision that leaks at distribution time.** `npm publish --verbose`,
  `pip` build output, `--debug` flags and CI logs all record paths, hostnames, registry URLs,
  tokens echoed in command lines, and sometimes the contents of files a step read.
- **Source maps and debug bundles are source.** A minified consumer bundle plus its `.map` is the
  original repository, comments included.
- **The consumer contract maps what the consumer trusts.** Documentation describing how a consumer
  loads, validates and executes a package tells you which parts of the artefact are read at all.

### 2. Download, then inventory instead of reading top to bottom

Fetch the artefact and unpack it into a scratch directory. The first pass is a listing, not a read:
file count, unexpected directories, anything that is not code.

```bash
# illustrative: inspect a package without executing or installing it
mkdir -p /tmp/t032 && cd /tmp/t032
curl -sS -O http://developer.training:8080/<artifact-path>
tar tzf ./*.tgz            # or: unzip -l, ar t for .deb, wheel: unzip -l
```

What a reviewer looks for: a `.map` beside a bundle, a `build.log`, a `.npmrc`, a lockfile
resolving to an internal host, a fixture lifted from a developer's machine, or a `publishConfig`
value that reveals the internal layout.

### 3. Follow the verbosity to the disclosed fact

The disclosed material is usually a credential-shaped string in a log line, an internal hostname
or path, a source comment, or a build stamp naming a component the public contract does not admit
exists. Cross-reference against the contract: a value the contract surfaces in a report is worth
far more than a stray path.

## Why this works (the vulnerability explained)

The class is **distribution-time over-sharing**. During development, verbosity is a virtue: you
want the full log, the paths, the versions, the map from bundle back to source. The moment the
same artefact crosses a trust boundary — to a customer, a registry, a partner's build system —
every one of those conveniences becomes an information leak, because the consumer (and anyone who
can download it) receives the build environment's *description of itself*.

Three properties make it dangerous rather than merely untidy. **Irreversibility:** published
versions are cached and mirrored, so unpublishing does not recall copies — a secret in `1.4.2`
stays compromised after `1.4.3` removes it. **Low signal-to-noise:** nobody diffs two tarballs by
hand, so the leak rides along in a release that passes every functional test. **Composability:**
the leak is rarely the whole exploit; it names hosts, versions or tokens that make the next step
cheap. The developer's mistake is not a missing check but the absence of a **publish-time review**
that asks "what else is in the box?" rather than "does it work?".

## Detection and fix

- **Signal:** artefact contents referencing build-machine paths (`/home/…`, `/builds/…`), internal
  hostnames or credentials; `.map`, `.log`, `.npmrc` or `.env` in a release; registry metadata
  pointing at a non-public endpoint.
- **Fix:** whitelist what a package ships (`files` in `package.json`, `MANIFEST.in`, explicit
  `package_data`) instead of blacklisting; strip source maps and debug logs in the release job;
  build in a clean, credential-free environment with the publish token injected only at the last
  step; scan artefacts for secrets before upload.
- Add a publish-time review of the unpacked file list. Deleting a leaked version afterwards is
  damage control, not a fix — rotate whatever was exposed.
