## Objective

The description is empty in the retained dataset; the lane evidence defines the card as the
superseded version of the deployment notebook. Recover the previous revision and the value it
removed.

## Background you need

- **S3 versioning** keeps every overwrite as a separate version with its own `VersionId`.
  `GET` without a version returns the latest; `GET ?versions` lists them all, and
  `GET ?versionId=…` fetches any of them.
- **Version history is not access-controlled separately by default.** If the bucket allows
  anonymous `ListBucket`, it usually allows anonymous `ListBucketVersions` and anonymous
  `GetObject` by version id unless the policy explicitly restricts them.
- **The security lesson is about remediation.** Rotating a value in the current object does
  nothing if the old object is still readable — the credential remains valid, and the
  "correction" only hides it from the UI.
- The key is the notebook from K13.1: `notebooks/deploy-2026-09.json`.

## Walkthrough

### 1. Recon — read the current object

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  https://objects.keplerops.test/fieldkest-workspaces/notebooks/deploy-2026-09.json
```

The lane found the version-2 notebook here, with `workspace_token` (K13.1's value) and the
job `SCHED-2841`. Nothing else in the notebook — no version id, no history pointer — which
is the hint that the history has to be asked for explicitly.

### 2. Finding the flaw — the store keeps the old copy

Request the version listing for the same key:

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  'https://objects.keplerops.test/fieldkest-workspaces/notebooks/deploy-2026-09.json?versions'
```

Two entries appear: the current version, and the one it replaced. In S3-compatible stores
the listing returns `VersionId`, `LastModified` and `IsLatest` per entry. The non-latest
entry is the "before the correction" artefact.

### 3. Exploitation — fetch the superseded version

```bash
curl --socks5-hostname 127.0.0.1:1080 -k \
  'https://objects.keplerops.test/fieldkest-workspaces/notebooks/deploy-2026-09.json?versionId=<old version id>'
```

The old notebook contains a `flag` field that the corrected version no longer has. The lane
recorded exactly that: the value for this card lives in the *old v1* of the notebook, in the
`flag` field, while v2 carries only the workspace token.

### 4. Getting the flag

Solved on attempt 1 by the lane; the per-card `flag` field is empty in the retained dataset,
so the value is recorded as **accepted, value not recorded**. The location is the `flag`
field of the superseded `notebooks/deploy-2026-09.json`.

## Why this works (the vulnerability explained)

Versioning turns **mutation into append**, which is normally a safety feature and here a
disclosure:

- The correction was applied as an overwrite. The overwrite creates version 2; version 1 is
  untouched and still addressable.
- Access control was written for "the object" and inherited by "all versions of the object".
  Nobody re-checks that old versions should be readable by the same principals — and the
  old version contains data the current policy would never expose.
- The UI shows only the latest version, so the correction *looks* complete. This is the
  general "deleted but still there" pattern: deletion markers and versioning both leave the
  bytes behind.

For a defender, the important consequence is that **rotation must be paired with version
deletion and access review**, or the old secret stays live. Overwriting a file is editing;
remediation is destroying the copies.

## Detection and fix

- **Detect:** `?versions` requests and `GetObject` with a `versionId` query parameter that
  is not the latest; anonymous access to non-current versions.
- **Fix:** restrict `s3:GetObjectVersion` and `s3:ListBucketVersions` to the roles that need
  history (backup, forensics); deny `GetObjectVersion` on non-current versions to
  everything else. Apply a lifecycle rule that expires non-current versions after a short
  window.
- **Fix the remediation process:** when a value leaks, rotate it at the source, purge old
  versions and lifecycle-expire the rest. Treat the object store's history as a copy of the
  secret, because it is.
