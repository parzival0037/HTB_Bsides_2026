## Objective

> Carry your delivery capability through the disclosed release-credential rollover. Make the
> replacement release work after the old credential stops being accepted.

A continuity test: the capability must survive the rotation, not be re-created after it. The previous
card required both current and retained interfaces to accept; here the credential changes underneath
you.

## Background you need

- **Rotation is not a rename.** A rollover retires the old key and publishes a successor. Old
  signatures stay cryptographically valid but become unacceptable *by policy*: the accepted key set
  changed.
- **Granularity decides your fate.** A *key id* check rejects everything signed earlier; a *lineage*
  check (key valid at signing time) keeps old releases working.
- **Capability vs. artefact.** The capability is "I can get a signed release accepted here": keep the
  bytes, lose the key, lose the capability.
- **Receipts are the proof.** Acceptance produces a receipt id, an audit entry and
  `RESULTS/{receipt_id}.json`.

## Walkthrough

### 1. Recon — find the disclosed rollover before it bites

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector
```

Package metadata carries channel state — current release, rollback slot, pending build — and release
records carry the signing lineage plus the rollover disclosure. Read the current release and its
predecessor: the difference is the rotation to survive. The record also names the key generation and
the rollover id the audit cites.

### 2. Finding the flaw — the verifier pins the key generation

Compare three artefacts: a release accepted before the rollover, the disclosure, and your
replacement. If the old release still validates against the published key set but your retired-key one
does not, the verifier pins something narrower than the lineage.

Two checks settle it: submit the replacement unchanged and note which gate rejects it (lookup,
approval, consumer check); then re-sign with the successor key and repeat — if the payload now
passes, only the credential changed.

### 3. Exploitation — dual-sign, then deliver

The capability-preserving move is one release acceptable to *both* verifiers while the window exists:

```bash
curl -sS ... -X PUT -u 'rowan.ito:<token>' \
  https://delivery.keplerops.test:8443/api/packages/@keplerops%2ffieldlink-connector
curl -sS ... -X POST https://delivery.keplerops.test:8443/api/releases/$REL/approval
curl -sS ... -X POST https://delivery.keplerops.test:8443/api/consumer-checks
curl -sS ... -X POST https://delivery.keplerops.test:8443/api/reconcile/tenant-package
```

Practically: keep the original signature (the retained interface verifies it), add the successor-key
signature (the current verifier requires it), and keep the payload identical to the accepted K29.3
release.

Acceptance echoes `"reference_assessment": "reference-compatible"`, writes
`RESULTS/{receipt_id}.json` and appends a `rollover-acceptance` audit with request id, principal,
receipt id and `rollover_id`.

### 4. Getting the flag

The worker's acceptance branch sets `result["flag"] = "FLAG{fb7f87b5a1ca1ce8}"` (`ci.py:783`, comment
`# K29.4`) after that rollover audit entry. Accepted value: `FLAG{fb7f87b5a1ca1ce8}`. It appears on
the *rollover acceptance*, not a plain release submission: the card rewards surviving the rotation.

## Why this works (the vulnerability explained)

The bug class is **credential lifecycle not modelled in the trust decision**.

- **Exact-key pinning breaks rotation.** With "current key id" as the accepted set, every previously
  legitimate release becomes unverifiable the moment the key rotates. The correct predicate is
  lineage membership plus validity at signing time.
- **No overlap, no dual signature.** Safe rotation has a window where both keys are accepted: new
  artefacts dual-signed, old ones still verifying. Without it the options are downtime or re-issuing
  everything.
- **Capability is provenance, not bytes.** Trust keys to a credential rather than a signed, timestamped
  lineage, so whoever holds the successor — or can dual-sign in the window — inherits delivery.

## Detection and fix

- **Detect:** acceptance failures clustered at a rotation timestamp; retired-key releases reaching
  approval; unexpected dual signatures; `rollover-acceptance` from a non-release principal.
- **Fix:** verify lineage plus signing-time validity, publish a key history with overlap windows, and
  require dual signatures during rotation. Bind `rollover_id` to the artefacts using it, review every
  rotated-credential acceptance, and version the retained verification path.
