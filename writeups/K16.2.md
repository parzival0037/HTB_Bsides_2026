# K16.2 — The next startup

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unauthorised modification of a scheduled workload's startup (command/args) — scheduler object writable by a non-owner, executed with the original service identity |
| **Tools** | `curl`, `kubectl`, `jq` |
| **Attack surface** | Schedule `SCHED-2841` / CronJob `sched-2841` in namespace `fieldlink`, plus the rehearsal run it triggers |
| **Prerequisite** | K16.1's schedule identifier and a token that can `PATCH` the schedule spec |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how changing the startup behaviour of a nightly support job means
editing the container's entrypoint rather than its payload, and why doing it without breaking the
output contract is the exercise. The technique is **reconstructed**; see the last section.

## Objective

> Change the scheduled workflow's startup behavior so its next rehearsal run carries Cinder's
> marker without breaking its support output.

Two constraints pull in opposite directions: the next run must be attributable to the Cinder
release set (`7.4.3-cinder.rset1` in the delivery package metadata), and it must still produce the
diagnostic summary support consumes, in the exact shape the downstream consumer expects. A failed
or differently shaped run is rejected and noticed.

## Background you need

**Startup vs payload.** A scheduled container has an entrypoint (`command`/`args`) and a payload
(inputs, mounts, package version). Startup is the entrypoint plus the environment it runs with.
Payload changes are often caught by a digest check; startup changes are not, because the object is
trusted by the scheduler.

**Output contract.** The support diagnostics API takes an expected return value for the package it
runs (`expected_output` = the exact return of `diagnostic_summary`). A rewrite must preserve that:
same function name, same return shape, same success signal — with the marker added alongside, not
in place of, the support fields.

## Walkthrough

> **Evidence status:** solved by another agent; only the CronJob/route identifiers survive. The
> commands are the intended path, not a captured transcript.

### 1. Re-read the spec you are about to change

```bash
curl -sS -H "Authorization: Bearer ${TOKEN}" \
  https://cloud-api.keplerops.test/api/schedules/SCHED-2841 | jq '.jobTemplate // .spec'
```

You need the current `command`, `args`, `env` and image. Save a copy: the rollback path is
"restore this exact object".

### 2. Decide where the marker goes

| Option | Effect | Risk |
|---|---|---|
| Wrap `command[0]` | marker visible at process start | must `exec` the original and forward exit codes |
| Prepend an activation step in `args` | the run pulls the Cinder release set | the support step must still run last |
| Add an `env` entry | travels with the run, no code change | only counts if the workflow reports env back |

Prefer the smallest edit the rehearsal runner will record, and keep the original entrypoint
reachable.

### 3. Write the change

```bash
# illustrative: patch only the entrypoint, leaving image, mounts and service account intact
curl -sS -X PATCH -H "Authorization: Bearer ${TOKEN}" \
  -H 'Content-Type: application/merge-patch+json' \
  -d '{"spec":{"jobTemplate":{"spec":{"template":{"spec":{"containers":[
        {"name":"support","command":["/bin/sh","-c",
         "export FIELDKEST_MARKER=7.4.3-cinder.rset1; exec /opt/support/run.sh \"$@\""]}]}}}}}}' \
  https://cloud-api.keplerops.test/api/schedules/SCHED-2841
```

Then verify the API returns what you meant, by re-reading
`.jobTemplate.spec.template.spec.containers[0].command`.

### 4. Let the next run happen, and check both outcomes

The schedule fires on its own; the rehearsal surface
(`POST https://review.keplerops.test/api/rehearsals/connector`) makes the run observable, and
`/api/runs/{run_id}` plus `/api/runs/{run_id}/log` show what executed. The card counts only if the
log shows the marker at startup **and** the support diagnostic summary in its usual shape. If the
summary is missing, restore the saved spec and try the smaller edit. The card's flag is accepted
with no stored value: the deliverable is the schedule state plus the marked run.

## Why this works (the vulnerability explained)

The scheduler stores a **stored authorisation**: run this code, as this service account, at this
time. Whoever can write the object inherits that authorisation without ever holding the service
account's credential. The check that matters is on the *write*, and it was scope-blind — the same
weakness as K16.1, one step further along.

It is quiet because there is no credential theft (a config edit), execution is delayed to the next
tick, and the run still uses the support service account, so identity alerting sees nothing.

## Detection and fix

- **Log signal:** `PATCH` on a schedule by a non-owning principal; any change to `command`/`args`
  of a production schedule; a run whose entrypoint differs from the last N while the identity matches.
- **Fix:** object-level write authorisation on schedules; admission policy pinning entrypoint and
  image digest so only declared parameters change; store the marker as an approved release-set
  parameter. On detection, diff against the last good spec, roll back, audit the modified window.
