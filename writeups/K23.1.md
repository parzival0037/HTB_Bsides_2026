# K23.1 — A context view left open

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K23

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Unauthenticated inventory endpoint — `/api/contexts` lists unpublished retrieval contexts, their conversations, documents and workspace bindings |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET https://assistant.keplerops.test/api/contexts` |
| **Prerequisite** | None — no cookie, no bearer |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how an inventory endpoint that exists for the admin UI becomes the
roadmap for the whole assistant — which contexts are unpublished, which conversations they contain,
which documents are indexed, and that a support context contains a document belonging to a *different*
customer.

## Objective

> Recover the assistant's exposed context inventory and the unpublished support-source entry it
> includes.

The "unpublished support-source entry" is the interesting half: a context with `published: false`
whose document list points outside its own tenant.

## Background you need

In this assistant a **context** is the retrieval scope: it groups conversations, documents and
selections bound to a workspace. `published` controls whether the workspace appears in the user-facing
list — a visibility flag, not an access control.

An inventory is high-value because each field is a handle:

| Field | What it gives an attacker |
|---|---|
| context id | the path segment for every document fetch (`/api/contexts/{id}/…`) |
| `published: false` | confirms the material is internal/restricted |
| conversations | conversation ids → transcript route (K23.2) |
| documents | document ids → source-text route (K23.3) |
| selections / workspace | which tenant/case the scope serves |
| tenant | the customer binding, i.e. whose data is in scope |

The K23 family is essentially: read the list, then dereference each pointer.

## Walkthrough

### 1. Fetch the inventory with no credentials

```bash
curl -sS https://assistant.keplerops.test/api/contexts | jq
```

The response has a top-level `flag` (this card's value) and a list of contexts. Two matter:

```json
{ "ctx-support-private-v4": { "published": false, "workspace": "support-private",
    "conversations": ["CONV-SUP-2841-19"], "documents": ["DOC-RILL-442"],
    "selections": ["SEL-SUP-2841-12"] },
  "ctx-rill-support-v3": { "published": false, "tenant": "TEN-RILL-022",
    "workspace": "rill-support", "conversations": ["CONV-RILL-442-8"] } }
```

### 2. Read the anomaly, not just the list

The support context is the ARWC case scope (`SUP-2841`, tenant `TEN-ARWC-047` once you follow the
selection), yet its `documents` array contains `DOC-RILL-442` — a Rillhaven document, i.e. another
tenant. Two contexts, two customers, one shared document id. That single line is the whole K23 chain:

- `ctx-support-private-v4` → conversation `CONV-SUP-2841-19` → K21.2/K21.3;
- selection `SEL-SUP-2841-12` → attachment `ATT-DIAG-698`, case `SUP-2841`, tenant `TEN-ARWC-047`;
- `DOC-RILL-442` → the Rillhaven restricted document (K23.3);
- `ctx-rill-support-v3` → conversation `CONV-RILL-442-8` → K23.2.

### 3. Getting the flag

The inventory response carried the flag at the top level. Lane notes record it as
`FLAG{7ff69ab443a968ef}` with the submission accepted; the card stores no value, so it is recorded as
accepted/not recorded.

## Why this works (the vulnerability explained)

The endpoint answers "what does the assistant know about?" without asking who is asking — the same
class as K21.1's `/api/config`: a UI-support route deployed with the front-end's assumptions (internal
network, authenticated user) and never given a check of its own.

The compounding error is that **identifiers are the capability**. Every downstream route takes an id
and validates the parent (context/conversation) but not the child's classification or tenant, so
publishing the id list makes the entire overlay addressable. `published: false` even flags which
entries are the interesting ones.

| What the system does | What it should do |
|---|---|
| list all contexts to anyone | list contexts the caller's role/tenant permits |
| `published` is a UI flag | `published: false` should deny non-admin reads |
| ids are stable and guessable | ids should be unguessable or capability-wrapped |
| membership is descriptive | membership should be enforced at read time |

## Detection and fix

- **Log signal:** unauthenticated `GET /api/contexts` (and `/api/config`) calls; inventory reads
  followed by document/conversation fetches from the same source; one source walking many contexts.
- **Fix:** authenticate the inventory and scope it to the caller's workspace/tenant; stop returning
  `documents`/`selections` ids to non-admin roles (return counts); treat `published: false` as an
  access decision; validate tenant consistency between a context and its documents at index time —
  that check alone would have caught `DOC-RILL-442` in the ARWC context.

## Notes and dead ends

- Recorded facts: unauthenticated `GET /api/contexts`, both contexts `published: false`, the support
  context holding `CONV-SUP-2841-19`, `DOC-RILL-442` and `SEL-SUP-2841-12` under workspace
  `support-private`, and the Rillhaven context `ctx-rill-support-v3` with `CONV-RILL-442-8` and tenant
  `TEN-RILL-022`. Field names/JSON shape are illustrative.
- The inventory alone does not return document text: without the `fieldkest_support` cookie the
  conversation and document routes do not answer. The inventory is the map, the cookie is the key.
- `/api/contexts` is a different surface from `/api/config` (K21.1); both are open and both leak ids.
- An "Authorization reference" token `599046b0487a95cb` in the AnythingLLM `support-private` material
  is *not* this card — it stayed unattributed in our notes.
