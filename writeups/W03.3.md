**What you are about to read:** how to test an "approved read-only integration" honestly —
read its contract, enumerate what the service actually returns, and state what is inside the
boundary and what is not. The bug class is the gap between the two.

## Objective

Establish what the approved planning read service actually publishes and what stays outside
its boundary: what the contract *claims*, what the service *returns*, and what is only
reachable through other services.

## Background you need

- **Client reference as contract.** `/.well-known/fieldkest-client` advertises routes,
  schemas, auth and scope. Integrators build against it and reviewers approve on that basis.
- **Descriptive vs enforced.** The document is discovery metadata; nothing stops the service
  returning extra fields, accepting undocumented parameters or joining another scope — only
  server-side projection and authorisation do.
- **Read-only is not harmless.** An integration returning operational data, cross-tenant
  identifiers or future schedule state has broken the boundary without writing anything.

## Walkthrough

### 1. Collect the contracts first

Fetch the client reference for each candidate service and keep them side by side:

```bash
for h in indexer cloud-api review; do
  curl -sS --socks5-hostname 127.0.0.1:1080 -k \
    "https://$h.keplerops.test/.well-known/fieldkest-client" \
    | jq -S . > "/tmp/contract-$h.json"
done
```

Note for each: declared routes, response schema, auth mechanism, and any scope words
("planning", "read", "approved").

### 2. Ask for exactly what the contract declares

Call each declared read route with the contract's credential, capturing raw JSON before any
client-side filtering:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -H "Authorization: Bearer $SUPPORT_TOKEN" \
  "https://indexer.keplerops.test/<declared-read-route>" | jq -S . > /tmp/actual.json
```

### 3. Diff declared schema against returned keys

```bash
jq -r 'paths(scalars)|join(".")' /tmp/actual.json | sort -u > /tmp/actual.keys
jq -r '.schema.properties|paths(scalars)|join(".")' /tmp/contract.json \
  | sort -u > /tmp/declared.keys
comm -23 /tmp/actual.keys /tmp/declared.keys   # returned but not declared
comm -13 /tmp/actual.keys /tmp/declared.keys   # declared but not returned
```

Both directions matter. **Returned-but-not-declared** fields (asset codes, tenant ids,
maintenance refs, future timestamps, operator identities) are the boundary leak;
**declared-but-not-returned** fields mean the contract is simply wrong.

### 4. Test the parameter surface

Routes often accept filters they do not advertise (`tenant`, `asset`, `since`, `include=`).
Send one at a time and compare shape and row count: a parameter that widens the result set
proves the boundary is documented, not enforced.

### 5. Draw the line

State it explicitly: the service publishes the declared planning fields plus the step-3
extras. Operational/process data, other tenants' rows and anything needing a per-customer
entitlement stay outside (behind delivery/support). Field projection and entitlements enforce
that line — never the contract file.

The accepted answer is that statement; the flag comes back once the correct scope is
requested. The solve record does not retain it, so it is reported as accepted.

## Why this works (the vulnerability explained)

The developer treated the client reference as the security definition: "we published a
narrow contract, therefore the integration is narrow". But a contract is a promise about
*shape*, not a restriction on *data*. When the handler serialises the stored object instead
of a projection, every field added later by another team becomes part of the integration's
output — silently widening an "approved" read service.

This is a general integration failure mode: schema-first design without response-side
allow-lists. Reviewing an integration from its `.well-known` document alone is unsafe — the
document and the implementation drift, and only the implementation decides what leaves.

## Detection and fix

- **Log signal:** fields returned that are absent from the published schema; undocumented
  parameters accepted; one integration principal reading rows across tenants or assets.
- **Fix:** serialise an explicit response model per contract version, reject unknown query
  parameters, authorise each row against the caller's entitlement, and add a contract test
  that fails when a response gains a field. Generate the well-known document from that model
  and version every response so drift is detectable.
