## Objective

> Read the supplied training-tank observation and work out how much water it actually
> contains — separate the measurement from the requested or setpoint level (register/word
> interpretation, scaling, engineering units).

The desk ships a frozen observation (`VC-017`) plus a sealed capture. Nothing needs to be
operated — the practice tank is a separate, live object — the record just has to be read
correctly, and that reading proven by opening the sealed record.

## Background you need

Process-control data is full of numbers that look interchangeable and are not:

- **Setpoint** (`requested_volume_l`) — what an operator or scheduler *asked for*: intent,
  not state.
- **Observed** (`observed_volume_l`) — what the instrument *measured*: the only field that
  describes the physical tank.
- **Units and scaling** — registers are integers with an implicit scale (×0.1, ×1, ÷10 …):
  `12000` at scale 0.1 is `1200.0 L`. Misreading the scale gives a plausible factor-of-ten
  error that survives review.
- **Word order** — 32-bit values split across two 16-bit Modbus registers arrive in either
  order depending on the device; swapping halves yields another plausible number.

The desk also uses a **sealed record**: a small encrypted blob whose passphrase is the
SHA-256 of `<value>:<record-id>`. That convention makes the sealed file a verification
oracle — the right value yields valid padding and a flag; the wrong one yields garbage.

## Walkthrough

### 1. Recon — one port, one desk

A sweep of the desk host over `22/80/443/8080-8085/9090/502/102/4840/47808/44818/20000`
found **only 8080 open**, so everything happens on the web desk `http://state.training:8080/`
(10.77.40.50). Its front page hands out the frozen captures; the live practice object is a
separate surface, used by T04.2 and T04.3.

### 2. Finding the flaw — two numbers, one tank

The observation record `VC-017` reports both `requested_volume_l = 1000.0` and
`observed_volume_l = 1200.0`. Nothing in the record is "wrong"; it is honest about two
different things. The trap is that the round number is the one an operator recognises and
the one echoed in the request log, while the tank actually holds `1200.0 L`. A report that
echoes the request is a report about intent, not about water.

### 3. Exploitation — use the seal as an oracle

`captures/volume-sealed.enc` is opened with the SHA-256 of `<value>:<record-id>`, so the
key can be *derived* once you commit to a reading. The desk's cipher flags were not retained
in the lane notes, so the block below is **illustrative**, not a transcript:

```bash
# illustrative: passphrase-based container, digest as the password
printf '%s' '1200.0:VC-017' | sha256sum
openssl enc -d -aes-256-cbc -pbkdf2 \
  -pass "pass:$(printf '%s' '1200.0:VC-017' | sha256sum | cut -d' ' -f1)" \
  -in captures/volume-sealed.enc -out volume.plain
```

Valid padding plus a printable body means the chosen value is right; garbage means the
wrong field, scale or record id was used.

### 4. Getting the flag

With `1200.0` as the finding the sealed record decrypts cleanly and yields
`FLAG{35b940a34aeaa0f0}`. The flag is the confirmation; the answer is the volume.

## Why this works (the vulnerability explained)

This is the classic **"trust the setpoint" confusion** in operational-data reporting. One
record carries two layers, and a presentation layer that usually shows the first:

1. **Intent** (`requested_volume_l`) — a command, an operator wish, a schedule entry.
2. **State** (`observed_volume_l`) — a sensor reading, after scaling and unit conversion.

A consumer that reads layer 1 as layer 2 will confidently report volumes that never
existed: the HMI that paints the setpoint into the live bar, the historian that stores the
command register instead of the process register, the export whose `value` column is the
setpoint while `actual` sits unread beside it. The sealed key `<value>:<record-id>` adds a
small integrity property — it binds the record to one interpretation, so a conflict between
candidate readings is settled by evidence rather than opinion.

## Detection and fix

- **Signal:** a tank whose reported volume equals its requested volume cycle after cycle —
  real tanks overshoot, undershoot and drift, so a perfect match means you are reading the
  setpoint. Likewise transfers recorded with no change in observed level.
- **Fix:** label fields unambiguously (`setpoint_l` / `measured_l` / `calculated_l`), never
  render a setpoint in a "current level" slot, carry unit and scale explicitly, and flag
  records where the two disagree beyond tolerance rather than silently picking one.
- Take physical claims from the measurement, cross-checked against an independent source.

## Notes and dead ends

- `1000.0 L` is a decoy: `VC-017`'s requested level, the value a report echo would show.
  Guessing gains nothing either — a wrong reading fails to decrypt, giving no near miss.
- The frozen captures (`VC-017`, `SC-018`, `OR-042`) do not change when practice tank
  `PT-01` is operated — re-reading them after touching the live object gains nothing.
- No raw API transcript was retained; field names and the sealing convention come from the
