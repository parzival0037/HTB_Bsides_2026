**What you are about to read:** how deleting a file in git is not revocation, how release records
point at commits that still contain retired signer material, and what "usable signing authority"
means.

## Objective

> Recover usable signing authority for the accepted release lineage from the protected source
> history and release records.

"Usable" is operative: a public key proves nothing, an encrypted blob is not enough, a private key
the verifier does not associate with the lineage is worthless. You need the combination the pipeline
accepts.

## Background you need

- **Git history is append-only in practice.** Removing a file in a new commit removes it from the
  working tree; the blob stays reachable from the earlier commit, and any API accepting a `ref`
  serves it: `GET /api/v1/repos/{owner}/{repo}/contents/{path}?ref={rev}`.
- A **release lineage** is a named trust family. Verifiers accept a release whose signature
  validates against a key published for that lineage — not necessarily the newest, because old
  releases must stay verifiable.
- Signing material at rest is encrypted, with the passphrase held somewhere *else*: that separation
  is all that stands between "encrypted blob in a repo" and "working signer". A release record links
  the build commit, the lineage and often the key id.

## Walkthrough

### 1. Recon — enumerate the source history, not just the tree

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/release-signer-history/commits?limit=50'
```

Commit messages are the map: "retire signer", "rollover", "publish verification key". Each lists the
files it touched, so a retirement commit removing `secrets/…` points at the commit before it.

### 2. Finding the flaw — the deleted path is still an object

Walk one step back and ask the contents API for the removed path at that revision (the blob still
exists at the earlier commit, though HEAD no longer has it):

```bash
curl -sS ... -u 'rowan.ito:<token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/release-signer-history/contents/secrets/release-signer.enc.json?ref=<parent-sha>'
```

A blob response means the retirement was cosmetic: the material is readable by anyone with read
access, which here is the ordinary developer account.

Two supporting reads make it usable rather than merely interesting: the **published verification
key** in the current tree gives the `key_id` and lineage, and the **release record** names the commit
and the lineage claimed — confirming this is the accepted line, not a decoy.

### 3. Making it usable

The recovered file is encrypted and the passphrase is documented where the rollover was recorded.
Mechanical, but exact:

1. parse the envelope for cipher and KDF parameters;
2. assemble the passphrase from the retained rollover record(s) — they exist because operators had
   to recover keys themselves;
3. decrypt, then confirm the private key matches the published public key (`key_id` included);
4. sign a test payload and verify it against the published key.

### 4. Getting the flag

Solved by a team agent; the accepted value is not recorded. Scoring: working signing authority tied
to the accepted lineage.

## Why this works (the vulnerability explained)

The bug class is **secret retention across a history boundary** — deletion treated as destruction.

- **Deletion is a new state, not an erasure.** `git rm` writes a tree without the blob, but history
  keeps every object fetchable by SHA. Retirement commits index what used to be secret, and a
  `ref`-parameterised API turns that index into retrieval.
- **Encryption with co-located key material is obfuscation.** If the record documenting the
  passphrase is in the same repo — or any record the same reader can see — the reader has both
  halves. Separation only works across a real trust boundary.
- **Trust is anchored to the lineage.** A verifier that checks lineage membership still accepts a
  retired signer for the releases it signed: revocation needs a verifier-side change, not a commit.

The pattern: for every retirement or rotation commit, ask what the previous commit still holds and
who can read it.

## Detection and fix

- **Detect:** reads of paths at refs older than the current tree, especially `secrets/`, `*.enc`
  and key-shaped names; contents requests whose `ref` is not a branch head.
- **Fix:** rotate the key whenever history exposure is possible — assume compromise, do not just
  delete. Keep signing keys in an HSM/KMS and expose a signing oracle; never commit wrapped key
  material, even with a split passphrase. Publish a revocation list and honour retirement per
  lineage.
- **Also:** history of sensitive repositories should be a separate, audited permission.

## Notes and dead ends

- Evidence is thin: the card retains the description and the documented source API. The commits, key
  ids and envelope fields above are **reconstructed**; no per-card transcript or flag was retained.
- The public key is *supposed* to be readable: it proves the lineage and grants nothing.
- A release record naming only the lineage is not enough: the commit reference is what makes the
  historical path retrievable.
