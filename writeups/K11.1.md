## Objective

Recover the policy program embedded in the retained rules compiler and identify the input it
actually evaluates.

## Background you need

- **Policy as a program.** Rather than scattered `if` statements, the service compiles rules into
  a small bytecode and evaluates it against structured input. The compiled artefact is ground
  truth: documentation describes intent, bytecode describes behaviour.
- **FKPC format:** a magic value, a header, and 4-byte instructions. Operands: `PUSH_FIELD`
  takes a field index (0–3), `PUSH_CONST` a constant index, `IN_SET` a set index. Constants and
  sets are documented in the repository README.
- **"The input it actually evaluates"** matters: a policy engine is only as meaningful as the
  fields it reads, so finding them separates signal from decoration.
- The client reference on `source-tools` exposes `evaluations` and `nonces` for
  `fieldkest-policyc`, so the compiled program can be run, not just read.

## Walkthrough

### 1. Recon — follow the handoff, not guesses

The unlocked hint is direct: read `work/build-operations/policy-compiler-handoff.md` on the
workstation; it names the `fieldkest/policy-compiler` repository. Then:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/policy-compiler/contents/?ref=main'
```

Two artefacts matter: the README (constants and sets) and the compiled policy blob the compiler
carries. The repository's *website* field points at the client reference on
`source-tools.keplerops.test:8443`, which names the evaluation route:

```bash
curl -sS ... https://source-tools.keplerops.test:8443/.well-known/fieldkest-client | jq .
```

### 2. Finding the flaw — the program is in the shipped artefact

The compiled policy is embedded in the compiler that ships, not held server-side. A decision
program the caller can read is a specification of the decision. Confirm the blob's shape:

```bash
xxd -l 64 policy.fkpc
# 46 4b 50 43 ...   "FKPC" magic, then the header, then 4-byte instruction words
```

### 3. Exploitation — disassemble enough to name the input

```python
# illustrative: minimal FKPC disassembly skeleton
import struct
blob = open("policy.fkpc", "rb").read()
assert blob[:4] == b"FKPC"
words = struct.unpack("<%dI" % ((len(blob) - 16) // 4), blob[16:16 + ((len(blob) - 16) // 4) * 4])
for w in words:
    print(f"op={w & 0xFF:#04x} arg={w >> 8}")
```

Map opcodes to the README's mnemonics and read the program as a sequence: `PUSH_FIELD 0..3`
shows which input fields are consulted; `PUSH_CONST`/`IN_SET` show accepted values. Field
indices that never appear are the ones documentation talks about but the program ignores.

Solved by a team agent: the accepted submission follows from recovering the program and

## Why this works (the vulnerability explained)

Shipping the decision program to the client is a **specification leak with execution
semantics**. Behaviour beats documentation: a README says "we check channel and version", while
bytecode says which field indices are read, in what order, against which constant sets — an
attacker's test oracle. Constants *are* policy: `IN_SET 2` becomes exact acceptance criteria once
the README supplies the set contents, which is what a fuzzer would otherwise discover. And the
evaluator is reachable, so a recovered program can be replayed against crafted inputs, turning
static analysis into a fast feedback loop. The rule: if a client must evaluate policy locally,
that policy is public — keep the keys and the authoritative decision server-side.

## Detection and fix

- **Detect:** downloads of the compiler artefact; evaluation requests that walk the input space
  with one-field variations; compiler use outside the vendor toolchain.
- **Fix:** keep authoritative policy server-side and expose an opaque verdict. If offline
  evaluation is required, sign the program, bind it to a client, and omit the constants that
  make it enumerable. Version the policy and log which version produced a verdict.
- Obfuscation is not a control: the format is documented for good reasons, so assume a reader.

## Notes and dead ends

- Evidence is moderate: the retained hints name the handoff document, repository, website-field
  pointer, FKPC encoding and operand semantics (field index 0–3, constant index, set index,
  README-documented constants/sets). The decoder is **reconstructed**; no compiler output was
  captured.
- Guessing opcode numbers is a dead end — the repository README is authoritative for the
  mnemonic table; derive numbers from it, not from byte frequency.
- Do not submit candidate flags from the constants: K11.1 asks for the program and its input;
  the acceptance conditions are K11.3.
