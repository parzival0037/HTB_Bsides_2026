# K05.2 — The version they kept

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Source-of-truth confusion — the release manifest, the channel slot and the retained customer record disagree, and the authoritative answer is the one the customer actually kept |
| **Tools** | `curl`, `jq`, `psql` (attempted), the delivery client reference |
| **Attack surface** | `GET https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector`, the package/reconcile routes, and `support.customer_records` |

**What you are about to read:** how to answer "which version does this customer run?" when three systems
disagree. The bug class is *version-state confusion*: a manifest says what was published, a channel slot
says what is promoted, a customer record says what was retained — and only the last answers the
question.

## Objective

> The version they kept.

The support ticket names `6.9.8`; the release manifest talks about `7.4.2`; a pending release
`7.4.3-cinder.rset1` sits beside an `arwc-stable` rollback slot of `7.4.2`. The card is to establish
which version the customer actually retained, and to say so with evidence rather than by picking the
newest number.

## Background you need

- **Three questions, three answers**: "what was released?" (manifest), "what is promoted?" (channel
  slot), "what does this tenant run?" (customer record). Mixing them is the classic support error.
- **Rollback slots hold older versions deliberately.** `7.4.2` as `rollback_slot` is not evidence the
  tenant runs it — only that the channel can fall back to it.
- **Retained maintenance records are the authoritative history**: native/backup deprecation is recorded
  per customer, and the migration history explains why an old major stayed pinned.
- **Authorisation gates the truth, not the route**: the record is reachable, but not by `rowan_data`.

## Walkthrough

### 1. Start from the published package metadata

```bash
curl -sS https://delivery.keplerops.test:8443/api/package-meta/fieldlink-connector | jq .
```

Here the confusion is visible: `pending_release` `7.4.3-cinder.rset1` and
`channels.arwc-stable.rollback_slot` `7.4.2`. Neither is a tenant's running version; reporting either as
such is the mistake this card catches.

### 2. Try the customer record directly

```bash
psql service=fieldlink -c "select * from support.customer_records where tenant_id = 'TEN-ARWC-047';"
```

With `rowan_data` this fails: `permission denied for schema support`, owned by `fieldlink_admin` /
`fieldlink_data_owner`; only `export.partition_bindings` is readable. That is a hard boundary, not a
puzzle.

### 3. Establish the retained version through the reconcile view

The delivery service exposes tenant-package reconciliation — the supported way to ask "what does this
tenant have?" without database access:

```bash
# illustrative: reconcile the tenant against the package channel
curl -sS -X POST https://delivery.keplerops.test:8443/api/reconcile/tenant-package \
  -H 'Content-Type: application/json' \
  -d '{"tenant_id":"TEN-ARWC-047","package":"@keplerops/fieldlink-connector"}' | jq .
```

The reconcile answer is the one to trust: it derives from the tenant's own record, the same input the
support ticket was written against — which is why the ticket names `6.9.8` at all.

### 4. Explain the discrepancy

The pieces fit once read as different questions: `6.9.8` is retained on `TEN-ARWC-047`, `7.4.2` is the
rollback slot, `7.4.3-cinder.rset1` is pending. Backup/native deprecation is recorded against the
retained line, which is why an old major is still in service.

### 5. Getting the flag

The accepted answer is the retained version for the tenant, from the customer record / reconcile view
(`6.9.8` per the support ticket). Accepted; the flag value is not reproduced here.

## Why this works (the vulnerability explained)

Package pipelines model state as a *graph of promotions*: build → release → channel → rollback slot.
Each layer is visible through a different endpoint and answers a different question; the bug is
answering the one you can reach instead of the one you were asked.

That matters in support work because the answer drives action: tell a customer they run `7.4.2` when
they retain `6.9.8` and every later instruction — patch, rollback, deprecation notice — is wrong. The
same failure shows up as a "latest" tag that is not deployed, a manifest version that differs from the
installed file, or a lockfile pinning an old major while the resolver reports the new one. The
discipline: name the source of each version claim and prefer the most specific — tenant record, then
channel, then release manifest.

## Detection and fix

- **Log signal:** reconcile queries whose inputs disagree with the tenant record; repeated permission
  failures against `support.*` — an analyst shortcutting the supported route.
- **Fix:** expose one "effective version" API that resolves tenant → channel → release and labels each
  layer; keep deprecation data with the retained record; put reconcile in the support runbook.
