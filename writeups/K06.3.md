## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Supply-chain code execution through a trusted package channel — a rehearsal service installs and runs a package published under a credential the attacker holds |
| **Tools** | `npm`, `curl`, `zip`/`tar`, review service API |
| **Attack surface** | `https://packages.keplerops.test` → `https://review.keplerops.test/api/rehearsals/connector` |

| **Flag** | accepted, value not recorded |

**What you are about to read:** the difference between a package that *looks* compatible and
one that *runs*, and how a consumer that resolves a package by name turns publishing rights
into code execution inside an isolated service.

## Objective

Publish a compatible connector package under the authority you recovered, then make the
isolated rehearsal consumer run its actual code and return your changed result.

## Background you need

- **A connector package is code, not data.** The consumer installs the package and calls an
  exported entry point. Compatibility is checked against the interface — export names and
  call shape — not against the implementation.
- **Isolation is real but partial.** The consumer runs in its own container, yet shares the
  package resolution path: it resolves the package name from the registry you can publish to.
- **"Run its actual code and return your changed result"** is the acceptance criterion:
  proof that the consumer executed *your* branch. A module that satisfies the interface but
  behaves like the original is not enough.
- The range documents `POST /api/rehearsals/connector` on the review service alongside
  `POST /api/jobs` and `GET /api/jobs/{job}`.

## Walkthrough

### 1. Recon — what does the consumer expect?

Two sources define the contract: the existing connector's package metadata (`npm view …
--json`, with the K06.2 identity, gives `main`, `version`, `engines`) and the service's
client document, which lists the rehearsal route and payload:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  https://review.keplerops.test/.well-known/fieldkest-client
```

### 2. Finding the flaw — resolution is by name and version, and you control both

The consumer does not pin a digest; it asks the registry for whatever version satisfies its
constraint. Publishing a compatible package under the same name, with a version inside that
constraint, means the next rehearsal resolves your artefact.

Two checks before publishing: the package passes the interface check (same exports, same
signature), and the exported function does something *observably yours* — returns a value
derived from input, or a marker in the result.

### 3. Exploitation — publish, then ask for a rehearsal

```bash
# illustrative
npm --userconfig /tmp/recovered.npmrc publish --registry https://packages.keplerops.test

curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' -H 'Content-Type: application/json' \
  -d '{"package":"<your package>","version":"<your version>"}' \
  https://review.keplerops.test/api/rehearsals/connector
```

The response is a job handle; polling returns the consumer's own output. If the code ran,
the result contains your marker or altered value rather than the vendor's default.

### 4. Getting the flag

Solved by a team agent; the accepted value is **not recorded** in the retained data. The
demonstrated path: publish a compatible package with the recovered authority, drive the
rehearsal consumer until it executes that package, and read the changed result.

## Why this works (the vulnerability explained)

The class is **trust transitivity across a package boundary**. The service trusts the
registry ("a package with this name resolves, so it is the vendor's") — true only while the
vendor is the sole publisher of that name or scope. The consumer validates *interface*, not
*identity*: a malicious module can satisfy every shape requirement and still misbehave,
because type/lint checks bound the boundary rather than the behaviour. And nothing in
resolution is content-addressed — no `integrity` pin, provenance attestation or vendor
signature — so version selection is the only control, and it is attacker-influenced.

## Detection and fix

- **Detect:** publishes of the name outside the vendor's CI identity; versions that leap
  into an existing constraint; the consumer resolving an unseen `dist.integrity`. Log the
  resolved tarball digest in the rehearsal job so it can be diffed.
- **Fix:** pin rehearsals to an exact version *and* digest, verify a provenance attestation
  before executing, and scope publish ACLs per package rather than per namespace. Run the
  consumer in a sandbox with no ambient credentials — that isolation is what keeps this at
  "code execution in a rehearsal" rather than "on the platform".

## Notes and dead ends

- Evidence is thin: the description, a cross-lane note that the review job is a prerequisite
  for later consumer work, and solved-state metadata. The commands are **reconstructed**
  from documented registry/review routes; no transcript was retained.
- A package that satisfies the interface but returns the *original* values is a dead end —
  the card requires the changed result, so the code must branch on your input.
- Do not reuse the K06.2 CI token for publishing; that identity is the *reader*.
