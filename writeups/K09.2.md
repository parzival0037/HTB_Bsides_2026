# K09.2 — The artifact without a link

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** team agent

**What you are about to read:** how "the UI only shows some artifacts" becomes an access
control problem, and how to enumerate what the runner kept instead of what it published.

## Objective

The description is empty in the retained dataset; the title and chapter define it. Find the
artifact a run retained but never linked from the results page, retrieve it through the run
store, and read its content.

## Background you need

- **Retained vs. published artifacts.** A CI service has two layers: the artifact page (what
  the job chose to publish) and the run store's retention list (everything kept for
  debugging, quarantine or later inspection).
- **The lists differ.** If the runner writes a file into its retention directory, it is
  addressable by name through the run API even though no page links it — "artifact without a
  link" is the whole finding.
- The range's run record carries `retained_artifacts` alongside `report_sha256`, `asset_id`,
  `connector_revision` and an embedded `report` object.
- Direct object access without a listing is only a barrier if names cannot be guessed — and
  run outputs are usually named deterministically.

## Walkthrough

### 1. Recon — read the retention list

```bash
# illustrative: fetch a run and look at what it retained
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  https://review.keplerops.test/api/runs/<run_id> | jq '{state, retained_artifacts, report_sha256}'
```

The service's own source comments state the design: *the run metadata lists retained artifacts
that are not on the Jenkins results page; the participant must access this service to find
them.* That is the vulnerability in the author's words.

### 2. Finding the flaw — the file is served straight from the name

For each name in `retained_artifacts`, the artifact route builds a path in the run's retention
directory:

```bash
# illustrative: fetch each retained artifact by name
for a in $(curl -sS ... /api/runs/<run_id> | jq -r '.retained_artifacts[]'); do
  curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
    -u 'rowan.ito:<fk_developer token>' \
    "https://review.keplerops.test/api/runs/<run_id>/artifacts/$a" -o "out-$a"
done
```

What is wrong is not that the files exist, but that the authorization model is "you know the
name": no check that the artifact came from your job, and no published/retained distinction.

### 3. Exploitation — use the digest to confirm what you have

```bash
sha256sum out-*        # compare against report_sha256 from the run record
```

A digest matching no published `report_sha256` identifies the orphaned artifact — the one the
card is about. Its content carries the accepted value.

### 4. Getting the flag

Solved by a team agent before the K09 lane's recorded run; no request/response was retained,
so the flag is **accepted, value not recorded**. The evidence is the service source comment
describing `/api/runs/{run_id}` as the home of retained artifacts.

## Why this works (the vulnerability explained)

Two catalogues, one store, one authorization check. The **publishing pipeline** decides what
is advertised; the **run store** decides what is kept. Keeping is cheap and useful, so
runners retain far more than they publish. The retention directory is served by a route that
resolves `{name}` inside the run's directory: the only gate is knowing run id and filename,
both disclosed by the run record. There is no "is this published?" predicate in the read
path, so the property rests on nobody knowing a deterministic filename — obscurity, not a
control. The same shape appears wherever a download endpoint is keyed by an opaque path
segment and the listing is filtered in the UI rather than in the API.

## Detection and fix

- **Detect:** downloads of names absent from the run's published set; a caller iterating
  names or run ids; artifact access for runs the caller did not submit.
- **Fix:** mark each retained artifact with a visibility flag at write time and enforce it on
  read. Serve published artifacts through authorised, expiring URLs; keep the debugging view
  behind an operator role and audit it.
- **Fix retention:** do not retain secret-bearing intermediates at all; if you must, encrypt
  them with a key the run API cannot use.

## Notes and dead ends

- Evidence is thin: metadata plus quoted service comments (`retained_artifacts` "not on the
  Jenkins results page"; fields `report_sha256`, `asset_id`, `connector_revision`, `report`).
  The commands are **reconstructed templates**; no captured response survives.
- Looking only at Jenkins `/artifact/reports/{file}` is the intended dead end — that shows
  what the job published, not what it kept.
- Do not mistake the embedded `report` object for the artifact; the card is about a *file*
  the record lists but does not inline.
