# K15.1 — An export in progress

> **Category:** 2. KeplerOps · **Points:** 50 · **Difficulty:** easy
> **Solved by:** pi lane K15

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Export job record readable through a delegated bearer with no per-job ownership check — the API authorises on the audience, not the requester |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://cloud-api.keplerops.test/api/exports/EXP-2841` |
| **Prerequisite** | An export-audience JWT (`fieldkest-export-access`, from K14.2) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a support engineer's in-flight export for an unresolved
customer case is readable as plain JSON once you hold any token minted for the export audience,
and how the record names the dataset and revision the job is operating on.

## Objective

> Recover the export job that support started for its unresolved customer case. Identify the
> actual dataset and job revision.

The case is the ARWC connector-latency ticket `SUP-2841`; support had an export in progress
against it. The task is to find the job record, not the customer's data.

## Background you need

An export job is an object with a lifecycle and a *definition*: a dataset (which
partition/tenant data goes out), a revision (which versioned view), a destination/handover point
and a state. Jobs are owned by the identity that created them — usually a support principal, not
the export workload.

Export APIs are commonly built machine-to-machine: one role (`support-export-editor`) may touch
*all* jobs, because only the export worker is expected to call it. When that role's token can be
obtained elsewhere (K14.2), "owned by someone else" stops being an access-control boundary.

## Walkthrough

### 1. Get a token for the export audience

Two exchanges exist. The workspace one identifies the human caller and is useful for recon but
not enough here:

```bash
curl -sS -u 'rowan.ito:fk_developer_…' -X POST \
  https://cloud-api.keplerops.test/api/workspaces/current/token-exchange

curl -sS -X POST -H "Authorization: Bearer ${SA_JWT}" \
  https://cloud-api.keplerops.test/api/token-exchange/fieldkest-export-access
```

The second returns a JWT with `aud=fieldkest-export-access` and role `role/support-export-editor`
(the mechanism is K14.2; the token is the prerequisite here).

### 2. Ask for the job by id

The job id is visible in the support trail: case `SUP-2841`, export `EXP-2841`.

```bash
curl -sS -H "Authorization: Bearer ${EXPORT_JWT}" \
  https://cloud-api.keplerops.test/api/exports/EXP-2841 | jq
```

### 3. Read what the record says

The response is the job record: state `in progress`, the owning support principal, the dataset,
the revision. Two fields are the point of the card:

- **dataset** — the actual collection being exported, not the job name or ticket id. Job ids are
  cosmetic; the dataset is what leaves the platform.
- **revision** — which versioned slice of it. A revision mismatch is how "we exported the wrong
  thing" incidents happen.

Because the job is still running, the record shows a destination/handover slot rather than a
finished object — which is what makes the handover-redirection cards possible at all.

### 4. Getting the flag

`GET /api/exports/EXP-2841` with the export-audience token returned the record and its flag in
the same response. Lane notes record the value as `FLAG{6b4342f2b090f8d2}` and the submission as
accepted; the card entry has no stored flag, so it is recorded as accepted/not recorded. Do not
resubmit it against K15.2 — the definition route returns a different one.

## Why this works (the vulnerability explained)

The check is on the **token audience**, not on the relationship between caller and job. Anyone
presenting `aud=fieldkest-export-access` is treated as "the export service", which is deliberately
allowed to read every job. That is sound only if the audience is hard to obtain and never leaves
the worker.

The chain: a workload JWT is exchanged for the export audience (K14.2); the resulting role is
co-extensive with the service's own rights; the job record has no `owner == caller` check because
the caller was assumed to be the service. Sequential, guessable ids (`EXP-2841`) remove even the
need to enumerate once the ticket number is known.

Correct behaviour: bind each job to its creating principal and require the export service to pass
an *on-behalf-of* subject checked against the job owner — or scope the exchanged token to a set of
job ids instead of a role.

## Detection and fix

- **Log signal:** export-audience tokens used from a workstation subnet or by more than one source
  identity; reads of jobs whose `created_by` differs from the caller.
- **Fix:** enforce `job.owner == caller` (or an explicit grant) at the record route; make job ids
  unguessable; scope exchange tokens per job; add an `act`/`obo` claim. Cancel or re-key the live
  job — an open destination slot is the foothold for K15.3.

## Notes and dead ends

- The record's `dataset` and `revision` **values** were not preserved; what survives is the id
  `EXP-2841`, its link to `SUP-2841`, and its `in progress` state. Do not invent a dataset name.
- The workspace exchange alone is insufficient: it yields a workspace token, and
  `/api/exports/...` still wants the export audience.
- `/api/exports/EXP-2841/runs` is denied to the export token (`k3s_rbac_denied`); run history is
  not part of this card. K15.3 stayed unsolved in the same lane — the role can read the
  destination but not rewrite it.
