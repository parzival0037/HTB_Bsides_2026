**What you are about to read:** how a "limited" workload identity is established from a

## Objective

Establish the limited workload identity available from this workspace and recover the protected
record within its actual scope.

## Background you need

- **Workload identity** is a cluster service account reached by exchanging a workspace-scoped
  token for a Kubernetes credential; the exchange route is advertised in the client reference.
- **"Limited" is the point.** `403 k3s_rbac_denied` on one path and a 200 on another *is* the
  scope map: probing denials matters as much as finding what is allowed.
- **A ConfigMap is a data object.** `fieldlink/bld-1842` is a build-record ConfigMap whose
  `data.access_token` is the protected value — a build pipeline token, not the workspace's.
- The k3s API is at `https://cloud-api.keplerops.test:6443` (context/namespace `fieldlink`).

## Walkthrough

### 1. Recon — read the client reference, not the UI

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  https://cloud-api.keplerops.test/.well-known/fieldkest-client | jq .
```

The document lists the workspace routes including the token exchange (`cloud.workspace-…`). That
is how the lane found the path without guessing.

### 2. Establish the workload identity

```bash
# illustrative form of the exchange described in the client reference
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -X POST -H 'Content-Type: application/json' \
  -d '{"workspace":"fieldlink-workload"}' \
  https://cloud-api.keplerops.test/api/workspaces/current/token-exchange | jq .
```

The response carries a bearer token for the workload service account — the lane's target identity
is `svc-fieldlink-workload` — used as `Authorization: Bearer $TOKEN` below.

### 3. Map the scope, then read inside it

The lane's recorded probes: `/api/exports/EXP-2841/runs` and
`/api/trust-records/TRUST-FLX-04` are denied (`k3s_rbac_denied`) — those belong to other lanes.
The ConfigMap read that works:

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k -H "Authorization: Bearer $TOKEN" \
  'https://cloud-api.keplerops.test:6443/api/v1/namespaces/fieldlink/configmaps/bld-1842'
```

Its `data.access_token` is this card's accepted value. The object is a build record, identified by
`"namespace":"fieldlink-build-records","version":"2026-09-18","workspace":
"fieldlink-workload"` — the "actual scope": the identity reads the build record for its own
workspace, and nothing else in the chapter's object store.

### 4. Getting the flag

The lane records the accepted submission (attempt 4) from `data.access_token` in the
`fieldlink/bld-1842` ConfigMap, read only via `svc-fieldlink-workload`. The per-card `flag` field
is empty, so it is **accepted, value not recorded**.

Near-misses: `trust-flx-04`'s `access_token` was submitted to this card earlier and rejected — it
belongs to the trust-document challenge. `SCHED-2841` and export values likewise belong elsewhere.

## Why this works (the vulnerability explained)

The class is **RBAC scope creep across a token-exchange boundary**. The workspace token is a
low-privilege artefact identifying a workload, and exchanging it is legitimate — but the service
account behind the exchange is granted read on resources the workload does not need, here a build
record in the `fieldlink` namespace. Once the exchange succeeds the caller inherits that
account's permissions. Kubernetes RBAC is additive and namespace-scoped: one over-broad `get` on
`configmaps` in a shared namespace is enough, because there is no per-object ACL on a ConfigMap.
The token in `data.access_token` is itself a credential, so the finding chains onward.

The lesson: a token-exchange service is a *privilege amplifier*. Its output must be scoped to
exactly the workload's needs — dedicated namespace, named resources, short TTL — otherwise the
lowest-privilege entry point in the platform becomes a route into every shared namespace.

## Detection and fix

- **Detect:** exchanges followed by reads of configmaps/secrets outside the workload's namespace;
  `403 k3s_rbac_denied` bursts (scope probing) from a service account; service-account tokens used
  from a workstation network position.
- **Fix:** give the exchanged identity a Role in its own namespace only, with `resourceNames`
  restricted to the objects it needs; never grant `get` on `configmaps` at namespace scope. Keep
  build tokens out of ConfigMaps (use a per-workload secret store) and make exchanged credentials
  short-lived and audience-bound.
- **Fix monitoring:** log the exchange (workspace → service account) with the subsequent API
  calls, so the amplification appears as one session.
