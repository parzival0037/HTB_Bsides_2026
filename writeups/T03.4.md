**What you are about to read:** the shift from *reading* an artefact to *publishing* one. The card
asks for a formatter package that is compatible with the consumer's documented interface and adds a
specific marker to the delivery report. The class is the one behind real supply-chain incidents: the
consumer trusts any package dropped into the slot, and the package has write access to the output
everyone reads.

## Objective

> Deliver a compatible formatter package that adds Cinder's rehearsal marker to the intended
> consumer's delivery report — build it against the documented interface, submit/upload it to the
> consumer the desk names, then read the resulting report.

Three requirements, in order: **compatibility** (it must be accepted and load), **effect** (the
report must carry the rehearsal marker) and **targeting** (it must be the named consumer's report).
Skipping one produces a package that runs but does not count.

## Background you need

- **A formatter is a code slot.** Consumers of this kind load a plugin to turn raw results into the
  report they publish. The interface is the contract — module shape, entry point, function signature,
  return type — and anything satisfying it executes inside the consumer.
- **The report is the output of trust.** Downstream teams read the report, not the raw data, so
  whoever controls formatting controls what the delivery record says.
- **"Compatible" is the only gate.** The desk documents the interface so the card is reproducible:
  no signature check, no publisher allow-list, no review step between upload and execution. That
  absence *is* the vulnerability; the rehearsal marker is a harmless way to demonstrate it.
- **Least-surprise packaging.** A formatter should read its input, produce its output and do nothing
  else; extra side effects are what a review would catch, and nothing reviews this one.

## Walkthrough

### 1. Read the consumer contract before writing anything

The desk front page links the consumer's documentation. Four things matter: the **interface
identifier/version** accepted (a name and a version string); the **entry point** loaded and the
**function** called; the **input** shape (raw result object) and **expected output** (report value);
and the **submission route** — how a package reaches the consumer, and which consumer is the named
one.

Nothing should be built until all four are answered from the documentation: the failure mode is a
package that is nice but rejected at load time. Before uploading, unpack your own artefact and read
it as the consumer would — entry point present, identifier and version matching, no stray files — and
dry-run the function against a sample input, which catches a wrong export name.

### 2. Build the minimal compatible artefact

Write the smallest module satisfying the interface, then package it in the accepted format with the
entry point declared exactly as documented. The skeleton is **illustrative**: the real names come
from the desk's contract, not retained verbatim.

```js
// illustrative: a formatter satisfying a documented interface
function format(input) {
  const report = input.report ?? input;   // shape per the contract
  report.marker = "CINDER-REHEARSAL";     // the required rehearsal marker
  return report;                          // exact documented return type
}
module.exports = { format };
```

### 3. Submit to the named consumer and read the report

Upload through the documented route, targeting the consumer the desk names, then fetch its report:
the accepted answer is that report, carrying your marker (flag accepted, value not recorded).

## Why this works (the vulnerability explained)

The consumer implements a **plugin architecture with no trust boundary**. Loading uploaded code is
convenient and it is how every formatter ecosystem works — Babel presets, ESLint processors, CI
report generators — but convenience is not authorisation. Four weaknesses chain:

1. **Capability without authentication.** The upload endpoint accepts any artefact that parses;
   nothing binds a package to a publisher identity.
2. **Execution in the consumer's context.** The formatter runs with whatever the consumer holds: its
   inputs, its output, its network position.
3. **Write access to the trusted artefact.** The report is what people believe, so a formatter that
   can set its fields can assert outcomes — a rehearsal that "happened", a check that "passed".
4. **Verification after the fact, if at all.** Consumers check what the report says, not how it was
   produced.

The rehearsal marker is the polite version: it proves the slot is writable without asserting anything
dangerous. Replace it with `result: "pass"` on a compliance report and the impact is obvious — which
is why formatter slots need signed packages, pinned versions, and an independent record of the raw
data.

## Detection and fix

- **Signal:** a package accepted from an unknown publisher; formatter output that differs from a
  recomputation of the raw input; report fields no allow-listed plugin version could produce.
- **Fix:** require signed artefacts verified against a publisher allow-list before load; pin
  formatter versions per consumer; run formatters in a sandbox taking raw input in and only the
  report value out; and keep the raw result beside the formatted report so the two can be diffed.

## Notes and dead ends

- No command transcript for this card was retained in the lane evidence. The lane brief states only
  the approach (build against the documented interface, submit/upload to the consumer the desk
  names, read the resulting report), so no endpoint path, package name or consumer host is asserted
  here, and the code sample is an illustrative skeleton.
- The flag value is unrecorded ("accepted, value not recorded"), so none is invented.
- The likely dead end is a *correct* formatter missing the documented identity (wrong interface
  version or export name): compatibility is tested first, so it never gets to write the marker. The
  second is uploading to the wrong consumer — a report from another job has the marker and is still
  the wrong answer.
