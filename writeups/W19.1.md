> **Category:** 3. ARWC · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

**What you are about to read:** how a diagnostic survives past the project that created it,
why "which project family?" is a provenance question rather than a naming question, and how
the support diagnostics interface retrieves and executes the retained artefact.

## Objective

Recover the retained engineering diagnostic associated with the outlet records and identify
its actual project family — not necessarily the customer whose records reference it.

## Background you need

- **Diagnostics as packages.** A diagnostic is a job plus a package: interface
  `fieldkest.connector/v3`, a CommonJS module exporting `diagnostic_summary`, and an
  `expected_output` that is the exact return value the service accepts. Delivery runs the
  package against the customer's records.
- **Retention outlives projects.** Diagnostics are filed under whichever customer needed them
  and never retired; their names keep the old project's vocabulary, so file location is not
  evidence of origin.
- **Provenance is embedded, not declared.** The family shows up in constants: asset class,
  outlet multiplicity, threshold tables, units and the `expected_output` vector.

## Walkthrough

### 1. Enumerate the customer's diagnostics

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: Bearer $SUPPORT_TOKEN" \
  https://support.keplerops.test:8443/api/customers/TEN-ARWC-047/diagnostics | jq .
```

The response lists the diagnostic jobs retained for the customer, older ones included. Note
ids and the advertised `connector_revision`.

### 2. Read the job, not just its label

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 -k \
  -H "Authorization: Bearer $SUPPORT_TOKEN" \
  https://support.keplerops.test:8443/api/diagnostics/$JOB | jq .
```

Job metadata gives the package interface, expected output and family/asset fields. Treat them
as claims until the source agrees.

### 3. Retrieve the package source

The package is uploaded with `PUT /api/diagnostics/{job}/package`; reading the retained job
shows the stored source, a CommonJS module:

```javascript
exports.diagnostic_summary = function (records) {
  // thresholds, outlet indexing and unit assumptions live here
  return { /* expected_output must match exactly */ };
};
```

Read constants, not comments: outlet count, indexing, units and thresholds identify the family;
a source assuming a different topology than the customer's records is a reused diagnostic.

### 4. Compare against the project families you can see

`ARWC-FINDINGS.md` records two tenants here: `TEN-ARWC-047` (outlet group `CRR-OG2`) and
`TEN-RILL-022` (`RILL-PUMP-442`). A diagnostic filed under ARWC whose source models another
family is the "nobody retired" case: written for another project, kept because deleting it was
nobody's job. The check is mechanical — if asset model, units and expected output do not match
the records, the family is whichever project the constants came from, and the label is wrong.

### 5. Deliver and read the flag

`POST /api/diagnostics/{job}/deliver` runs the package; the response carries the result and
this card's flag when package and expected output line up. The value is not retained here.

## Why this works (the vulnerability explained)

The pipeline never validates provenance: it stores a package, runs it against customer
records and accepts any source returning the declared `expected_output`. The customer
association is a human filing decision from years earlier; the family is a property of the
code. When they disagree every downstream interpretation is wrong — thresholds calibrated for
one plant get applied to another, and reading the "ARWC diagnostic" tells you something false
about the ARWC asset.

Same trust error as unsigned build artifacts or reused test vectors: the label is metadata,
the bytes are truth. A correct system binds the package to a tenant *and* an asset family with
a signature and a compatibility check, and refuses mismatched scope.

## Detection and fix

- **Log signal:** a package whose constants do not match the customer register; packages
  reused across tenants; `deliver` on jobs older than their project.
- **Fix:** sign diagnostics and record provenance (project, asset family, version) at import;
  validate declared scope before running; quarantine mismatches and alert on out-of-family
  use. Pin `expected_output` to the package release so a stale vector cannot validate the
  wrong behaviour.

## Notes and dead ends

- **Reconstructed, not observed.** Solved by the team agent; the retained record has the
  description and route map but no captured response and no flag value. Tenants are documented
  in `ARWC-FINDINGS.md`; that the retained diagnostic belongs to the other family is the
  card's reconstructed answer, not a quoted API result.
- The job's customer field is not origin — it records who filed the job, not who wrote the
  diagnostic. Of the diagnostics chain's flags (job creation, package upload, delivery), only
  the one tied to the retained diagnostic answers this card.
