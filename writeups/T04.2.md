**What you are about to read:** how a single integer hides several independent booleans, and
why "the ready light is on" is not the same as "the outlet may move". We decode
`status_word = 5`, find the one set bit that blocks the transfer, and confirm it live.

## Objective

> Decode the supplied controller status capture and identify the condition preventing the
> practice outlet from moving (a bit/flag in a status word).

The frozen capture `SC-018` is a snapshot of the practice tank's controller. A transfer
request comes back `rejected` and the outlet stays closed even though the controller reports
itself ready. The task is to name the specific blocking condition.

## Background you need

- **Packed status words.** Devices rarely expose one field per condition. To save registers
  they pack 8–16 flags into one integer: bit 0 = ready, bit 1 = running, bit 2 = fault/hold.
  The value is meaningless without the bit map, which lives in documentation, not in the data.
- **Set bits are additive.** `5` is not "five", it is `0b0101` — bits 0 and 2 asserted
  together. Code that compares the whole word against a single known value misreads every
  combination it did not enumerate.
- **Two independent truths.** "Ready" (bit 0) describes capability, "hold" (bit 2) describes
  permission. Both can be true at once and the restrictive one wins.
- **Sealed records** here open with the SHA-256 of `<finding>:<record-id>`, so naming the
  condition correctly is what makes the capture decrypt.

## Walkthrough

### 1. Recon — what is actually listening

A sweep over `22/80/443/8080-8085/9090/502/102/4840/47808/44818/20000` found **only 8080
open**, so all work is against `http://state.training:8080/`. The desk hands out three frozen
captures (`VC-017`, `SC-018`, `OR-042`) and exposes a live practice tank `PT-01`.

### 2. Finding the flaw — one integer, two lights

The `SC-018` capture reports `status_word = 5`, `outlet = closed`, `request = rejected`. `5`
looks like a healthy small number and bit 0 really is set, so a human reading "ready" would
stop there. `bin(5)` is `0b101`: bit 0 is `ready`, bit 2 is `service_hold`. The controller is
simultaneously ready to work and under a maintenance hold — and the hold is what refuses the
transfer. `closed` and `rejected` are consequences, not separate faults.

### 3. Exploitation — confirm against the live object

The frozen capture is half the evidence; the live API shows the same condition in the request
path. Before touching anything the tank reads `status_word 5`, `1200.0 L`, outlet closed, and
a transfer attempted in that state is refused — the desk's documented rule is that *hold
blocks new transfer*. Clearing it is the next card (T04.3).

So the finding is the string `service_hold` — not `5`, and not `ready`. Derive the sealed
passphrase from it and open `captures/status-sealed.enc`. The desk's cipher flags were not
retained in the lane notes, so this is **illustrative**, not a transcript:

```bash
# illustrative: digest as the passphrase for the sealed status capture
printf '%s' 'service_hold:SC-018' | sha256sum
openssl enc -d -aes-256-cbc -pbkdf2 \
  -pass "pass:$(printf '%s' 'service_hold:SC-018' | sha256sum | cut -d' ' -f1)" \
  -in captures/status-sealed.enc -out status.plain
```

### 4. Getting the flag

Valid padding plus a readable body confirms the finding, and the plaintext carries
`FLAG{5cdc1c2fcc92fb42}`. As in T04.1, the flag is the receipt; the answer is the condition.

## Why this works (the vulnerability explained)

A packed status word is a **lossy interface to a multi-dimensional state**. The bug is not the
arithmetic — it is treating one derived light as the whole truth. Three failure modes recur,
and this challenge hits all three:

1. **Whole-word comparison.** Code testing `status == 1` for "ready" fails closed (or fails
   open) as soon as another bit is asserted. Correct code tests `status & READY_BIT`.
2. **Display collapse.** An HMI has room for one lamp, so it shows "ready" because bit 0 is
   set, while the bit that actually blocks the plant is invisible. Operators then file tickets
   about a machine that "says it is fine".
3. **Diagnosis by symptom.** "Request rejected, outlet closed" reads like an authorization or
   comms fault; it is the expected consequence of a hold bit, and chasing it wastes time.

The sealed record closes the loop: the passphrase is the *interpretation* (`service_hold`), not
the raw value, so only a correct bit-map reading produces a decryptable record.

## Detection and fix

- **Log signal:** transfer requests rejected while the device reports `ready`, or a status
  word outside the set of values the client enumerates.
- **Fix (device/HMI):** publish and honour the full bit map, render each bit as its own
  indicator, never hide a permissive bit behind a capability lamp, and include the raw word in
  the rejection reason.
- **Fix (client):** test bits by mask and constant (`status & 0x04`), handle unknown bits
  explicitly rather than failing open, and surface the specific blocking condition.

## Notes and dead ends

- The trap is the word `ready`: genuinely set (bit 0), genuinely irrelevant to whether the
  outlet may move.
- Do not carry this finding into T04.4 — there the sealed value is the report's displayed
  result string (`green`), not a status-bit name. Mixing them costs an attempt.
- `OPTIONS` on the practice API returns `501`; undocumented paths such as
  `/api/practice/sealed` return `404`. Use the documented GET/POST interface.
- No raw request transcript was retained for this card; the decode follows the recorded
  `status_word = 5` capture and the desk's documented hold rule.
