# K10.1 — Whose preview is this

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** me (manual)

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Preview association leak — the renderer associates an arbitrary support attachment with a protected document identity and discloses which identity it believes it is presenting |
| **Tools** | `curl`, `jq`, preview service API |
| **Attack surface** | `https://preview.keplerops.test` (`associations`, `reviews`, `render`, `prepare`) |
| **Prerequisite** | A support attachment reference from the SUP-2841 thread; a valid session on the preview host |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a preview pipeline that resolves "what document is this
attachment?" answers with a *protected* document identity — and why that association alone is
the finding.

## Objective

Recover the restricted preview association for the supplied support attachment, and establish
which document identity the viewer believes it is presenting.

## Background you need

- **Preview services key documents by content and association.** You upload an attachment, the
  service normalises it (convert, extract text, hash), then looks up "which document is this?"
  — that lookup is the *association*.
- **Document identity (DOC-…)** is the protected handle used for access control. If a preview
  response discloses the DOC id for material you supplied, you learn which protected document
  your input maps onto.
- **The association endpoint takes a source.** The retained evidence names
  `associations?source=SUP-K-2841`, viewer request `PRV-771`, document
  `DOC-9BC054D6F95DFA6A`.
- Support context: `SUP-2841` is the ARWC connector callback-latency ticket on osTicket; the
  support API on `:8443` exposes `handovers/current` and diagnostics jobs.

## Walkthrough

### 1. Recon — the preview service's four verbs

```bash
# illustrative: ask for the association of the supplied attachment
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  'https://preview.keplerops.test/api/associations?source=SUP-K-2841' | jq .
```

The response is the restricted association: the viewer request it belongs to, and the document
identity the viewer will present.

### 2. Finding the flaw — the answer is the protected identity

The leak is not an IDOR on a numeric id; it is that the service *volunteers* the protected
mapping. Two properties make it a finding: the association is scoped by the source string, not
the caller (any session naming `SUP-K-2841` gets the same record), and the record names the
document identity plus the viewer request — precisely the "which identity does the viewer
believe it is presenting" question, answered server-side.

### 3. Exploitation — confirm it against a render

```bash
# illustrative: prepare → render, then read the identity the viewer reports
curl -sS ... -X POST -d '{"source":"SUP-K-2841","attachment":"<attachment ref>"}' \
  https://preview.keplerops.test/api/prepare
curl -sS ... https://preview.keplerops.test/api/render/<preview id> | jq .
```

If the render reports the same `DOC-…` as the association, the association is not speculative
metadata: the viewer genuinely believes your input belongs to that protected document. That is
the demonstration K10.2 and K10.3 build on.

### 4. Getting the flag

Solved manually. The preview association for source `SUP-K-2841` was accepted — the record
tying `PRV-771` to `DOC-9BC054D6F95DFA6A`. The per-card `flag` field is empty in the retained
dataset, so the value is **accepted, value not recorded**.

## Why this works (the vulnerability explained)

The class is **authorization derived from an association rather than from the requester**. The
pipeline must answer "what is this?" before "may you see it?", so it resolves the attachment to
a protected document identity and then uses *that identity* for access control. But the
resolution step is unauthenticated with respect to the protected document: the caller only
needs the source key. The DOC id becomes an oracle — you can test which of your inputs map to
which protected documents without being allowed to open them — and because the same identity is
used downstream, controlling the mapping (K10.2) means controlling what the viewer serves
(K10.3). The service also leaks the existence and identity of protected material, often enough
to enumerate a customer's document set.

## Detection and fix

- **Detect:** association lookups for source keys the caller does not own; one session asking
  for many sources; responses containing `DOC-` identifiers for documents never opened.
- **Fix:** authorize `source` against the caller's support entitlements before resolution;
  return an opaque preview handle instead of the protected document id; log source and resolved
  identity so cross-tenant lookups are visible.
- **Fix the model:** separate internal, privileged resolution from caller-scoped presentation,
  and never let a caller-visible response carry the internal access-control key.
