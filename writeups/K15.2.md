# K15.2 — A job outside your account

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** pi lane K15

## Where this happens

![Range map — three segments, hosts and services](../docs/img/segments.png)

Primary service for this card: `cloud-api.keplerops.test`. The map shows which segment it sits in and how
traffic reaches it (browser terminal → kali → rowan-dev → SOCKS relay → 10.77.x).

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Missing object-level authorisation (IDOR) on a restricted sub-resource: the export *definition* is served to any holder of the export role, regardless of who created the job |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `https://cloud-api.keplerops.test/api/exports/EXP-2841/definition` |
| **Prerequisite** | The export-audience JWT (K14.2) and the job id `EXP-2841` (K15.1) |
| **Flag** | accepted, value not recorded |

**What you are about to read:** the difference between reading the job record (K15.1) and reading
its *definition* — the restricted object, because it spells out the dataset, the selection
predicate, the revision pin and where output is handed over. Same audience-trusts-caller bug, one
level deeper.

## Objective

> Obtain the restricted export definition for the customer's job even though your identity does
> not own it.

The job belongs to a support principal working the ARWC case; our identity is a developer account
that exchanged its way into the export audience. The definition should be visible only to the job
owner and the export worker.

## Background you need

**Object-level authorisation.** Route-level checks ("may this caller call `/api/exports/*`?") and object-level checks ("may this
caller see *this* export?") are different controls; frameworks make the first easy and the second
manual, so the second is where IDOR lives.

**Why the definition is the sensitive part.** A record tells you *that* an export exists; a
definition tells you *what it selects*: dataset/partition (which tenant is in scope), the
filter/predicate (how rows are chosen, and how to widen them), the revision pin, and the
destination. With it you can reason about data without touching it — and plan a handover
redirection because you now know the destination format.

## Walkthrough

### 1. Confirm you are outside the owning account

```bash
curl -sS -u 'rowan.ito:fk_developer_…' -X POST \
  https://cloud-api.keplerops.test/api/workspaces/current/token-exchange | jq
```

`rowan.ito` is a developer identity; `EXP-2841` was created by support for `SUP-2841`. Under a
correct ownership model every definition read should be `403`.

### 2. Get the export-audience token

```bash
EXPORT_JWT=$(curl -sS -X POST -H "Authorization: Bearer ${SA_JWT}" \
  https://cloud-api.keplerops.test/api/token-exchange/fieldkest-export-access | jq -r .token)
```

Same audience and role as in K14.2. Nothing about this token says `rowan.ito`, which is why the
ownership check never fires.

### 3. Read the record, then the definition

```bash
curl -sS -H "Authorization: Bearer ${EXPORT_JWT}" \
  https://cloud-api.keplerops.test/api/exports/EXP-2841            # K15.1: the record
curl -sS -H "Authorization: Bearer ${EXPORT_JWT}" \
  https://cloud-api.keplerops.test/api/exports/EXP-2841/definition # K15.2: the definition
```

The definition route is *not* stricter than the record route. It returns the full definition for a
job we do not own: dataset, revision, selection and the handover stanza.

### 4. Getting the flag

The definition response carried the flag directly. Lane notes record it as
`FLAG{bd60dc9d170bc2c7}` with the submission accepted; the card stores no value, so it is
recorded as accepted/not recorded. It is a different flag from the record route — one challenge
per endpoint.

## Why this works (the vulnerability explained)

Three layers each assume another one did the check:

1. **Authn:** a valid JWT with the right audience — satisfied by the exchanged token.
2. **Route authz:** "does this role include `exports:read`?" Yes; the export worker needs it for
   every job.
3. **Object authz:** "is `job.owner` the caller, or is the caller acting for the owner?" Never
   implemented, because the endpoint was written for a single trusted machine caller where the
   answer is always yes.

So the definition is protected by a role that is shared by design. Once the role is obtainable by
a non-worker identity, it becomes a skeleton key — and sequential ids (`EXP-2841`) mean no
guessing is needed.

The fix is not "add a role check" (there is one) but to decide per object: compare the authenticated
principal, or its on-behalf-of subject, against `job.created_by`.

## Detection and fix

- **Log signal:** one role reading records/definitions across many `created_by` values; definition
  reads for several jobs from one token; export-role tokens used outside the worker's identity.
- **Fix:** object-level authorisation on both routes; an `obo`/`act` claim checked against the
  owner; tokens scoped to a job-id allow-list; non-sequential export ids. If the definition embeds
  destination credentials, treat the handover config as compromised once it leaks.

## Notes and dead ends

- The lane report states the mechanism directly: `GET /api/exports/EXP-2841/definition` with the
  export JWT, flag accepted. The JSON field names inside the definition were not preserved, so the
  field list here is generic.
- `/api/exports/EXP-2841/runs` is denied even to the export token (`k3s_rbac_denied`); not needed
  for this card.
- K15.3 ("Change the handover point") needed a write on the definition, and the export role is
  read-only there — that is where the lane stopped.
- Do not confuse the definition with the exported object: the object lives in
  `s3://fieldlink-exports`, retained collections are not listable, and K15.4 needed the exact
  bucket/key/digest that this card does not provide.
