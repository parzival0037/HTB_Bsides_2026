**What you are about to read:** how a release review that is "not in the repository" turns
out to be perfectly readable anyway. The bug class is the *second copy*: a document governed
in one system is pasted into an issue tracker, and the tracker's permissive default outlives
the review's original restrictions.

## Objective

> A release review is missing from the checkout; find its staff work-board record and
> recover the attached review plus unresolved comments.

Two deliverables, and the second matters as much as the first: the attachment and the
discussion that never reached a conclusion. The brief's hint — "an internal service
reachable from the workstation" — is telling you to stop reading git history and start
reading the tracker.

## Background you need

- **A release review is normally a repository artifact** — a signed-off document stored where
  release tooling can enforce it.
- **Work boards are collaboration systems, not systems of record.** They accept any
  attachment, use a project-wide permission model, and rarely implement the retention rules
  of the system they copy from.
- **"Missing from the checkout" is a scoping statement, not a deletion.** If a reviewer
  linked the document into a ticket, the copy still exists there.

So the technique is *document discovery across systems*: enumerate the tracker, pull the
attachment, then read the thread for the context the reviewer withheld.

## Walkthrough

### 1. Confirm the checkout really lacks it

```bash
grep -ril 'review' ~/work/<checkout> --include='*.md' | head
git -C ~/work/<checkout> log --oneline --all -- '*review*'
```

Nothing: not on a branch, not in a tag, not in a stash. That is the signal to change systems
rather than keep digging — a referenced document usually still exists somewhere.

### 2. Find the board, then the record (reconstructed)

No transcript survives, so this is the shape of the step, not a capture. Browser history,
bookmarks and shell history name the internal board; the range map places the work-board
workload on the service cluster at `10.77.50.11`. Board APIs are list-then-detail, so filter
the list on the release identifier from the checkout and take the item id:

```bash
# illustrative template, not a captured transcript — endpoints vary per board
BASE=http://<workboard>:<port>
curl -sS "$BASE/api/items?q=<release-id>" -H "Authorization: Bearer <token>" | jq '.[].id'
```

### 3. Take the attachment and the comments

Both hang off the same item: `attachments[]` carries a download URL, and a `/comments`
sub-resource carries the unresolved thread.

```bash
curl -sS -o review.pdf "$BASE/api/items/<item-id>/attachments/<att-id>" -H "Authorization: Bearer <token>"
curl -sS "$BASE/api/items/<item-id>/comments" -H "Authorization: Bearer <token>" | jq '.[]'
```

Together they are the answer: the review states the assessment, the unresolved comments record
the concerns nobody closed.

### 4. Getting the flag

The accepted answer is the value carried by the recovered review or its unresolved comment
thread. Accepted; which of the two held the value was not recorded, so it is not reproduced.

## Why this works (the vulnerability explained)

The vulnerability is a *copy with the wrong policy*. In the repository the review inherits
git's controls — branch protection, review requirements, commit signing, retention. In the
work board the same bytes become an attachment governed by project membership: anyone who
can read the project can read it, and nobody re-evaluates that when the original review is
restricted or withdrawn.

Nothing here bypasses the board's authorisation. The board grants exactly what it was
configured to grant; the bug is that the *data* was placed under a weaker policy than its
classification required. Same class as a production dump in a shared drive or a customer
record in a ticket attachment — the second copy silently becomes the weakest link, and it is
the copy nobody deletes when the release closes. Classification must follow the bytes, not
the container.

## Detection and fix

- **Log signal:** attachments on board items that reference a release identifier, downloaded
  by identities outside the release group.
- **Fix:** link, don't copy — store a reference to the system of record. If copies are
  unavoidable, apply the source classification to the attachment, expire it with the
  project, and delete working copies at close-out.
