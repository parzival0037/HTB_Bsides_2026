# 09 — Cloud and containers: tokens all the way down

Cloud identity is not a login. It is a chain of credentials: a workload gets a projected
service-account JWT, exchanges it for a role-scoped token, and presents that to a resource
server. Object storage has its own policy language; a CI job is a principal with a workspace,
inputs and published outputs. Every link in the chain is both a credential and an
authorisation decision.

## 1. What this class of bug is

Precisely: **authorisation is evaluated per resource, by the resource server, against the
caller's effective identity.** Two consequences follow. First, any service that mints
credentials is a privilege amplifier: its output must be scoped to the caller *and* the task,
not to the union of everything the target role can do. Second, "the workload is low-privilege"
is a statement about intent, not about reach — reach is the union of every binding attached
to the identity it becomes.

Container platforms make this concrete. Kubernetes RBAC is additive and namespace-scoped;
there is no per-object ACL on a ConfigMap, so `get configmaps` in a shared namespace reads
every ConfigMap there, including build records and trust documents. An object store separates
`ListBucket` from `GetObject` and keeps old versions; a CI job separates "who may trigger"
from "what the job can read", and archives whatever it is told to archive.

## 2. Why it exists

The root assumption is: **"the credential is scoped because the thing that holds it is
small."** A pod is small; its service account may not be. Five variants recur:

- **"Low-privilege workload, low-privilege token."** The token's reach is whatever
  RoleBindings name its service account — often a namespace-wide `get` added so the workload
  "can read its config". One over-broad rule is enough; there is no per-object check to stop
  it.
- **"Namespace equals tenant."** Namespaces isolate names, not data by default. A shared
  `fieldlink` namespace held build records, trust documents and role maps, and one RoleBinding
  to that namespace covered all of them.
- **"The bucket is private."** `ListBucket` and `GetObject` are different permissions.
  Granting anonymous listing makes the key space public while objects stay unreadable — and
  the key names alone (`notebooks/deploy-2026-09.json`, `exports/EXP-2841/…`) are a map of the
  deployment.
- **"Configuration is not a credential."** Trust records and role maps are configuration, so
  they land in ConfigMaps — and they carry bootstrap bearers and describe who may act as whom.
  Storing the record in the same scope as the workload it authorises closes a self-authorising
  loop: compromise the workload, read the record, re-mint the identity.
- **"The example is synthetic."** Documentation endpoints are often generated by exporting a
  real object. A fixture would say `svc-example`; a copied production record says
  `svc-assistant-completion` and names a real credential handle.
- **"The CI job is a sandbox."** A job is an identity plus a workspace. Anyone who can supply
  the code it runs (`provider.zip`, a build parameter) acts with the job's credentials, and
  everything the job archives is a publication decision. A green build is a claim about the
  step, not about the data.

## 3. How to spot it

- A kubeconfig, a service-account token file, or `/var/run/secrets/kubernetes.io/serviceaccount/`
  on a host that is not obviously a cluster node.
- A `/.well-known/<client>` document that lists a token-exchange route, a workspace route, or
  an export route. These references describe the intended trust flow — read them first.
- Routes shaped `/api/workspaces/current/token-exchange`, `/api/token-exchange/{audience}`,
  `/api/exports/{id}`, `/api/trust-records/{id}`. Each is a credential or a policy object.
- Namespace-scoped object names that look like records: `bld-1842`, `trust-flx-04`,
  `role-export-access`. A ConfigMap with `access_token`, `token`, `secret` or `credential` in
  its data is a credential store.
- Object store: an unauthenticated `GET /` returning a bucket name; `?list-type=2&prefix=…`;
  `?versions`; `ListBucketResult` without a signature.
- Jenkins: `/job/<name>/<n>/api/json` with a non-empty `artifacts` array on a `FAILURE`,
  `/consoleText`, `/artifact/…`, `buildWithParameters`, `crumbIssuer`.
- Artifact and log names that suggest credentials: `*token*`, `*note*`, `env*`, `*.zip`
  workspaces, `REVNOTE-*`.
- Assistant/overlay APIs with `/api/config` listing example ids and `/api/completions/examples/{id}`.
  A documentation route that returns principals and credential handles.

## 4. How to test it

Read-only first: every command below observes; none changes cluster or bucket state.

```bash
# 1. What identity do I have, and what can it actually do?
kubectl config view --minify -o json | jq '{server:.clusters[0].cluster.server,
  ns:.contexts[0].context.namespace}'
kubectl -n fieldlink auth can-i --list        # verbs x resources; read-only, safe

# 2. Decode the service-account JWT before using it.
kubectl config view --raw -o jsonpath='{.users[0].user.token}' > sa.jwt
cut -d. -f2 sa.jwt | tr '_-' '/+' | base64 -d 2>/dev/null | jq '{iss,sub,aud,exp}'
```

`auth can-i --list` is the scope map. If it says `get configmaps` at namespace scope, the
question is no longer "can I read config" but "what else is in this namespace".

```bash
# 3. Exchange once, and check who you became.
curl -sS -X POST -H "Authorization: Bearer ${SA_JWT}" -H 'Content-Type: application/json' \
  -d '{"workspace":"my-workload"}' \
  https://cloud-api.example.test/api/workspaces/current/token-exchange | jq '{sub,aud,exp}'
# sub != your service account -> the exchange widens identity.

# 4. Read one object inside the scope, and one outside it.
curl -sS -k -H "Authorization: Bearer ${TOKEN}" \
  'https://cloud-api.example.test:6443/api/v1/namespaces/fieldlink/configmaps/bld-0001'
curl -sS -k -H "Authorization: Bearer ${TOKEN}" \
  'https://cloud-api.example.test:6443/api/v1/namespaces/fieldlink/secrets'
# 200 then 403 is the scope, stated by the server. Two calls tell you more than ten guesses.
```

Object storage is tested the same way: list, then fetch one key, then ask for history.

```bash
curl -sS https://objects.example.test/ | head          # ListBuckets anonymously?
curl -sS 'https://objects.example.test/bucket?list-type=2&prefix=exports/' | head
curl -sS 'https://objects.example.test/bucket/exports/EXP-0001/handover.json?versions' | head
```

A listing without credentials is the finding; one fetched object proves severity. Do not
bulk-download a tenant export — one object is evidence, a mirror is an incident. For CI,
enumerate metadata before content:

```bash
curl -sS -u "$USER:$TOKEN" https://ci.example.test/job/report/1842/api/json \
  | jq '{result, artifacts:[.artifacts[].relativePath]}'
curl -sS -u "$USER:$TOKEN" https://ci.example.test/job/report/1842/consoleText | tail -40
```

`result: FAILURE` with a non-empty `artifacts` array means the failed build still published
files. The console tells you what the job expected; the artifacts tell you what it kept.

## 5. Case study from this range

**K13.4 — the exchange that reads the build record.** The client reference at
`https://cloud-api.keplerops.test/.well-known/fieldkest-client` advertises the workspace
token exchange. The lane records a bearer token for `svc-fieldlink-workload`; the request
body is reconstructed, the route and identity are not.

```bash
curl -sS --socks5-hostname 127.0.0.1:1080 --cacert ca.crt \
  -X POST -H 'Content-Type: application/json' -d '{"workspace":"fieldlink-workload"}' \
  https://cloud-api.keplerops.test/api/workspaces/current/token-exchange | jq .
```

With that token, one ConfigMap read succeeds:

```bash
curl -sS -k -H "Authorization: Bearer $TOKEN" \
  'https://cloud-api.keplerops.test:6443/api/v1/namespaces/fieldlink/configmaps/bld-1842'
```

`data.access_token` is the accepted value. The object calls itself a build record —
`namespace: fieldlink-build-records`, `version: 2026-09-18`, `workspace:
fieldlink-workload` — a record for its own workspace, in a namespace shared with everything
else. The denials map the scope: `/api/exports/EXP-2841/runs` and
`/api/trust-records/TRUST-FLX-04` both answer `k3s_rbac_denied`. RBAC is additive and
namespace-scoped, so one `get` on `configmaps` is enough. See [K13.4](../writeups/K13.4.md).

**K14.1 — the trust document the workload can read.** The kubeconfig token on the workstation
is a `fieldlink` service account. `kubectl auth can-i --list` shows `secrets`, `pods`,
`serviceaccounts`, `leases` and `rolebindings` forbidden — and `configmaps` allowed.
`trust-flx-04` is the workload's own trust document: the relation it describes, plus an
`access_token` (`FLAG{418e19c3ed0c13ef}` lane-recorded; the YAML shape is illustrative).

```bash
kubectl -n fieldlink get configmap trust-flx-04 -o yaml
```

The document that says "this workload, for this audience, may become that role" is readable
by the workload it authorises, and it carries the bootstrap bearer. That is a self-authorising
loop: a compromised workload does not need to escalate, it re-mints itself. The same object
through the cloud API (`/api/trust-records/TRUST-FLX-04`) answers `k3s_rbac_denied` — the
stricter path is not the vulnerable one. See [K14.1](../writeups/K14.1.md).

**K24.1 — the example that is a live job.** The support overlay authenticates a session with
`Cookie: fieldkest_support=…`; a bearer or JWT returns `session_required`. `/api/config`
lists the retained artefacts, including example `COMP-JOB-17`, and the example route returns
the job's operative references: `cred-completion-handover`, `svc-assistant-completion`,
`HANDOVER-COMP-2841`, plus the flag (`FLAG{664724eb7d7073e9}`). The transcript is
reconstructed; the identifier triple and the flag are recorded.

Any one reference is uninteresting; together they describe one execution path — *this*
account, with *this* credential, writes *that* handover. A hand-built fixture would have said
`svc-example`; the endpoint is a second, less-protected door to the same object. See
[K24.1](../writeups/K24.1.md).

**K02.1 / K02.2 — history and artifacts are storage too.** `fixtures/report-crr-og2.json` is
absent from `main`, but the Gitea contents API resolves it at an earlier revision
(`?ref=80560bc`), returning base64 that restores the blob byte-exactly; the deletion commit is
`c37effd7…`. Byte-exactness matters: the review consumer binds the fixture by digest. The
failing Jenkins build `#1842` also keeps `reports/REVNOTE-1842.json`, which holds a
`review_token` and the input contract (`fieldkest.report/v2`, `provider.py:render_report`);
the workspace zip is a second copy. See [K02.1](../writeups/K02.1.md) and
[K02.2](../writeups/K02.2.md); [K02.3](../writeups/K02.3.md) turns a submitted `provider.zip`
into a green build — that supply-chain step is chapter 06.

## 6. Variations and near-misses

- **Object storage scoping.** K13.1 is an anonymous root listing naming
  `fieldkest-workspaces`, exposing a notebook whose `workspace_token` then failed STS
  (`web identity token must be a valid JWT`) — a leaked token is not automatically usable.
  K13.2 fetches a superseded version via `?versions` / `?versionId=`; K13.3 reads a tenant
  export under a sibling prefix. Prefixes are not tenants; history is a copy of the secret.
  See [K13.1](../writeups/K13.1.md), [K13.2](../writeups/K13.2.md),
  [K13.3](../writeups/K13.3.md).
- **RBAC verbs, not roles.** `create pods` mounts any service account in the namespace;
  `get secrets` reads every Secret; `pods/exec` runs code in a workload with more rights than
  you; `impersonate` skips authentication. Wildcards are the accidental cluster-admin.
- **Shared namespaces.** A build record, a trust document and a role map in one namespace are
  one `get configmaps` away. A namespace is a naming boundary, not a data boundary.
- **CI publication.** `archiveArtifacts **/*` publishes debug dumps, env files and notes; the
  workspace zip publishes what was not declared; the console publishes expected values. Trigger
  permission is authority: `buildWithParameters` accepting a `provider.zip` runs your code with
  the job's identity.
- **Examples and fixtures.** A "sample" exported from production carries production
  principals; the tell is a real service name or credential handle in "documentation".
- **Not the bug:** a dedicated namespace whose Role reads all *its own* ConfigMaps, with no
  other data present; a deliberately public bucket with no secrets; a genuinely synthetic
  fixture (`svc-example`); a build log containing only a hash; a `403 k3s_rbac_denied`.

## 7. How to fix it

- **Scope the identity, not the pod.** Give each workload its own namespace, or a Role with
  `resourceNames`. Never grant namespace-wide `get` on `configmaps`/`secrets`; disable token
  automount where unused.
- **Make exchanges narrow.** Allow-list audiences per caller, cap the issued role at the
  intersection with the caller's own rights, use short TTLs, log caller → audience → subject,
  and return a token only — never the role record.
- **Separate data classes in storage.** Block public bucket policies; no anonymous
  `ListBucket`; separate buckets or KMS keys per tenant/data class; deny `GetObjectVersion`
  and `ListBucketVersions` to ordinary roles; lifecycle-expire non-current versions.
- **Keep credentials out of configuration.** Bootstrap bearers belong in a Secret or nowhere;
  prefer projected short-lived tokens. Move trust and role maps to the control plane.
- **Treat artifacts as publications.** Archive an allow-list, scrub tokens, restrict read and
  trigger permissions, pin provider digests, sign outputs, and verify provenance at the
  consumer instead of trusting `state=success`.
- **Generate examples from a scrubbed schema.** Placeholders for principals, credentials and
  handover ids — or keep them in the docs repo, not behind an API.

## 8. Exercises

1. **Prove RBAC reach, then fix it.** In a local kind/minikube cluster, create namespace
   `lab`, service account `sa`, two ConfigMaps, and a Role granting `get` on `configmaps`
   (no `resourceNames`). Show `kubectl auth can-i --list --as=system:serviceaccount:lab:sa`
   and read both objects. Add `resourceNames: ["allowed"]`, show one read is `forbidden`, and
   explain why the first rule read the whole namespace.
2. **Scope a bucket.** With local MinIO, create a bucket with anonymous `ListBucket` only.
   Show `curl /bucket` lists keys while `curl /bucket/key` is denied, then retrieve an older
   version with `?versions` / `?versionId=`. Write the policy that closes both, and say why
   deleting the current object is not remediation.
3. **Triage a build and a fixture.** Given `{"result":"FAILURE","artifacts":[
   {"relativePath":"reports/REVNOTE-1842.json"},{"relativePath":"out/report.json"}]}`, list
   three requests you would make next, predict which artifact holds a credential, and which
   holds the contract to satisfy. Then classify two examples — one naming `svc-example` /
   `cred-example`, one naming `svc-assistant-completion` / `cred-completion-handover` — and
   name the one pipeline change that would have prevented the leak.
